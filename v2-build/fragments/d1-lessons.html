L0 - Foundation ramp: AI minimums and AWS minimums

Zero prior knowledge assumed. Every later lesson names these terms without re-teaching them.

The problem

Every later lesson names AWS services and AI terms as if you already know them. Without a ramp, the first mention of a token or a Lambda stops you cold. This lesson builds the minimum map: what a model reads, what the AWS parts do, and how the parts connect.

Mental model

A model does not read words. It reads tokens, which are pieces of words. The word "Generative" splits into "Gener" plus "ative", which is two tokens. Billing counts tokens in and tokens out, so tokens are money.

The context window is the maximum tokens the model can see in one request. Input plus output must fit inside it. An embedding is a list of numbers that places a piece of text on a meaning map, so nearness means similar meaning. Temperature is a randomness dial: low values give steady factual answers, high values give varied creative ones. Top-p and top-k are two more dials that trim the candidate set before the pick. An agent is a model that calls tools in a loop until the job is done.

Three ways exist to change what a model does, from cheap to costly. Prompt engineering changes the instructions only. RAG (Retrieval-Augmented Generation) pastes fresh facts into the prompt at query time, with no weight change. Fine-tuning trains the weights further on your examples, which bakes in behavior. Pick the cheapest rung that solves the problem.

AWS rents you the parts of a data center. EC2 (Elastic Compute Cloud) is a rented virtual server that runs 24/7 until you stop it. Lambda runs one function on one event and then vanishes, with a hard cap of minutes per run. Step Functions is a workflow engine that can wait hours and call services in order. S3 (Simple Storage Service) is durable object storage and the home for documents, datasets, and logs. DynamoDB is a fast key-value store and the home for session state and metadata. It is not a vector store. VPC (Virtual Private Cloud) is your private network inside AWS. IAM (Identity and Access Management) is the badge reader: every call carries an identity, and a policy states allow or deny.

A Region is a geographic cluster of data centers, and models are not served in every Region. An AZ (Availability Zone) is one isolated data center inside a Region. You use several so one failure does not stop you. For observability, CloudWatch holds metrics and logs, CloudTrail is the audit log of who called what, and X-Ray traces one request across services.

Worked example: tokens and the window

Take a request with a 1,000-token system prompt, 5,000 tokens of user input, and 2,000 tokens of output. Total equals 1,000 + 5,000 + 2,000 = 8,000 tokens. If the model window is 8,000 tokens (toy size, not a real limit), the request fits exactly. Add 500 more input tokens and the total becomes 8,500, which exceeds the window, so the call fails or truncates [Version-dependent]. The window is a hard budget, and every token you add on one side removes room from the other.

Limits and traps

Check yourself original exam-style practice

Q1 (recall). An agent must keep conversation state for weeks and also store PDF source documents. Which two services do you pick?

Correct: DynamoDB for the conversation state, S3 for the PDFs. DynamoDB is a fast key-value store built for state, S3 is durable object storage built for documents. S3 alone fails because object storage is the wrong shape and speed for session reads. DynamoDB alone fails because it is not a document store and cannot hold vectors or large binaries well.

Q2 (recall). Token spend spikes at 3am. Which tool finds the cause: CloudWatch or CloudTrail?

Correct: CloudWatch, with its metrics and anomaly detection. CloudTrail records who called which API, which is audit data, not performance data. Picking CloudTrail confuses audit with monitoring, which is the exam trap.

Q3 (transfer). A workflow waits up to 2 hours for a human approval, then calls a model. Which two services handle the wait and the call, and why can one service not do both?

Correct: Step Functions holds the wait, Lambda (or a direct Bedrock step) makes the model call via bedrock:InvokeModel. Lambda cannot do both because its runtime cap is minutes-scale, so a 2-hour wait kills it. Step Functions orchestrates but is not the compute that runs your code.

L1 - D1: Requirements, model selection, resilience, customization lifecycle

Skills 1.1.1-1.1.3, 1.2.1-1.2.4. Decide the technique first, the model second, the plumbing third.

The problem

Teams pick a model first and never pick a technique. A fine-tune where RAG fits burns months of data work and a large budget, then goes stale on the first manual update. A giant model where a small one fits burns money on every single request. The damage comes from deciding in the wrong order.

Mental model

Use the escalation ladder: prompt engineering, then RAG, then fine-tuning, then (out of scope for this exam) training from scratch. Climb one rung only when the lower rung fails a named test. The analogy is a car repair: you try the tune-up before the engine rebuild, and you can state why the tune-up failed.

A PoC (proof of concept) is a small build that tests three things before scale: feasibility, speed, and value. Skill 1.1.2 exists because a PoC on Amazon Bedrock (the managed model API service) costs little and answers those three questions in days. Skill 1.1.3 then says: turn what worked into standard reusable components, reviewed against the Well-Architected Framework GenAI Lens, so the tenth deployment matches the first.

Model selection (skill 1.2.1) is a trade across four axes: capability, cost, latency, and regional availability. A model that wins on capability but is not served in your Region loses by default. Resilience (skill 1.2.3) means the system keeps answering through an outage: retry, switch Region, switch model, degrade gracefully. Customization (skill 1.2.4) is a lifecycle, not a single training run. The stages are adapt, register the version, deploy through a pipeline, roll back on failure, and retire at end of life.

Worked example: token cost and context budget

Assumptions: input price $3.00 per 1M tokens, output price $15.00 per 1M tokens [Version-dependent]. One request carries 8,000 input tokens and 500 output tokens. Cost per request = (8,000 / 1,000,000) x $3.00 + (500 / 1,000,000) x $15.00 = $0.024 + $0.0075 = $0.0315. At 1M requests per month, the bill is $31,500. A smaller model at $0.30 input and $1.50 output per 1M [Version-dependent] gives (8,000 / 1,000,000) x $0.30 + (500 / 1,000,000) x $1.50 = $0.00315 per request. At 1M requests per month that is $3,150: a 10x cut for the same traffic.

Context budget on a 200k toy window: system prompt 3,000 + retrieved chunks 8 x 5,000 = 40,000 + user input 2,000 + reserved output 10,000 = 55,000. Free space = 200,000 - 55,000 = 145,000 tokens. The model breaks here. If retrieved chunks grow to 160,000 tokens, the sum passes the window and the call fails. Chunk count is a budget decision, not just a quality decision.

How AWS does it

Bedrock is the front door. Your app calls bedrock:InvokeModel with a model ID and a JSON body, and gets text back. For chat, bedrock:InvokeModelWithResponseStream streams tokens as they arrive, which cuts perceived latency. If your Region does not serve the model you want, an inference profile (for example a us. prefix profile) routes the request cross-region to where it is served [Behavior].

Skill 1.2.2 in practice: the app never names a model. A Lambda reads the active model ID from AWS AppConfig (a managed configuration store) at request time. The read uses appconfig:GetLatestConfiguration [Unverified]. The Lambda then calls Bedrock with that ID. Amazon API Gateway (the managed front door for APIs) fronts the Lambda. Flip the config value and traffic moves to the new model with no code change and no deploy.

Skill 1.2.3 in practice: a Step Functions circuit breaker. Try the primary model first. On throttling or outage, route through the cross-region inference profile. If that fails, fall back to a smaller cheaper model. If that fails, return a cached or static answer. Each rung trades answer quality for availability, which is graceful degradation by design.

Skill 1.2.4 in practice: fine-tune on Amazon SageMaker AI (the managed ML platform). LoRA (Low-Rank Adaptation) freezes the base weights and trains two small matrices per layer, so the adapter is megabytes while the model is gigabytes. The artifact goes into SageMaker Model Registry with a version number, an automated pipeline deploys it to an endpoint (sagemaker:InvokeEndpoint serves traffic). Rollback means pointing the endpoint at the prior registry version. Retire means a scheduled swap to the replacement, not a silent delete.

Limits and traps

Fine-tuning teaches style and behavior, it does not reliably teach fresh facts. A fine-tuned model will still invent the new product price, because facts come from retrieval, not from weight updates. Cross-region inference adds latency and moves data across borders, which is a compliance flag in regulated workloads. Provisioned throughput reserves capacity for steady load, it is not a discount for spiky traffic, and idle reserved capacity still bills. A PoC proves feasibility, never production readiness: the exam tests whether you know what a PoC cannot promise.

Q1 (recall). A support bot must answer from a product manual that updates monthly, with citations. Pick prompt engineering, RAG, or fine-tuning, and give the one-sentence reason.

Correct: RAG, because the facts change monthly and citations need the source text at query time. Fine-tuning fails since weights go stale on each manual update. Prompt engineering fails since instructions alone cannot supply facts the model never saw.

Q2 (recall). A classifier handles 1M calls a day and each call costs too much. What is the first move: fine-tune, or switch to a smaller model with tiered routing?

Correct: switch to a smaller model with tiered routing (simple queries to the small model, hard ones escalated). Fine-tuning changes behavior, not per-token price, so it does not fix a cost problem. The exam tests cost-capability trade-offs, not bigger-is-better.

Q3 (transfer). Your primary model has an outage in your Region during peak traffic. Sketch the fallback order and name what each step sacrifices.

Correct: retry with backoff, then the cross-region inference profile (sacrifices latency and data residency), then a smaller backup model (sacrifices answer quality), then a cached or static answer (sacrifices freshness). Each rung trades quality for availability, which is graceful degradation. Skipping straight to the static answer fails because it wastes the middle rungs.

L2 - D1: Data validation and processing pipelines

Skills 1.3.1-1.3.4. The model cannot clean its own input, the pipeline must.

The problem

A model reads whatever you feed it and answers with full confidence. Feed it a corrupt PDF, a mislabeled audio file, or a table with shifted columns, and you get a fluent, confident, wrong answer. No prompt trick fixes data the pipeline never checked. Quality gates belong before inference, not after.

Mental model

Think of a kitchen prep line. The wash station (validate) rejects rotten produce. The chop station (process) cuts each item to the shape the recipe needs. The plate station (format) arranges it for the diner. The chef (model) never sees the raw delivery. Skills 1.3.1 through 1.3.4 map to those four stations in order: validate, process by type, format per model, and enrich quality.

Validation asks "is this data fit to use": complete, fresh, de-duplicated, correctly typed. Processing asks "is it in the shape the model can read": audio becomes text, scans become text, tables become rows. Formatting asks "does this request body match what this specific model expects": providers differ, so one JSON shape does not fit all models. Enrichment asks "can we add signal before the call": extract entities, normalize spellings, rewrite noisy text.

Worked example: reject, dedupe, save

Assumptions: 10,000 PDFs land in S3, input price $3.00 per 1M tokens [Version-dependent]. Validation rejects 800 corrupt or empty files: 800 / 10,000 = 8% rejected before any money is spent. The corpus holds 50M tokens, de-duplication removes 15%, which is 0.15 x 50M = 7.5M tokens. Savings per full-corpus pass = (7.5M / 1M) x $3.00 = $22.50. At 100 passes per month, the pipeline saves $2,250 per month, which pays for the validation stage many times over. The model breaks here. If de-duplication is too aggressive, it removes near-duplicate contracts that differ in one clause. Recall drops, and the savings cost you answers.

How AWS does it

S3 is the source of truth: raw files land in a bucket, and every stage reads and writes buckets or prefixes. AWS Glue Data Quality runs rulesets over the data for skill 1.3.1: completeness, freshness, schema match. A custom Lambda validator covers rules no managed check expresses (lambda:InvokeFunction). SageMaker Processing runs batch transforms for skill 1.3.2: heavy jobs over large datasets on ephemeral compute.

Each data type gets its own extractor. Amazon Transcribe turns audio into text (transcribe:StartTranscriptionJob [Unverified]). Amazon Textract pulls text and tables from scanned images (textract:DetectDocumentText [Unverified]). Bedrock multimodal models read images directly when the use case needs vision. For skill 1.3.4, Amazon Comprehend extracts entities such as names and dates (comprehend:DetectEntities [Unverified]). A Lambda normalizes spellings and formats. Bedrock itself can rewrite noisy text into clean input.

For skill 1.3.3, format per model. The Bedrock Converse API takes a messages list with roles (user, assistant) plus inference parameters. Provider-specific request bodies differ in field names and limits [Version-dependent]. Format against the target model contract. Dialog apps keep the full turn history in order, one mislabeled role corrupts the conversation. Amazon CloudWatch metrics track reject rates per stage, so a spike in validation failures pages the team before bad data reaches the model.

Limits and traps

Schema checks cannot catch semantic lies: a fluent paragraph with a false date passes every format rule. Validation at ingest does not replace validation at query time, because user input arrives raw on every request. Formatting is provider-specific. A request body built for one model family can fail on another with a validation error. "One JSON fits all" is the trap. Processing improves the odds, it never guarantees truth, which is why L3 adds retrieval grounding.

The decisive requirement is volume times schedule regularity: daily terabytes with audit needs point to the managed path, while a small event-driven flow points to the Lambda chain. If the requirement changed to a one-off cleanup of 50 files, the Lambda chain would win. The managed path adds setup cost for no repeat value.

Q1 (recall). Support tickets arrive as text and need product names pulled out before the model sees them. Which service: Transcribe, Comprehend, or Textract?

Correct: Comprehend, with entity extraction. Transcribe fails because it handles audio, not text. Textract fails because it reads scanned images, not plain text. The exam tests one-service-per-data-type mapping.

L3 - D1: Vector stores and retrieval mechanisms (RAG core)

Skills 1.4.1-1.4.5, 1.5.1-1.5.6. The largest lesson in D1: this is where answers stop being invented.

The problem

A model answers from weights frozen at training time. Ask about last month policy change or your private runbook, and it invents a fluent answer with no basis. The business cost is not a wrong answer, it is a wrong answer delivered with total confidence. Retrieval fixes this by fetching the facts first and forcing the model to reason from them.

Mental model

Think of a library. An embedding gives every text chunk a coordinate on a meaning map. "Refund policy" sits near "return rules" even though they share no words. The vector store is the card catalog sorted by meaning, not by alphabet. Retrieval walks in with the question coordinate and pulls the nearest chunks. RAG pastes those chunks into the prompt, so the model reasons from your text instead of its memory.

Two searches exist. Keyword search matches exact words, it misses paraphrase. Semantic search matches meaning via vectors, it misses exact codes and names. Hybrid search runs both and merges the lists, and a reranker model reorders the merged top results for precision. Chunking decides the unit of retrieval: too small and meaning shatters across cuts, too large and noise dilutes the match.

Worked example: storage, chunks, and cosine

Embedding storage. Assumptions: N = 50,000 documents, D = 1,024 dimensions, 4 bytes per float. Bytes = 50,000 x 1,024 x 4 = 204,800,000. Convert: 204,800,000 / 1,048,576 = 195.3 MiB. So the raw vectors need about 195 MB before any index overhead. That is why the vector index lives on storage built for it, not in a key-value table.

Chunk count with overlap. Assumptions: document length L = 12,000 tokens, chunk size C = 1,000, overlap O = 200. New tokens per chunk after the first = C - O = 800. Chunks = ceil((L - O) / (C - O)) = ceil(11,800 / 800) = ceil(14.75) = 15. Fifteen chunks cover the document, and each boundary shares 200 tokens with its neighbor, so no sentence is cut blind.

Cosine similarity on a 2-D toy. Let a = [1, 0] and b = [0.6, 0.8]. Both are unit length: |a| = 1, |b| = sqrt(0.36 + 0.64) = 1. Cosine = (a . b) / (|a| |b|) = (0.6 + 0) / 1 = 0.6, about a 53-degree angle. Distance identity: for unit vectors, |a - b|^2 = (a - b) . (a - b) = |a|^2 - 2(a . b) + |b|^2 = 1 - 2cos + 1 = 2(1 - cos). Here 2 x (1 - 0.6) = 0.8. Check directly: a - b = [0.4, -0.8], squared length = 0.16 + 0.64 = 0.80. The identity holds, which means nearest by cosine equals nearest by Euclidean distance on normalized vectors. Where the model breaks: on raw unnormalized vectors the identity fails. Normalize before you compare. Long chunks then stop outranking short ones for no semantic reason.

How AWS does it

The managed path is Amazon Bedrock Knowledge Bases. You point it at an S3 document repository. It chunks the documents with a fixed-size, hierarchical, or semantic strategy. It embeds them with a Bedrock embedding model such as Amazon Titan embeddings. It stores vectors in a managed vector index. Sync runs via bedrock:StartIngestionJob [Unverified]. At query time your app calls bedrock:Retrieve for chunks or bedrock:RetrieveAndGenerate for the full RAG answer in one call.

The self-managed path is Amazon OpenSearch Service with the Neural plugin for vector search. Amazon Aurora with the pgvector extension is the Postgres-native option. OpenSearch sharding splits the index across nodes as it grows, multi-index designs isolate specialized domains, hierarchical indexing speeds coarse-to-fine search. Metadata lives alongside: S3 object metadata for timestamps, custom attributes for authorship, tags for domain, and DynamoDB for document metadata. Note the exam trap: DynamoDB holds metadata, never the vectors.

Precision comes from filters and reranking. Metadata filters prune by tenant, date, or domain before the vector search runs, which also enforces access control at retrieval time. Hybrid search merges keyword and vector results inside OpenSearch. A Bedrock reranker model then reorders the top candidates, it costs extra latency and tokens, so you rerank tens of results, not thousands.

Query handling upgrades the question before search. Expansion adds synonyms via Bedrock. Decomposition splits one hard question into sub-questions via Lambda. Transformation chains (rewrite, then route, then search) run on Step Functions. The app reaches all of this through one stable interface. Use a function-calling interface for vector search, or an MCP (Model Context Protocol) client for vector queries. The model code then never changes when the store changes.

Freshness is a correctness control. Incremental updates add only changed documents, change detection (S3 events) triggers re-ingest, scheduled refresh pipelines re-sync on a cadence. A stale index serves stale facts with full confidence, so sync lag is a bug, not a nicety.

Limits and traps

Top-k retrieval can miss the one decisive chunk, recall is not precision, and a reranker only reorders what retrieval found. Chunk too small and meaning shatters. Chunk too large and noise dilutes the match. Tune chunk size per corpus, never copy it from a blog. Embeddings capture meaning, not truth: a well-embedded false document retrieves beautifully. DynamoDB is metadata only and never the vector index, the exam sets this trap in several wordings. Cosine similarity assumes normalized vectors, skip normalization and the ranking silently skews toward long chunks.

Q1 (recall). 50,000 support docs need semantic search with low latency. Do you scan a DynamoDB table per query, or use a vector index?

Correct: a vector index (Bedrock Knowledge Bases or OpenSearch vector search). A DynamoDB scan reads the whole table per query and has no vector index, so latency grows with corpus size. DynamoDB holds document metadata only, that is the exam trap.

Q2 (recall). RAG answers cite the manual but the facts are two versions old. The model and prompts are unchanged. What broke, and what is the fix?

Correct: the vector index is stale, the sync pipeline broke. Fix: re-run ingestion (bedrock:StartIngestionJob) and repair the scheduled refresh or S3-event trigger. Retraining or re-prompting fails because the model was never the problem.

Q3 (transfer). One knowledge base serves three tenants, and each tenant must see only its own documents. Where do you enforce this, and how?

Correct: at retrieval time, with a metadata filter on tenant_id applied before the vector search. Filtering after retrieval fails because other-tenant data may already sit in the model context. A separate index per tenant also works but multiplies ops cost, the filter is the standard answer.

L4 - D1: Prompt engineering, management, and governance

Skills 1.6.1-1.6.6. Prompts are production code: version them, test them, audit them.

The problem

Prompts start as strings pasted into code. Six months later nobody can say which version answered a customer. A careless edit ships with no test. A small wording tweak quietly drops accuracy. The failure is not the wording, it is the absence of every control that code takes for granted: versions, reviews, tests, and audit trails.

Mental model

Treat a prompt like a config file in production. It gets a version number and a review before release. A test suite runs on every change. A log records who used which version when. Amazon Bedrock Prompt Management is the version store. Amazon Bedrock Prompt Flows is the visual builder for chains with branches and pre/post steps. Amazon Bedrock Guardrails is the policy layer that filters content (full teach in D3).

Prompt craft uses named techniques. Role definition tells the model who it is ("you are a support classifier"). Few-shot gives input-output examples. Chain-of-thought asks for step-by-step reasoning, which lifts accuracy on hard tasks at the price of more output tokens. Structured output (a JSON schema) forces machine-readable answers. Feedback loops feed bad outputs back into the next prompt revision.

Worked example: regression gate and prompt bloat

Regression gate. Assumptions: 200 golden prompt cases with known-good outputs. Version 4 passes 186: 186 / 200 = 93.0%. Version 5 passes 172: 172 / 200 = 86.0%. The delta is 14 newly failing cases, so version 5 does not ship until those 14 are fixed or explained. This is prompt regression testing: the same discipline as unit tests, applied to word choice.

System prompt bloat. Assumptions: 1M calls per month, input price $3.00 per 1M tokens [Version-dependent]. A 3,000-token system prompt costs (3,000 / 1M) x $3.00 = $0.009 per call in system-prompt tokens alone, which is $9,000 per month. Compress it to 1,000 tokens with no quality loss and the cost falls to $3,000 per month, a $6,000 monthly saving from editing words. The model breaks here. Compression that deletes a constraint (for example the output schema) saves money and breaks the integration. Every cut re-runs the golden set.

How AWS does it

Bedrock Prompt Management stores templates with variables (for example {{customer_tier}}). It versions each save. It serves a chosen version at runtime (bedrock:CreatePrompt [Unverified]). Approval workflows gate promotion: a reviewer approves v5 before it becomes default. S3 can hold the template repository for teams that want raw files, but then versioning and approvals are your code to write.

Bedrock Prompt Flows builds complex systems without custom orchestration. It supports sequential chains where step two consumes step one output. It supports conditional branches on the model reply. It offers reusable prompt components shared across flows, with Lambda pre/post-processing around any node. For conversation, Step Functions runs clarification workflows ("which order do you mean"). Comprehend detects intent. DynamoDB stores the turn history so the model remembers the session.

Governance closes the loop. CloudTrail records which identity invoked which prompt version (cloudtrail:LookupEvents reads the trail). CloudWatch Logs holds the access log. Quality assurance runs on three rails. A Lambda checks each output against the expected shape. Step Functions walks edge cases. CloudWatch tracks the golden-set pass rate per version so regressions page the team. Guardrails sit in front as the policy layer: denied topics, content filters, and PII redaction (bedrock:ApplyGuardrail [Unverified]), the safety deep teach lives in D3.

Limits and traps

A system prompt cannot override the model safety training. Jailbreak instructions fail closed. The exam tests whether you know the policy layer wins. Chain-of-thought raises accuracy but also token cost and latency, so you reserve it for hard tasks. Pin the model version and the prompt version together. One without the other is not reproducible. The same prompt on a new model is a new system. Governance has a cost, a solo prototype does not need an approval board, and the exam rewards proportionate answers.

Valid but inferior, and technically invalid

Valid but inferior: one mega-prompt that classifies, extracts, and formats in a single call.

input --> MEGA-PROMPT (classify + extract + format) --> output
happy path: correct ..... edge case: which step failed? unknown
no per-step test, one edit risks all three jobs
result: works until it does not, then undebuggable

Technically invalid: a prompt chain that loops with no stop condition.

prompt --> model --> prompt --> model --> ... (no max steps)
each lap bills tokens, nothing stops the loop
result: runaway bill, chains need step caps and timeouts

Check yourself original exam-style practice

Q1 (recall). The team needs prompt versions, an approval step, and a log of which version served each request. Which AWS combo: S3 alone, or Prompt Management plus CloudTrail?

Correct: Bedrock Prompt Management plus CloudTrail. Prompt Management gives versions and approvals. CloudTrail logs who invoked which version. S3 alone fails because versioning and the audit wiring are code you must write and maintain.

Q2 (recall). A new prompt version drops the golden-set pass rate from 93% to 86%. What is the correct response: ship it, or roll back?

Correct: roll back to the prior version and fix the 14 regressions first. Shipping fails because the regression gate exists to block exactly this. The exam tests whether process beats urgency.

Q3 (transfer). A support bot must ask a clarifying question when user intent is unclear, then remember the answer for the rest of the session. Sketch the design.

Correct: Comprehend detects low-confidence intent, a Step Functions clarification workflow asks the follow-up, DynamoDB stores the turn history as session memory, the next prompt includes the clarified intent. Skipping the memory store fails because the bot would ask again on every turn.
