Stage 8A - Confusion matrices: name the decisive requirement

Twelve pairs the exam loves to confuse. This stage teaches discrimination, not new mechanisms. Short callbacks name the lesson that taught each option.

How to read a matrix

The exam rarely asks for a definition. It shows a scenario and asks for the best fit. The wrong answers look right because they share most traits with the right one.

Each matrix below compares options that look alike. Rows name what they share and what splits them. More rows name when each wins, when each loses, what each costs, and what each demands in operations. A last row names the misconception that traps test-takers.

Treat bolded phrases in these matrices as clues, never as rules. A phrase suggests a direction. The decisive requirement in the scenario decides the answer. If the phrase and the requirement disagree, the requirement wins.

Stage 8B - Minimal-pair drills: one change flips the answer

Twelve drills on the six most exam-decisive pairs. Same scenario, one changed requirement, flipped answer.

How to run a drill

A minimal pair changes one requirement and flips the answer. The rest of the scenario stays fixed.

Each drill quotes the exact changed phrase. Read the scenario and name the winner. Apply the change and re-decide.

If you cannot name the phrase that flipped your answer, you guessed.

Pair A - RAG vs fine-tuning

Drill A1. A support bot answers from a 2,000-page product manual. The manual ships a new version every month. The team must choose between RAG and fine-tuning.

Change: "The manual ships a new version every month" -> "The style guide is fixed and the product facts never change".

Flip: The answer flips from RAG to fine-tuning. Monthly fact changes make trained weights go stale between runs. A fixed style with stable facts is a behavior gap, and fine-tuning teaches behavior while citations matter less than consistent tone.

Drill A2. A bank answers loan-officer questions from policy PDFs. Every answer must cite the exact policy section.

Change: "Every answer must cite the exact policy section" -> "Every answer must match the bank approved tone, and the policy text never changes".

Flip: The answer flips from RAG to fine-tuning. Citations need source text at query time, which only retrieval provides. Fixed text with a tone requirement is a style gap with labeled examples, which fine-tuning fits.

Pair B - Bedrock managed inference vs SageMaker self-hosted endpoints

Drill B1. A startup ships a chat feature on a standard chat model. The team has no ML operations staff and wants the fastest launch.

Change: "lowest operational overhead" -> "maximum customization".

Flip: The answer flips from Bedrock managed inference to a SageMaker endpoint. Custom runtimes and full hardware control need instances the team configures. The managed API cannot host a custom container, so the team pays the operations cost for control.

Drill B2. A team serves document Q&A on a model from the Bedrock catalog.

Change: "the model ships in the Bedrock catalog" -> "the model is proprietary, fine-tuned in-house, and Bedrock does not serve it".

Flip: The answer flips from Bedrock to SageMaker. Bedrock serves its catalog models. A proprietary model needs a self-hosted endpoint where the team owns the container and the GPU size.

Pair C - On-demand vs provisioned throughput vs batch inference

Drill C1. A fraud check runs 400,000 requests per month with sharp unpredictable spikes.

Change: "intermittent traffic" -> "sustained predictable traffic".

Flip: The answer flips from on-demand to provisioned throughput. Above break-even, steady volume makes the fixed unit cheaper than per-token billing. Spiky traffic would waste idle units, but predictable load keeps utilization high.

Drill C2. A ticket-scoring job runs all day as tickets arrive. It holds provisioned units around the clock.

Change: "scores stream in all day" -> "one nightly bulk run with results needed by morning".

Flip: The answer flips from provisioned to batch inference. Batch is the cheapest per token for offline bulk with a loose deadline. Provisioned units billed all day for a job that runs at night waste the idle hours.

Pair D - Prompt caching vs semantic result caching

Drill D1. A support bot sends the same 8,000-token system prefix on every call. Prompt caching cuts the repeat cost.

Change: "the same 8,000-token system prefix repeats on every call" -> "the prefix carries per-user values, so no two prefixes match".

Flip: The answer flips from prompt caching to semantic caching. Exact-match caching dies when the prefix varies per request. The questions still repeat in meaning, so the team embeds each question and serves stored answers, which still skips model calls.

Drill D2. Users ask paraphrases of 500 FAQ questions. Answers stay valid for a day. Semantic caching serves the repeats.

Change: "paraphrased repeats of stable answers" -> "byte-identical repeats of one long shared prefix".

Flip: The answer flips from semantic caching to prompt caching. Exact prefix matches hit every time and cost less than embedding lookups. The meaning match adds nothing when every byte already matches.

Pair E - Bedrock Agents vs Step Functions orchestration

Drill E1. A shopping assistant looks up orders and drafts refunds. Every action today is a read-only lookup.

Change: "read-only lookup" -> "irreversible account modification".

Flip: The answer flips from a free agent loop to a Step Functions approval gate. Irreversible actions need a human decision before the tool fires. Step Functions holds the wait that Lambda cannot, then the loop resumes with the decision.

Drill E2. A claims agent picks tools on the fly. Sometimes it checks fraud, sometimes policy, based on the claim text.

Change: "the agent chooses tools per situation" -> "the workflow is a fixed 5-step sequence with retries and a 2-hour human review wait".

Flip: The answer flips from Bedrock Agents to Step Functions. Dynamic tool choice needs the model in the loop. A fixed sequence with long waits needs the workflow engine, which owns retries and waits natively.

Pair F - Dense vs lexical vs hybrid retrieval

Drill F1. Engineers search runbooks with exact error codes like ERR-4401. Lexical search wins.

Change: "queries use exact error codes" -> "queries are natural-language descriptions of symptoms".

Flip: The answer flips from lexical to dense retrieval. Exact codes need keyword match. Symptom descriptions share no words with the runbook, so vectors match meaning where keywords find nothing.

Drill F2. Support search mixes part numbers and plain-language questions. Hybrid search wins today.

Change: "queries mix codes and natural language" -> "every query is an exact part number and the latency budget allows one index".

Flip: The answer flips from hybrid to lexical. Hybrid pays merge and rerank latency for coverage the workload no longer needs. Exact-term queries on one index run faster and simpler.

Stage 8C - L12 worked-scenario drills: the 7-step best-answer method

Six end-to-end scenarios across domains. One decision method for all of them.

The 7-step best-answer decision method

Step 1 extracts the objective and quotes the scenario phrase. Step 2 extracts the hard constraints. Step 3 names the layer: model, retrieval, network, IAM, encryption, orchestration, deployment, capacity, evaluation, or governance. Step 4 removes every option that violates a constraint.

Step 5 ranks what remains. Step 6 checks hidden dependencies. Step 7 validates that the answer is complete.

W1 - RAG vector-store pick original exam-style practice

Scenario. A 200-person SaaS company holds 80,000 support articles. Three engineers own the search. None has search expertise. They need semantic search with tenant isolation and monthly document updates. Launch is in three weeks.

  1. Objective. Quote: "Launch is in three weeks" and "semantic search". The goal is fast shipment of meaning-based search.
  2. Hard constraints. Three engineers, no search expertise. Tenant isolation. Monthly updates. 80,000 articles.
  3. Layer. Retrieval.
  4. Eliminate. Self-managed OpenSearch needs search expertise the team lacks. It fails the team constraint.
  5. Rank. Bedrock Knowledge Bases first: managed chunking, embedding, and index. Aurora pgvector second: medium ops for a SQL team. OpenSearch last.
  6. Hidden dependencies. Tenant isolation needs a tenant_id metadata filter on every query. Monthly updates need an S3-event sync trigger. The managed chunking strategy is fixed.
  7. Validate. Bedrock Knowledge Bases plus the tenant filter plus the sync trigger covers search, isolation, and freshness. The design is complete.

Final pick. Bedrock Knowledge Bases with a tenant_id metadata filter and S3-triggered ingestion sync.

Counterfactual. Change "none has search expertise" to "the team must own custom hybrid scoring". The answer flips to self-managed OpenSearch. Custom scoring needs the control that the managed path cannot give.

W2 - Agent-safety design original exam-style practice

Scenario. A shopping assistant looks up orders freely. It processes refunds up to $500. The refund tool charges the card. The fraud team requires a human check on every refund above $50.

  1. Objective. Quote: "processes refunds" with "a human check on every refund above $50". The goal is safe refunds with human approval.
  2. Hard constraints. Lookups are free. Refunds are irreversible. The threshold is $50. Card charges must never double.
  3. Layer. Orchestration and safety.
  4. Eliminate. A free agent loop fails: it can fire the refund with no gate. A Lambda-held wait fails: the minutes cap kills a long human wait.
  5. Rank. Bedrock Agents plus a Step Functions approval gate first. Return of control to the app second. A manual review queue last: too slow.
  6. Hidden dependencies. The refund tool needs an idempotency key: retries are normal in agent loops. Tool results stay untrusted data. Guardrails screen the inputs.
  7. Validate. The agent calls get_order freely. Above $50 the workflow pauses for the human. The loop resumes with approve or deny. The idempotency key blocks double charges. Complete.

Final pick. Bedrock Agents with a Step Functions approval gate on refunds above $50 and an idempotent refund tool.

Counterfactual. Change "the agent writes a schema-valid refund summary" to "the agent must produce a financially correct refund total". The pick flips from model-written text to a deterministic calculator tool call. A JSON schema proves shape, never arithmetic.

W3 - Cost-optimization routing choice original exam-style practice

Scenario. A Q&A app serves 2,000,000 requests per month. About 80% are simple FAQ lookups. The rest need deep reasoning. One large model serves all traffic today. The bill must fall by half with no quality drop on hard queries.

  1. Objective. Quote: "The bill must fall by half with no quality drop on hard queries". The goal is lower spend with the quality bar intact.
  2. Hard constraints. 2M requests per month. An 80/20 split. Quality measured on the hard 20%.
  3. Layer. Deployment and cost.
  4. Eliminate. One large model for all traffic fails the cost goal. The cheapest model for all traffic fails the quality bar.
  5. Rank. Tiered routing first: small model for FAQ, large model for hard queries. Semantic caching on FAQ repeats second. Prompt caching third: the prefix is short here.
  6. Hidden dependencies. A classifier routes each query. Its error rate needs measurement. Cost per success is the gate, not cost per call. FAQ answers need a TTL.
  7. Validate. The router sends 80% to the small model. The golden set confirms hard-query quality. Cost per success falls by half. Complete.

Final pick. Tiered model routing with semantic caching on repeated FAQ questions.

Counterfactual. Change "80% are simple FAQ lookups" to "every query needs deep reasoning". Tiering dies and provisioned throughput on the large model wins for the steady volume.

W4 - Cross-account private-connectivity design original exam-style practice

Scenario. Account A holds the app in a private subnet. Account B holds Bedrock access and the KMS (Key Management Service) key for the data. Compliance forbids any traffic on the public internet. Both accounts demand least privilege.

  1. Objective. Quote: "forbids any traffic on the public internet". The goal is private cross-account model access.
  2. Hard constraints. Two accounts. A private subnet. Least privilege on both sides. KMS-encrypted data.
  3. Layer. Network, IAM (Identity and Access Management), and encryption.
  4. Eliminate. A NAT gateway plus internet fails the compliance rule. One shared role fails least privilege.
  5. Rank. A VPC (Virtual Private Cloud) interface endpoint with PrivateLink in account A plus a cross-account role first. VPC peering second: heavier. A public endpoint with IP rules last: it violates the rule.
  6. Hidden dependencies. The endpoint policy must allow bedrock:InvokeModel. The KMS key policy must name account A plus a grant. Private DNS must resolve the endpoint. The trust policy needs an external ID against the confused deputy.
  7. Validate. The call stays on the private network. Both policies allow. The external ID is present. A decrypt round trip succeeds. Complete.

Final pick. An interface endpoint in account A plus a cross-account role with an external ID. The endpoint policy scopes to the model. A KMS grant covers account A.

Counterfactual. Change "forbids any traffic on the public internet" to "public internet allowed, only auth matters". The endpoints drop out and an IAM-only design wins.

W5 - Evaluation-design question original exam-style practice

Scenario. A team ships prompt updates weekly to a RAG support bot. They must catch quality drops before users do. They track relevance, groundedness, and tone. The budget allows one engineer-day per week for evaluation.

W6 - Resilience and fallback design original exam-style practice

Scenario. A checkout fraud check calls a Bedrock model at 500 requests per second. The model is served in one Region only. Peak season allows at most 30 seconds of degraded answers.

  1. Objective. Quote: "at most 30 seconds of degraded answers". The goal is fast recovery at peak load.
  2. Hard constraints. 500 requests per second. A single-Region model. A 30-second degradation budget.
  3. Layer. Resilience and deployment.
  4. Eliminate. Single-Region on-demand only fails: a regional outage outlasts the budget. Unbounded retries fail: they add latency under load.

  7. Validate. Failure drills show recovery inside 30 seconds. The breaker trips on error rate. The fallback serves cached verdicts. Complete.

Final pick. A cross-region inference profile with a Step Functions circuit breaker and a cached fallback.

Stage 8D - Troubleshooting playbooks: the ten L11 missed

Cross-domain failures beyond the twelve playbooks in L11. Same loop, new territory.

How to run a playbook

L11 taught twelve playbooks. These ten cover the failures L11 left out.

Every playbook follows one loop.

The loop runs: symptom, likely causes, evidence, diagnostic order, minimal correction, verification, prevention.

The ten playbooks

Wrong request schemas. Symptom: the call fails with a validation error before the model runs. Likely causes: the body was built for model family A but sent to family B. A required field is absent. A field has the wrong type. Evidence to collect: the exact request body, the model ID, and the error text. Diagnostic order: read the error field name, compare the body against the target model contract, then confirm the model ID. Minimal correction: rebuild the body per the model contract, or switch to Converse for one schema. Verification: one successful call per model family in use. Prevention: contract tests per model in the pipeline.

Unsupported model features. Symptom: tool-use blocks go ignored, or streaming returns full text with no chunks. Likely causes: the model predates the feature, the API lacks support for it on that model, or the Region lacks it. Evidence to collect: the model ID, the API name, and the feature list for that model. Diagnostic order: confirm the model supports the feature, confirm the API supports it on that model, then check the Region. Minimal correction: switch to a model with the feature, or hand-roll the tool loop on InvokeModel. Verification: a canary call shows the feature working. Prevention: keep a capability matrix per model in config and fail fast at startup.

Missing permissions. Symptom: AccessDenied on bedrock:InvokeModel though the code path looks right. Likely causes: the identity policy misses the action. An explicit deny hides in another policy. The endpoint policy blocks the call. The KMS key policy misses the caller. Evidence to collect: the CloudTrail error event, the identity policy, the endpoint policy, and the key policy. Diagnostic order: read the CloudTrail error first, then the identity policy, then the endpoint policy, then the key policy. Test the endpoint policy from outside the VPC. Minimal correction: add the missing allow and never broaden to star. Verification: the exact call succeeds under the same identity. Prevention: run IAM Access Analyzer on every policy change.

DNS failures. Symptom: the endpoint hostname does not resolve inside the VPC, and calls time out at connect. Likely causes: private DNS is off on the interface endpoint, the app uses the public hostname, or the DHCP option set is wrong. Evidence to collect: name resolution output from inside the VPC and the endpoint DNS settings. Diagnostic order: resolve from inside versus outside the VPC, check the private DNS flag on the endpoint, then check the DHCP options. Minimal correction: enable private DNS on the interface endpoint. Verification: the hostname resolves to private IPs from the subnet. Prevention: add a connectivity test to the deploy pipeline.

Security-group failures. Symptom: the connection hangs with no error, just a timeout. Likely causes: the security group misses the outbound HTTPS rule. The NACL (network access control list) misses the inbound reply rule. A NACL is stateless, so the reply needs its own rule. Evidence to collect: the security group rules, the NACL rules, and VPC flow logs. Diagnostic order: check the security group outbound rule, check the NACL inbound reply rule, then read flow logs for rejects. Minimal correction: add the missing rule: outbound on the security group, both directions on the NACL. Verification: the call completes and flow logs show accepts. Prevention: keep the rules in IaC and alarm on flow-log rejects.

Timeouts. Symptom: calls fail at a fixed duration, and long agent runs die mid-loop. Likely causes: the Lambda minutes cap, the API Gateway timeout, an agent loop with no step cap, or one slow tool in the loop. Evidence to collect: the duration of failed calls, the timeout setting per layer, and loop step counts. Diagnostic order: match the failure time to a layer limit, check the loop step count, then time the slowest tool. Minimal correction: move long waits to Step Functions, cap agent steps, and stream for chat UX. Verification: the 99th-percentile latency fits under the smallest layer limit. Prevention: document a timeout budget per layer and alarm near the line.

Excessive agent steps. Symptom: the agent runs 40 turns on a 3-turn task, and the token bill spikes. Likely causes: no max steps configured, a tool returns output the model cannot parse, or no stop condition exists. Evidence to collect: step counts per run, tool outputs in the trace, and the stop config. Diagnostic order: count the steps, read the trace for the repeated failed tool, then check max steps and timeouts. Minimal correction: set a step cap and a per-run token budget, and fix the failing tool output format. Verification: 95% of runs finish under the cap. Prevention: add a circuit breaker after repeated tool failures and alarm on step counts.

Duplicate side effects. Symptom: customers get charged twice, or two tickets exist for one request. Likely causes: a retry without an idempotency key, a webhook delivered twice, or the agent retried the tool. Evidence to collect: duplicate records with timestamps, retry logs, and the tool key handling. Diagnostic order: match duplicates to retry events, check for the idempotency key on the call, then check webhook dedupe. Minimal correction: add idempotency keys on every mutating call and dedupe webhooks by event ID. Verification: replay a duplicate delivery and confirm one effect lands. Prevention: require idempotency in the tool contract and test it in the pipeline.

Unauthorized retrieval. Symptom: tenant A sees tenant B documents inside answers. Likely causes: the query carries no metadata filter, the filter runs after retrieval, or the attribute name is wrong. Evidence to collect: the filter text on the query, the tenant IDs on retrieved chunks, and the index mapping. Diagnostic order: reproduce with two tenants, read the filter on the query, then confirm the tenant attribute exists on the chunks. Minimal correction: apply the tenant_id filter before the vector search on every query. Verification: a cross-tenant probe returns zero hits. Prevention: assert the filter in code and fail closed when it is absent. Keep separate indexes for regulated tenants.

Hallucinations despite relevant context. Symptom: the chunks hold the right facts, yet the answer invents new ones. Likely causes: the prompt buries the context, no grounding check runs, the temperature is too high, or long context dilutes the key facts. Evidence to collect: the prompt with chunk positions, the answer claims, and grounding scores. Diagnostic order: confirm the chunks sit in the prompt, map each claim to a chunk, then check temperature and the prompt version. Minimal correction: lead with "answer only from the context", add the contextual grounding filter, lower the temperature, and trim chunks. Verification: the groundedness score clears the bar on the golden set. Prevention: run the grounding check in the eval pipeline with the prompt regression gate.
