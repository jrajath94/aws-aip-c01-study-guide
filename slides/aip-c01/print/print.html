How AWS asks questions

Each question has a company, a constraint, and a design that is broken or incomplete. Several options look correct. One option meets every constraint at the same time.

  1. Read the last sentence of the stem. Note what it asks for.
  2. List each constraint. Examples are a cost ceiling, a latency budget, a compliance rule, and an existing AWS footprint.
  3. Pick the option that meets all constraints.
  4. Choose the simplest managed option. Choose custom work only when a constraint forces it.

Part 1B · Concepts course

Build the vocabulary first, then the services

Each lesson starts from one first principle. The next lesson depends on the one before it. Read the lessons in order. The exam uses these ideas in every domain. If a question uses a word you cannot define, return to the lesson for that word.

Lesson 1 · Tokens and the context window

First principle. A model reads and writes tokens. A token is a piece of text, often a word part. The model has a fixed limit on the tokens it can hold in one call. That limit is the context window.

Input tokens include the instructions, the conversation, and any retrieved text. Output tokens are the reply. Both count toward the context window. Both are billed. Output tokens usually cost more per token than input tokens. Count tokens before the call to avoid overflow. CountTokens estimates the count for a supported model.

Diagram: tokens fill one context window.

Exam tie. Domain 4 task 4.1 uses token price. Domain 1 task 1.2 uses the context window as a model axis. Domain 5 task 5.2 uses token count for truncated output.

Exam trap. Context overflow drops the end of a long input. The output looks cut off or ignores the last section.

Lesson 2 · Inference

First principle. Inference is the step where a trained model reads input and produces output. Each call has two phases. The model first reads the whole input. It then writes the output one token at a time.

Time to first token depends mostly on the input length and the queue. Tokens per second depends on the model and capacity. Streaming sends each token as it appears, which improves perceived speed. It does not shorten the total generation time. Three AWS modes serve inference. On-demand charges per token and has no commitment. Provisioned Throughput reserves model units for a steady rate. Batch inference runs offline from S3 to S3 at a lower price for select models.

Diagram: inference has a read phase and a write phase.

Exam tie. Domain 2 task 2.2 chooses the mode. Domain 4 task 4.2 measures time to first token and throughput. Domain 4 task 4.1 uses the mode as a cost lever.

Exam trap. Buying Provisioned Throughput does not change the speed of one call. It changes the reserved capacity. The call must use the provisioned model ARN.

Lesson 3 · Embeddings and similarity

First principle. An embedding maps text to a list of numbers, called a vector. Texts with similar meaning get vectors that point in similar directions. Similarity is a score that compares two vectors.

Titan Text Embeddings v2 outputs 1024, 512, or 256 dimensions. More dimensions hold more detail and cost more storage and compute. Cohere Embed separates queries from documents with an input type value. Use search_query for questions and search_document for passages. Embedding calls use InvokeModel with an embedding model. Converse does not produce embeddings.

Diagram: three vectors in a plane. Two requests with similar meaning point the same way.

Exam tie. Domain 1 task 1.4 and task 1.5 test the dimension choice and the input type. Domain 2 task 2.3 tests the API choice.

Exam trap. A bigger embedding model does not fix a bad chunk. The chunk must hold one complete answer.

Lesson 4 · Vector search and reranking

First principle. Vector search finds the stored vectors closest to a query vector. It returns the top-k results. Closest is not the same as most relevant. A reranker scores each candidate against the question.

Hybrid search adds keyword matching to vector search. Keyword search finds exact codes and citation strings. Vector search finds related meaning. Metadata filters narrow the search. Check the store documentation for when the filter applies.

Exam tie. Domain 1 task 1.4 selects the store. Domain 1 task 1.5 selects hybrid search, reranking, and query rewrite.

Exam trap. Reranking fixes order. It does not add a chunk that retrieval missed.

Lesson 5 · Retrieval-augmented generation (RAG)

First principle. A model answers from its weights, which are fixed at training time. RAG adds facts at query time. The system retrieves text from your documents and places it in the prompt. The model answers from that text and cites it.

RAG has two paths. The ingest path runs ahead of time. It chunks, embeds, and stores documents. The query path runs per request. It embeds the question, retrieves chunks, optionally reranks, and generates an answer with citations. Knowledge Bases runs both paths for you.

The RAG diagram in Part 2 shows both paths. Read it after this lesson.

Exam tie. Domain 1 tasks 1.4 and 1.5 cover RAG. Domain 3 task 3.1 uses grounding checks on the answer. Domain 5 task 5.1 splits retriever metrics from generator metrics.

Exam trap. Fine-tuning does not add changing facts. Use RAG for facts that change.

Lesson 6 · Chunking

First principle. A chunk is the unit of text that retrieval returns. A chunk must hold one complete answer. Too large, and the chunk adds noise. Too small, and the chunk loses context.

Fixed-size chunking works for short, self-contained text such as FAQs. Hierarchical chunking uses small child chunks for matching and larger parent chunks for context. It suits manuals and contracts. Semantic chunking splits on meaning and costs more to process. Custom chunking with Lambda keeps tables and figures whole. The chunking strategy is set when the data source is created. To change it, create a new data source and sync it.

Exam tie. Domain 1 task 1.3 selects the chunking strategy. Domain 5 task 5.2 traces quality drops to a changed chunking setting.

Exam trap. A table split across chunks can lose its values. A chunk can look correct alone and still be wrong.

Lesson 7 · Customization: from prompts to LoRA and distillation

First principle. Customization changes the model or its input. Each rung changes more and costs more. Start with the cheapest rung. Stop when the requirement is met.

Prompt engineering changes only the instructions. RAG adds facts at query time. Fine-tuning changes the model weights with labeled examples. LoRA is a parameter-efficient method. It freezes the base weights and trains small adapter matrices. The update is the product of two small matrices, so the adapter is much smaller than the base model. You can store several adapters and load the one that fits the task. Distillation trains a smaller student model to copy a larger teacher model on one task. The student is cheaper and faster for that task.

Diagram: LoRA keeps the base weights frozen and trains a small adapter.

Exam tie. Domain 1 task 1.2 covers the customization ladder. Domain 2 task 2.2 covers SageMaker AI deployment of a custom model. Domain 3 task 3.4 covers model documentation for a tuned model.

Exam trap. LoRA does not fix facts that change. A tuned adapter still holds the facts from its training data. Use RAG for changing facts.

Lesson 8 · Agents and tools

First principle. An agent is a loop. The model reasons about the next step. It calls a tool. It observes the result. It repeats until a stop condition is met. A loop needs limits, because each step costs time and money.

A tool has a schema, which names its inputs. An action group in Bedrock Agents links the agent to a Lambda function. AgentCore Gateway exposes tools through MCP. Each tool call can pass through Policy in AgentCore before it runs. Trace records each step, the chosen tool, and the observation.

Exam tie. Domain 2 task 2.1 covers the agent loop, action groups, and aliases. Domain 2 task 2.2 covers AgentCore. Domain 3 task 3.1 covers the policy check.

Exam trap. A prompt that says "stop after three steps" is not a control. Enforce the limit in the workflow or the tool layer.

Lesson 9 · Safety layers

First principle. No single control stops every failure. Each layer checks something different. Input checks run before the model. Output checks run after it. Data controls protect storage and access.

Guardrails apply six policy types on input and output. Contextual grounding checks test whether the answer is supported by the source. The prompt attack filter detects jailbreak and injection patterns on input. Comprehend detects PII in text. Macie finds sensitive data in S3 at rest. KMS encrypts data at rest. PrivateLink keeps API traffic inside the VPC.

Exam tie. Domain 3 tasks 3.1 and 3.2 cover these layers. Domain 3 task 3.3 covers the audit side.

Exam trap. A denied topic is not a prompt attack detector. Use the prompt attack filter for attacks.

Lesson 10 · Evaluation

First principle. An evaluation compares outputs with a standard. The standard can be a known answer, a rubric, or a human judgment. The method must match the claim.

Automatic metrics suit facts with known answers. An LLM judge scores qualities such as faithfulness at scale. A judge must be calibrated against human ratings first. A golden set holds trusted prompts and answers. Regression suites rerun the golden set on each change. Canary releases send a small share of traffic to a new version.

Exam tie. Domain 5 tasks 5.1 and 5.2 cover evaluation methods, golden sets, and release gates.

Exam trap. An uncalibrated judge gives opinions, not measurements.

Lesson 11 · Operations signals

First principle. A production system emits three kinds of signal. Metrics count things over time. Traces follow one request across services. Logs hold the payloads. Each signal answers a different question.

CloudWatch metrics track tokens, invocations, and throttles. Anomaly detection builds a band from history and alarms when a value leaves it. X-Ray traces requests and downstream calls. Invocation logs hold prompts and completions. Logs Insights searches them. Model Monitor watches drift in structured features, not free-text quality.

Exam tie. Domain 4 task 4.3 covers monitoring. Domain 5 task 5.2 covers debugging.

Exam trap. Metrics alone cannot rebuild what the model received. Keep the payload logs under access control.

Part 1C · Service deep dives

AWS AppConfig and Amazon SageMaker AI, from first principles

Both services appear in many questions. AppConfig controls how a running application reads its settings. SageMaker AI hosts and prepares models. Read each service from the purpose, then the parts, then the exam tie.

AWS AppConfig

First principle. A running application reads its settings from somewhere. If a setting changes, the application must pick up the change without a code release. AppConfig is the place that holds the settings and rolls them out.

Parts. A configuration profile defines where the settings live. The stores are the AppConfig hosted configuration store, AWS Secrets Manager, Systems Manager Parameter Store, and Amazon S3. A deployment strategy sets how fast a change reaches the application. It can roll out in steps over a period of time. Validators check the configuration before deployment. They check syntax and meaning. Alarms watch CloudWatch metrics during a deployment. If an alarm fires, AppConfig rolls the change back. Feature flags let you release a capability to some users first.

Diagram: a configuration change passes a validator, rolls out over a strategy, and rolls back on an alarm. Schematic, based on the official overview.

Model switch pattern. Store the model ID in a hosted configuration profile. The Lambda function reads the ID at runtime. A change to the ID rolls out with a deployment strategy. A CloudWatch alarm on errors rolls it back. No code release is needed. This is the pattern in Domain 1 task 1.2.

Exam trap. AppConfig controls settings. It does not route traffic to a model by prompt complexity. It does not host the model.

Amazon SageMaker AI

First principle. A custom or fine-tuned model needs a place to run, a way to track versions, and a way to watch its behavior. SageMaker AI covers those three needs. Read its parts in that order.

Hosting. A real-time endpoint serves steady traffic with autoscaling. A serverless endpoint serves intermittent traffic and scales to zero. Its memory runs from 1 GB to 6 GB. Provisioned Concurrency keeps capacity warm for predictable bursts. The first request after idle time can have a cold start. An asynchronous endpoint queues long requests. Its payload comes from S3. The result goes to S3. It supports processing times up to one hour and near real-time latency.

Registry. The model registry groups model versions. Each version has an approval status. A registry can share versions across accounts. Pipelines can require approval before deployment. A rollback points the endpoint to an earlier approved version.

Monitoring. Model Monitor watches drift in structured features and predictions. It does not score free-text answer quality. The SageMaker documentation states that Model Monitor is no longer open to new customers. Check that status before you rely on it.

Customization. SageMaker AI fine-tunes a model. LoRA trains small adapters on top of frozen base weights. Distillation trains a smaller student from a teacher. Register each tuned version. Deploy it to an endpoint. Track the approval status.

Exam trap. SageMaker AI endpoints host models. Bedrock hosts the managed foundation models. Pick by who owns the model.

Visual unit 1

Converse and InvokeModel: two doors to one model

First principle. Your application sends a request. Converse uses one request format for chat and tools across models. InvokeModel sends the body that one provider expects.

  • Use Converse for chat, tool use, and multimodal input on supported models.
  • Use InvokeModel for embeddings and provider-specific fields.
  • A Claude body needs anthropic_version and max_tokens when you call InvokeModel.

Exam tie. Domain 2 task 2.3 and Domain 1 task 1.2 test this choice. Embeddings always use InvokeModel.

Exam trap. Converse does not produce embeddings. A Titan body sent to Claude fails.

Visual unit 2

On-demand, Provisioned Throughput, and batch: three load shapes

First principle. Capacity is a shape problem. Spiky, steady, and offline load need different purchases. Match the purchase to the shape of the traffic.

  • On-demand pays per token and has no commitment. It suits spiky or unknown traffic.
  • Provisioned Throughput reserves model units. It suits a steady baseline.
  • Batch runs offline from S3 to S3. It suits work that can wait for hours.

Exam tie. Domain 2 task 2.2 and Domain 4 task 4.1. Mixed traffic uses a reserved baseline and on-demand spikes.

Exam trap. More model units do not help a call that still uses the base model ID.

Visual unit 3

Cross-Region inference profiles

First principle. A profile ID names a set of Regions. A request that uses the profile can run in any Region in that set. The profile spreads load. It does not keep data in one place.

  • Call the profile ID, such as one with the us. or eu. prefix.
  • A geographic profile keeps routing inside its listed Regions.
  • A global profile can route outside a strict residency boundary.

Exam tie. Domain 1 task 1.2 and Domain 4 task 4.1. Domain 3 task 3.2 covers data scope.

Exam trap. Cross-Region inference is not automatic failover for your app. Add retries and fallback in the application.

Visual unit 4

Prompt caching: the stable prefix pays once

First principle. A model reads the prompt from the start. If the start is the same as an earlier call, the system can reuse that work. The reused part must match exactly and sit before the changing text.

  • Mark the static prefix with a cache checkpoint.
  • Keep the user message at the end.
  • The default time to live is 5 minutes.

Exam tie. Domain 4 task 4.1 and Domain 2 task 2.5. The API marks the checkpoint with a cachePoint block. Caching lowers the cost of a repeated prefix.

Exam trap. A changing value inside the prefix breaks the cache. Move it to the end.

Visual unit 5

Semantic cache: match the meaning, not the words

First principle. A semantic cache stores answers next to the embedding of each question. A new question is embedded. If a stored question is close enough, the stored answer returns. Otherwise the model answers and the pair is stored.

  • Hit: return the stored answer. No model call.
  • Miss: call the model, then store the answer.
  • Works when many questions repeat with different words.

Exam tie. Domain 4 task 4.1 and Domain 4 task 4.2. Embeddings come from Domain 1 task 1.4.

Exam trap. Personal or unique questions rarely hit. A semantic cache saves little for them.

Visual unit 6

Chunk shape: fixed, hierarchical, and whole tables

First principle. A chunk is one piece of a document that retrieval can return. A chunk must hold one complete answer. The shape of the document decides the shape of the chunk.

  • Fixed size suits FAQs and short text.
  • Hierarchical keeps small child chunks for matching and larger parents for context.
  • Custom Lambda chunking keeps a table or figure whole.

Exam tie. Domain 1 task 1.3. Domain 5 task 5.2 traces quality drops to chunking.

Exam trap. A table split across two chunks loses its values. Each half can look correct alone.

Visual unit 7

Hybrid search and reranking: a funnel

First principle. Retrieval returns many candidates. Each search method finds different candidates. Merge the lists. Then score each candidate against the question and keep the best few.

  • Keyword search finds exact codes and citation strings.
  • Vector search finds related meaning.
  • The reranker orders candidates by relevance. It does not add missing chunks.

Exam tie. Domain 1 task 1.5. Domain 5 task 5.1 measures retriever quality.

Exam trap. Similarity is not relevance. Rerank before generation.

Visual unit 8

Agent versions: DRAFT, version, alias

First principle. Editing an agent changes DRAFT. Callers do not use DRAFT. A version is a frozen snapshot. An alias points to one version. Callers use the alias, so you can move traffic without changing the caller.

  • Edit DRAFT, then prepare the agent.
  • Create a version from the prepared DRAFT.
  • Point the alias to the new version.

Exam tie. Domain 2 task 2.1. Domain 5 task 5.2 covers the old-behavior symptom.

Exam trap. A passing console test on DRAFT does not prove the alias works.

Visual unit 9

AgentCore components around one agent

First principle. An agent needs a place to run, memory, tools, identity, rules, and traces. AgentCore puts those parts behind one service. Each part answers one question about the agent.

  • Runtime hosts the agent code from any framework.
  • Memory keeps context. Gateway exposes tools as MCP tools.
  • Identity decides who can call. Policy checks each tool call. Observability records traces.

Exam tie. Domain 2 task 2.2. Domain 3 tasks 3.1 and 3.2. Domain 4 task 4.3.

Exam trap. AgentCore is not a model. It hosts and governs the agent around the model.

Visual unit 10

Lambda limit versus a waiting workflow

First principle. A Lambda invocation ends after at most 15 minutes for a standard function. A wait for a person can last days. A durable workflow stores its state and resumes later.

  • Keep each Lambda step short.
  • Step Functions Standard keeps state for waits and runs up to one year.
  • A callback task token pauses the flow until a person or system responds.

Exam tie. Domain 2 task 2.2 and Domain 1 task 1.6.

Exam trap. A Lambda that waits for a person pays for the wait and hits the limit.

Visual unit 11

API Gateway timeout versus a stream

First principle. An API Gateway REST integration has a default timeout of 29 seconds. A slow model call that runs longer loses its connection at that point. A stream that stays open can carry tokens for longer.

  • Raising the Lambda timeout does not change the gateway limit.
  • WebSocket APIs keep a connection open for streams.
  • An asynchronous job returns a job ID, then the client polls or receives the result.

Exam tie. Domain 2 tasks 2.3 and 2.4.

Exam trap. Streaming improves perceived speed. It does not extend a REST timeout.

Visual unit 12

Retry with backoff and jitter

First principle. A failed call can succeed later. Retrying at once adds load to a service that is already busy. Waiting longer after each failure spreads the load. Random jitter stops many clients from retrying at the same moment.

  • Wait longer after each failure.
  • Add random jitter to each wait.
  • Stop after a maximum number of attempts, then fall back.

Exam tie. Domain 2 task 2.4. Domain 4 task 4.1 covers quotas and throttling.

Exam trap. A tight retry loop makes an overload worse. It is never the correct answer.

Visual unit 13

Judge calibration before trust

First principle. An LLM judge gives a score. A score means something only when it agrees with people. Rate a fixed golden set with humans. Run the judge on the same set. Compare the two.

  • Low agreement means the judge is not valid for the claim.
  • Pin the judge model ID. A new judge gives new scores.
  • Human review covers tone and voice.

Exam tie. Domain 5 task 5.1. Domain 3 task 3.4 uses judges for fairness checks.

Exam trap. An uncalibrated judge gives opinions, not measurements.

Visual unit 14

Canary and rollback: release in steps

First principle. A new version can fail on real users. A canary sends a small share of traffic to it first. Metrics decide the next step. If a metric breaks, traffic returns to the last approved version.

  • Start at a small share, such as 10 percent.
  • Move traffic only when the alarms stay quiet.
  • Rollback points traffic to the last approved version.

Exam tie. Domain 5 tasks 5.1 and 5.2. Domain 2 task 2.3 covers AppConfig and aliases.

Exam trap. A re-sync or a prompt edit is a release. It needs the same gate.

Visual unit 15

Four monitoring signals, four questions

First principle. Each signal answers one question. Metrics count. Traces follow one request. Logs hold payloads. Quality checks score answers over time.

  • Metrics: is it slow or expensive?
  • Traces: which step is slow?
  • Logs: what did the model receive? Judge: is the answer good?

Exam tie. Domain 4 task 4.3. Domain 5 task 5.2.

Exam trap. Metrics alone cannot rebuild a wrong answer. Keep the payloads.

Visual unit 16

Who called versus what was sent

First principle. CloudTrail records who called which API, when, and from where. Invocation logs record the prompt and the response. These are two different records. Each one answers a different audit question.

  • CloudTrail answers identity and timing.
  • Invocation logs answer content.
  • Encryption with KMS protects both at rest.

Exam tie. Domain 3 task 3.2 and task 3.3.

Exam trap. CloudTrail does not show row content. Invocation logs show the original request even when output is masked.

PrivateLink and the VPC boundary

First principle. A VPC endpoint gives private IP access to an AWS service. Traffic from the VPC stays on the AWS network. Each Bedrock plane has its own endpoint.

  • bedrock-runtime serves model invocations.
  • bedrock-agent and bedrock-agent-runtime serve agents.
  • bedrock serves the control plane.

Exam tie. Domain 3 task 3.2.

Exam trap. One runtime endpoint does not cover agent calls. Check each plane.

Visual unit 18

Organization rules with SCPs and condition keys

First principle. A service control policy sets the most a member account can do. A condition key limits one action. A condition on the guardrail identifier can make the guardrail mandatory on each call.

  • The IAM layer applies even if application code changes.
  • A call without the guardrail identifier is denied.
  • This is a rule across accounts, not a setting in one app.

Exam tie. Domain 3 task 3.3.

Exam trap. A guardrail that only the app calls can be skipped. Enforce it in IAM.

Visual unit 19

Outposts versus a Region

First principle. A Region runs in AWS data centers. Outposts runs AWS services on your premises. Data processed on Outposts stays at the site for the rule that requires it.

  • Use a Region for most workloads.
  • Use Outposts when a rule says the data stays on site.
  • The same AWS programming interfaces apply on Outposts.

Exam tie. Domain 2 task 2.3.

Exam trap. A Region in the cloud does not keep data on your premises.

Visual unit 20

Distillation and cascade routing

First principle. A large model is accurate and costly. A small model is cheaper and faster. Distillation trains the small model to copy the large one on one task. Cascade routing tries the small model first and escalates only when needed.

  • Distillation builds a cheaper student for a narrow task.
  • Cascade escalates on uncertainty or complexity.
  • Routing needs a signal. Without a signal the router cannot decide.

Exam tie. Domain 1 task 1.2. Domain 4 task 4.1 and task 4.2.

Exam trap. Sending every request to the largest model wastes money.

G1 · Vector quantization: fewer bits, less memory

First principle. A float32 vector dimension uses 4 bytes. Quantization stores fewer bits per dimension. Smaller vectors need less index memory, and index memory is often the largest cost in a RAG system.

Facts. In OpenSearch with the Faiss engine, FP16 scalar quantization (SQfp16) halves memory. It needs OpenSearch 2.13 or later. Source: OpenSearch k-NN vector quantization, an OpenSearch project page, not an AWS page. Binary quantization stores 1 bit per dimension, which is 32 times smaller than float32. 2-bit and 4-bit options give 16 and 8 times. Those figures come from an AWS blog post, a secondary source.

Arithmetic (design guidance). One 1,536-dimension float32 vector is 6,144 bytes, about 6 KB. Ten million vectors need about 60 GB. One binary vector is 1,536 bits, or 192 bytes. Ten million binary vectors need about 1.9 GB.

Accuracy. The 2 percent accuracy loss in the cursor branch is one example. It is Not in source as a general figure. Measure the loss on your data. Rescore the top candidates with full-precision vectors or a reranker.

H1 · Error codes: which errors to retry

First principle. An error tells you who must act. A quota error needs a slower rate, a capacity error needs a retry, and an input error needs a code fix. Retrying an input error never works.

Facts. ThrottlingException (HTTP 429) means the request exceeded an account quota. Q14 · Prompt caching: checkpoints, TTL, and the prefix rule

First principle. A cache reuses a prefix that matches exactly. Put the static text first, and put the changing text last.

Facts. Implicit caching is on by default and is best effort. Explicit caching uses cache checkpoints. In Converse, add a cachePoint block. In InvokeModel for Claude, add cache_control. A checkpoint needs a minimum of 512 to 4,096 tokens before it, depending on the model. Claude models allow up to four checkpoints per request. Checkpoints are processed in this order: tools, system, then messages. Source: Prompt caching for faster model inference.

Facts. The default TTL is five minutes, and each cache hit resets it. Some models also accept a one-hour TTL with "ttl": "1h". Adding the ttl field to a model that supports only five minutes causes a ValidationException. Caching works for on-demand inference, not batch inference. Cached tokens are billed at the cache-read rate. The inputTokens field excludes cached tokens, so total input equals inputTokens plus cacheReadInputTokens plus cacheWriteInputTokens. Source: the same page.

Design guidance. For calls that arrive more than five minutes apart, use the one-hour TTL on a supported model. For a steady stream of calls, the five-minute TTL stays warm at no extra cost.

Exam tie. Domain 4 task 4.1 (cost) and task 4.2 (performance).

Exam trap. A timestamp or a user name at the top of the prompt changes the prefix on every call. The cache then misses on every call.

R1 · Knowledge base evaluation: which metric answers which question

First principle. A RAG system can fail in two places. Retrieval can miss the right text. Generation can ignore the text or add text that is not in it. Measure each place with its own metric.

Facts. A retrieve-only evaluation job has two built-in metrics. Context relevance measures how relevant the retrieved texts are to the question. Context coverage measures how much of the ground truth the retrieved texts cover. Context coverage needs a ground truth in the prompt dataset. Source: Use metrics to understand RAG system performance.

Facts. A retrieve-and-generate evaluation job has built-in metrics for correctness, completeness, helpfulness, logical coherence, faithfulness, citation precision, citation coverage, harmfulness, stereotyping, and refusal. Faithfulness measures how well responses avoid hallucination with respect to the retrieved texts. Source: the same page.

Exam tie. Domain 5 (evaluation and troubleshooting).

Exam trap. Faithfulness checks support from the retrieved text. It does not check the answer against outside facts.

R2 · OpenSearch shard count: size the shards first

First principle. A shard is a unit of storage and search work. Too few large shards slow recovery. Too many small shards waste CPU and memory.

Facts. By default, OpenSearch Service creates five primary shards, and each has one replica. That is ten shards for each index. You cannot easily change the number of primary shards of an existing index. Decide the count before you index the first document. Source: Choosing the number of shards.

Facts. Keep each shard between 10 and 30 GiB for search latency. Keep each shard between 30 and 50 GiB for write-heavy log analytics. Estimate the primary shard count with this formula: (source data plus room to grow) times (1 plus indexing overhead), divided by the desired shard size. For 66 GiB that does not grow, 30 GiB shards give about three shards. Keep no more than 25 shards for each GiB of Java heap on a node. Source: the same page.

Design guidance. Size the index from current data and expected growth. Then check the shard count against the heap of each node.

Exam tie. Domain 1 (vector store setup and scale).

Exam trap. More shards do not make search faster. Each shard uses CPU and memory, so many small shards can cause performance problems.

R3 · Lambda environment variables: encryption is not a secret store

First principle. A value in function configuration is visible to anyone who can read that configuration. Store credentials in a service built to hold secrets.

Facts. Lambda stores environment variables encrypted at rest. You can set a customer managed key with KMSKeyARN. The variables total 4 KB at most. Keys start with a letter, have at least two characters, and contain only letters, numbers, and underscores. Source: Working with Lambda environment variables.

Facts. AWS recommends AWS Secrets Manager instead of environment variables for database credentials and API keys or authorization tokens. Source: the same page.

Facts. An update to the environment with update-function-configuration replaces the whole Variables structure. Include every existing value in the request. Source: the same page.

Design guidance. Keep non-secret settings, such as a bucket name or a log level, in environment variables. Read credentials from Secrets Manager at run time.

Exam tie. Domain 3 (controls and secrets).

Exam trap. Encryption at rest does not make a value a secret. The page still recommends Secrets Manager for credentials.

R4 · S3 events invoke Lambda: permission and loop risk

First principle. A storage event can start code. The code must have permission to run. The event must not start the same code again without end.

Facts. Amazon S3 invokes the Lambda function asynchronously when an object is created or deleted. You configure the bucket notification, or the Lambda console adds the trigger for you. The function's resource-based policy must allow S3 to invoke it. If the function uses the AWS SDK to manage S3, its execution role needs S3 permissions. Source: Process Amazon S3 event notifications with Lambda.

Design guidance. Write function output to a second bucket. Or limit the trigger to one prefix that holds incoming objects.

Exam tie. Domain 2 (event-driven integration).

Exam trap. If a function writes to the bucket that triggers it, the function can run in a loop. The official page gives this warning.

R5 · Step Functions: timeouts, retries, and catchers

First principle. A workflow must stop a slow step, retry a transient failure, and route a final failure to a safe path.

Facts. A Task state reports States.Timeout when it runs longer than TimeoutSeconds. The whole execution also reports States.Timeout when it runs longer than its own TimeoutSeconds. Source: Handling errors in Step Functions workflows.

Facts. A Retry field defaults to IntervalSeconds 1, MaxAttempts 3, and BackoffRate 2.0. JitterStrategy defaults to NONE. MaxDelaySeconds caps the wait between retries. A Catch field sends the error to a Next state. When both fields exist, Retry runs first. Source: the same page.

Facts. States.Runtime is not retriable. A retry or catch on States.ALL does not catch it. Source: the same page.

Facts. A prompt node in a flow uses a prompt from Prompt management. Source: the same page.

Design guidance. Test each variant on the same test values. Compare the outputs before you choose a variant for production.

Exam tie. Domain 2 (implementation and prompt management) and Domain 5 (testing).

Common misconception. A prompt in application code has no version history. Prompt management keeps saved versions and lets an application deploy a chosen version.

N2 · Converse API: tool use and guardrails in one call

First principle. One request format for every chat model keeps application code stable when the model changes.

Facts. The Converse API sends messages to a model. You call Converse for a full response, or ConverseStream for a streamed response. You can use Converse to implement tool use and guardrails in your application. Converse needs permission for bedrock:InvokeModel. Source: Carry out a conversation with the Converse API.

Facts. The Converse API is available on the bedrock-runtime endpoint. Source: the same page.

Design guidance. Put the tool definitions and guardrail settings in the Converse request. Keep the tool result handling in your code.

Exam tie. Domain 2 (implementation and integration).

Common misconception. InvokeModel and Converse need different permissions for the same chat. Both calls use the bedrock-runtime endpoint. Converse needs bedrock:InvokeModel.

N3 · SageMaker AI real-time endpoints for low-latency inference

First principle. A real-time endpoint serves one request at a time with low latency. Use it when a user waits for the answer.

Facts. Real-time inference suits interactive workloads with low-latency requirements. You deploy a model to SageMaker AI hosting services and get an endpoint. The endpoint is fully managed. Source: Real-time inference.

Design guidance. Use Bedrock when you need managed foundation models. Use a SageMaker AI endpoint when you host your own model artifact in S3.

Exam tie. Domain 1 (model deployment) and Domain 4 (performance).

Common misconception. A batch job is the right pattern for an interactive chat. Real-time endpoints serve interactive, low-latency requests.

N4 · Bedrock Flows: linked prompts, models, and AWS services

First principle. A workflow links steps. Each step passes its output to the next step.

Facts. Amazon Bedrock Flows links prompts, foundation models, knowledge bases, and other AWS services into one workflow. The flow uses a visual builder. A flow can call AWS Lambda. Charges depend on the resources the flow uses. Source: Amazon Bedrock Flows.

Design guidance. Use a flow when the steps are fixed. Use Lambda code or Step Functions when the steps depend on complex branching in your code. Source for the Step Functions comparison: unit R5.

Exam tie. Domain 2 (orchestration).

Common misconception. A flow runs for free because the builder is in the console. Each model call in a flow is billed.

N5 · AgentCore Gateway: one entry point for tools and models

First principle. Agents need one controlled path to tools. A gateway puts that path in one place.

Facts. Amazon Bedrock AgentCore Gateway is a fully managed AI gateway. It gives one secure entry point for agent traffic. It connects agents to tools, to other agents, and to large language models. Source: Amazon Bedrock AgentCore Gateway.

Facts. The protocol details for MCP tool servers are Not in source in this build. The fetched page describes the gateway at the level above.

Design guidance. Put tool access rules in the gateway. Keep the tool code behind it.

Exam tie. Domain 2 (agents and tool integration) and Domain 3 (access control).

Common misconception. A gateway is only a model router. The official page describes it as the entry point for agents, tools, other agents, and models.

N6 · API Gateway as the front door for AI APIs

First principle. A stable API hides the backend. Clients call one contract, and the backend can change behind it.

Facts. Amazon API Gateway creates, publishes, maintains, monitors, and secures REST, HTTP, and WebSocket APIs. The APIs can access AWS services and other web services. Source: What is Amazon API Gateway.

Design guidance. Put API Gateway in front of a Lambda function that calls Bedrock. Clients keep one contract. The Lambda function owns the model choice.

Exam tie. Domain 2 (integration) and Domain 3 (security).

Common misconception. A GenAI gateway is an AWS product name. The official API Gateway page does not name a GenAI gateway product. Treat the GenAI gateway as a design pattern built from API Gateway and Lambda. Its exact product form is Not in source.

N7 · Amazon Q Developer: an assistant for building and operating AWS

First principle. A developer assistant helps people. It does not serve end users in your application.

Facts. Amazon Q Developer is a generative AI assistant. It helps you understand, build, extend, and operate AWS applications. In an IDE, it gives software development help, such as code chat and inline code completions. It is built on Amazon Bedrock. Source: What is Amazon Q Developer.

Facts. The page states an IDE plugin support end date. Check the page for the current support status before you plan a rollout.

Design guidance. Use Amazon Q Developer for staff who build AWS applications. Build a Bedrock application for your own end users.

Exam tie. Domain 1 (service selection).

Common misconception. Amazon Q Developer replaces a Bedrock application for customers. It is a developer assistant. Your customers need your own application.
