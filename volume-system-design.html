1. First, understand the requirements. Then, design any GenAI application.

Every system design question on the exam is the same. A scenario gives you limits. The correct answer is the cheapest architecture. This architecture must meet all limits. Some people choose services too fast. For example, they say "this needs a Knowledge Base".

These people fail. Other people find the limits first. For example, they find "40,000 documents, updated monthly, citations required, answers under 3 seconds". These people choose correctly. Each limit removes options. Only one design remains.

There are two types of requirements. Functional requirements show what the system does. For example, it answers questions from company documents. It looks up live order status. It sends answers to a chat UI. It gets human approval before it gives refunds.

Non-functional requirements show how well the system does it. For example, latency is how fast each answer must arrive. Scale is requests per day and peak multiples. Cost is the monthly budget. Knowledge freshness is how often documents change. Safety shows who the users are.

It also shows what must never happen. Availability shows what happens when a region has an outage.

Clarify before you design. These questions are half the score in a real design discussion. The exam rewards the answer that finds the missing number. For example, how many requests per day? How fresh must the knowledge be? Does the app need streaming?

What is the cost budget? The scenario usually answers each question in one line. You must find all of them.

Then, estimate. Cost in GenAI is tokens. So, convert early with this equation:

The estimation equation

tokens per day = requests per day &times; tokens per request

monthly bill = tokens per day &times; 30 days &times; price per token

Here: requests per day is the traffic volume. tokens per request is input tokens plus output tokens for one call. price per token is the model price. The price is usually for one million tokens.

Worked example. A support copilot has 100,000 requests each day. Each request has 1,500 input tokens and 300 output tokens. This is 100,000 &times; 1,800 tokens. This equals 180,000,000 tokens per day. 180M &times; 30 equals 5.4 billion tokens each month.

This number shows if prompt caching, batch inference, or a smaller model belongs in the design.

Latency estimation works the same way. Every hop has a limit. The slowest hop decides. Chapter 2 teaches the exact service limits. For example, API Gateway timeouts, Lambda caps, batch inference hours. You do not need the numbers now.

You need the habit of checking the slowest hop.

This rule organizes the whole volume: Start with the simplest approach. This approach must meet every limit. Then, stop. A plain prompt is better than RAG if no new knowledge is necessary. RAG is better than fine-tuning if documents change. Complexity costs money, latency, and failure modes.

So, use complexity only when a limit needs it. Chapter 9 turns this rule into three mechanical ladders. Every chapter between here and there teaches the steps.

It moves upward. It stops at the first approach that meets every limit. Verify proves the choice with an evaluation loop. This happens before and after shipping. See chapter 7.

2. Sync versus async invocation patterns

Why this chapter comes next. Chapter 1 gave you the design procedure. This procedure is: clarify, estimate, choose, verify. The first real decision is how your application calls the model. This chapter shows four invocation patterns. It also shows the ladder that chooses between them.

There are four ways to call a model. Each way has a different latency, payload, and cost. The exam tests the decision. It does not test the syntax.

2.3 Timeouts and retries

The timeout chain. Each hop has a limit. The smallest limit wins. API Gateway has a 29-second integration timeout. Lambda has a 15-minute maximum. The model's own limits constrain Bedrock model invocation.

Design each hop's timeout. Make it comfortably above the p99 of the hop below it. Or separate with a queue.

The retry policy.

  1. Back off with jitter. Use the SDK's exponential backoff with jitter. Do this for throttling (ThrottlingException) and temporary 5xx errors.
  2. Do not retry a bad request. ValidationException means your request body is wrong. Retrying will fail in the same way.
  3. Use a fallback for hard failures. If the main model has errors, retry one time on a smaller model. Or give a cached response.

This graceful degradation is the resilience pattern. The exam rewards this pattern.

Circuit breaking. Agents call downstream tools. Wrap these calls in a Step Functions circuit breaker. Or use a Lambda-level breaker. After N failures in a row, stop calling for a cool-down period. This stops a bad downstream system.

It prevents burning model tokens on retries that will fail.

"2M requests per day baseline plus 10x Friday spikes with sub-3-second latency" means a hybrid solution. Use Provisioned Throughput for the baseline. Use on-demand via Lambda for the spikes. Use streaming for perceived latency. "Entirely SageMaker with GPU autoscaling" fails on cost. It also fails on cold starts.

"fixed EC2 for peak" fails on cost. The exam always punishes single-lever answers. These answers do not fit scenarios with many limits.

Trap, stated plainly.

Provisioned Throughput does not fix outputs that are not deterministic. If the same inputs give different answers, do this. Set temperature to 0. Use deterministic prompts. Use prompt versioning. Do not add more capacity.

PT fixes throttling and latency. It never fixes randomness.

3.1 What a Knowledge Base is

Why this chapter comes next. A Knowledge Base is the managed RAG service. Data sources feed it. Documents and their sync schedules live in data sources.

Amazon Bedrock Knowledge Bases (KB) is the managed RAG service. RAG means retrieval-augmented generation. You do not retrain a model on your documents. You get the correct passages when you ask a question. You give them to the model with the question. So the model answers from those passages.

The KB is the AWS-managed bundle. It does the ingestion, chunking, embedding, indexing, and retrieval for you.

It exists because foundation models are fixed in time. They know nothing about your company. Without RAG, you get three failures. You get hallucinated facts. These are wrong answers that sound confident. You get stale answers.

Training data is months old. You get no citations. There is no way to show which document an answer came from. Fine-tuning is the only other option. It is slower. It costs more.

It cannot cite sources. It becomes stale when a document changes.

Two pipelines run inside it. The exam tests that you know both.

  1. Ingestion (offline, on a sync schedule). Documents go into a data source. This is usually an S3 bucket. The KB parses the documents. It parses PDF, DOCX, TXT, CSV, HTML, and other types. The KB splits documents into chunks (see 3.3). It converts each chunk into an embedding vector. It uses the configured embeddings model (see 3.4). The KB writes the vectors, chunk text, and metadata into the vector store (see 3.5). You start this with a sync job. The sync job runs on a schedule or on demand.
  2. Retrieval (online, per user question). The system embeds the question. It uses the same embeddings model. The vector store returns the nearest chunks (top-k). A reranker can re-score them. The system puts the chunks into the model's prompt as context. The model answers. The RetrieveAndGenerate API does all of this. It also does generation in one call. It returns source citations. The Retrieve API gives you raw chunks. You do the generation yourself with Converse (see 3.7).

Key exam split:

RetrieveAndGenerate

= one call. Bedrock generates the answer. The response includes citations.

Retrieve

= You get chunks only. You control the prompt and the model call. Use Retrieve plus Converse if you need custom prompt control. Use it if you need inline guardrails. Use it if you need streaming.

3.2 Data sources and sync

This chapter is next because: Documents come in on a schedule. The next step is to divide them. Chunking is the name for this step. Chunking is the most important retrieval control.

A data source is where the KB gets documents. Supported sources are: Amazon S3 (the native source), a web crawler (public or sitemap URLs), Confluence, SharePoint, and Salesforce. Each data source has its own chunking settings. Each data source has its own sync schedule.

Separate data sources are important. You set chunking for each data source when you create it. You cannot change chunking later. If you change chunking, you must create the data source again. So, documents that need different chunking go into different data sources. For example, put manuals in one data source with hierarchical chunking.

Put FAQs in another data source with fixed-size chunking. Sync schedules are also different. A product catalog changes every day. It gets a daily sync. Archived contracts get a one-time sync.

Sync runs on a schedule. The schedule can be hourly, daily, weekly, or custom. Or, you can run sync on demand. The exam may say "documents updated quarterly." The correct answer always includes an automated sync schedule. It never includes a one-time manual load. Incremental sync gets new and changed files.

Deleted files follow the sync's deletion policy.

Common misunderstanding.

"The KB reads my S3 bucket live at query time." This is not true. Retrieval searches the vector index. The vector index only knows what the last sync ingested. If answers are old after a document update, the sync did not run. This does not mean the model is broken. This is the first thing to check when "the KB does not know about the new policy."

3.3 Chunking strategy comparison

This chapter is next because: Chunks have a size. Now each chunk becomes a vector. This is the embeddings model choice.

A chunk is a part of a document. It is small enough to embed and retrieve as one unit. Chunking is the most important decision in a RAG system. It decides what the retriever can "see." If a chunk is too large, it includes text that is not relevant. This makes the match less good. If a chunk is too small, it loses the context needed to answer.

The KB changes each document into raw text. Then, it uses the strategy. Fixed-size splits on token count with a configurable overlap percentage. Overlap keeps sentences from being cut in half at boundaries. Hierarchical builds a tree. Small child chunks are for precise matching.

Each child chunk links to a larger parent chunk. The system injects the parent chunk as context. Semantic splits at meaning boundaries (topic shifts). This costs more compute at ingestion. You set the strategy for each data source when you create it.

3.4 Select an Embeddings Model

Why this chapter comes next. Vectors exist. The vectors need a home. The vector store is the home. Choose the vector store one time. Choose it when you make the KB.

These are the two exam-relevant choices:

The two choices are relevant to the exam.

  • Amazon Titan Text Embeddings v2. This is the default option. This option is low cost. You can set the dimensions. The dimensions are 1024, 512, or 256. Smaller dimensions use less vector storage. Smaller dimensions make search faster. Smaller dimensions reduce accuracy a small amount. Use 1024 when quality is most important. Use 256 for very large data sets. Use 256 when storage and latency are most important.
  • Cohere Embed. This is the multilingual choice. It has an input_type parameter. This parameter separates search queries from documents. This improves the match quality. Use it if the corpus or the users use many languages.

The query side embeds only the question. The question is small. This is why RAG is cheap to operate. The expensive part happens one time. It does not happen for each question. Dimension choice increases storage.

1024-dimension vectors use about 4 times the space of 256-dimension vectors.

Common misunderstanding.

"Bigger embeddings are always better." This is true up to a point. After that point, you pay for storage. You pay for latency. You get no measurable gain. "I can swap the embeddings model later" is false. You must re-ingest the data.

Changing the model means you must re-embed every chunk. This is because vectors from different models live in different spaces. You cannot compare them.

3.6 Retrieval configuration

Why this chapter comes next. You configure retrieval here. The last step connects it to the model call. Guardrails are on the path.

Retrieval configuration decides which chunks reach the model. There are three controls: how many (top-k), which subset (metadata filters), and how good (hybrid search plus reranking).

  • Top-k. This is the number of chunks that the system returns per query. A small k (3 to 5) is low cost and specific. A large k (20+) gives more context. But it uses more tokens. It can also give the model too much noise. Adjust this value. Start with 5. Increase it only if answers do not have information that is in the data.
  • Metadata filters. Each chunk can have metadata. This includes the source file, department, date, and tenant ID. Filters limit retrieval to a subset before similarity ranking. For example, you can select only the 2026 policy documents. This also provides multi-tenant isolation at the data layer. It works with separate knowledge bases or IAM scoping.
  • Hybrid search. Vector search finds meaning. Keyword search finds exact terms. These terms include product codes, names, and error strings. Hybrid search does both. It combines the results. Use it when queries have exact identifiers. Pure semantic search can change these identifiers.
  • Reranking. A second model re-scores the top-k chunks. It checks for true relevance to the question. Vector similarity is not the same as relevance. This fixes the problem when retrieved chunks look related but the answer is wrong. Bedrock provides rerank models. Apply them after the first retrieval pass.

The debug order for bad RAG answers (memorize this).

  1. Check retrieval. Do the correct chunks return? If not, fix chunking, embeddings, or filters.
  2. Check relevance. Chunks look similar but are not truly relevant. Add reranking or hybrid search.
  3. Check generation. The model does not use the given context. Make grounding stronger in the prompt. Or add a contextual grounding check.

Never start by changing the generation model.

How to read this diagram

  1. Step 1, Retrieve: This is the only Bedrock call that uses the vector store. It returns chunks. Each chunk has a source URI and a relevance score. If the scores are low for all chunks, stop here. The problem is retrieval. No prompt trick later will fix it.
  2. Step 2, prompt assembly: Your code controls this. Put the chunks in a clear context block. Add the user question. Add a grounding instruction. For example, "answer only from the context. Say you do not know if the answer is not there." This instruction is the cheapest way to prevent hallucination.
  3. Step 3, Converse with guardrailConfig: One API call carries the model ID, messages, inference config, and the guardrail identifier plus version. Guardrails check the input before the model sees it. This is where the system blocks prompt-injection attempts and PII in the question.
  4. Step 4, generation: The model answers from the context you gave. You used Retrieve. You did not use RetrieveAndGenerate. So, you can also stream the answer with ConverseStream. See chapter 2.
  5. Step 5, output screening: Guardrails check the answer before the user sees it. In RAG, the contextual grounding check is here. It checks that the retrieved chunks support the answer. This directly fights hallucination.

What breaks if a component fails

  • Retrieve returns bad data. Check the chunking strategy. Check the sync freshness. See sections 3.2 and 3.3.
  • Guardrail blocks correct questions. The denied-topic definitions are too broad. Or a content-filter threshold is too strict. Adjust the policy. Do not remove the guardrail.
  • The answer has no citations. You used Retrieve. But you did not pass the source URIs to the response. RetrieveAndGenerate does this automatically.

Guardrails placement rule.

This includes text from non-Bedrock models.

4.1 Agent anatomy and the orchestration loop

Why this chapter comes next. The reasoning loop is the engine. Action groups are its hands. They are the tools the agent can call.

A Bedrock Agent is a managed reasoning loop. It uses a foundation model. Give it an instruction. For example, "you are a travel assistant that can book and refund flights." Give it a foundation model to reason with. Give it an IAM role. The role scopes what it can touch.

The agent then runs a ReAct loop. It reasons about the user request. It decides which tool to call. It calls the tool. It reads the result. It repeats until it can answer.

Tools come from action groups. Knowledge comes from attached knowledge bases. Safety comes from attached guardrails.

This closes a gap. A bare model call leaves this gap open. A model alone cannot look up a live order status. It cannot cancel a booking. Bedrock runs the think-act-observe cycle. It keeps session state.

It returns a final answer. You do not write the orchestration loop yourself.

The orchestration loop, step by step.

  1. Invoke. Your app calls invoke_agent. It uses the bedrock-agent-runtime endpoint. It uses an agentId. It uses an agentAliasId. This is the prepared, versioned deployment. Never use DRAFT in production. It uses a sessionId. This ties turns together. The agent keeps short-term memory for the session. Optionally, use enableTrace to see the reasoning.
  2. Reason. The model reads the instruction. It reads the conversation history. It reads the action-group API schemas. It reads any KB context. Then it decides. It can answer directly. It can retrieve from the KB. Or it can call a tool.
  3. Act. If it calls a tool, Bedrock invokes the action group's executor. This is usually a Lambda function. It uses the function name. It uses parameters parsed from the model's output.
  4. Observe. The tool result returns to the model. The model reasons again. This loop repeats. It repeats until the model produces a final answer. Or it repeats until it hits a stopping condition.
  5. Respond. The final answer streams back. Trace events stream back if you enabled them.

Lifecycle terms the exam tests. You must run prepare-agent after any configuration change. This compiles the instruction. It compiles the schemas. It compiles the KB attachments. This makes a working agent.

The agent runs the old version until you do this. The classic "agent ignores my new action group" bug is a missing prepare-agent. Aliases point at prepared versions. Production traffic uses an alias. It does not use the DRAFT.

Common misunderstanding.

"The agent remembers everything forever." Agent session memory is short-term. The idle session TTL is about minutes. Community notes document it around 600 seconds. Verify this at build time. For memory across days or weeks, store conversation state in DynamoDB yourself. See chapter 5.

Or use a long-term memory service.

4.2 Action group and Lambda function contract design

Why this chapter is next. The system defines contracts. Here is the loop in action. One message has three jobs. The system traces each job turn by turn.

An action group is a named set of tools. The agent can call these tools. One executor supports the action group. There are two ways to define the tools:

  • OpenAPI schema. You describe a REST API. You describe paths, methods, parameters, request shapes, and response shapes. Use it when the tool is already an HTTP service.
  • Function schema. You define simple named functions directly. You define parameters directly. Use it for small tools. Writing an OpenAPI file is too much work for these tools.

The executor is usually a Lambda function. Bedrock calls it with a structured event. The event has the action group name, the function (API path or function name), and the parameters that the model extracted. Your Lambda function runs the logic. It returns a structured result. This input/output contract is the whole integration.

The model only sees the schema. It never sees your code.

Design the contract well. Keep functions small and for one purpose. For example, use "getOrderStatus" not "doOrderStuff". Name parameters exactly as the business names them. Return small JSON. Every token that the tool returns goes back into the model's context.

So, long tool output uses too much money and context window. Validate inputs in the Lambda function. The model will sometimes invent a parameter value. Your code is the last defense.

4.6 Tracing and debugging

Why this chapter is next. You can debug one agent. Some problems need many agents. This chapter shows multi-agent and framework options.

This is like a stack trace for an agent.

The debug order for agents.

  1. Agent ignores a new or changed action group: Did you run prepare-agent again? Does the alias for production point to the prepared version? This is the most common agent error on the exam.
  2. Agent calls the tool with wrong parameters: The schema is not clear. Change parameter names. Add descriptions. Make required fields truly required.
  3. Agent loops or never finishes: Add stop conditions. Set a maximum number of tries. Add a Step Functions timeout for the whole task. Give instructions that say when to stop and ask the user.
  4. Agent answers from old documents: The KB sync did not run. Use the same fix as in chapter 3.

5.3 Send data to the client

Why this chapter is next. Streaming makes latency seem lower. Caching stops model calls when inputs are the same.

Users see latency as the time to the first token. They do not see it as the time to the last token. Streaming makes perceived latency much lower. It does not change quality.

The Lambda calls ConverseStream. Bedrock sends tokens as server-sent events. The Lambda sends them to the client. There are two client patterns. Use API Gateway with chunked transfer encoding. This is simple.

It has a 29-second integration timeout limit. Or use WebSockets or direct SSE for long streams. These streams last longer than the timeout. For very long generations, use the async queue pattern from chapter 2. Send progress updates over the socket while the job runs.

Common misunderstanding.

"Streaming makes generation faster." This does not change the total generation time. It changes when the user sees the first word. The exam tests this difference. A scenario needs lower perceived latency. It does not need a quality change.

5.4 Caching layers

Why this chapter is next. Caching reduces the bill. The last layer is about access. It is about how models change without redeploys. This means auth and model switching.

  • Prompt caching. Use this for repeated large static prefixes. This includes system prompts, few-shot examples, and long documents. Attach these to every call. Set a cachePoint in the Converse request. Use this on supported models. Cached input tokens cost less. Constraints apply. Minimum token thresholds apply per model. The TTL is short. It is about 5 minutes by default. It is up to one hour on supported models. So, it helps high-frequency repeated prefixes. It does not help occasional prefixes.
  • Semantic cache. Use this for repeated similar questions. For example, "what is the refund policy" asked 10,000 ways. Store question embeddings and answers in DynamoDB or ElastiCache. When a new question comes, check similarity. Do this before calling the model. The hit rate is high only when queries repeat. The exam rejects semantic caching for highly personalized queries.
  • Deterministic request hashing. Use this for exactly repeated requests. These have the same prompt and parameters. Hash the request. Cache the response. This is the cheapest cache. It has zero model cost on hits.

5.5 Auth and model switching

Auth. Use Cognito user pools for end users. This is for sign-up, sign-in, and groups for tiered access. Use IAM roles for service-to-service calls. The authorizer on API Gateway enforces this. It does this before Lambda runs.

For enterprise scenarios, IAM Identity Center permission sets give per-team access to models and KBs.

Model switching without redeploys. Use the three parts from the blueprint. Lambda holds the routing logic. API Gateway gives the stable endpoint and throttling. AppConfig holds the model identifiers and feature flags. This is runtime config.

Operations changes a flag. The Lambda reads it on the next invocation. CloudFormation is a distractor here. Its changes are deployments. This breaks "no code changes." EventBridge is the other distractor. It routes events.

It does not store configuration.

"Operations must switch between three models without code deployments." This is a select-all-that-apply question. It has exactly three correct answers. These are AppConfig, API Gateway, Lambda. Every other combination breaks one constraint. Remember these three.

Trap, stated plainly.

There are two timeout problems. One puts a slow agent loop behind API Gateway's 29-second integration timeout. Use the async queue pattern instead. The other "fixes" slow responses by raising timeouts. Stream the responses instead. Timeouts are safety limits.

They are not performance tools.

6. Cost, latency, and quality tradeoffs

6.1 The five cost controls

Why this chapter is next. There are five controls. Each control changes a different part of the bill. Now, see the math. It shows how much each control changes the bill.

There are five independent ways to change the bill. Each way changes a different part of the cost equation. This includes tokens in, tokens out, requests, and capacity.

Lever What it attacks How it works When it wins Watch out
On-demand (baseline) You pay for each token. This is the default price. You do not make a commitment. The traffic is spiky. The traffic is experimental. The traffic is unpredictable. This is the most expensive price per token at a steady high volume.
Prompt caching Repeated input tokens Use cachePoint on the static prefix. You pay less for cached tokens. You use the same long system prompt or document on most calls. You need minimum token thresholds. The TTL is short (about 5 minutes default). This is not useful if every prompt is unique.
Batch inference You pay per token for deferred work. The system takes S3 input. The system gives S3 output. The system processes data over hours. This is non-interactive bulk work. Provisioned Throughput There is a risk of throttling. There is latency variance. You commit hourly for reserved model units. The terms are 1 to 6 months. This gives a predictable steady baseline. Provisioned Throughput is for reserved capacity. The scenario verb selects the answer. "Unavailable in region" means profiles. "Route by complexity" means routers. "Guaranteed throughput" means Provisioned Throughput.

model (assume routing is correct; eval proves it in chapter 7):
  70% on small:  input 63B tokens... roughly 1/10th the price
  New blended total lands near $150,000 / month. Saved about 72% vs baseline.

Lever 3, batch for the 10% of traffic that is nightly report generation:
  that slice moves to batch at ~50% off its on-demand price.

Combined realistic landing zone: $120,000-$160,000 / month, about a 70-78%

How to read this math

  1. Start with tokens, not requests. Cost is input tokens multiplied by input price. Then add output tokens multiplied by output price. Requests are only a multiplier. The exam wants you to think in tokens.
  2. Output tokens are most important. The output price per token is usually many times the input price. You cannot cache output. Shorter answers and limits on response size are real ways to save money.
  3. Caching helps the biggest repeated input. Here, the 1,200-token static prefix is 80 percent of input tokens. Caching it with an 80 percent hit rate removes most of the input cost. If the prefix was different for each call, caching would save nothing. This is the exam's caching distractor.
  4. The cascade is the biggest way to save money because most queries are easy. The risk is that hard queries go to the wrong place. This is why the cascade needs the evaluation loop from chapter 7. This loop is its safety net. Cost math without a quality check will make you fail the scenario.
  5. Provisioned Throughput is not in this math on purpose. This workload is sudden support traffic, not a steady baseline. Provisioned Throughput would add fixed cost. This cost would not match the traffic pattern. The exam punishes Provisioned Throughput as a cost-only choice for sudden traffic.

The multi-lever rule.

"Token costs increase by 30 percent each month. Reduce spending without making the user experience worse." This is never a single answer. The best option combines five things. Use a smaller model for low-priority traffic. Use prompt caching for repeated prefixes. Use Provisioned Throughput only for the predictable part.

Use prompt compression. Use complexity-based routing. Options with only one solution are distractors.

6.3 Latency controls and quality controls

Latency controls (what changes response time).

  • Streaming: This reduces perceived latency (time to first token). It does not reduce total time.
  • Smaller models: These reduce both time per token and total time. This is the main latency control, with Provisioned Throughput.
  • Provisioned Throughput: This removes latency spikes from throttling when there is a load. It guarantees capacity.
  • Pre-computation and caching: Semantic cache hits give an answer in milliseconds. There is zero model time.
  • Parallel calls: Independent retrievals and model calls run at the same time. The total time is the maximum time, not the sum.
  • Prompt compression and context pruning: Fewer input tokens mean less prefill time.

Quality controls (what changes answer quality).

  • Retrieval quality (chunking, embeddings, reranking): This is the main control for RAG. Bad input gives bad output.
  • Model size: Bigger models reason better. The cascade trades this on purpose.
  • Temperature, top-p, top-k: Use low temperature (near 0) for factual tasks. Use higher temperature for creative tasks. These control randomness. They do not control cost.
  • Prompt versioning and eval gates: See chapter 7. Quality decreases silently if you do not measure it.

How to read this diagram

  1. Step one: hybrid search. Keyword and vector search run together.
  2. Step two: merge the results.
  3. Step three: the reranker re-scores the top chunks with a stronger model.

Common misunderstanding.

Temperature, top-p, and top-k do not control cost. They change randomness and quality. The exam offers them as wrong answers for cost and consistency. The correct answer for consistency is temperature 0 plus prompt control. The correct answer for consistency is caching plus PT. Keep the three types separate: cost controls, latency controls, quality controls.

"Sub-3-second latency with 10x Friday spikes" needs three controls. PT controls the baseline. On-demand overflow controls spikes. Streaming controls perceived latency. An option with only one control is wrong. Learn to count the limits in the question.

Check one control for each limit.

Trap, stated plainly.

Do not buy Provisioned Throughput to save cost on spiky traffic. PT is an hourly commitment. You pay for it even if you do not use it. So, it increases the bill on bursty traffic. It looks like an optimization. Do not use temperature or top-p as cost controls.

They change randomness. They never change the invoice.

7.1 The evaluation methods

Why this chapter comes next. There are four ways to score outputs. The next question is which metric fits which task.

There are four ways to score model outputs. Each way has a different cost. Each way has a different trust level.

Method Metrics When to use it
Programmatic (automatic) Accuracy, toxicity scores, stability. Use built-in or custom datasets. These are objective, repeatable benchmarks. They are fast and cheap. But they do not see style and nuance.
LLM-as-a-judge Correctness, completeness, faithfulness (hallucination), harmfulness, refusal behavior, style and tone. You can define custom metrics. This is human-like quality judgment at scale. It is the main method for RAG evaluation. It checks retrieval relevance plus generation faithfulness. It is the main method for agent evaluation. Trap set.

Programmatic evaluation for style or brand voice is wrong. These are subjective. They need human evaluation or LLM-as-judge. Human evaluation as the only evaluation for large-scale regression is wrong. This costs too much money and time. The exam wants automated gates with human spot checks.

A bigger model is not a fairness fix. Fairness needs metrics. Fairness needs A/B testing. Fairness needs LLM-as-judge, continuously.

7.3 LLM-as-a-judge setup on Bedrock

Why this chapter comes next. The judge runs. The last step is to make the judge a gate. The gate blocks deploys when scores regress.

Bedrock model evaluations use judge models. The judge models score your outputs. You provide a dataset. The dataset has prompts and optional reference answers. This is the golden dataset. You select built-in metrics.

How to read this diagram

  1. Left: sample outputs from the model under test.
  2. Middle: the rubric prompt. It tells the judge how to score.
  3. Right: the judge model. It returns scores, not text.

Or, you define custom metrics in plain language. Bedrock runs the evaluation. It is a managed job.

How to set up the item well.

  1. Build the golden dataset first. Make a few hundred representative prompts. Make sure the prompts have known good answers. Store the answers in S3. This dataset is the base for every gate below. You have no regression signal without this dataset.
  2. Separate the judge from the contestant. Do not judge a model with itself when the stakes are high. Use a strong independent judge model. Document the judge model. This makes results comparable across runs.
  3. Give the judge the rubric and the context. For RAG evaluation, the judge must see the retrieved chunks. This helps the judge score faithfulness. For agents, the judge must see the trace. This helps the judge score tool use. A judge without context makes its own standards.
  4. Calibrate against humans. Run the judge and a human panel on the same sample. Measure their agreement. If they disagree often, fix the rubric. Do not fix the model.

Concrete numbers (illustrative). A 500-prompt golden set costs about $10 per gate run. The math uses $0.02 per judgment. This cost is low enough to run on every prompt change. Gates work only if they are cheap enough to use every time.

Common misunderstanding.

"LLM judges are objective." This is not true. They have biases. They prefer longer answers. They prefer their own model family. They prefer a confident tone. Calibration and a written rubric make them trustworthy.

Automation does not make them trustworthy.

7.4 Eval gates in CI/CD

A quality checkpoint stops deployment if scores decrease. The pipeline works like this: Every prompt change, model change, or KB re-sync starts the evaluation job. The job runs against the golden dataset. Scores must pass thresholds. Then the new version can ship.

Developer changes prompt / model / KB content
        |
        v
[Gate 1: programmatic regression]  accuracy, toxicity, latency on golden set
        |  fail -> block, notify
        v
[Gate 2: LLM-as-judge]  faithfulness, completeness, style vs previous version
        |  fail -> block, notify
        v
[Gate 3: canary]  5% of live traffic, compare metrics to baseline
        |  regression -> automatic rollback
        v
[Gate 4: human spot check]  sample of canary outputs, brand voice sign-off
        |
        v
Full rollout. Continuous monitoring after deploy: hallucination rate on
golden probes, semantic drift checks, bias drift alerts (chapter 8).

How to read this diagram

  1. Gate 1 is cheap and fast: Programmatic checks run in minutes. They run on every change. They find crashes, format breaks, and toxicity spikes. Nothing subjective passes here. You cannot measure subjective things here.
  2. Gate 2 is the quality comparison: The judge scores the new version. The judge scores the old version. The judge uses the same dataset. You look for decreases in quality. You do not look for absolute scores. A new prompt scores 2 points lower on faithfulness. Do not ship this prompt. This is true even if the prompt is still "good."
  3. Gate 3 is the real world: Canary traffic is a small live slice. It tests a release. It shows what the golden set missed. This includes new phrasing, edge users, and load effects. Automatic rollback on quality decrease is the goal. A canary you must watch manually is not useful.
  4. Gate 4 is the human backstop: This gate uses a small sample. It requires high judgment. Brand voice and subtle tone issues are found here.
  5. After deploy: Use continuous probes. Run hallucination detection on a schedule. Use golden datasets for this. Use output diffing for consistency. Use reasoning-path tracing for agents. Quality is a time series. It is not a one-time check.

The monitoring stack, mapped.

You can detect hallucinations in near-real-time. You can detect abnormal token spend. This needs minimal custom work. Use Bedrock evaluation jobs. Use LLM-based judgments for hallucinations. Use CloudWatch anomaly detection on token metrics.

Building Glue and Athena pipelines for this costs too much. SageMaker Model Monitor is the wrong tool. It is for tabular ML drift. It is not for GenAI text quality. CloudTrail is for audit. It is not for metrics.

CloudWatch is the metrics answer.

"Compare two models for summarization quality including brand voice" means use LLM-as-judge for scale. Use human evaluation for brand voice. "Validate a new prompt version before rollout" means use regression testing. Also use canary testing. The exam always pairs the subjective metric with the human method.

How to read this diagram

  1. Read top to bottom as a request's journey. Every request passes through every layer. It passes in order. A missing layer is a gap. An attacker can use this gap. It is not an optimization.
  2. WAF and authentication are the perimeter: They decide who can talk to the application. Everything below assumes an authenticated caller. It does not assume a trusted caller.

8.1 IAM least privilege

Why this chapter comes next. Permissions are for each component. Now, consider the data itself. This includes encryption at rest and private network paths.

Each component gets only the permissions it needs. It gets no more permissions. Permissions are for specific resources. The router Lambda can invoke specific model ARNs. It cannot invoke bedrock:*. The agent's role can read specific knowledge bases.

It can invoke specific action-group Lambdas. The action-group Lambda's resource-based policy allows invocation only from the agent.

Concrete shape. Use one IAM role for each component. This includes the router Lambda, agent, action-group Lambda, and eval job. Each role has resource-level ARNs. For multi-tenant systems, use separate KBs for each tenant. Use IAM boundaries.

Do not use one shared KB with prompt instructions. For enterprise-wide model access, use a central GenAI gateway. This gives each team one audited path. It avoids direct Bedrock calls from everywhere.

Common misunderstanding.

"The model's built-in safety is enough." This is never the most correct answer for a sensitive audience. The exam expects layered controls. Use guardrails, IAM, network, evaluation, and human review. Match these to the risk.

8.2 KMS and VPC endpoints

Why this chapter comes next. The service encrypts data. Data stays off the public internet. The next layer records who did what. This is audit.

KMS. KMS encrypts all data at rest that the system uses. This includes S3 document buckets, DynamoDB session tables, EBS volumes, and model invocation logs. Use customer-managed keys for compliance workloads. This lets you control key rotation and access. TLS is the default for all AWS API calls in transit.

VPC endpoints (PrivateLink). Interface endpoints for the Bedrock planes keep traffic off the public internet. These are com.amazonaws.<region>.bedrock (control plane), bedrock-runtime (invocations), bedrock-agent and bedrock-agent-runtime (agents). With endpoints, Lambda functions in private subnets reach Bedrock. They do not need a NAT gateway. They do not need an internet path.

"Keep Bedrock traffic private" is always the VPC endpoint answer.

8.3 CloudTrail and audit

Why this chapter comes next. You covered the audit trail. Now, consider the model boundary itself. This is Guardrails layering.

The split the exam tests. CloudTrail records who called which API. It records when and from where. This is the audit trail. CloudWatch Logs holds application and decision content. It shows what the prompt said.

It shows what the model answered. Trail is for compliance. For example, "who accessed the KB last Tuesday." Logs is for debugging. For example, "why did the agent choose that tool." Know which question each answers.

Model invocation logging. Bedrock can log full requests and responses to S3 or CloudWatch for forensics. These logs can contain PII in compliance environments. Encrypt them with KMS. Or, disable logging. Rely on metadata-only records.

Logging unencrypted invocations to CloudWatch in a healthcare scenario is an exam trap. The correct answer adds KMS or disables it.

Lineage. A regulator asks "which data produced this answer." The answer uses Glue Data Catalog registration. It uses metadata tags on documents. It uses source citations from RetrieveAndGenerate. It uses the CloudTrail audit trail. No single one is enough.

Concrete numbers (illustrative). CloudTrail records every Bedrock API call. It records the caller identity, timestamp, and source IP. A mid-size chatbot fleet can make tens of thousands of management events each day. Size trail storage and retention to your compliance window. Remember that Trails answer "who called what." 8.4 Guardrails layering

Why this chapter comes next. Guardrails filter at inference. One data class needs its own end-to-end pipeline. This is PII.

The control matrix (memorize).

Control What it does Configured by
Content filters Hate, insults, sexual content, violence, misconduct, prompt attacks. Severity threshold for each category: NONE, LOW, MEDIUM, HIGH.
Denied topics Block subject areas. For example, block medical diagnosis, block investment advice. Natural-language topic definitions
Word filters Exact-match blocklists Custom word lists

The layering pattern. First, use Comprehend pre-filter on the input. Then, use Guardrails on the model call. Use Guardrails on inputs, outputs, or both. Then, use a Lambda post-processing step. Then, use API Gateway response filtering.

Each layer finds a different type of failure. The exam scenario is about a children's tutor. The scenario needs to block profanity in. It needs to prevent harm out. It needs to stop jailbreaks. It needs to ground facts.

This full stack solves the scenario.

The exam's favorite confusion set. The exam drills this.

"Prevent the model from discussing medical diagnoses" is about denied topics. It is not about content filters. "Redact SSNs" is about sensitive information filters. It is not about word filters. Word filters match exact strings. PII needs entity detection with block or mask.

8.5 PII redaction flow.

This is an end-to-end pipeline. It finds personal data at rest. It catches personal data in flight. It blocks personal data at inference.

At rest (S3 document lake):
  Amazon Macie scans buckets, finds PII at scale, labels findings
        |
In flight (application path):
  Amazon Comprehend detects PII entities in real time (30+ types),
  Lambda redacts or masks before the text reaches the model
        |
At inference (model boundary):
  Bedrock Guardrails sensitive-information filters block or mask
  PII on inputs and outputs
        |
After (retention):
  S3 Lifecycle policies expire raw logs and transcripts on schedule;
  invocation logs KMS-encrypted or disabled in regulated workloads

How to read this diagram.

  1. Macie works at rest and at scale: It scans S3 buckets. It reports where PII is. It does not sit in the request path. A scenario about "find PII across 10,000 documents in S3" uses Macie.
  2. Comprehend works in flight: It does real-time entity detection on text. The text passes through your pipeline. A scenario about "redact PII from chat messages before they reach the model" uses Comprehend plus a Lambda.
  3. Guardrails work at the model boundary: Block or mask for each entity type on inputs and outputs. This is the last automated checkpoint. It is before the model sees text. It is before the user sees the answer.
  4. Lifecycle and logging close the loop: PII that you do not keep cannot leak. Expire transcripts on schedule. Treat invocation logs as PII-bearing. Do this unless you prove they are not PII-bearing.

"Protect PII in customer-service GenAI conversations with minimal custom work" is a select-three question. The answers are Macie, Comprehend, Guardrails. The distractors use Translate. Translate keeps meaning. It gives zero protection. The distractors use Rekognition.

Rekognition is a vision service. Comprehend is the text answer. Count the planes: at rest, in flight, at inference. Use one service per plane.
