1. Ingestion gaps: AppFlow and Transfer Family

These are two managed services. They move data INTO AWS. Both are exam favorites for "choose the ingestion service" scenarios. They look similar until you learn the one-line difference.

Amazon AppFlow

Amazon AppFlow is a fully managed integration service. It moves data between SaaS applications and AWS services. It moves data in both directions. You do not write custom connectors. SaaS applications are software you use over the internet. Examples are Salesforce or ServiceNow.

GenAI applications need enterprise data. That data lives in SaaS tools. Examples are support tickets in Zendesk, cases in Salesforce, and employee records in Workday. Without AppFlow, engineers write and maintain fragile API scripts. These scripts break when the SaaS vendor changes pagination or rate limits. AppFlow replaces that glue code with a managed flow.

It also solves the credential problem. Connection credentials are in a central location. They are not in code.

A flow works in four steps. First, a connector profile authenticates one time to the SaaS application. It uses OAuth or credentials. AppFlow stores the credentials in AWS Secrets Manager. The flow never embeds secrets. Second, a flow definition names a source.

It names a destination. It names field mappings. This is which source field goes to which destination field. It names optional transformations. The transforms: masking, truncation, concatenation. It names filters.

These are only records matching a condition. Third, a trigger runs the flow. It runs on demand, on a schedule, or when an event happens. The SaaS application emits a change event. Syncs can be near real time. Fourth, incremental pulls get only records changed since the last run.

They do not get full snapshots. Common destinations are Amazon S3, Amazon Redshift, Salesforce itself, and other AWS services. The data is ready for Glue ETL or a Knowledge Base ingestion job. Flows integrate with the Glue Data Catalog. The synced data is queryable.

About numbers: AppFlow pricing counts flow runs plus data processed. This is illustrative. It is about one dollar per flow run plus data processed. It is not per seat. The exam does not test exact pricing. It tests the trigger and mapping concepts.

What matters numerically: a scheduled flow syncs 10 million records one time each day. It costs about the same compute if the records changed or not. This is why incremental pulls are the cost answer in scenario questions.

Key exam facts.

(1) AppFlow moves data from SaaS to AWS. It uses no code. (2) Flows support on-demand, scheduled, and event-driven triggers. (3) Incremental pulls sync only changed records. (4) Credentials are in Secrets Manager through connector profiles. (5) Private connections can use AWS PrivateLink.

SaaS traffic never crosses the public internet.

Trap.

AWS will offer Amazon EventBridge or a custom Lambda poller as distractors. This is for "sync Salesforce cases into S3 for RAG." EventBridge routes events. It does not do field mapping, transformation, or incremental record pulls. If the scenario mentions field mapping or masking PII during the sync, the answer is AppFlow.

How to read this diagram

AWS Transfer Family

AWS Transfer Family is a fully managed file-transfer service. It runs SFTP (SSH File Transfer Protocol), FTPS (FTP over TLS/SSL), FTP (plain File Transfer Protocol), and AS2 (Applicability Statement 2, a B2B messaging protocol) servers. Amazon S3 or Amazon EFS backs these servers. Enterprises exchange data as file drops. A partner uploads a nightly CSV over SFTP. A vendor sends invoices over AS2.

Before Transfer Family, you ran your own SFTP servers on EC2. You handled patching, scaling, and key management. Then you copied files into S3. Transfer Family removes the server fleet. AWS manages the protocol endpoint. S3 is the storage.

So, a file drop is one hop from a GenAI ingestion pipeline. Partners keep using their existing clients.

Setup runs in three steps. Create a Transfer Family server for a protocol. For example, use SFTP. Point it at an S3 bucket or EFS file system. Users authenticate with SSH keys, passwords, or an external identity provider. Each user maps to a home directory inside the bucket.

Uploads and downloads go straight to S3 objects. An S3 event notification can then trigger the next step. This can be Lambda validation, Bedrock Data Automation, or a Knowledge Base ingestion job. One rule set is very important. Public endpoints support SFTP only. Plain FTP runs only on VPC-internal endpoints.

Unencrypted FTP must not cross the public internet.

It does not access the source database for each click. GenAI applications make data worth watching. This includes token spend per team, evaluation scores over time, RAG retrieval hit rates, and user feedback. Engineers query that data in Athena or OpenSearch. Product owners and finance need dashboards. QuickSight turns S3, Athena, Redshift, and RDS data into shareable dashboards.

Neptune Analytics is a serverless graph-analytics engine. It is part of the Amazon Neptune family. It loads graph data into memory. It runs analytical queries on the data. This includes vector similarity search. Do not confuse Neptune Analytics with Neptune Database.

Neptune Database is a transactional graph database. D1 ch11 for GraphRAG covers Neptune Database. Neptune Analytics is an analytics engine. You use it for fast traversals. You use it for nearest-neighbor vector queries. It works with millions of nodes.

3. Security and inference primitives

The system has data. The system analyzes the data. This chapter shows the guards around the app. This chapter shows the dials inside the model calls.

AWS Secrets Manager

AWS Secrets Manager stores secrets. Secrets are database passwords, API keys, and OAuth tokens. Secrets Manager encrypts secrets with KMS. Its main feature is automatic rotation. Secrets Manager can change a secret on a schedule. It does this without human action.

It does this without breaking applications that read the secret. Hardcoded credentials leak. Manually rotated passwords are not changed. Rotation is operationally difficult. Changing a password breaks every client that uses the old password. Secrets Manager solves this with staged rotation.

The system creates and tests the new password. The old password still works. Then the new password becomes current. Applications read the secret at runtime. They use the API. They do not embed the secret.

Rotation works like this. You set a rotation interval. For example, set it to 30 days (rotate-secret --rotation-rules AutomaticallyAfterDays=30). A Lambda function does the rotation. AWS provides ready-made rotation functions for RDS (MySQL, PostgreSQL, Oracle, SQL Server), Redshift, DocumentDB, Neptune, and MongoDB Atlas. You write a custom Lambda for other systems.

Every rotation does four steps in order: createSecret (make the new value, staged as AWSPENDING), setSecret (put it on the database), testSecret (check if the new credential works), finishSecret (change AWSPENDING to AWSCURRENT). If any step fails, the old secret stays current. Nothing breaks. Applications call GetSecretValue (or use the Secrets Manager JDBC driver or container injection). They cache briefly. Rotation happens in stages.

A reader that got the secret seconds before rotation still has a valid credential.

How to read this diagram

  1. Step one: the schedule fires.
  2. Step two: the Lambda function creates, sets, and tests the new secret.
  3. Step three: apps read the new version. Nothing breaks.

AWS WAF

AWS WAF (Web Application Firewall) filters HTTP requests. It filters requests before they reach your application. Amazon CloudFront

Amazon CloudFront is the AWS content delivery network (CDN). It is a global network of edge locations. These locations cache content near users. A distribution is the CloudFront setup. It maps your domain to origins. Origins are S3 buckets, load balancers, or API Gateway.

Cache behaviors are path-pattern rules. They control what content to cache and for how long. Users are far from your origin region. Each request that crosses an ocean adds latency. CloudFront serves cached content from the nearest edge in milliseconds. It routes non-cached content over the AWS backbone.

This is faster than the public internet. For GenAI applications, CloudFront also ends TLS at the edge. It absorbs DDoS attacks with Shield Standard. It hosts WAF inspection before traffic goes to your API.

The request path: A viewer requests app.example.com/chat. DNS sends them to the nearest edge location. Cache behaviors match the path. /static/* can cache for one day from S3. /api/* can send to API Gateway with no caching. If content is cached, the edge answers at once. If content is not cached, the edge gets it from the origin one time. It stores the content based on the TTL.

Then it serves the content. Private S3 origins use OAC (Origin Access Control). OAC lets CloudFront get access to a private bucket. It uses the bucket policy. OAI (Origin Access Identity) is an older method. OAC works with the S3 REST endpoint.

It does not work with the S3 website endpoint. For access control, a signed URL gives access to one file. Signed cookies give access to many files. For example, a whole premium video course. Geo restriction blocks or allows whole countries at the edge. Custom-domain certificates must be in us-east-1 (ACM).

This is because CloudFront is a global service. The WAF scope rule is the same.

Default TTLs are from hours to one day. You can set them for each behavior. Invalidations remove cached objects before the TTL ends. This is the answer for "I fixed it, but users see the old page." The edge count is hundreds. It is in more than 90 countries. (This is an example.

The exam tests concepts, not the count.)

top_k: the sampling parameter AWS hides from Converse

Top_k is a decoding parameter. At each generation step, the model considers only the k most likely next tokens. The model samples among them. A small k (for example 10) makes output focused and deterministic. A large k (for example 200) allows rarer, more creative tokens. It is the sibling of temperature (randomness scale) and top_p (nucleus sampling over cumulative probability).

D4 teaches both. Temperature and top_p shape the probability distribution. But sometimes you want a hard cutoff. You want to "never consider anything outside the top 50 candidates, no matter what." Top_k gives that cutoff. It is useful for constrained tasks. These tasks include classification or structured extraction.

A long tail of weird tokens is a pure risk.

How it works, and the exam trap: In raw InvokeModel request bodies, top_k is a normal provider parameter. It is usually written top_k or topK. This depends on the provider. But in the Converse API, inferenceConfig documents only four fields. These fields are maxTokens, stopSequences, temperature, and topP. There is no standard topK field in Converse inferenceConfig.

Alternatively, use InvokeModel with the raw body. This confuses readers. topK does exist in the Bedrock Agents InferenceConfiguration. It has the same name.

It is a different API. It has different rules.

Typical top_k values range from 1 to a few hundred. 1 is greedy within the top candidate. This is nearly deterministic. Provider defaults vary. The operational guidance mirrors top_p. For factual extraction, use low top_k with low temperature.

For brainstorming, use higher values. Do not combine aggressive top_k with aggressive top_p without testing. They interact.

TTFT: time to first token

TTFT (time to first token) is the latency. It is the time from when you send your request until the first token of the response arrives. This is the metric users feel in a streaming chat. It is the pause before text starts to appear. Its related metrics are: TPOT (time per output token, the steady streaming rate after the first token) and end-to-end latency (TTFT plus everything after). Streaming improves perceived latency.

But "streaming helps" is not measurable without naming the metric. TTFT separates the difficult part (prefill: processing your whole prompt before generating anything) from the easy part (decoding one token at a time). Amazon Bedrock sends TTFT as a native CloudWatch metric. So, you can set an alarm on it. This changes "the app feels slow" into a graph.

Use a streaming API: ConverseStream or InvokeModelWithResponseStream. TTFT is only useful for streaming. Non-streaming calls have a single end-to-end latency. Bedrock publishes TimeToFirstToken to the AWS/Bedrock CloudWatch namespace. It also publishes InvocationLatency, which covers all invocations. You do not need code changes or opt-in.

What increases TTFT: long prompts (the system processes the whole prompt before the first token), large models, cold provisioned throughput, and queueing under throttling. What decreases TTFT: shorter prompts, prompt caching (a cached prefix skips recomputation), smaller or faster models, and streaming. Set CloudWatch alarms on p95 TTFT. This makes regressions page someone. It does not silently annoy users.

Illustrative magnitudes: a short prompt on a fast model can show TTFT in the hundreds of milliseconds. A 100k-token prompt can push TTFT into many seconds. This is because prefill work increases with prompt length. The exam tests the concept and the metric name. It does not test specific millisecond values.

Divider strings for chunking

A divider string is a unique delimiter. You put it between logical sections of a document during preprocessing. A later split-on-delimiter chunker breaks the text at section boundaries. For example, a Lambda preprocessor puts \n\n###SECTION###\n\n between detected headings before chunking. The chunker then splits on that marker. It does not split on blind character counts.

This is a course-taught preprocessing technique. It is not an AWS-documented feature. Treat it as a pattern. Do not treat it as a service. Fixed-size chunking has a failure mode. It can split in the middle of a table.

How to read this diagram

  1. Box one: paragraph dividers. Each chunk holds one whole idea.
  2. Box two: line dividers. Some ideas split across chunks.
  3. Box three: space dividers. The meaning breaks.

It can split in the middle of a procedure. It can split in the middle of an argument. This makes chunks that confuse retrieval. Divider strings are a cheap fix. One preprocessing pass marks the true boundaries. The chunker respects them.

Each chunk stays semantically whole.

This is how it works. After Textract or BDA extraction, a Lambda preprocessor scans the text. It looks for structural signals. These are headings, page breaks, and table boundaries. It puts in a divider string. This string never occurs naturally in the text.

A random-looking token is safer than a common word. The chunking step splits on the divider first. Then it applies size limits within each section. Sections longer than the target get sub-split. Small adjacent sections may merge. Each chunk keeps metadata.

This metadata notes its source section. This improves citation and reranking later.

For example, use a 512-token target chunk size. Divider-first splitting on a 40-page manual gives chunks. These chunks are near the target size. They have fewer mid-sentence breaks than pure fixed-size splitting. There are no AWS quotas here. This is application code.

Binary vectors and FP16 quantization

Vector embeddings are float32. They use 4 bytes per dimension. Quantization stores them with fewer bits per dimension. Binary vectors use 1 bit per dimension. This is 32 times smaller. FP16 scalar quantization uses 16 bits.

This is 2 times smaller. You accept a small accuracy loss. You get large memory and cost savings in the vector index. Memory cost is often the largest cost in a RAG system. Quantization reduces this cost.

Worked example: the index memory math

One vector has 1,536 dimensions. Each dimension uses 4 bytes.

The vector has 1,536 x 4 = 6,144 bytes. This is 6 KB.

Ten million of the items:

The index memory is 6 KB. Multiply 6 KB by 10,000,000. The index memory is 60 GB.

Binary quantization stores 1 bit per dimension. It does not store 32 bits per dimension. So, each vector is 1,536 bits. This is 192 bytes. This is 32 times smaller.

The quantized index is 60 GB / 32 = 1.875 GB. This is less than 2 GB.

The index needed 60 GB of memory. Now the index uses less than 2 GB of memory. This lets you use a smaller instance class. This lets you keep the whole index in memory. The accuracy cost is about 2%. This is an example.

Measure the accuracy cost with your own data. The full-precision rerank step exists for this reason.

Binary quantization turns each float dimension into one bit. This is the sign. This gives 32 times compression compared to float32. The distance becomes Hamming distance. This is very fast. This is best for large-scale first-pass retrieval.

Approximate ranking is acceptable here. 2-bit and 4-bit quantization are middle options. They give 16 times and 8 times compression. They give better accuracy than binary. FP16 scalar quantization halves memory. This is 2 times compression.

It has a very small accuracy change. On OpenSearch, SQfp16 uses the Faiss engine. Faiss is the open-source vector-search library. OpenSearch 2.13 and later versions use Faiss. Lucene-based scalar quantization started in OpenSearch 2.16. The standard method is to retrieve a larger set of candidates with quantized vectors.

Then rerank the top candidates with full-precision vectors. Or rerank them with a reranker model. AWS testing showed an accuracy impact of about 2 percent. This was for binary quantization in tested workloads. This is an example. Measure this on your own data.

The OpenSearch neural plugin enables vector search. This plugin includes k-NN and neural search. It enables vector search on Amazon OpenSearch Service. You configure quantization options on the index's vector field.

Key exam facts.

(1) Binary uses 1 bit per dimension. This gives 32 times compression. FP16 uses 2 bits per dimension. (2) Use quantized vectors to find candidates. Then, rerank the candidates with full precision. (3) OpenSearch Faiss-engine SQfp16 is available from version 2.13.

Lucene scalar quantization is available from version 2.16. The Neural/k-NN plugin makes vector search possible.

Trap.

AWS offers two options for an expensive vector index. AWS offers to add more nodes. AWS offers to move to a bigger instance. Quantization is the cost-efficient answer. Scale is the second cost-efficient answer. Quantization is not lossless.

Quantization is approximate. The rerank step exists because quantization is approximate.

Amazon EMR

Amazon EMR (Elastic MapReduce) is a managed big-data platform. It runs open-source distributed frameworks. These frameworks are Apache Spark, Hadoop (MapReduce/YARN), Hive, Presto/Trino, HBase, and Flink. AWS provisions, configures, and scales the cluster. You submit data-processing jobs. There are three types: EMR on EC2 (classic clusters), EMR on EKS (run on your Kubernetes cluster), and EMR Serverless.

EMR Serverless lets you submit a Spark or Hive job without managing a cluster. GenAI training and large-scale RAG ingestion need much data processing. This includes deduplicating billions of web documents, joining click logs, and computing embeddings in bulk. EMR is the managed platform for Spark-scale ETL. It is not central to the exam's GenAI core. But it appears as the "big ETL" answer in data-pipeline scenarios.

The cluster topology has a primary node. The primary node coordinates. Core nodes run tasks and host HDFS. Optional task nodes only do compute. They are good for Spot instances. For storage: EMRFS lets the cluster read and write S3 directly.

This is durable and decoupled. HDFS on core nodes is fast but temporary. The AWS Glue Data Catalog is the shared Hive metastore across clusters. Jobs run as steps. These are Spark/Hive applications. You can configure concurrency.

It has no cluster to manage. It has pay-per-job billing.
