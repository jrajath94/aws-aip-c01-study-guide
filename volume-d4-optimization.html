01. On-demand inference pricing and token economics

Every team meets this domain the same way: the first production invoice. The demo was cheap. Then real traffic arrived, the chat history grew, the retrieved context ballooned, and the bill multiplied while nobody was watching. Nobody changed the model. The tokens just kept flowing, and the users started saying the chat feels slow. Cost and speed are the same problem wearing two faces, and this volume teaches both.

The default way you pay for Bedrock: per token, split into input tokens and output tokens, at a per-model rate.

The bill, in one paragraph

On-demand inference is Bedrock's pay-as-you-go pricing. You call InvokeModel or Converse with a model ID, and AWS bills input tokens (everything you send: system prompt, conversation history, tools, the user's message) plus output tokens (everything the model generates), each at that model's per-thousand-token price. A token is a chunk of text the model processes, roughly three quarters of an English word. Output tokens cost more than input tokens because generating text is the expensive part: it takes a full forward pass of the model for every single token.

It exists because GenAI traffic is unpredictable. An app in beta, a demo, an internal tool with fifty users: committing to hourly capacity would be absurd. On-demand means zero spend when idle and payment only for what you use. The failure mode it removes is idle waste: you never pay for GPU time you did not use.

The silent cost killer: on the next turn of a chat, the whole conversation history goes in again as input tokens. A 20-turn chat re-pays the full history on every single turn. Nothing caches by default; nothing remembers for free. Bedrock meters InputTokenCount and OutputTokenCount per invocation and reports them to CloudWatch, so your bill is exactly auditable.

The cost equation

cost per call = (input_tokens / 1000) × input_price + (output_tokens / 1000) × output_price

monthly cost = cost per call × calls per month

Where: input_tokens is everything you send (system prompt, conversation history, tools, the user message); output_tokens is everything the model generates; input_price / output_price are the model's per-token rates (illustrative $3.00/$15.00 per 1M in the worked example below). Nothing caches by default: history re-bills every turn.

A worked example

Prices are illustrative and vary by model and region; the math pattern is what matters. Take a flagship model at $3.00 per million input tokens and $15.00 per million output tokens, and a lightweight model at $0.25 and $1.25.

  input  = 2,500 tokens * $3.00/1M   = $0.0075

Reading the diagram: the prompt enters an input meter that counts every token in the system prompt, history, and user message; the response enters an output meter, priced higher because generation costs more compute; both counts multiply by their rates and sum to the dollar total. If you do not watch the input meter, history accumulation silently multiplies your bill on multi-turn chats. If you do not watch the output meter, unbounded max tokens lets the model spend your budget on rambling answers.

Trap

"On-demand is the expensive option, so I should always use provisioned throughput or batch to save money." Wrong. On-demand is the cheapest option when traffic is spiky or low, because the other options charge for idle capacity or require commitments. Provisioned throughput has an hourly fee whether you use it or not; if your app idles at night, you pay for sleeping hours. The exam loves offering provisioned throughput as a cost fix for bursty traffic. It is a latency and capacity guarantee, not a discount for unpredictability.

How the exam asks it: "a startup is prototyping a chat feature, usage is unpredictable, the CFO wants the lowest bill during the experiment." The answer is on-demand inference. Distractors: provisioned throughput (predictable pricing, but charges for idle hours), batch inference (hours of latency, useless for chat), buying reserved capacity.

02. Token efficiency and prompt optimization

Every token you do not send is a token you do not pay for.

The free lever, pulled first

Token efficiency is the discipline of spending the fewest tokens that still get the job done. The techniques:

  1. Context pruning. Drop conversation history or document chunks that are no longer relevant instead of resending everything.
  2. Prompt compression. Rewrite verbose instructions into dense ones without changing meaning.
  3. Response size limits. Cap output with maxTokens and explicit length instructions.
  4. Token estimation and tracking. Count tokens before sending, alert when calls exceed budgets.

Prompts bloat naturally. Developers paste a 3,000-word instruction doc into the system prompt, keep the full 50-turn history "just in case," and set no output cap. The model answers fine, and the bill quietly doubles. The default behavior of every chat app is to resend everything every time, and that default is expensive. Every pricing lever later in this volume works better on a lean prompt.

The mechanics. Estimate before you send: tokenizers count tokens per model family. Rough rules: about 4 characters per token in English, about 0.75 words per token. Log the estimate per call so you can see which features are token-heavy. Prune context: for conversation history keep a sliding window (last N turns) or summarize older turns into a compact recap; for retrieval, retrieve fewer, better chunks instead of dumping ten chunks "to be safe." Every chunk you drop is tokens unbilled. Compress instructions: "Please provide a comprehensive, detailed, in-depth analysis covering all aspects" becomes "Analyze concisely." Keep two strong few-shot examples instead of eight mediocre ones, and test that quality holds after compression. Compression is an optimization loop, not a one-time edit. Cap the output: set maxTokens in the inference config and add explicit length guidance ("answer in under 100 words"); unbounded outputs are the output-token equivalent of an uncapped budget. Track per feature: tag invocations by feature or prompt version so token metrics reveal which prompt is the expensive one. Optimization without measurement is guessing.

This is usually the first lever to pull because it costs nothing to implement and it multiplies every other lever.

Reading the diagram: the bloated prompt on the left is the natural state of an unoptimized prompt, everything included, nothing questioned: oversized document, duplicate paragraphs, long chat history. The scissors box in the center is the optimization work: deduplicate, window the history, compress the instructions, cap the output. The compact prompt on the right does the same task at one third the size with only relevant context retained. What breaks: prune too aggressively (dropping history the task actually needs) and quality drops; you traded cost for wrong answers, so always re-evaluate after compression. Skip measurement and you optimize the wrong prompt; the expensive one is rarely the one developers guess. Set output caps without length guidance and the model may cut off mid-sentence: pair maxTokens with an instruction to be concise.

Trap

"Prompt compression means making the model dumber." Compression trims verbosity, not capability: removing "please" padding and duplicate examples does not reduce what the model knows. The trap version: the exam offers "switch to a smaller model" for a scenario where the real problem is a bloated prompt on the right model. Always fix the prompt first; it is free. A second trap: using temperature or top-p as cost controls. Those control randomness and quality, not token counts or cost.

How the exam asks it: "token costs are growing 30% month over month; the CFO wants cuts without UX degradation; prompts include long histories and verbose instructions." The correct answer is multi-lever: prune context, compress prompts, cap output length, estimate and track tokens per feature. Distractors are single-lever answers: only prompt caching, only a smaller model. The exam rewards the candidate who stacks the free levers first. The tell is "without UX degradation": quality must be re-verified, which points to prompt work plus evaluation, not just a cheaper model.

Why this comes next. Lean prompts cut tokens, but the repeated static prefix is a different tax. Chapter 3 discounts the part of the prompt you pay for over and over.

03. Prompt caching

Stop paying full price for the part of the prompt that never changes.

The discount for static prefixes

Prompt caching is a Bedrock pricing feature that discounts input tokens for the repeated, static part of your prompt. You mark a cache point in your request: everything before the point (system prompt, few-shot examples, a long reference document) gets its computed state stored by Bedrock. On the next call with the same prefix, Bedrock reuses that state instead of reprocessing it, and bills those cached input tokens at a reduced rate. With the Converse API you add a cachePoint to the message or system content; with InvokeModel you use provider-specific cache_control markers.

Look back at the Topic 01 example: the 2,000-token system prompt was re-billed on every call. Real apps do this constantly: a support bot with a 5,000-token policy manual in the system prompt, an agent loop re-sending tool definitions every turn. A healthy app at scale can see 30 to 70 percent of its input tokens being the same static prefix. Caching converts that waste into a discount.

The mechanics. You place one or more cache points in the request. Bedrock requires a minimum token count before the point (a minimum prefix length, model dependent; think hundreds to a couple thousand tokens). Below the minimum, nothing caches. On the first call, Bedrock processes the prefix fully, billed at the standard rate plus a small cache-write surcharge, and stores the intermediate computed state keyed by the exact prefix content. On later calls with an identical prefix, Bedrock detects the cache hit, skips recomputation, bills cached input tokens at the discounted rate, and latency drops because the model starts generating from partway through. The cache entry lives for a time to live (TTL): a short default of about 5 minutes, with longer options of about 1 hour on supported models. If the prefix content changes by even one token before the cache point, or the TTL expires, the cache misses and the prefix is recomputed. Supported models only: primarily the Claude family (3.5 and later) and Amazon Nova. You cannot cache on models that do not implement it.

Illustrative pricing: cached input tokens cost roughly 10% of standard input tokens (a 90% discount), with a cache-write cost of about 25% above standard on the first call. Numbers vary; treat as illustrative.

App: 8,000-token system prompt + few-shot examples (static),
     500 tokens of new user input per call, 1M calls/month.

Without caching:
  input = 8,500 tokens/call * $3.00/1M = $0.0255/call -> $25,500/mo input

With caching (first call writes cache, rest hit):
  cache write (1 call):  8,000 * $3.75/1M = $0.03  (one time per TTL window)
  cached reads: 8,000 * $0.30/1M = $0.0024/call  -> $2,400/mo
  new input:      500 * $3.00/1M = $0.0015/call  -> $1,500/mo
  total input ~ $3,900/mo instead of $25,500/mo.

The 500-token dynamic part still costs full price. Caching discounts only what you marked as static.

Reading the diagram: the long system prompt sits above a cache point marker as the cached layer, computed once and never recomputed within the TTL; only the small user message below the point is processed fresh each call. The two wins are lower latency (prefix already computed) and lower cost (discounted cached tokens). What breaks: if the prefix changes between calls (timestamps or user IDs injected into the system prompt), every call cache-misses and you pay full price plus write surcharges. If the TTL expires between infrequent calls, the first call after the gap pays the full recompute. Caching only pays when the prefix is byte-identical and calls arrive within the TTL.

Trap

"Prompt caching fixes my throttling problem." No. Prompt caching is a cost lever: it discounts repeated input tokens. It does not reserve capacity. If you are being throttled at peak, the answer is provisioned throughput (Topic 10) or rate-limit handling (Topic 12). The exam deliberately offers prompt caching as a distractor in throttling scenarios and as a distractor provisioned throughput in "same long system prompt every call" scenarios. Match the lever to the constraint: repeated prefix cost -> caching; capacity and latency guarantee -> provisioned throughput.

How the exam asks it: "an agent re-sends a 10,000-token tool specification on every turn; token costs are growing; the workload is otherwise fine." The answer: add cache points before the static tool definitions, on a supported model. Distractors: provisioned throughput (solves nothing here), batch inference (breaks real-time), reducing temperature (irrelevant to cost). The tell is "same long prefix on every call" or "repeated static system prompt."

Why this comes next. Prompt caching discounts repeated tokens on calls you still make. Chapter 4 goes further: skip the model call entirely when the question has been asked before.

04. Semantic caching

Do not call the model at all when you already know the answer.

Answering from memory instead of the model

Semantic caching stores model responses and reuses them for new questions that mean the same thing, even if the wording differs. A cache layer (built on ElastiCache for speed or DynamoDB for serverless simplicity) holds past question-and-answer pairs with their embeddings, vector representations of meaning. A new question is embedded, compared by vector similarity to cached questions, and if it is close enough, the stored answer returns immediately: zero model call, zero tokens, near-zero latency. Deterministic request hashing is the simpler cousin: exact-match caching for byte-identical requests.

Real traffic repeats itself. "What are your hours?", "how do I reset my password?", "where is my order?" arrive thousands of times a day in slightly different words. Answering each one with a fresh model call is pure waste: the answer does not change. Semantic caching converts repetition into savings at the source, before any token is billed.

The mechanics. Store: after the model answers a question, the cache stores the question's embedding (its meaning as a numeric vector), the question text, and the answer, with a TTL (time to live). Lookup: a new question is embedded with the same embedding model and compared against cached embeddings by cosine similarity; above the similarity threshold (e.g. 0.95, illustrative), it is a hit. Hit: return the stored answer. No model invocation, no input or output tokens, latency in milliseconds. Miss: call the model normally, then store the new pair for future hits. Placement: ElastiCache (Redis) for sub-millisecond lookups at high throughput; DynamoDB for a serverless cache with no cluster to manage. The vector similarity search can run in the cache layer or via a vector index. Invalidation: cached answers go stale when the underlying facts change (prices, policies). TTLs and explicit invalidation on data updates keep the cache honest.

The hit rate is everything. Measure it on real traffic before committing to the architecture.

Reading the diagram: the incoming question enters the cache box first, not the model. On a hit, a similar past question is found and the stored answer returns immediately; the model is never called. This is the money branch. On a miss, the question flows to the model, which generates an answer that loops back into the cache for storage, so the next similar question hits. The mechanism is meaning-based matching, not exact text matching. What breaks: a similarity threshold set too loose returns wrong-but-similar answers, so tune the threshold with evaluation. Facts that change without cache invalidation produce confidently stale answers. And if queries are highly personalized (each user's question unique), the hit rate collapses and the cache is dead weight: the exam explicitly rejects semantic caching for personalized recommendations.

Trap

"Semantic caching and prompt caching are the same thing." They attack different costs. Prompt caching discounts repeated input tokens on calls you still make (Bedrock feature, static prefix). Semantic caching eliminates the call entirely for repeated meanings (your architecture, ElastiCache or DynamoDB). A second trap: semantic caching for highly personalized queries. Personalized means every question is unique, so the hit rate is near zero and the cache adds latency and complexity for nothing. The exam names this exact rejection.

How the exam asks it: "a FAQ bot receives millions of questions; analysis shows heavy repetition with varied wording. Minimize cost and latency." Answer: a semantic cache (ElastiCache or DynamoDB) in front of the model with similarity matching and TTL invalidation. Distractors: prompt caching (still makes the call, and the questions vary so the prefix is not static), provisioned throughput (capacity, not repetition), fine-tuning (irrelevant). The tell is "repeated similar questions" plus cost and latency goals. The anti-tell: "personalized recommendations" disqualifies semantic caching.

05. Retrieval tuning: fewer, better chunks

Retrieved context is usually the biggest line in a retrieval prompt. Tune it before you pay for it.

Every chunk is input tokens

A RAG application retrieves document chunks and pastes them into the prompt so the model can answer from your data. (RAG, retrieval-augmented generation, is covered from zero in Domain 1; chunking strategies and embeddings live there too.) Each chunk costs input tokens on every call, and the default instinct is to retrieve generously: ten chunks of 500 tokens "to be safe" is 5,000 tokens before the user has even asked anything. Worse, extra chunks are not just expensive, they are noisy. Irrelevant chunks distract the model and quality drops while the bill rises. That is the felt problem this chapter answers.

Retrieval tuning means spending the fewest context tokens that still contain the answer. Four levers, cheapest first.

1. Retrieve fewer chunks: lower top-k. Top-k is the number of chunks the retriever returns for each query. If you retrieve ten and the answer always sits in the top three, seven chunks are pure waste. Drop top-k from 10 to 3 and re-run your evaluation: if answer quality holds, you just cut the retrieval token cost by 70 percent. This is the prompt-pruning of the RAG world, and it is free.

2. Rerank, then truncate. A reranker is a small model that scores candidate chunks precisely for relevance to the query. The pattern: retrieve cheaply and broadly (say 20 candidates by vector similarity), rerank them, keep only the top 3 for the prompt. The broad first pass protects recall (the answer is somewhere in the 20), the reranker protects precision (only the best 3 cost tokens). Reranking adds milliseconds and a small per-call cost, far less than stuffing 20 chunks into a flagship prompt.

3. Make each chunk denser. A 500-token chunk that contains one useful paragraph wastes 400 tokens. Semantic chunking (splitting on topic shifts) and hierarchical chunking (small retrievable children that map to larger parents) put more signal in fewer tokens. The chunking mechanics are Domain 1's territory; the Domain 4 point is that chunk design is a token-cost decision, not just a quality decision.

4. Filter before you search. Metadata filtering (only this year's documents, only this product line) shrinks the candidate set before vector search runs. A smaller candidate set means a smaller top-k can still find the answer, which means fewer tokens in the prompt. It also cuts retrieval latency.

Always re-evaluate after tuning retrieval. The failure shape is a top-k set so low, or a reranker so misaligned, that the answer chunk never reaches the prompt: then the model guesses, and you traded a token bill for hallucinations. Retrieval tuning is an optimization loop: measure answer quality on a fixed test set, cut tokens, re-measure.

Trap

"Add more chunks to fix wrong answers." More chunks raise cost and often lower quality through noise. The exam's RAG-cost scenario wants fewer, better chunks: lower top-k, rerank and truncate, denser chunking. A second trap: reaching for a bigger model when the answers are wrong because the retrieval is bad. If the right chunk never reaches the prompt, no model can answer correctly; fix retrieval first, it is free.

How the exam asks it: "a RAG application retrieves 10 chunks per query; token costs are growing; answers are usually correct but verbose; quality must not drop." Answer: reduce top-k, add a reranking step and keep only the top few chunks, verify with evaluation. Distractors: a larger model (more expensive, does not fix retrieval), fine-tuning the model on the documents (wrong tool for changing knowledge; that is Domain 1's trap), prompt caching (helps only if the retrieved chunks repeat verbatim across calls, which they do not).

Why this comes next. With prompts lean and context trimmed, the next question is whether you need the expensive model at all. Chapter 6 routes each request to the cheapest model that handles it.

06. Right-sizing models and cascading with routers

The cheapest correct answer is usually a smaller model.

Match the model to the difficulty

Right-sizing means matching the model to the task's difficulty instead of using the flagship for everything. Model cascading automates this: a small classifier or router examines each incoming request and sends simple ones (classification, extraction, short answers) to a cheap lightweight model, escalating only complex ones (multi-step reasoning, long generation) to the expensive flagship. Bedrock's prompt routers (also called model routers) are the managed version: you configure routing criteria and Bedrock splits traffic by predicted complexity.

Most production workloads are bimodal: 70 to 90 percent of requests are easy (FAQ lookup, tone rewrite, entity extraction) and a minority are hard. Running the flagship on easy work is like hiring a senior architect to sort mail. The cost gap between model tiers is roughly 10x, so every easy request routed down saves an order of magnitude. Without routing, teams either overpay on the flagship or under-serve hard queries on the small model. Cascading gets both right per request.

The mechanics. Classify: each request passes through a router, which can be a tiny model, a rules engine (keyword or intent patterns), or Bedrock's managed prompt router. Its job is one binary decision: simple or complex. Route simple: easy requests go to the lightweight model (Haiku-class, Nova Lite-class, Llama 8B-class), 5 to 15x cheaper per token with lower latency. Escalate complex: hard requests go to the flagship. Optionally the small model attempts first and escalates on low confidence: a two-stage cascade that catches router mistakes. Measure: track quality per route (evaluation scores, user feedback, escalation rate). If the router misclassifies too often, tune its criteria. Routing is an optimization loop, not a one-time config. The metric that matters is quality per dollar, not raw quality: a router sending 80% of traffic to a model 10x cheaper, with no measurable quality drop on those requests, cuts the bill by roughly 70%. The router itself must be nearly free (rules or a tiny model); a router that costs as much as the savings is a net loss.

Trap

"Bigger models are always better, so routing easy work to a small model risks quality." The exam tests this backwards assumption. Quality is measured per task: a lightweight model that scores identically on simple extraction is not lower quality, it is correctly sized. The real risk is misclassification, which you control with evaluation. Also watch the router confusion trap from Topic 11: prompt routers route by complexity for cost, inference profiles route by region for availability. Different tools, different scenarios.

How the exam asks it: "token costs are growing; analysis shows 80% of requests are simple FAQ lookups currently served by the flagship model; quality must not drop." Answer: add a prompt router or cascade sending simple queries to a lightweight model and complex ones to the flagship. Distractors: fine-tuning the flagship (wrong lever, huge effort), prompt caching (helps only with a repeated prefix), provisioned throughput (capacity, not cost). The tell is "simple queries on an expensive model."

07. Fine-tuning a small model for your workload

When the same narrow task runs millions of times, stop renting the flagship's generality. Bake the behavior into a small model.

The most expensive lever, for the most repeated work

Fine-tuning trains a model on your labeled examples so a behavior becomes part of the weights instead of instructions repeated in every prompt. Supervised fine-tuning uses prompt-and-response pairs (a support tone, a classification task, a response format). Distillation trains a small, cheap student model to imitate a large teacher model on your one narrow task, giving near-teacher quality at student cost. The full mechanics, continued pre-training, imported models, and LoRA (low-rank) adapters live in Domain 1, Chapter 8; this chapter is only about when the economics justify it.

Cascading (Topic 06) still leaves the hard slice of traffic on the flagship, and some workloads carry a giant system prompt on every call just to enforce a consistent tone or format. A 40-page style guide costs tokens on every one of 50 million monthly calls, and the model still drifts. Fine-tuning exists for exactly this shape: a narrow, repeated behavior where consistency matters and the per-call tax of instructions never ends.

The economics. Training costs once: hundreds to a few thousand high-quality labeled examples, hours of compute. Serving usually needs Provisioned Throughput for the custom model, an hourly commit. The per-call price then drops to small-model rates. The arithmetic only works at scale: the one-time training plus the serving commit must be smaller than the flagship tokens you stop buying, month after month.

08. Latency vs throughput: streaming and perceived speed

Users judge speed by the first token, not the last one.

Perceived latency is the metric that matters

Streaming delivers the model's response token by token as it is generated, instead of waiting for the full response and sending it at once. With ConverseStream or InvokeModelWithResponseStream, your app receives a stream of events and renders each token the moment it arrives. Time to first token (TTFT) is the delay before the first token appears; total latency is the delay until the last token. Streaming does not change total latency. It changes perceived latency, which is what users feel.

A 500-token answer might take 15 seconds to generate fully. A blank screen for 15 seconds feels broken; the first words in 1 second with the rest flowing feels instant, even though the total time is identical. Chat products live or die on this perception. Streaming also lets you start downstream work early: begin rendering, begin text-to-speech, or detect a refusal before the full response completes.

The mechanics: your app calls the streaming API variant, the connection stays open (server-sent events style) while the model generates, and each token is flushed as an event the moment it is produced. Your client appends it to the visible text immediately. TTFT depends on input size and model size: a huge prompt or a giant model delays the first token. Total time depends on output length and generation speed.

On the way to the browser, streaming passes through your stack, and that chain must stream end to end: API Gateway supports streaming responses but has payload and timeout limits, so for long streams teams use WebSocket APIs or stream directly from the client to Bedrock. Streaming pairs with the other latency levers: smaller models lower TTFT, prompt caching skips prefix recomputation, provisioned throughput removes queueing delay.

Illustrative. A support chat generates 400-token answers at 30 tokens/second on a flagship model.

Non-streaming:
  user waits the full generation: 400 / 30 = 13.3 seconds of blank screen.

Streaming:
  TTFT ~1.2s (prompt processing + first token)
  user sees words at 1.2s, text completes at ~14.5s total.
  Same total time, but the user perceives a 1.2s response.

Switching to a lightweight model at 60 tokens/sec:
  TTFT ~0.6s, total ~7.3s. Faster AND cheaper per token.
Perceived latency vs total latency

perceived latency = TTFT    total latency = TTFT + output_tokens / tokens_per_sec

Where: TTFT (time to first token) is prompt processing plus the first token; total latency adds the whole generation. Worked from the numbers above: 400 tokens at 30 tokens/sec means 13.3 seconds of blank screen without streaming, but a 1.2s perceived response with it. A lighter model at 60 tokens/sec gives 0.6s TTFT and 7.3s total: faster and cheaper per token.

The two axes are independent: streaming fixes perceived latency, smaller models fix actual latency. A "feels slow" complaint is usually solved by streaming first.

Inference parameters: temperature, top-p, top-k, max tokens

Four knobs on every model call, and none of them is a cost lever. Temperature controls randomness: at 0 the model picks the most likely token every time (the most deterministic setting); higher values sample more creatively. Top-p limits sampling to the smallest set of tokens whose probabilities sum to p (also called nucleus sampling). Top-k limits sampling to the k most likely tokens. Max tokens caps the output length: the model stops there no matter what.

They are motivated by consistency, not cost. A contract that demands near-identical answers to identical queries is answered by temperature 0, deterministic caching, and prompt versioning: not by provisioned throughput, which stabilizes latency, not randomness. Max tokens is the one with a cost shadow, because it caps output spend, which is why it also appears in Topic 02's output caps. But temperature and top-p never change the per-token price; they change the shape of the answer.

Two failure shapes. Tuning temperature to fix a cost problem: randomness knobs do not change token counts. Raising max tokens "to be safe": unbounded outputs are the output-token equivalent of an uncapped budget.

Reading the diagram: the non-streaming timeline is one long bar of silence, then the entire answer appears at once, with the time-to-first-token line far to the right. The streaming timeline shows tokens arriving in chunks from almost the start, the TTFT line near the left, text building while generation continues. Total durations are similar; the difference is entirely in when the user sees something. What breaks: if your delivery path buffers the stream (a proxy that waits for the full body, API Gateway limits on long connections), users get non-streaming behavior despite your streaming API call. And if the model is huge and slow, TTFT stays bad: streaming cannot fix a model that is simply too slow; only a smaller model or caching can.

Trap

"Streaming makes the model faster." It does not change generation speed at all; it changes when the user sees output. The exam pairs this with a second trap: using streaming to fix a hard latency SLA. If the scenario demands a guaranteed sub-3-second complete response, streaming helps perception but the guarantee comes from provisioned throughput and model choice. Also watch for "streaming reduces cost": it does not; token counts are identical.

How the exam asks it: "users complain the chatbot feels slow; responses take 10+ seconds to appear; answers are correct." Answer: enable streaming (ConverseStream) so tokens render incrementally. Distractors: provisioned throughput (fixes capacity, not perception, and costs more), a larger model (slower and pricier), batch inference (wrong direction entirely). The tell is "feels slow" or "time to first token" language with correct-but-slow answers.

09. Batch inference

Half-price inference for work that can wait.

Overnight work at roughly half price

Batch inference is Bedrock's asynchronous, discounted inference mode. Instead of calling the model and waiting, you upload a file of many requests (JSON Lines, one request per line) to S3, start a batch job, and Bedrock processes everything in the background. Results land in another S3 location hours later. The price is roughly 50% below on-demand for the same model, because AWS schedules your work into idle capacity windows.

Not every model call needs an answer in seconds. Nightly document classification, weekly report summarization, backfilling embeddings for a knowledge base: these are offline workloads. Paying on-demand rates and holding open connections for work nobody is waiting on is wasteful. Batch trades latency for price. Without it, teams either overpay on-demand for overnight jobs or build their own queue-and-retry machinery around real-time calls.

The mechanics: you write requests as a .jsonl file, each line one complete model invocation (model ID, prompt body), and upload it to S3. You call CreateModelInvocationJob with the input S3 URI and an output S3 URI. Bedrock validates the file and queues the job, then drains the queue in the background with spare capacity. Typical completion is measured in hours, not seconds, and there is no latency SLA. Results are written as another JSONL file to your output S3 prefix, one result per line, including per-request errors for malformed lines. An IAM role grants Bedrock read access to the input bucket and write access to the output bucket.

Nightly job: summarize 200,000 product reviews.
Each call: 1,500 input tokens, 200 output tokens.
Illustrative flagship pricing: $3.00/$15.00 per 1M in/out tokens.

On-demand:
  input  = 200,000 * 1,500 = 300M tokens * $3.00/1M   = $900
  output = 200,000 *   200 =  40M tokens * $15.00/1M  = $600
  total = $1,500 per night

Batch (50% discount):
  total = $750 per night  ->  $273,750/year saved if run nightly.
The batch discount

batch cost ≈ 0.5 × on-demand cost

yearly savings = nightly savings × 365

Where: the ~50% discount applies to the same model on the same tokens, because AWS schedules batch work into idle capacity. Worked from the numbers above: $1,500 per night on-demand becomes $750 per night in batch, so $750 × 365 = $273,750 saved per year. What you give up: answers arrive hours later instead of seconds.

The only thing you gave up: answers arrive hours later instead of seconds.

Reading the diagram: the JSONL file of requests sits in S3 with no application holding an open connection; the batch job box shows a clock (hours of latency) and a 50% discount tag, because Bedrock schedules this work into spare capacity; results accumulate in S3 as JSONL for your app to poll. What breaks: malformed JSONL lines fail individually and you discover it hours later from the output file, so validate first. If the IAM role lacks S3 write permission on the output prefix, the whole job fails. And if the workload is actually interactive, batch is the wrong tool no matter how cheap: the exam tests whether you notice the latency requirement.

Trap

"Batch inference is just a slower on-demand, so I can use it for my chat app to save money." No. Batch has hours-scale latency and no SLA; using it for anything interactive breaks the product. The exam frames this as "a company wants to cut inference costs for its real-time chatbot" and offers batch as a tempting 50%-off distractor. The latency requirement in the scenario disqualifies it instantly. Batch is only correct when the scenario says words like "nightly", "offline", "no strict latency requirement", or "results needed by morning".

How the exam asks it: "a media company must generate summaries for 500,000 archived videos; results needed within 24 hours; minimize cost." The answer: batch inference with S3 input and output. Distractors: provisioned throughput (paying for idle hours on a one-shot job), on-demand with a big Lambda fleet (full price plus operational overhead), fine-tuning (irrelevant). The tell is "offline" plus "cost is the priority."

10. Provisioned Throughput

Reserve capacity when steady traffic and latency guarantees matter more than per-token price.

Buying certainty by the hour

Provisioned Throughput (PT) is reserved inference capacity on Bedrock. You purchase model units, each a fixed amount of processing capacity for a specific model, on a commitment term (commonly 1 month or 6 months). You pay an hourly rate per unit for the whole term, used or not. In exchange, requests routed to your provisioned model get dedicated capacity: consistent latency, no throttling from shared on-demand quotas, and a guaranteed throughput floor. You create it with CreateProvisionedModelThroughput and get back a provisioned model ARN (Amazon Resource Name). Invocations must target that ARN to use the reserved capacity.

On-demand shares capacity with everyone. At peak, your requests compete with other customers and you can be throttled; latency varies. For a production app with a latency SLA (sub-3-second responses) or steady high volume, that variance is unacceptable. PT buys certainty: your baseline traffic always has a lane.

The mechanics that matter. Sizing: estimate steady-state load in tokens per minute and buy enough model units to cover it; the console and documentation give per-model guidance. Commit: 1 or 6 months, with longer commits cheaper per hour. The hourly meter runs 24/7 for the whole term, idle or busy. Routing, the step everyone gets wrong: buying PT does nothing by itself. Your code must invoke the provisioned model identifier (ARN), not the base model ID. Code that calls the base model ID after buying PT still goes to the on-demand pool, still gets throttled, and you pay for idle reserved capacity. That is the classic exam bug.

Autoscaling: PT supports autoscaling policies that add model units when utilization crosses a threshold and remove them when traffic drops, within minimum and maximum bounds you set. It handles growth inside the term, but scaling up takes time to take effect, so it does not replace burst planning.

The hybrid pattern, the exam's "most correct" production answer: PT covers the predictable baseline (the 2M requests/day that always arrive), and on-demand overflow handles the spikes (the 10x Friday rush). You never provision for the peak. You provision for the floor.

Illustrative numbers. A model unit costs $20/hour on a 6-month term. Your app has a steady baseline that would cost $15/hour on-demand running 24/7, plus Friday spikes that triple the load.

Option A: all on-demand.
  baseline $15/hr * 720 hrs/mo  = $10,800/mo
  spikes add ~$4,000/mo        = $14,800/mo total
  risk: throttling at peak, latency variance.

Option B: PT for baseline + on-demand overflow.
  1 model unit covers the baseline: $20/hr * 720 = $14,400/mo
  spikes on-demand: ~$4,000/mo
  total = $18,400/mo. MORE expensive than all on-demand!

Option C: PT only when the baseline is big enough.
  If baseline were $30/hr on-demand, PT at $20/hr wins:
  PT: $14,400 + spikes $4,000 = $18,400
  on-demand: $30*720 + $8,000 = $29,600. PT saves $11,200/mo.
The provisioned-throughput decision

PT cost/month = hourly_rate × model_units × ~720 hours

PT wins iff on-demand baseline/month > PT cost/month

Where: hourly_rate is per model unit for the whole term, used or not; ~720 hours is a month of 24/7 billing. Worked from the numbers above: PT at $20/hr is $14,400/month for the baseline, so against a $15/hr on-demand baseline it loses ($18,400 vs $14,800), but against a $30/hr baseline it wins ($18,400 vs $29,600: $11,200/month saved). Always do the arithmetic before recommending it.

The lesson: provisioned throughput is NOT a discount for everyone. It wins when your steady baseline is large enough that the hourly rate beats the per-token rate. For small or spiky baselines, on-demand is cheaper. Always do the arithmetic before recommending it.

The solid block is the capacity you bought: model units, hourly fee, committed term, always on, always billed, even at 3 a.m. The decision diamond routes steady baseline traffic to the reserved block and overflow spikes to the on-demand lane. That hybrid split is the production pattern the exam rewards. What breaks: if code invokes the base model ID instead of the provisioned ARN, reserved capacity sits idle while requests throttle on the on-demand pool. If autoscaling is not configured, a growth spike outruns the reserved units and throttles anyway. If the baseline shrinks, you keep paying the hourly fee for the whole term.

Trap 2: "we bought provisioned throughput but we are still throttled." Capacity is not the bug; routing is. The code must target the provisioned model ARN. The exam presents this as a debugging question: "after purchasing PT, throttling continued; what is wrong?" Answer: the application still invokes the base model ID.

How the exam asks it, two shapes. Design: "2M requests/day baseline, 10x Friday spikes, sub-3s latency, minimize cost." Answer: PT for baseline plus on-demand overflow. Distractors: all-PT (overprovisioned idle cost), all-on-demand (throttling risk), EC2 fleet (operational overhead). Debugging: "PT purchased, throttling persists." Answer: route invocations to the provisioned model ARN. Distractor: "buy more model units."

11. Inference profiles and cross-region routing

Route around regional limits: more capacity, automatic failover, one identifier.

FACT-CHECK 2026-09-28: prefix list and profile ID format corrected against live sources. Cross-region inference profile prefixes are us., eu., apac., and global. (plus us-gov. for GovCloud). There are no au. or jp. prefixes (APAC regions use apac.). Inference profile ID format verified as e.g. us.anthropic.claude-haiku-4-5-20251001-v1:0.

One identifier, many regions

An inference profile is a Bedrock routing identifier that sends your request to a model in one of several regions instead of pinning you to a single region. Profiles carry geographic prefixes: us., eu., apac., and global. (plus us-gov. for GovCloud regions). When you call a profile ID like us.anthropic.claude-haiku-4-5-20251001-v1:0 (illustrative naming), Bedrock routes the request across the regions where the model is available, picking one with capacity. If one region throttles, the profile can fail over to another. You call the profile ID instead of the bare model ID: Converse accepts the profile as a model identifier or ARN, and InvokeModel takes the profile ID.

Two problems motivate this. First, models are not available in every region, and quotas differ per region. An app deployed in one region can hit that region's quota wall while another region sits idle. Second, regional outages happen. Inference profiles pool capacity across regions and provide automatic failover without your code managing region lists. Without them, every team hand-builds retry-across-regions logic, which is exactly the operational overhead the exam wants you to avoid.

The mechanics: you choose a profile scope, and the scope is a data-residency decision. us. keeps data in US regions, eu. in Europe, global. can route anywhere. A compliance scenario saying "data must stay in the EU" makes global. wrong and eu. right. Your code passes the profile ID as the model identifier; Bedrock's routing layer selects a destination region with available capacity. Quotas are managed at the source region of the profile: your throttling limits follow the profile, not each destination region separately. Traffic stays on the AWS backbone, encrypted in transit; cross-region here does not mean the public internet. Failover is automatic on capacity errors: a throttled request in one region is retried in another profile region, transparently to your code.

Illustrative quota numbers. Your application needs 500 requests per minute to a model whose per-region on-demand quota is 200 RPM in each of three US regions.

Single region:  200 RPM quota  ->  throttled at 40% of needed load.
us. profile:    3 regions pooled -> effective capacity up to ~600 RPM,
                and failover if one region degrades.
Cost: identical per-token rates. The profile is a routing feature,
      not a pricing feature. No extra charge for the routing itself.

The win is capacity and resilience, not price. Do not present inference profiles as a cost lever.

Reading the diagram: one request leaves the app carrying a profile ID like us...., never naming a region. It lands in a primary region with available capacity. On throttling or outage, the dashed failover arrow shows Bedrock retrying in another profile region automatically. One response returns. Retry logic lives in the platform, not your code. What breaks: the wrong profile prefix for the residency constraint (global. for an EU-only workload) violates compliance. Profiles do not grant model access, they only route, so if the model is not enabled in the profile's regions, calls fail with access errors. And if your code passes the bare model ID, you get none of this routing and stay pinned to one region.

Trap

The exam's three-way confusion set, tested repeatedly: inference profiles route for availability and resilience (geographic prefixes), prompt routers / model routers route for cost and quality (send easy prompts to cheap models), and provisioned throughput reserves capacity (hourly commit). A scenario about regional failover wants an inference profile; a scenario about cutting cost on simple queries wants a router or cascade; a scenario about latency SLAs on steady traffic wants provisioned throughput. Each mechanism answers a different question. If you mix them up, the distractor wins.

How the exam asks it: "a model is available in only two regions; the app needs resilience against regional outages and throttling; minimal code changes." Answer: call the inference profile ID. Distractors: deploying EC2 with an ALB in a second region (does not solve Bedrock-side throttling), custom retry logic across regions (operational overhead), provisioned throughput (reserves capacity in one region, no failover). The tell is "regional" plus "failover" plus "minimal operational overhead."

12. Rate limits, quotas, and throttling with retries

Every API has a speed limit. Production code respects it instead of crashing into it.

Throttling is a signal, not a bug

Rate limits and quotas are the maximum request rates AWS allows per account, per region, per model. Exceed them and Bedrock returns a throttling error (ThrottlingException). Throttling is AWS deliberately rejecting excess requests to protect shared capacity. The correct client behavior is retries with exponential backoff and jitter: wait, then retry, waiting longer each time, with a small random offset so that many clients do not retry in lockstep and cause a second wave.

Shared infrastructure needs protection from bursts: without throttling, one customer's runaway loop could starve everyone else's on-demand traffic. And without client-side retries, every transient throttle becomes a user-facing error. The retry pattern converts a momentary "slow down" signal into invisible resilience: most throttled requests succeed on the second or third attempt with no user impact.

The mechanics: your app sends requests faster than the quota, and Bedrock returns ThrottlingException for the excess. The AWS SDKs retry throttling errors automatically with exponential backoff by default: wait about 1s, then about 2s, then about 4s, and so on, up to a max attempts limit. Jitter randomizes each wait so thousands of clients do not hammer the API at the same instant. If you write custom retry logic, retry only retryable errors (throttling, transient 5xx). Do not retry validation errors: a malformed request body fails identically forever, and retrying it wastes quota. At the architecture level, API Gateway adds its own throttling (per-method rate limits, usage plans, API keys), which protects your backend from client bursts before they reach Bedrock. When retries alone cannot keep up, the structural answers are provisioned throughput (dedicated capacity, Topic 10), inference profiles (spread load across regions, Topic 11), or a quota increase from AWS support.

Illustrative. Quota: 100 requests/minute for a model. Your app's Friday spike sends 300 requests in one minute.

Without retries:
  ~200 requests get ThrottlingException -> user-facing errors.
  Failure rate: 67%.

With exponential backoff + jitter (SDK default, ~5 attempts):
  most throttled requests land in the next minute's quota window.
  Failure rate drops to low single digits, latency rises slightly.

With provisioned throughput sized for 150 RPM + on-demand overflow:
  baseline never throttles; overflow retries handle the rest.
  This is the layered answer the exam rewards.
The retry payoff

failure rate = throttled requests / total requests

Where: the quota gates excess requests, and retries spread them into later quota windows. Worked from the numbers above: 200 of 300 requests throttled is a 67% failure rate without retries; exponential backoff with jitter (the SDK default, ~5 attempts) drops it to low single digits. Retries handle transient spikes; sustained overload needs structural capacity.

Retries are the first layer, not the whole answer. Retries handle transient spikes; structural capacity handles sustained overload.

Reading the diagram: burst arrows hit the quota gate at once; the gate is doing its job, not malfunctioning. Requests under the quota pass; excess requests are blocked. Blocked requests enter the backoff loop with waits doubling 1s, 2s, 4s plus jitter, then feed back into the gate spread over time and mostly pass. What breaks: retrying immediately with no backoff re-hits the gate and can make the throttle worse (retry storms). Retrying non-retryable errors like validation failures burns quota on requests that can never succeed. And if the overload is sustained rather than bursty, no retry pattern saves you: you need more capacity (PT, profiles, or a quota increase).

Trap

"Throttling means something is broken; I should request a quota increase immediately." Throttling during a brief spike is normal and is handled by retries. Quota increases are for sustained, legitimate growth. The exam's trap is offering "request a quota increase" as the fix for a transient burst scenario, or offering "buy provisioned throughput" when the throttling is a 30-second spike that retries would absorb. Match the fix to the duration: seconds of overload -> retries; hours of overload -> capacity.

How the exam asks it: "during traffic spikes the application throws ThrottlingException; most spikes last under a minute; minimize changes." Answer: rely on SDK retries with exponential backoff and jitter, possibly plus API Gateway throttling to smooth client bursts. Distractors: provisioned throughput (overkill for sub-minute spikes), quota increase (for sustained load), catching the exception and dropping the request (user-facing failure). The tell is "brief spikes" plus "minimal changes."

13. CloudWatch metrics for Bedrock

You cannot optimize what you cannot see. These four metrics are the dashboard.

Four metrics, then alarms

Amazon CloudWatch collects operational metrics from Bedrock automatically. The four you must know by name: Invocations (number of model calls, your volume baseline), InputTokenCount and OutputTokenCount (tokens in and out, your cost baseline; multiply by rates to get spend), InvocationThrottles (count of throttled requests, your capacity signal), and latency metrics (time per invocation, your performance signal). On top of raw metrics, CloudWatch gives you alarms (notify or act when a threshold crosses), anomaly detection (machine-learning baselines that flag unusual spikes without you setting thresholds), and dashboards combining these into one view.

GenAI bills are opaque by default: tokens flow, money flows, and nobody sees the link until the invoice. Metrics make the link visible in near real time. A sudden 3x jump in OutputTokenCount with flat Invocations means responses got longer (a prompt change, or the model rambling). A spike in InvocationThrottles means you are hitting quota walls. Without metrics you debug by guessing; with them you debug by reading.

The mechanics: every Bedrock invocation emits metric data points to CloudWatch automatically, no setup required for the basics. You build a dashboard with the four key metrics sliced by model ID and time, so you can see which model drives cost and when spikes happen. You set alarms: alert when InvocationThrottles exceeds a threshold, or when projected token spend crosses budget. AWS Budgets and Cost Anomaly Detection cover the dollar side with alerts on unusual spend patterns. CloudWatch anomaly detection learns the normal weekly pattern of your token metrics and flags deviations (a runaway loop, a prompt regression) without manual thresholds. For forensics you drill from metric to log: the spike in the dashboard leads you to CloudWatch Logs Insights queries over invocation logs (Topic 14) to find the offending prompts.

Your dashboard shows this week vs last week for one model:

InputTokenCount:    2.0B  ->  2.1B    (+5%)
OutputTokenCount:   0.3B  ->  0.9B    (+200%)
InvocationThrottles:  120  ->   95    (flat)

Reading: volume is flat, but output tokens tripled.
Diagnosis: something changed the responses, not the traffic.
Likely causes: a prompt edit removed the length limit, or maxTokens
was raised, or a new feature asks for long-form output.

This is the exam skill: read the metric pattern, name the cause, pick the fix. Flat throttles plus spiking tokens is never a provisioned-throughput question.

Reading the diagram: rising invocation bars show call volume (flat bars with rising cost elsewhere means each call got more expensive, not that you have more calls). The two token lines separate when responses get longer: a prompt or maxTokens issue. Red spikes on throttles mean quota walls: the capacity question. 14. Model invocation logging and X-Ray tracing

Metrics tell you something is wrong. Logs and traces tell you what.

What was said, and where the time went

Model invocation logging records the full request and response of Bedrock calls to S3 or CloudWatch Logs: the prompt that went in, the completion that came out, token counts, timestamps. AWS X-Ray adds distributed tracing: it follows one user request across every service it touches (API Gateway to Lambda to Bedrock to DynamoDB), recording how long each step took, so you can see exactly which step is slow or failing in a multi-step agent chain.

Metrics aggregate; debugging needs specifics. When the dashboard shows output tokens tripled, only the logs show you the prompt version that caused it. When an agent takes 40 seconds, only a trace shows whether the time went to the model, a tool call, or a slow database. Without logging, hallucinations and cost spikes are unreproducible mysteries. Without tracing, multi-step latency is a guessing game.

The mechanics: enable invocation logging in Bedrock settings, choosing S3, CloudWatch Logs, or both. Each log record includes the request body, response body, model ID, and token counts. Encrypt or disable in sensitive environments: logs contain raw prompts and responses, which may include PII. In healthcare or finance scenarios the exam expects KMS encryption on the log destination, or logging disabled where compliance forbids it; logging invocations to an unencrypted bucket in a healthcare scenario is a distractor. Query with CloudWatch Logs Insights for prompt and response forensics: find the longest responses, the most expensive calls, or every call that used a particular prompt version. Enable X-Ray tracing on your Lambda functions, API Gateway, and agent steps. Each request gets a trace ID; each service call becomes a segment with timing. For an agent, the trace shows the sequence (agent reasoning to tool call 1 to model call to tool call 2 to final answer), and the longest segment is your bottleneck. Bedrock's agent tracing and the enableTrace option on agent invocation show the reasoning steps inside the agent itself. Tool and multi-agent observability means tracking call patterns (which tools fire most), multi-agent coordination (supervisor to collaborator handoffs), and usage baselines so anomalies stand out.

An agent answers product questions in 38 seconds on average. The X-Ray trace for one request:

Trace total: 38.2s
  API Gateway + Lambda overhead:        0.4s
  Agent reasoning (model call 1):        4.1s
  Tool call: product database query:    29.8s   <-- bottleneck
  Agent reasoning (model call 2):        3.2s
  Response formatting:                  0.7s

Reading: the model is fine. The database tool call eats 78% of
the time. Fix the query or cache its results; do not buy a faster
model or provisioned throughput. The trace just saved you from
optimizing the wrong component.
Reading a trace

bottleneck share = slowest span / trace total

Where: trace total is the sum of all spans; the fix targets the longest span, not the model. Worked from the numbers above: the database tool call takes 29.8s of a 38.2s trace, so 29.8 / 38.2 ≈ 78% of the time. Fix the query or cache its results; do not buy a faster model.

Logs answer "what did we ask and what did it say"; traces answer "where did the time go." You need both.

Reading the diagram: the bottom chain runs the actual work left to right (tool call 1, model call, tool call 2, final answer). Each step has a trace span on the timeline above it; the longest span is the bottleneck, read it first. Full request and response payloads land in S3 and CloudWatch Logs below: when the trace says "tool 2 was slow," the logs say "here is the exact query and response." Metrics, logs, and traces are three views of the same request. What breaks: with logging disabled you cannot reconstruct what the model was asked, so cost and hallucination forensics become impossible. Unencrypted logs in a regulated workload are a compliance violation, not just a debugging gap. And if X-Ray is not enabled on the Lambda functions, the trace has gaps and the slow step hides between instrumented services.

Trap

"CloudTrail shows me the prompts and responses." No. CloudTrail logs API-level events: who called InvokeModel, when, from where (the audit plane). It does not record prompt or response bodies. Prompt and response forensics need model invocation logging to S3 or CloudWatch Logs (the data plane). The exam tests this distinction directly: a scenario asking "which service records the full prompt text for debugging" wants invocation logging, and CloudTrail is the distractor.

How the exam asks it: "a multi-step agent is intermittently slow; the team must find which step (tool calls vs model calls) causes the delay, and must be able to audit exact prompts later; healthcare data is involved." Answer, select-three style: X-Ray tracing across the agent chain, model invocation logging to S3 with KMS encryption, CloudWatch Logs Insights for analysis. Distractors: CloudTrail for prompt forensics (wrong plane), unencrypted logging (compliance violation), "add provisioned throughput" (optimizes the wrong component without evidence).

15. Best practices: the cost ladder

The whole domain in one ordered list: cheapest lever first, most expensive last.

The ladder, cheapest first

  1. Measure first: CloudWatch metrics, dashboards, anomaly detection. Never optimize blind.
  2. Shrink the prompt: context pruning, prompt compression, output caps. The free lever.
  3. Tune the retrieval: fewer, better chunks (lower top-k, rerank and truncate). Retrieved context is usually the biggest token cost.
  4. Skip the call entirely: semantic caching for repeated questions, deterministic hashing for identical ones.
  5. Discount the static prefix: prompt caching for repeated long system prompts and few-shot blocks.
  6. Right-size the model: prompt routers and cascading, small model for simple requests, flagship for complex.
  7. Bake repeated behavior into a small model: fine-tuning or distillation for narrow tasks at massive scale. The most expensive lever; only after the free ones.
  8. Defer what can wait: batch inference for offline work at roughly half price.
  9. Guarantee the baseline: provisioned throughput for steady traffic, with on-demand overflow for spikes.
  10. Route across regions: inference profiles for capacity, failover, and data residency.
  11. Stream responses: perceived latency without changing the model.
  12. Retry correctly: exponential backoff with jitter for throttling, structural capacity for sustained overload.
  13. Govern spend: AWS Budgets, Cost Anomaly Detection, token tagging, prompt versioning in Prompt Management.

This ladder is the domain's backbone. The exam's best-practice questions are almost always ladder questions: the correct answer is the cheapest lever that fits the scenario's constraints. "Overnight" points to batch. "Repeated questions" points to semantic caching. "Same long prefix" points to prompt caching. "Simple queries on a flagship" points to routing. "Steady baseline with SLA" points to provisioned throughput. Work down the ladder, not up.

The full-stack answer, the shape the exam loves most. A production chat app on a flagship model:

Starting point: 1M calls/mo on a flagship model, 3,000 input +
400 output tokens/call, illustrative $3.00/$15.00 per 1M.
  input:  3.0B tokens * $3.00/1M  = $9,000
  output: 0.4B tokens * $15.00/1M = $6,000
  total = $15,000/mo.

Apply the ladder:
  1. Prune + compress: 3,000 -> 1,200 input tokens.  -$5,400
  2. Prompt caching on the 800-token static prefix (90% off
     cached portion, high hit rate).                    -$1,700
  3. Semantic cache: 40% of questions repeat.           -$3,200
  4. Cascade: 70% of remaining calls go to a lite model
     at ~1/12 the price.                                -$2,900
  New total ~ $1,800/mo.  88% reduction, same UX,
  verified by re-running evaluations after each step.

Every lever stacked, each on the scenario it fits, none redundant. Notice streaming (latency) and retries (reliability) ride along because the ladder is not only about cost.

Reading the diagram: the ladder climbs from the cheapest free lever (measure first, shrink the prompt, tune the retrieval) up through skip-the-call (semantic cache), discount-the-prefix (prompt caching), right-size (router), bake-it-in (fine-tuning, the most expensive rung), defer (batch), guarantee (PT), route (profiles), stream, retry, and govern spend at the top. The order is the point: each rung is more expensive or more operational than the one below. What breaks: pulling an expensive rung first (buying provisioned throughput before compressing prompts) wastes money the free levers would have saved. Skipping "measure first" means you optimize the wrong bottleneck.

Reading the diagram: the SaaS cost-control diagram maps the same ladder onto a production SaaS architecture: lean prompts and semantic caching at the request edge, routers sending traffic to the right model tier, batch jobs draining offline work, PT covering the steady baseline with on-demand overflow, and a CloudWatch dashboard with budgets and anomaly detection watching the whole stack. The pattern is identical; only the deployment shape changes.

The scenario shapes

  • Optimization under constraint ("token costs growing 30%/month, no UX degradation"): stack the free levers (prompt compression, caching, caps), re-verify quality with evaluation.
  • Performance plus volatility ("sub-3-second responses, 10x traffic spikes"): streaming for perceived latency, smaller models, provisioned throughput for baseline plus on-demand overflow, retries with backoff for spikes.
  • Debugging a broken setup ("bought provisioned throughput, still throttled"): check the invocation target. It must be the provisioned model ARN, not the base model ID.
  • Consistency ("99.5% of identical queries must return identical results"): temperature 0, deterministic caching, prompt versioning. Temperature and top-p control randomness, a different topic, but cost and consistency meet here: caching and versioning make behavior predictable.
  • Quality plus spend ("hallucinations rising, spend rising"): evaluation jobs catch quality regressions, Cost Anomaly Detection catches spend regressions.

The exam's portfolio question gives you a whole system (chat plus agents plus batch jobs) and asks for the cost and latency design. The answer is a ladder walk: each component gets its cheapest fitting lever, and the portfolio is the stack.

Trap

"There is one best pricing model." There is not. The exam's "most correct answer" is almost always a hybrid matched to the traffic shape: PT for the floor, on-demand for the spikes, batch for the offline tail, caching for the repeated head. Any option that applies a single lever to a multi-constraint scenario is the distractor. Read every constraint in the stem, map each to one ladder step, and pick the answer that covers all of them.
