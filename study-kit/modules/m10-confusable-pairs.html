Confusable pairs atlas: how to tell look-alike answers apart in long questions

After this module, you can read a long scenario, find the one constraint that decides the service, and reject each look-alike option with one reason. Most lost points in this exam come from two services that do part of the same job. The fix is to ask what the service does at run time, what it accepts as input, and what it returns. This module teaches that test for 32 pairs, ordered by how often they appear in the practice corpus.

The deciding constraint

Most long questions contain five to eight services, and only one or two of them match the stated constraint. Start with the constraint word, not with the service names. Words about who owns the runtime, how long the job runs, who must read the output, and when a rule applies decide most answers. The tree below starts from a scenario and ends at a service family. Use it first, then open the pair section for the two services that remain.

Figure: First split the scenario by whether a model reply is required.

Signal words that point to a model reply: generate, summarize, draft, answer, foundation model, token, prompt, grounded. Signal words that point to plumbing: trigger, retry, wait, route, queue, schedule, event, handler. The same sentence can contain both, so decide what the question asks you to choose.

Rule: Name the one constraint in the scenario before you read any option. Write it in your own words.

Exam tip: Long stems often add a sentence that changes the answer, such as a limit on data location, a latency target, or a staff role. Underline that sentence first.

Confusable pairs atlas

Each section below gives one pair. The count line shows how often the practice corpus put the two services against each other. Counts add both directions, and labels that differ only by the words Amazon Bedrock are merged. A count of 0 means the two services did not meet directly in the corpus. In those cases, the nearest row is shown. The pairs with a count of 0 are still in the atlas because the learner needs them.

Each pair uses the same layout. You get a decision tree, three lines for purpose, input, and effect, one question to ask yourself, the signal words for each side, and the trap. The source line lists the AWS pages or Sundog slides behind the facts.

Bedrock versus Lambda

Corpus count: 98 (74 and 24 in the two directions). The most frequent pair in the corpus.

flowchart TD A["Task needs a generated
reply"] -->|Yes and the model is
managed| B["Amazon Bedrock"] A -->|No only code runs
between services| C["AWS Lambda"] B -->|Glue code still
needed around the
call| D["Lambda calls Bedrock"] C -->|Code calls a model| D

Figure: Bedrock returns the reply. Lambda decides when and how the call happens.

  • Purpose: Bedrock gives managed access to foundation models. Lambda runs your code in response to an event.
  • Input: Bedrock takes messages or a prompt plus model settings. Lambda takes an event from a trigger, such as an API call or a queue message.
  • Effect: Bedrock returns generated content. Lambda returns whatever your code returns, often after calling Bedrock.

Ask yourself: Does the requirement describe the content of a reply, or the code that runs around the reply?

  • Bedrock signal words: model, foundation model, prompt, token, summarize, grounded answer, guardrail.
  • Lambda signal words: event, trigger, handler, transform payload, call an API, retry in code, glue.

Trap: Lambda appears in most correct architectures, so it looks like the answer whenever it is named. Lambda is the caller in these designs. Pick it only when the requirement is about code between services.

Source: https://docs.aws.amazon.com/bedrock/latest/userguide/flows.html, Sundog slide page 118.

Bedrock versus CloudWatch

Figure: Bedrock produces the output. CloudWatch watches the calls.

  • Purpose: Bedrock runs model inference. CloudWatch monitors resources and applications with metrics, logs, alarms, and dashboards.
  • Input: Bedrock takes prompts. CloudWatch takes metric data points and log events from services.
  • Effect: Bedrock returns model output. CloudWatch raises alarms and shows trends.

Bedrock versus Step Functions

Corpus count: 53 (33 and 20 in the two directions).

flowchart TD A["Requirement describes
steps and state"] -->|Steps with waits
branches and
approvals| B["AWS Step Functions"] A -->|One model call with
one prompt| C["Amazon Bedrock"] B -->|Each step calls a
model| C

Figure: Step Functions owns the order of work. Bedrock owns one model call.

  • Purpose: Step Functions coordinates a sequence of tasks with state, retries, waits, and parallel branches. Bedrock performs model inference.
  • Input: Step Functions takes a state machine definition and a payload. Bedrock takes a prompt or messages.
  • Effect: Step Functions records each execution and its state transitions. Bedrock returns one generated reply per call.

Ask yourself: Does the question care about what happens between steps, or about the text of one reply?

  • Step Functions signal words: state machine, retry, wait, approval, branch, parallel, long-running, audit history.
  • Bedrock signal words: single prompt, reply, model, token, summary, answer.

Trap: A state machine around one model call adds work with no benefit. When the stem asks only for a reply, Bedrock is the answer even if a workflow service is mentioned.

Source: https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html, https://docs.aws.amazon.com/bedrock/latest/userguide/flows.html.

Bedrock versus Guardrails

Corpus count: 44 (25 and 19, both with Bedrock as the correct answer, merged across both label forms).

flowchart TD A["Requirement asks for a
rule on text"] -->|Rule screens prompts
or replies| B["Bedrock Guardrails"] A -->|Requirement asks
which model answers| C["Amazon Bedrock model"] B -->|Attached to a
Bedrock call| C

Figure: Guardrails is a policy layer. It does not pick or host a model.

  • Purpose: Guardrails screens inputs and outputs against configured policies. Bedrock gives access to the model that produces the output.
  • Input: Guardrails takes the text and a guardrail configuration. Bedrock takes the prompt and a model ID.
  • Effect: Guardrails blocks, masks, or only detects content. Bedrock returns the model output, which Guardrails can then screen.

Ask yourself: Is the requirement a model choice or a policy that screens text in each request?

  • Guardrails signal words: block, mask, denied topic, PII filter, harmful content, grounding threshold, policy.
  • Bedrock signal words: model, invoke, converse, tokens, throughput, model ID.

Trap: Guardrails appears in the same answer as a model call, so it is easy to pick it as the model. A guardrail is attached to a request and does not return a reply by itself. The model still comes from Bedrock.

Source: https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-sensitive-filters.html, https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-contextual-grounding-check.html, Sundog slide pages 21 and 57.

Figure: Custom weights can reach Bedrock, but the team still chooses the training path.

  • Purpose: Bedrock gives API access to managed foundation models. A SageMaker AI endpoint hosts a model on infrastructure you choose.
  • Input: Bedrock takes a model ID and a request body. SageMaker takes a model artifact, a container, and an instance type.
  • Effect: Bedrock returns inference from a managed model. SageMaker returns inference from your hosted model, with control over scaling and deployment settings.

  • SageMaker signal words: instance type, container, multi-model endpoint, asynchronous inference, model registry, own weights.

Trap: A model that was fine-tuned in SageMaker AI does not force a SageMaker endpoint. Bedrock can serve an imported model when the artifact and architecture are supported. A customized Bedrock model also needs Provisioned Throughput before you can call it.

Bedrock versus API Gateway

Figure: API Gateway receives and checks the call. Bedrock writes the reply.

CloudWatch versus CloudTrail versus X-Ray

Corpus count: 33 (CloudWatch over CloudTrail 20, CloudTrail over CloudWatch 8, CloudWatch over X-Ray 5).

flowchart TD A["Question to answer"] -->|Who called which
action| B["AWS CloudTrail"] A -->|Where did the time
go across hops| C["AWS X-Ray"] A -->|Metric crosses a
threshold| D["Amazon CloudWatch"]

Figure: Each service answers one kind of question. Do not swap them.

  • Purpose: CloudWatch monitors metrics, logs, and alarms. CloudTrail records account activity and API actions. X-Ray traces individual requests across services.
  • Input: CloudWatch takes metric points and log events. CloudTrail takes API activity from the account. X-Ray takes trace segments from an SDK or from Lambda.
  • Effect: CloudWatch raises alarms and shows dashboards. CloudTrail gives an audit record with the identity, time, and resource. X-Ray gives a trace map and timing for each hop.

Ask yourself: Is the question about who acted, which hop is slow, or which value crossed a line?

  • CloudWatch signal words: alarm, threshold, dashboard, metric, log group, error rate.
  • CloudTrail signal words: who, principal, audit, governance, management event, history.
  • X-Ray signal words: trace, segment, service map, latency per hop, bottleneck, downstream call.

Trap: X-Ray shows where a request spent its time, but it does not tell you which user changed a setting. CloudTrail does the second job and does not show latency per hop.

Source: https://docs.aws.amazon.com/xray/latest/devguide/aws-xray.html, https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html, https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/WhatIsCloudWatch.html, Sundog slide page 459.

Bedrock versus CloudTrail

Figure: CloudTrail records that a call happened. It does not produce the reply.

  • Purpose: Bedrock produces model output. CloudTrail records actions that users, roles, and services take, including API calls.

Lambda versus CloudWatch

Step Functions versus Lambda

Corpus count: 24 (12 and 12 in the two directions).

flowchart TD A["Order and waiting between
steps"] -->|Yes| B["AWS Step Functions"] A -->|No the hard part is
one task body| C["AWS Lambda"] B -->|Each task can run a
Lambda function| C

Figure: Step Functions manages the sequence. Lambda does one unit of work.

  • Purpose: Step Functions runs a state machine with retries, waits, and branches. Lambda runs one function invocation.
  • Input: Step Functions takes a state machine definition and an execution input. Lambda takes an event.
  • Effect: Step Functions records state and execution history. Standard workflows run up to one year and follow exactly-once execution. Express workflows run up to five minutes and follow at-least-once or at-most-once execution.

Ask yourself: Does the stem care about the path through several steps, or about what one step computes?

  • Step Functions signal words: wait, retry across steps, approval, branch, parallel, long-running, durable.
  • Lambda signal words: single task, transform, call an API, handler, short run.

Trap: Retry loops and sleep logic written inside a Lambda function can work for short jobs. When the stem asks for durable state and an execution history, the orchestration belongs in Step Functions.

Lambda versus EventBridge

Corpus count: 22 (17 and 5 in the two directions).

flowchart TD A["Event must reach the right
consumers"] -->|Routing by event
pattern| B["Amazon EventBridge"] A -->|Code runs when the
event arrives| C["AWS Lambda"] B -->|Matched events
invoke| C

Figure: EventBridge decides who receives an event. Lambda does the work.

  • Purpose: EventBridge routes events from sources to targets by rules. Lambda runs code for a single event.
  • Input: EventBridge takes events from AWS services, applications, and partners. Lambda takes the events it is given.
  • Effect: EventBridge delivers matched events to one or more targets. Lambda returns a result or performs an action.

Ask yourself: Does the stem ask which consumers receive an event, or what a consumer does with it?

  • Lambda signal words: process, compute, transform, handler, one consumer.

Trap: A single Lambda function that reads every incoming message and branches in code is not a router. When many sources must reach many targets by pattern, the routing belongs in EventBridge.

Corpus count: 20 (all 20 in the direction where Lambda was the correct answer).

flowchart TD A["Needs controls beyond one

IAM or open access| C["Lambda function URL"] C -->|Public internet only| D["No PrivateLink path"]

Figure: A function URL is simple. It is also public, so private access rules it out.

Trap: Function URLs use the public internet only. The page states that they do not support PrivateLink. A stem that requires private connectivity cannot pick a function URL. The page also does not list request validation or usage plans, so Not in source for those features.

Provisioned Throughput versus batch versus on-demand

Corpus count: 17 for Bedrock as the on-demand answer over Provisioned Throughput. Batch has no direct row in the corpus.

flowchart TD A["Workload shape
decides capacity"] -->|Steady high
volume or
custom model| B["Provisioned
Throughput"] A -->|Large job with
results in S3
later| C["Batch inference"] A -->|Spiky or
interactive
traffic| D["On-demand"]

Figure: Pick the capacity model from the traffic shape, the timing of results, and the model type.

  • Purpose: Provisioned Throughput reserves model units for a model at a fixed hourly price. Batch inference runs many prompts asynchronously. On-demand uses account quotas and pays per use.
  • Input: Provisioned Throughput needs a purchased model ARN used as the model ID. Batch takes input files in S3. On-demand takes ordinary inference calls.
  • Effect: Provisioned Throughput gives predictable capacity with a commitment choice of none, one month, or six months. Batch writes results to S3 when the job completes. On-demand returns each reply as it is generated, within quotas.

Ask yourself: Does the business need a reply now, a reply later, or a guaranteed rate every hour?

  • Provisioned Throughput signal words: predictable, steady, model units, reserved, customized model, commitment.
  • Batch signal words: overnight, large dataset, S3 input and output, no user waiting, asynchronous.
  • On-demand signal words: spiky, interactive, sporadic, pay per use, account quotas.

Trap: Batch is not an answer for interactive chat, even at high volume. Provisioned Throughput is not an answer when traffic is sporadic and the stem asks for the lowest fixed cost. The page also states that batch inference is not supported for provisioned models.

Source: https://docs.aws.amazon.com/bedrock/latest/userguide/prov-throughput.html, https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference.html, Sundog slide pages 225, 290, and 291.

Read a long question

Each scenario below is short and original. Read the constraint words first, then remove each option by type. Name one reason for each removal. The answer comes last. Use the same method on the real stem.

Scenario one: policy answers with citations

A bank wants an assistant that answers loan questions from policy documents stored in S3. Each answer must show the paragraph that supports it. The team does not want to write retrieval code or run a vector database.

Constraint words: policy documents, show the supporting paragraph, no retrieval code, no vector database.

  • A Lambda function with a self-managed vector store is out. It adds the retrieval work the stem bans.
  • A SageMaker AI endpoint is out. It hosts a model, but it does not manage retrieval or citations.
  • Comprehend is out. It labels text, but it does not write a cited answer.

Answer: Bedrock Knowledge Bases with a managed knowledge base. It runs retrieval and generation and returns the passages used.

Scenario two: data screened in each request

A clinic sends free text from patients to a model. Patient names and phone numbers must be masked before the model reads the text. Staff also want the model to refuse dosage advice, and that rule must act on each request.

Constraint words: masked before the model reads, refuse a topic, each request.

  • Macie is out. It scans S3 objects at rest, so it does not screen a live prompt.
  • A regex in Lambda alone is out. Regex misses names that depend on context, and it cannot enforce a topic rule.
  • Comprehend alone is out. It masks PII, but it does not enforce a topic rule on the model reply.

Answer: Bedrock Guardrails with a sensitive information filter set to mask and a denied topic. The guardrail acts inline on the prompt and the reply.

Scenario three: who acted and how slow it was

An operations team must find which IAM principal changed a model access setting last week. The same team needs an alert when the latency of the assistant stays above a threshold for ten minutes. The two answers must come from different evidence.

Constraint words: which principal, last week, alert, threshold, latency.

  • X-Ray is out for the first need. It traces requests, and it does not record who changed a setting.
  • CloudTrail alone is out for the second need. It records actions, and it does not raise a latency alarm.
  • Model Evaluation is out for both. It scores answer quality, and it does not record actions or watch latency.

Answer: CloudTrail for the principal and change record, and a CloudWatch alarm on latency. Each service answers only its own question.

Scenario four: a large job with results later

A publisher must summarize two million archived articles before the next morning. Results go to an S3 bucket, and no user waits for a reply. The team wants the lowest cost for this job.

Constraint words: two million, before morning, results in S3, nobody waits.

  • A Lambda loop calling on-demand inference is out. It is synchronous, and the stem expects a batch process with results in S3.
  • Provisioned Throughput is out. The batch page states that batch inference does not support provisioned models, and a commitment is not the lowest cost for a one-time job.
  • Step Functions express synchronous execution is out. It has a five-minute limit, and the job is too large for one execution.

Answer: Bedrock batch inference with input and output in S3.

Scenario five: analysts change the path

Business analysts must change the steps of a generative workflow without writing code. Each step calls a prompt, a knowledge base, or a Lambda function. The team wants versions of the workflow and an alias that the application calls.

Constraint words: analysts without code, prompt, knowledge base, versions, alias.

  • Agents are out. The model would choose the tools, and the stem fixes the path for analysts.
  • Lambda alone is out. Each change would need a code deployment.
  • Step Functions is out. It coordinates service tasks in a state machine, and the stem centers on prompt and knowledge base nodes that analysts edit.

Answer: Bedrock Flows. The visual builder, versions, and alias match the stem.

Exam tip: Write the constraint in five words or fewer before you read the options. Then remove options by type first. A type removal takes one sentence. A detailed comparison of two near-identical options is slower and less reliable.

Distractor patterns seen in the tests

Most wrong options are not random. They follow a small set of patterns. Recognizing the pattern lets you reject an option without knowing every detail of the service.

  • Right family, wrong layer. A policy feature is offered as a model choice, or a model is offered as a control. It is wrong because each layer has a different job, and a policy does not pick a model.
  • Right purpose, wrong time. A tool that checks data after it sits in storage is offered for data in a live request. It is wrong because the stem asks for a control at request time.
  • Right service, wrong network surface. A private endpoint for one API set is offered for another API set. It is wrong because each Bedrock API surface has its own endpoint.
  • Build it yourself. Custom code is offered where a managed feature exists. It is wrong when the stem asks for less operational work or for a managed control.
  • Managed feature where ownership is required. A managed model API is offered when the stem asks for control of the serving container. It is wrong because the stem names the ownership boundary.
  • Wrong capacity model. Committed capacity is offered for sporadic traffic, or on-demand is offered for a steady high load with a fixed rate need. It is wrong because the capacity choice follows the traffic shape.
  • Storage posed as retrieval or retrieval posed as storage. A store that returns items is offered as an answer writer, or a model is offered as a store. It is wrong because the stem asks for one of the two jobs.
  • Monitoring posed as evaluation. A dashboard is offered for answer quality. It is wrong because health metrics do not show whether an answer is correct.
  • Config posed as secret. A plain parameter store is offered for a credential that must rotate. It is wrong because rotation belongs to the secrets service.
  • Heavy orchestration for a simple call. A workflow service is offered for one model call. It is wrong because it adds state and cost with no requirement that needs it.
