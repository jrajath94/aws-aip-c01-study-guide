How to think: five steps for each question

Each question has one answer type and one set of constraints. Work through five steps in order. Do not start with the options.

flowchart TD S1["1. Read the last sentence
and name the answer type"] --> S2["2. List each constraint
word in the stem"] S2 --> S3["3. Mark each constraint as
hard or soft"] S3 --> S4["4. Pick the managed option
that meets every hard
constraint"] S4 --> S5["5. Check the choice for a
trap and for soft
constraints"]

Figure: the order of work for each question. Step 4 uses hard constraints only.

  • Step 1: Name the answer type. Write one of four words: service, configuration, failure cause, or design.
  • Step 2: Write each constraint as a short phrase. Examples are cost, latency, Region, effort, and existing footprint.
  • Step 3: Mark a constraint as hard when the stem says must, only, required, or never. Mark all other constraints as soft.
  • Step 4: Remove each option that breaks one hard constraint. Keep the simplest managed option that remains.
  • Step 5: Read the remaining option once more. Check its scope, its layer, and its limit against the stem.

Decision rule: A hard constraint removes an option. A soft constraint only breaks a tie between options that remain.

Trap: The option that meets most constraints is still wrong. One broken hard constraint removes that option.

Exam tip: Write the constraints before you read the options. Options written to look right are easier to accept when you have no list.

Source: method for this course, built from the repo guide Part 1 (how AWS asks questions) and Part 8 (method for each question). The hard and soft labels are a study aid.

4. Latency versus throughput versus batch

Latency is what the user feels. Throughput is what the system handles. Batch inference is offline work from S3 to S3.

flowchart TD A["Stem names a speed
or volume target"] --> B["Does a user wait
for the reply"] B -->|Yes| C["Real-time call on
on-demand or
Provisioned
Throughput"] B -->|No| D["Batch inference
from S3 to S3"] C --> E["Which target does
the stem name"] E -->|Perceived
speed| F["Stream the
response"] E -->|Slow call| G["Trace each step
with X-Ray"] G --> H["Slow retrieval
step"] H --> I["Index tuning,
query

hybrid search"] E -->|Steady volume| J["Provisioned
Throughput for the
baseline"] E -->|Spiky volume| K["On-demand for the
spikes"]

Figure: the target word in the stem picks the lever.

  • Streaming improves perceived speed. It does not raise throughput. It does not shorten total generation time.
  • Buying Provisioned Throughput does not change the speed of one call. It reserves model units. The call must use the provisioned model ARN.
  • Batch inference reads input from S3 and writes output to S3. It is not supported for provisioned models.
  • Set the batch job time limit with a timeout duration in hours.
  • For a slow step, measure each step first. A slow retrieval step needs index tuning, query preprocessing, or hybrid search.
  • Precompute predictable answers when speed matters for repeated questions.

Decision rule: Name the target first. Perceived speed, call speed, and volume each point to a different lever.

Trap: Batch does not fit a user waiting on a reply. A bigger model does not fix a slow search step.

Exam tip: Latency and throughput are different targets. Read the metric word before you pick a lever.

Figure: diagnose the stage that failed, in order.

  • Check the chunks first. Then check the ranking. Then check the generator model.
  • Changing the generator model does not repair broken retrieval.
  • Score the retriever with context relevance and context coverage. Score the generator with faithfulness.
  • When answers are wrong, run retrieve-only first. When the retrieved text is good but ignored, run retrieve-and-generate.

Trap: Reranking fixes order. It does not add a chunk that retrieval missed. Temperature does not fix bad retrieval.

  • Guardrails has six policy types: content filters, word filters, denied topics, sensitive information filters, Automated Reasoning checks, and contextual grounding checks.
  • A denied topic covers a whole subject in plain language. A word filter covers exact strings and misses rephrased requests.
  • The prompt attack category applies to input. With InvokeModel, tag the user input. Untagged input is not checked for prompt attacks.

Trap: Grounding is not safety. A denied topic is not a prompt attack detector. Detect mode is not a block.

Exam tip: Claims that a control prevents all prompt injection or eliminates hallucinations are wrong. No control is absolute.

12. Versions, rollback, and release gates

Every release is a version you can roll back. A prompt, model, chunk setting, guardrail, or agent change is a release.

flowchart TD A["Stem names a change to
prompt, model, chunks,
guardrail, or agent"] --> B["Store the change as a
version"] B --> C["Run the golden set"] C --> D["Quality gate passed"] D -->|No| E["Block the release"] D -->|Yes| F["Canary to a small share of
traffic"] F --> G["Alarm fires"] G -->|Yes| H["Roll back to the last
approved version"] G -->|No| I["Move traffic to the full
share"] A --> J["Agent configuration change"] J --> K["Prepare the agent and move
the alias"]

Figure: each release passes the same gates, and a failed gate blocks it.

  • Prompt Management keeps saved versions and variants. An application deploys a chosen version.
  • Agent edits go to DRAFT. Create a version, then point an alias to it. Callers use the alias.
  • The SageMaker AI Model Registry gives each version an approval status. A rollback points to an earlier approved version.
  • AppConfig rolls out a change in steps. A CloudWatch alarm rolls the change back.
  • A canary starts at a small share, such as 10 percent. Traffic returns to the last approved version if an alarm fires.

Decision rule: Version the change, run the golden set, pass the quality gate, then canary. Roll back to the last approved version.

Trap: A prompt that changes in place has no safe rollback point. A re-sync is a change and needs the same gate. A console test on DRAFT does not prove the alias works.

Exam tip: Inference. A rollback needs a stored approved version. Choose the option that keeps one.

Figure: read the code first, then pick the fix.

  • Tokens per minute and tokens per day cap token use. Watch the InvocationThrottles metric in CloudWatch.
  • Call CountTokens before the call. Compare the count with the model limit.
  • Retry with exponential backoff and random jitter. Set a maximum number of attempts.
  • After the last attempt, fall back to a second model or a cached answer.
  • For sustained traffic, a quota increase or Provisioned Throughput fits a quota error.

Decision rule: Read the code first. Retry capacity errors with backoff and jitter. Fix input errors. Request more quota for quota errors.

Trap: A tight retry loop is never correct. Retries that add load make an overload worse. Retrying an input error never works. A 429 quota error and a 503 capacity error need different fixes.

Exam tip: Throttling after buying capacity points to the base model ID. Call the provisioned model ARN.

Source: repo guide, Part 5 Domain 4, task 4.1, Part 6 Domain 5, task 5.2, visual unit 12, Part 8A3, error code unit H1.

16. When a native service stores the data versus when a model service does

Read what each service stores and returns. Look-alike services differ in that one fact.

flowchart LR A["Stem names a data
need"] --> B["Durable store of

Figure: a store keeps data. A model service returns output.

  • DynamoDB gives single-digit millisecond lookup by a key, such as a customer or session ID. Native TTL removes old records.
  • The agent session expires. Its TTL is set in seconds, between 60 and 5400.
  • Neptune traverses explicit relationships for GraphRAG. It is a distractor for plain document search.
  • Bedrock hosts managed foundation models. SageMaker AI endpoints host a model that you own.
  • Converse does not produce embeddings. Use InvokeModel with an embedding model.
  • Guardrails block, mask, or filter content. They do not extract fields. Amazon Translate changes language and does not detect PII.

Decision rule: Use a store for data that must persist. Use a model service for generated, embedded, or extracted output.

Trap: Speed does not make a service durable. A guardrail does not validate data. Converse is not an embeddings API.

Exam tip: Look-alike names do not decide the service. The stored or returned output does.

AWS caveats

Each rule below comes from the repo guide. Rules marked Inference are reasoning from the guide.

  • Prefer the managed option that meets the stated constraint. Source: repo guide, Part 1 How AWS asks questions.
  • A cheaper option that breaks one constraint is wrong. Source: repo guide, Part 1, and visual unit 22.
  • A broader or more capable option is not a better answer by default. Inference: the guide says the flagship model is not the default answer, and bigger models do not fix broken retrieval.
  • Name only the constraints that the stem states. Do not add one. Inference: the guide says custom work is chosen only when a constraint forces it.
  • A guardrail does not validate data quality or extract fields. Source: repo guide, Part 2 Domain 1, task 1.3.
  • A cache does not reserve capacity. Prompt caching lowers the cost of a repeated prefix. Source: repo guide, Part 3 Domain 2, task 2.5.
  • A prompt does not enforce a control. A prompt that says stop is not a limit. Source: repo guide, Part 1B Lesson 8.
  • Grounding reduces hallucination. It does not remove it. Grounding is not safety. Source: repo guide, Part 4 Domain 3, task 3.1.
  • No control is absolute. Answers that claim full prevention are wrong. Source: repo guide, Part 4 Domain 3, task 3.1.
  • A cross-Region profile is not automatic failover. Add retries and fallback in the application. Source: visual unit 3.
  • Streaming does not extend a REST timeout and does not raise throughput. Source: visual unit 11, and repo guide, Part 5 Domain 4, task 4.2.
  • Provisioned Throughput does not speed up one call. It reserves capacity. Source: repo guide, Part 1B Lesson 2.
  • Reranking orders the chunks. It does not add a chunk that retrieval missed. Source: repo guide, Part 2 Domain 1, task 1.5.
  • A Region in the cloud does not keep data on your premises. Source: visual unit 19.
  • Converse is not an embeddings API. Source: visual unit 1.
  • Encryption does not change the network path. PrivateLink does not encrypt data at rest. Source: repo guide, Part 8D, unit G3.
  • The IAM layer still applies when application code changes or is skipped. Source: visual unit 18.
  • MCP is the tool connection standard. It is not a safety control. Source: repo guide, Part 2 Domain 1, task 1.5.
  • CloudTrail does not show row content. Invocation logs keep the original request. Source: visual unit 16.
  • Metrics alone cannot rebuild a wrong answer. Keep the payloads under access control. Source: visual unit 15.
  • Model Monitor does not score free-text answer quality. Use a judge or a golden set. Source: repo guide, Part 5 Domain 4, task 4.3.
  • An uncalibrated judge gives opinions, not measurements. Source: repo guide, Part 6 Domain 5, task 5.1.
  • A re-sync or a prompt edit is a release. It needs the same gate. Source: repo guide, Part 6 Domain 5, task 5.1.
  • A console test on DRAFT does not prove the alias works. Source: visual unit 8.
  • Detect mode is not a block. A blocked message needs the Block action. Source: repo guide, Part 4 Domain 3, task 3.1.
  • Batch does not fit a user waiting on a reply. Source: repo guide, Part 5 Domain 4, task 4.1.
  • A tight retry loop is never correct. Retries need jitter, a maximum attempt count, and a fallback. Source: visual unit 12.
  • A standard Lambda function runs at most 15 minutes. Source: repo guide, Part 3 Domain 2, task 2.2.
  • Bedrock Agents, Amazon Kendra, and Amazon Q Business are closed to new customers. Use the documented alternative. Source: repo guide, status notices in Parts 1C, 2, and 3.
  • Multiple response: count the answers the stem requires. Select all of them. Source: repo guide, Part 8 Method for each question.
