Amazon Bedrock model access

Converse API

Converse sends chat and tool use through one request format for supported models.

  • Methods or APIs: Converse for a full response. Converse needs permission for bedrock:InvokeModel. It runs on the bedrock-runtime endpoint. A request can carry inferenceConfig and additionalModelRequestFields.
  • Pro: One request shape for many models keeps app code stable when the model changes. Tool definitions and guardrail settings sit in the same request.
  • Con: Converse does not produce embeddings. A prompt from Prompt management cannot include additionalModelRequestFields in the request.
  • Choose it when: the app needs chat, tool use, or multimodal input on a supported model.
  • Do not choose it when: the call must return a vector. Use InvokeModel with an embedding model.
  • Native pairing: Lambda or API Gateway calls Converse. The response trace object shows guardrail results when a guardrail runs.

Decision rule: Use Converse for chat and tool use. Use InvokeModel for embeddings and provider-specific bodies.

Trap: Converse does not produce embeddings. Send an embedding call to InvokeModel.

Exam tip: A scenario that names chat or tool use across models points to Converse. A scenario that names vectors points to InvokeModel.

ConverseStream

ConverseStream sends tokens as they arrive, so the client reads a stream.

  • Methods or APIs: ConverseStream. The client must read the stream. The repo guide says it needs its own streaming permission. The permission name is Not in source.
  • Pro: The first visible token appears sooner. Users see progress on long replies.
  • Con: Total generation time does not change. A REST integration still stops at the 29-second default. The 29-second value is Not in source on the quotas page, so confirm it.
  • Choose it when: a person reads the reply as it generates, and the path to the browser holds a stream.
  • Do not choose it when: the caller cannot read a stream, or a batch job collects the output.
  • Native pairing: WebSocket APIs or server-sent events carry the stream to the browser. A standard Lambda function runs at most 15 minutes per invocation.

Decision rule: Stream when a person watches the reply. Use WebSocket APIs or server-sent events for long streams.

Trap: A stream does not extend a REST timeout. A higher Lambda timeout does not fix a gateway timeout either.

Exam tip: A stream shortens the wait for the first token. A scenario that names a total time limit needs a different path.

InvokeModel

InvokeModel sends the request body that one model provider expects.

  • Methods or APIs: InvokeModel. A Claude body needs anthropic_version and max_tokens. Embedding calls always use InvokeModel with an embedding model.
  • Pro: It reaches provider-specific fields. It is the named path for embeddings.
  • Con: The app builds each provider body. A Titan body sent to a Claude model fails.
  • Choose it when: the call makes an embedding, or a provider-specific field must go in the body.
  • Do not choose it when: a chat or tool call can run on Converse for the same model.
  • Native pairing: CloudTrail records InvokeModel calls for audit. Invocation logs record the request and the response. The repo guide names Titan Text Embeddings v2 and Cohere Embed as embedding models.

Decision rule: Use InvokeModel for vectors and provider-specific bodies.

Trap: With InvokeModel, tag user input for prompt attack checks. Untagged input is not checked for prompt attacks.

Exam tip: A body error after a model change points first to the body fields of that provider.

InvokeModelWithResponseStream

InvokeModelWithResponseStream sends tokens as they arrive from an InvokeModel call.

  • Methods or APIs: InvokeModelWithResponseStream. Invocation logging covers it. Prompt attack checks need tagged user input on it.
  • Pro: Tokens reach the client early. It suits provider bodies that must stream.
  • Con: The client must read the stream. Total generation time does not change. Stream parsing for each provider: Not in source.
  • Choose it when: the client reads tokens as they arrive, and the provider body needs streaming.
  • Do not choose it when: the app needs only the final result. Use InvokeModel.
  • Native pairing: WebSocket APIs or server-sent events carry the stream to the browser. Guardrail input tags apply on this call path.

Decision rule: Stream only when the client reads tokens. Otherwise call InvokeModel.

Trap: A stream does not get past a REST gateway limit. Use a path that holds the stream open.

Exam tip: A stream is a perceived speed fix. It is not a total time fix.

CountTokens

CountTokens estimates the token count for a supported model before a call.

  • Methods or APIs: CountTokens. The repo guide pairs it with Converse in its service tie-in. Request and response fields: Not in source.
  • Pro: It checks the input size against the context window before the call. It helps avoid overflow.
  • Con: It gives an estimate, and it works for supported models only. Exact field names: Not in source.
  • Choose it when: a long input may fill the context window or leave no room for the output.
  • Do not choose it when: the target model is not a supported model.
  • Native pairing: Design guidance. A Lambda step counts tokens, compares the count with the model limit, then calls Converse.

Decision rule: Count tokens before the call when the input is near the limit.

Trap: Context overflow drops the end of a long input. The output then looks cut off or ignores the last section.

Exam tip: A cut-off output points to the token limit. Check the count before you change the model.

On-demand inference

On-demand inference charges per token and has no commitment.

  • Methods or APIs: Calls to the base model ID use on-demand capacity.
  • Pro: No commitment. Spiky or unknown traffic fits. It is the first mode to use in a proof of concept.
  • Con: Quotas cap tokens per minute (TPM) and tokens per day (TPD). Throttled calls need retries. The throttle metric is InvocationThrottles.
  • Choose it when: traffic is spiky or unknown, or the approach is still under proof.
  • Do not choose it when: a steady, measured baseline must meet a latency target. Use Provisioned Throughput for that baseline.
  • Native pairing: Lambda calls the model ID. Step Functions holds long flows, and each Lambda step stays short.

Decision rule: Start on demand. Buy reserved capacity only after the baseline is measured.

Trap: Reserved capacity bought before a proof of concept is a poor pattern. Prove the approach on real data first.

Exam tip: Spiky or unknown load points to on-demand. A steady, measured baseline points to reserved capacity.

Source: repo guide, Part 1B Lesson 2, Part 1E visual unit 2, Part 2 section 1.1, Part 3 section 2.2, Part 5 section 4.1.

Provisioned Throughput

Provisioned Throughput reserves model units for a steady rate, and it bills hourly.

  • Methods or APIs: CreateProvisionedModelThroughput returns a provisionedModelArn. GetProvisionedModelThroughput shows the status until it reads InService. The provisioning mode is By Model Units. The purchase covers a base model or a custom model.
  • Commitment terms: none, 1 month, or 6 months. A commitment needs an AWS support request for model units first.
  • Model units: The count is set at purchase. Throughput per model unit: Not in source.
  • Pro: Reserved capacity suits a steady baseline. It does not speed up one call.
  • Con: A commitment does not fit spiky traffic. Batch inference does not support provisioned models. A capacity purchase does not change the speed of one call.
  • Choose it when: traffic is steady, measured, and has a latency target.
  • Do not choose it when: traffic is spiky, or the baseline is not yet measured.
  • Native pairing: The app must call the provisioned model ARN. Mixed traffic uses on-demand for spikes. SageMaker AI endpoints host models you own, which is a different host.

Purchase steps

  • Open the Bedrock console and choose Provisioned Throughput.
  • Choose Purchase Provisioned Throughput, then select the base or custom model.
  • Set the provisioning mode to By Model Units, then pick the commitment term.
  • Enter the model units, confirm the purchase, and wait for In service.

Provisioned model ARN

Calls must use the provisioned model ARN. A call to the base model ID still uses on-demand capacity. The repo guide flags this as a common cause of throttling after a purchase.

Decision rule: Reserve model units only for a measured baseline. Send baseline calls to the provisioned model ARN.

Trap: More model units do not help a call that still uses the base model ID.

Exam tip: Throttled calls after a capacity purchase point to the model ID in the call. Check that ID first.

Batch inference

Batch inference runs offline jobs with the input and output in S3.

  • Methods or APIs: The create model invocation job operation creates the job. The API route is Not in source. The console asks for a service role, an S3 input location, and an S3 output location. The job time limit is a timeout duration in hours.
  • S3 input: One or more JSONL files in S3. Each line is one record with a recordId and a modelInput. If recordId is missing, Bedrock adds one to the output.
  • Record format: modelInput matches the InvokeModel body by default. With type Converse, it matches the Converse request body.
  • S3 output: The results go to the S3 output location. Output order is not guaranteed to match input order.
  • Limits: Quotas apply to records per file, records per job, and file size. The numeric values: Not in source.
  • Pro: A lower price than on-demand for select models. Jobs run without a live client. The discount amount: Not in source.
  • Con: Batch does not support Provisioned Throughput models. Batch with Converse does not support tool calling. The cache does not apply to batch.
  • Choose it when: the work can wait for hours and the input sits in S3.
  • Do not choose it when: a user waits for a chat reply.
  • Native pairing: S3 holds the input and the output. For tool calls in batch, use the InvokeModel type.

Batch job steps

  • Choose a service role for batch inference, or create a custom role.
  • Create the job and choose the model.
  • Point the job at an S3 input location and an S3 output location.

Decision rule: Use batch for offline work with S3 input. Use on-demand for any reply a user waits for.

Trap: Batch output order can differ from input order. Join each result to its input on recordId, not on position.

Exam tip: A user who waits for a reply needs real-time calls. Batch is wrong for that case.

Cross-Region inference profiles

A cross-Region inference profile ID names a set of Regions. A request that uses it can run in any Region in that set.

  • Methods or APIs: Call the profile ID, such as one with a us. or eu. prefix. A geographic profile routes inside its geography, such as the US or the EU. A global profile routes to any supported commercial Region.
  • Pro: More throughput and availability within the same model family. Data stays on the AWS network and is encrypted in transit. The repo guide cites about 10 percent savings for global profiles.
  • Con: Requests can run in another Region in the profile. A global profile can route outside a strict EU boundary. The profile does not give automatic failover for your app. The quota Region for a routed request: Not in source.
  • Choose it when: the app needs more throughput or availability, and the residency rule allows the Regions in the profile.
  • Do not choose it when: a strict single-Region rule applies. Cross-Region guardrail inference also routes to another Region in the same geography, so check that rule too.
  • Native pairing: Retries and fallback in the application. CloudTrail logs the request in the source Region with additionalEventData.inferenceRegion.

Decision rule: A rule that names a geography needs a geographic profile. A rule that allows any commercial Region can use a global profile.

Trap: Cross-Region inference is not automatic failover. Add retries and fallback in the application.

Exam tip: An EU residency rule rules out a global profile. Pick the geographic EU profile.

Source: repo guide, Part 1E visual unit 3, Part 2 routing table, Part 4 section 3.2, Part 8A4 routing unit. Quota Region: Not in source.

Intelligent prompt routing

Intelligent prompt routing picks one of two models in one model family for each request, by predicted response quality and cost.

  • Methods or APIs: The call shape for the router: Not in source. The repo guide names it as a Bedrock feature.
  • Pro: Routes by predicted response quality and cost. Your code does not write the rule.
  • Con: The official docs describe it as optimized for English prompts only. It chooses between two models, not more.
  • Choose it when: the prompts are English, and both candidate models sit in one family.
  • Do not choose it when: the prompts are not English, or your own routing policy is required.
  • Native pairing: Lambda routing with AppConfig when you need your own rules and a model ID read at runtime.

Decision rule: Use intelligent routing for English prompts across two models in one family. Write your own routing rules for anything else.

Trap: A cross-Region profile does not choose a model by prompt complexity. Intelligent routing does that job within one model family.

Exam tip: Cost by predicted quality points to intelligent routing. Throughput and availability point to a profile.

Prompt caching

Prompt caching reuses an exact prompt prefix that sits before a cache checkpoint.

  • Methods or APIs: In Converse, add a cachePoint block. In InvokeModel for Claude, add cache_control. Claude allows up to four checkpoints per request. Checkpoints process in this order: tools, system, then messages. The response reports cacheReadInputTokens and cacheWriteInputTokens. The inputTokens field excludes cached tokens.
  • Minimum tokens: A checkpoint needs 512 to 4,096 tokens before it. The exact value varies by model.
  • TTL: The default time to live is 5 minutes. Each cache hit resets it. Some models accept a one-hour TTL set with "ttl": "1h". On a model that supports only five minutes, that ttl field causes a ValidationException.
  • Pro: A repeated long prefix costs less. Cached tokens bill at the cache-read rate.
  • Con: Cache writes cost extra, so the benefit needs repeat volume. The cache works for on-demand inference, not batch. It does not reserve throughput.
  • Choose it when: the same long prefix repeats within the TTL window on on-demand calls.
  • Do not choose it when: the prefix is short, changes on each call, or runs as batch.
  • Native pairing: Lambda builds the prompt with the static prefix first and the user message last. The console has a caching toggle. Its menu path: Not in source.

Cache checkpoint placement

Put instructions, tools, and documents first. Put the changing user message last. A value that changes inside the prefix forces a miss on each call.

Decision rule: Add a checkpoint only when the static prefix is above the minimum and repeats within the TTL.

Trap: A timestamp or user name at the top of the prompt changes the prefix on each call. The cache then misses on every call.

Exam tip: The cache lowers the cost of a repeated prefix. It does not raise throughput. Reserved capacity is Provisioned Throughput.

Source: repo guide, Part 1E visual unit 4, Part 5 section 4.1, Part 8A5 caching unit. Console menu path: Not in source.

Semantic cache

A semantic cache returns a stored answer when a new request is close in meaning to a stored request. The repo guide presents it as a pattern built on embeddings.

  • Methods or APIs: Embed each new request with an embedding model, such as one called through InvokeModel. Compare the vector with stored vectors. Return the stored answer on a hit. On a miss, call the model and store the pair. The store type: Not in source.
  • Pro: A hit returns the stored answer with no model call. It works when many requests repeat with different words.
  • Con: The threshold decides how close is close enough. Personal or unique requests rarely hit. The repo guide names no Bedrock semantic cache feature.
  • Choose it when: many requests repeat in different words.
  • Do not choose it when: requests are personal or unique, so hits stay rare.
  • Native pairing: Titan Text Embeddings v2 or Cohere Embed for the vectors. The repo guide notes Cohere uses an input type for queries and passages.

Decision rule: Set the cache threshold on a golden set before you use a semantic cache.

Trap: Prompt caching is not a semantic cache. Prompt caching reuses an exact prefix at the model. A semantic cache returns a stored answer before the model runs.

Exam tip: Many paraphrases of one request point to a semantic cache. A long repeated prompt prefix points to prompt caching.

Token economics

Cost = (input tokens / 1,000,000 × input price) + (output tokens / 1,000,000 × output price)

  • Illustrative prices: 3 USD per million input tokens and 15 USD per million output tokens. These are not current AWS prices.
  • Worked example: 4,000 input tokens cost 0.012 USD. 1,000 output tokens cost 0.015 USD. The total is 0.027 USD.
  • Output ratio: At these illustrative prices, one output token costs five times one input token.
  • Cached input: Total input equals inputTokens plus cacheReadInputTokens plus cacheWriteInputTokens. Cached reads bill at the cache-read rate. Cache write and read rates: Not in source.
  • Batch: A lower price than on-demand for select models. The discount: Not in source.
  • Provisioned Throughput: Billed hourly, with a commitment of none, 1 month, or 6 months.
  • Price table: Not in source for this build. Check the Bedrock pricing page for current prices.

Decision rule: Count input and output tokens separately. Cap output length first when replies run long.

Trap: More capacity does not fix a cost that comes from long prompts. Shorten the prefix or cache it.

Exam tip: Cost from a long repeated prompt points to caching. Cost from steady load points to reserved capacity.

Model invocation logging

Model invocation logging records requests and responses for Converse, ConverseStream, InvokeModel, and InvokeModelWithResponseStream.

  • Methods or APIs: Turn on invocation logging in the Bedrock settings. Choose an S3 destination with a bucket policy, a CloudWatch Logs log group, or both. The screen path for the toggle: Not in source.
  • Record shape: S3 delivery is gzipped JSON. Each entry records the identity ARN, request metadata, and token counts. Athena and S3 Select can query the S3 delivery.
  • Retention: Logs stay until you delete the logging configuration. A Bedrock retention period: Not in source.
  • Pro: The exact payload is available for audit and debugging. Token counts come with each call.
  • Con: Invocation logs are off by default. Logs can hold prompts, completions, and sensitive data. Logs keep the original request even when a guardrail masks the output.
  • Choose it when: an audit needs the words sent to the model and the words returned.
  • Do not choose it when: strict compliance rules bar stored content. Disable logging in that case.
  • Native pairing: KMS encrypts the log store. S3 Object Lock gives write-once retention. CloudTrail gives identity and timing. X-Ray finds the slow step. Logs Insights searches CloudWatch Logs delivery.

Setup steps

  • Choose an S3 destination, or choose a CloudWatch Logs log group.
  • Add a bucket policy to the log bucket, and replace the example values.
  • Turn on invocation logging in the Bedrock settings.

Decision rule: Use invocation logs for content. Use CloudTrail for who called and when.

Trap: CloudTrail does not show row content. Invocation logs keep the original request even when the output is masked.

Exam tip: Metrics alone cannot rebuild what the model received. A scenario that asks for the content points to invocation logs.

Custom models

Customization changes the model or its input. Each rung of the ladder changes more and costs more.

  • Methods or APIs: The repo guide places fine-tuning on SageMaker AI. A Bedrock documentation link covers fine-tuning and continued pre-training as reference only. Fine-tuning changes weights with labeled examples. Continued pre-training trains on unlabeled text to teach a domain. The API calls: Not in source.
  • LoRA: Freezes the base weights and trains small adapter matrices. The repo guide describes LoRA for SageMaker AI. A Bedrock LoRA path: Not in source.
  • Distillation: A smaller student model learns one task from a larger teacher. The Bedrock distillation API: Not in source.
  • Pro: Stable behavior at high volume. A distilled student is cheaper and faster for its task.
  • Con: Fine-tuning does not hold facts that change. Tuned models need approval before deployment.
  • Choose it when: prompts and RAG fail, and the behavior is stable at high volume.
  • Do not choose it when: the facts change. Use RAG for changing facts.
  • Native pairing: SageMaker AI fine-tunes and hosts the custom model. Each tuned version goes into Model Registry. Model Cards record intended use and evaluation results.

Decision rule: Try prompts, then RAG, then fine-tuning. Fine-tune only for stable behavior at high volume.

Trap: Fine-tuning on documents that change is wrong. Knowledge goes to retrieval. Behavior goes to weights.

Exam tip: A scenario with changing facts points to RAG, not to tuning.

Model choice on five axes

A model choice reads five axes: capability, cost per token, latency, context window, and Regional availability.

  • Methods or APIs: Not in source for an axis API. Each axis uses the limits and prices of each model. The price table: Not in source.
  • Axis detail: Capability covers reasoning, multilingual work, code, and vision. Cost has separate input and output prices. Latency covers time to first token and tokens per second. The context window holds instructions, history, retrieved text, and the request. Regional availability asks whether the model runs in your Region.
  • Pro: A fixed checklist makes the choice repeatable.
  • Con: The repo guide sets no weights for the five axes. Weights: Not in source.
  • Choose it when: a team compares candidate models for one workload.
  • Do not choose it when: the result is accepted without a test on your own data.
  • Native pairing: AppConfig holds the model ID, and Lambda reads it at runtime. A change to the ID rolls out with a deployment strategy.

Decision rule: Order of decision is latency needs, then reasoning difficulty, then cost. Test the final choice on your own data.

Trap: The flagship model is not the default. It can break a latency budget. A cheap model that is not offered in your Region is not a choice.

Exam tip: Check the Region before the price. A low price in the wrong Region fails the filter.

Model lifecycle and versions

A model registry groups the versions of a model and tracks the approval status of each version.

  • Methods or APIs: update_model_package sets ModelApprovalStatus to Approved or Rejected. In the Studio console, the approval control sits on the Deploy tab of the model version.
  • Rollback: A rollback points the endpoint to an earlier approved version. Keep that version in the registry.
  • Bedrock model version IDs and retirement dates: Not in source.
  • Pro: Each release has a version and an approval record. A rollback has a target.
  • Con: Registry approval adds a step before deployment. The registry covers SageMaker AI models. Its Bedrock counterpart: Not in source.
  • Choose it when: a custom model or an endpoint needs versions and rollback.
  • Do not choose it when: a prompt or model changes in place with no saved version. Version it first.
  • Native pairing: AppConfig rolls back a model ID change when an alarm fires. CloudTrail records InvokeModel and Converse calls for the audit trail.

Bedrock error codes and fixes

An error code shows who must act. A quota error needs a slower rate, a capacity error needs a retry, and an input error needs a code fix.

  • ThrottlingException, HTTP 429: The account exceeded a quota. Retry with exponential backoff and random jitter. Request a quota increase, or buy Provisioned Throughput for sustained traffic.
  • ServiceUnavailable, HTTP 503, and overloaded_error, HTTP 529: Capacity errors, not quota errors. Retry with backoff and jitter. Consider cross-Region inference.
  • ValidationError, HTTP 400: The input breaks a constraint. Fix the request. Do not retry.
  • AccessDeniedException, HTTP 403: IAM permissions are missing or expired. Fix the policy or the role.
  • ResourceNotFound, HTTP 404: The model ID or resource name is wrong. Fix the identifier.
  • Body error: A provider body sent to the wrong model fails. A Claude body needs anthropic_version and max_tokens.
  • Connection drops: NAT gateways, interface VPC endpoints, and Network Load Balancers drop idle TCP connections after 350 seconds. Enable TCP keep-alive in the SDK client. Set the OS keep-alive interval below 350 seconds. Both settings are needed.
  • Region-only AccessDeniedException: The troubleshooting table in the repo guide points to IAM resource ARNs for that Region. A later check found that the error page lists no Region-based cause. Confirm model availability in the Region and the ARNs.

AWS Lambda

Short compute steps. Standard functions run up to 15 minutes.

  • Methods or APIs: update-function-configuration, the --timeout CLI flag, and KMSKeyARN for a customer managed key on environment variables.
  • Pro: Holds short steps, such as format checks, custom chunking, and action group executors.
  • Pro: Reads the model ID from AppConfig at runtime. A model switch needs no code release.
  • Con: A standard function ends at 15 minutes. Waits in Lambda bill for the full duration.
  • Con: Anyone who can read the function configuration can read its environment variables.
  • Choose it when: each step is short and stateless, and it ends well inside 15 minutes.
  • Do not choose it when: a step waits for a person, or a flow runs past 15 minutes. Use Step Functions.
  • Native pairing: Lambda sits behind API Gateway. An action group in Bedrock Agents links the agent to a Lambda function. S3 events can invoke it.

Decision rule: Keep each Lambda step short. Move a long or waiting flow to Step Functions.

Trap: A Lambda function that waits for a person pays for the wait and hits the 15-minute limit.

Exam tip: When the wording says a step waits for approval, a Lambda function alone is the wrong pick.

Timeout path

The guide gives this console path for the timeout.

  • Open the Lambda console and choose the function.
  • Choose the Configuration tab, then General configuration.
  • Choose Edit. For Timeout, enter a value from 1 to 900 seconds.
  • Choose Save. The CLI flag is --timeout. The default is 3 seconds.

The maximum is 900 seconds. For longer work, use asynchronous jobs or Step Functions. Lambda Managed Instances functions invoked asynchronously allow up to 90 minutes. Do not assume that for a standard function.

Environment variables and secrets

  • Lambda stores environment variables encrypted at rest. Set a customer managed key with KMSKeyARN.
  • Keys start with a letter and have at least two characters. They use only letters, numbers, and the _ character.
  • The variables total 4 KB at most.
  • An update with update-function-configuration replaces the whole Variables structure. Include every existing value.
  • Keep non-secret settings, such as a bucket name or log level, in environment variables.
  • Read credentials from AWS Secrets Manager at run time. The guide recommends it for database credentials, API keys, and tokens.
  • Give the function an execution role. Keep long-term access keys out of environment variables.

Decision rule: Store secrets in Secrets Manager. Use environment variables only for settings that are not secret.

Trap: Encryption at rest does not make a value a secret. The guide still recommends Secrets Manager for credentials.

S3 event triggers and loop risk

  • Amazon S3 invokes the function asynchronously when an object is created or deleted.
  • Set the trigger in the bucket notification, or let the Lambda console add it.
  • The function resource-based policy must allow S3 to invoke it.
  • If the function uses the AWS SDK to manage S3, its execution role needs S3 permissions.
  • Write function output to a second bucket. Or limit the trigger to one prefix that holds incoming objects.

OpenSearch Serverless is managed vector search that combines filters and vectors.

  • Methods or APIs: Faiss engine, FP16 scalar quantization (SQfp16), and the collection types Time series, Search, and Vector search.
  • Pro: Combines metadata filters with vector search.
  • Pro: Knowledge Bases lists OpenSearch Serverless as a vector store. The guide names it for frequent, interactive search.

  • Con: More shards do not make search faster. Each shard uses CPU and memory.

Shards and sizing for OpenSearch Service

  • By default, OpenSearch Service creates five primary shards, and each has one replica. That is ten shards for each index.
  • You cannot easily change the primary shard count of an existing index. Decide it before indexing the first document.
  • Keep each shard between 10 and 30 GiB for search latency. Keep each shard between 30 and 50 GiB for write-heavy log analytics.
  • Estimate primary shards as (source data plus room to grow) times (1 plus indexing overhead), divided by the desired shard size.
  • Example from the guide: 66 GiB that does not grow, with 30 GiB shards, gives about three shards.
  • Keep no more than 25 shards for each GiB of Java heap on a node.

Decision rule: Size the index from current data and growth. Then check the shard count against node heap.

Trap: More shards do not make search faster. Many small shards can cause performance problems.

Vector quantization

  • A float32 dimension uses 4 bytes. Quantization stores fewer bits for each dimension.
  • FP16 scalar quantization (SQfp16) halves memory with the Faiss engine. It needs OpenSearch 2.13 or later. The source is an OpenSearch project page, not an AWS page.
  • Binary quantization stores 1 bit for each dimension. That is 32 times smaller than float32. The 16 and 8 times figures for 2-bit and 4-bit come from a secondary AWS blog.
  • Design arithmetic: one 1,536-dimension float32 vector is 6,144 bytes. Ten million vectors need about 60 GB.
  • Design arithmetic: ten million binary vectors need about 1.9 GB.
  • Rescore the top candidates with full-precision vectors or a reranker.

Decision rule: Use binary quantization for a first pass over a large index. Rescore for final ranking.

Trap: Binary quantization without rescoring can lose accuracy. Measure the loss on your data. A general loss figure is Not in source.

Exam tip: When the wording asks to cut vector memory, look for quantization.

Glossary

Source: repo guide, Part 8C Glossary

Short definitions for the terms that the exam uses.

Token

A piece of text the model reads or writes.

Context window

The fixed limit of tokens in one call.

Embedding

A list of numbers that represents the meaning of text.

RAG (retrieval-augmented generation)

Retrieve source text first, then send it with the question to the model.

Chunking

Splitting documents into pieces before embedding.

Knowledge Base

Bedrock managed RAG that syncs a data source, chunks and embeds it, retrieves, and can return citations.

Hybrid search

Combines keyword matching and vector similarity in one query.

Reranker

A model that scores retrieved candidates for relevance before generation.

Temperature

A sampling setting where lower values make the next-token choice more deterministic.

Top K

The number of most likely candidate tokens the model considers for the next token.

Top P

The share of the cumulative probability distribution the model considers for the next token.

Max tokens

The maximum number of tokens the model returns.

Prompt caching

Reuses an exact prefix marked with a cache checkpoint.

Batch inference

Offline jobs with input and output in S3.

Provisioned Throughput

A purchase of model units for a steady throughput.

Cross-Region inference profile

A profile that routes requests across Regions in one geography for throughput and availability.

Intelligent prompt routing

Routes each request between two models in one family, by predicted response quality and cost.

Guardrail

A Bedrock control with six policy types that checks input and output.

DRAFT, version, alias

DRAFT is the editable agent state, a version is a frozen copy, and an alias points callers to a version.

MCP (Model Context Protocol)

A standard for agents to find and call tools.

Cedar

The policy language that Amazon Verified Permissions uses to decide if a request is allowed.

Cognito user pool

Authenticates users and issues JSON web tokens (JWTs).

Cognito identity pool

Exchanges a trusted token for temporary AWS credentials.

CloudFormation stack

A set of resources created and deleted together from one template file.

Textract

A document service that detects and extracts text, forms, and tables.

LLM-as-a-judge

A model scores another model's output against criteria.
