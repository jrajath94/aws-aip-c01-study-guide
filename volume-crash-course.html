D1: Foundation Models, Data & Compliance (31%)

This is the biggest domain. It sets the vocabulary for all later domains. D1 tests three things. It tests which GenAI approach fits the scenario. It tests how to call and feed Bedrock models correctly. It tests how to keep data compliant while you do this.

Almost every question uses the approach ladder plus one API or service detail.

The approach ladder: Climb only when the cheaper step does not work.

How to read this. Read bottom to top: prompt engineering, RAG, agents, fine-tuning. Each rung lists what it solves: formatting at the bottom, private facts one rung up, doing things with agents, stable behavior at the top. Takeaway: the exam rewards the cheapest rung that works, never the fanciest.

A foundation model is a large model. It is pre-trained on much data. You adapt it instead of training it from the start. Amazon Bedrock is the managed AWS service. It provides foundation models from many providers. These providers include Anthropic Claude, Meta Llama, Mistral, Cohere, Amazon Titan and Nova, AI21, and Stability.

It uses one set of APIs. So, you never manage GPUs. The ladder shows the order you try solutions. Start with the cheapest solution first.

Prompt engineering is the bottom step. You change instructions and examples in the prompt. This does not add new knowledge. It does not need training. It does not add new cost. It solves formatting, tone, extraction structure, and simple classification.

RAG (Retrieval-Augmented Generation) is the next step. The model finds facts from your documents when it gives an answer. It cites these facts. It solves private, changing, or cited knowledge. The model was never trained on this knowledge. Agents are next.

The model takes actions through tools. It calls APIs, queries databases, and runs multi-step plans. This step solves anything that needs action, not just an answer. Fine-tuning is the top step. You retrain parts of the model. You use labeled examples.

A new behavior becomes part of the model's weights. It solves stable behavior, tone, and format needs. Prompts cannot reliably keep these.

Rule: Start at the bottom. Climb only when the cheaper step cannot meet a stated need. "Documents change" makes fine-tuning useless. (Weights become old.) "Must cite sources" makes fine-tuning useless. (Weights cannot cite pages.) "Takes actions" makes RAG useless. (Knowledge bases do not call APIs.) "New tone" makes RAG useless.

(Retrieval does not change behavior.) Read the need. Find which step it names. Pick the cheapest step that meets all needs.

Picking the model: filter, then rank

How to read this. First box: filter by region, modality, latency SLA, and compliance. Arrow into the second box: rank only the survivors on golden-dataset quality and cost per call. Takeaway: filter before you rank; never compare models that can never qualify.

Model selection is a filtering process. It is not a popularity contest. First, filter by capability floor. Run candidate models on a golden dataset. (This is a small set of prompts with good answers.) Remove any model below your quality level. Provider benchmarks never meet this level for you.

They measure the provider's prompts, not yours. Second, filter by regional availability. Bedrock publishes a list of supported models per region. A model in us-east-1 may not exist in eu-west-1. Model access is a one-time console action. Do this for each model and each region.

It costs nothing to enable. Third, rank the remaining models by cost and latency. Measure tokens per request. Measure time to first token on realistic inputs. Fourth, check the context window. (This is the maximum tokens a model accepts in one call.

It is specific to the model. Large models handle hundreds of thousands. Small models handle tens of thousands.) Check it against your longest realistic input plus the expected output. If the input does not fit, you need chunking, summarization, or a bigger window. The model with the lowest cost that meets all criteria wins. Check again every three months.

Prices and capabilities change.

There are two availability tools. Never swap them. Cross-region inference profiles send requests across regions for resilience. If one region throttles or goes down, traffic moves to another. They are the answer to "model X is only in two regions and we need resilience." They do not work with data-residency rules. This is because routing across regions moves data across regions.

Prompt routers (also called model routers) send requests by predicted prompt complexity for cost. Simple queries go to a cheap, small model. Hard queries go to the main model. They are the answer to "80% of our traffic is simple FAQ on an expensive model." Use a router for cost. Use a profile for availability. The exam tests this pair directly and often.

  1. Left: inference profiles. They move traffic between regions for availability.
  2. Middle: prompt routers. They send simple prompts to cheap models for cost.

Calling the model: four APIs, one decision

Converse is the unified Bedrock runtime API. It has one request shape. It includes modelId, messages (user and assistant roles), system, inferenceConfig (maxTokens, temperature, topP, stopSequences), optional toolConfig (function definitions), optional guardrailConfig (attaches a Bedrock Guardrail, the content filters and policy checks taught fully in D3, by guardrail identifier plus version, with a trace flag), optional cachePoint (prompt caching marker), and additionalModelRequestFields (the escape hatch for provider-specific extras). It works across providers. It is the default for text generation, tool use, and inline guardrails.

InvokeModel is the original API. You send the provider's raw JSON body. You get the provider's raw response. For Claude, you must include anthropic_version: "bedrock-2023-05-31" and max_tokens. If you do not, the call fails with a validation error. InvokeModel is the ONLY way for embeddings.

This is because Converse is only for text generation. The exam offers Converse as a wrong answer for embedding tasks. It is always wrong.

Reading a Converse response: output.message.content is a list of content blocks. The stopReason field tells you why generation ended. end_turn means the run finished. max_tokens means the output was cut during generation. It did not finish. A good-looking answer with this stop reason is cut short. Increase maxTokens or make the input shorter. guardrail_intervened means the guardrail blocked the call.

How to read this diagram

  1. Top row: end_turn. The run finished. Trust the answer.
  2. Middle row: max_tokens. The output was cut. Raise maxTokens or shorten the input.
  3. Bottom row: guardrail_intervened. The guardrail blocked the call. Check which policy fired.

Latency and cost have their own call shapes. Streaming (ConverseStream, InvokeModelWithResponseStream) returns tokens as the model generates them. It changes how fast it feels, not the total time. A chat that starts answering in less than one second feels fast. This is true even if the full answer takes ten seconds. Streaming is the answer to "users report slow responses" on interactive traffic.

Batch inference is the offline shape. It uses a JSONL file (one JSON object per line) into S3. Results go out to S3. It has hours of latency. It is about 50 percent cheaper per token than on-demand. It is the answer to "cheapest for nightly bulk work with no SLA." Never use it for interactive SLAs.

Async invocation (start_async_invoke) is for a single slow request. One prompt that no one waits for. The result goes to S3. Batch is many prompts from S3. Async is one slow prompt. Streaming sends tokens to a waiting user.

Prompt caching needs one condition. It needs a repeated long prefix. This is usually a long system prompt or document block. Many calls share it. Mark the boundary with cachePoint. Cache hits bill at a lower input-token rate.

The minimum prefix length depends on the model. It is about one thousand tokens. The cache TTL is 5 minutes by default. It can be up to 1 hour on supported models. Unique traffic makes caching useless. No repeated prefix means no savings.

The metric that shows caching works is cache read hit rate. It is not total token spend.

How to read this diagram

  1. Left: the precondition. A long prefix repeats across calls.
  2. Middle: the mark. cachePoint tells Bedrock what to cache.
  3. Right: the proof. Watch cache read hit rate, not total spend.

RAG in depth: This is the most tested pattern in the domain.

RAG uses your documents to ground the model. At ingestion, the system chunks documents into small pieces. Each piece fits the context window. Each piece keeps a tight focus to match precisely. The system converts each chunk to an embedding.

An embedding is a vector of numbers. Similar meanings are close together in this vector. Vectors, text, and metadata go into a vector store. At query time, the system embeds the question with the same model. The store returns the nearest chunks. The model makes an answer and cites the chunks.

An Amazon Bedrock Knowledge Base is the managed version. Point it at data sources. Data sources include S3, web crawlers, Confluence, and SharePoint. Data sources also include Salesforce. It handles chunking, embedding, storage, and sync. RetrieveAndGenerate does the full loop in one call.

Embeddings have two choices for the exam. Amazon Titan Text Embeddings v2 is the low-cost default. It has configurable dimensions: 1024, 512, or 256. Changing from 1024 to 256 reduces vector storage by 75 percent. It also makes search faster. This change has an accuracy trade-off.

You measure this trade-off on a golden dataset. Cohere Embed is the multilingual choice. It supports more than 100 languages. It takes an input_type parameter. This parameter is search_query or search_document. It embeds queries and documents with different prefixes.

These prefixes are good for each role. Embedding calls use InvokeModel. They do not use Converse.

The rule for retrieval is important. Use the same embedding model and dimensions at ingestion and query time. If you do not, retrieval breaks silently. This is because the vector spaces do not align. If answers are confident but wrong after a re-sync, the re-sync changed the embedding model version. Or the re-sync changed the chunking configuration.

Find the change and fix it.

Vector store choice depends on data size. Small datasets, under about 1 million records, use Aurora Serverless with pgvector. This has the fewest self-managed components. It is the answer for "least operational overhead." Large datasets use OpenSearch Serverless. It uses approximate search. This includes HNSW or IVFFlat indexes.

How to read this diagram

  1. Left: Titan Text Embeddings v2. Pick the dimension count for your cost and quality target.
  2. Right: Cohere Embed. Use it for multilingual text.
  3. Bottom rule: the query must use the same model and dimensions as ingest.

These are approximate index types. They trade a small loss in recall for large speedups. "100% recall required on small data" means exact flat search. Approximate indexes trade recall for speed by design. Small data makes the exact scan affordable. Do not embed relational tables into a vector store.

Structured data with SQL-shaped questions uses text-to-SQL against RDS or Aurora. It does not use chunks. Unstructured documents, like PDF, HTML, and Word, belong in the knowledge base.

The exam names two quality upgrades. Hybrid search combines keyword matching with vector similarity. BM25 is the classic keyword-ranking formula. Exact terms and meaning both count. A reranker re-scores the top retrieved chunks. Cohere Rerank on Bedrock is an example.

It uses a stronger model and keeps the best chunks. Together, they answer "retrieval quality is too low and we did the basics." The checklist for silent retrieval problems has three items. First, embedding model mismatch between ingest and query. Second, chunk boundaries that split key facts across chunks. Third, a knowledge base sync that is not in-sync.

Custom models: behavior, not knowledge

How to read this. Two columns answer one question. Left: need new knowledge (facts the model never trained on) so the answer is RAG. Right: need new behavior (tone or format prompts cannot hold) so the answer is fine-tuning. Takeaway: never fine-tune to teach facts.

Bedrock offers four ways to adapt a model. The exam tests which gap each one fills. Fine-tuning is supervised. It trains on labeled prompt-and-response pairs in S3. It teaches behavior. This includes support tone, classification, and response format.

Useful runs start with hundreds to a few thousand high-quality labeled examples. Quality is more important than quantity. Continued pre-training trains further on unlabeled domain text. It teaches vocabulary and domain knowledge. Distillation trains a small, low-cost student model. It imitates a large teacher model on one narrow task.

It gives near-teacher quality at student cost. This is the answer to "same narrow task millions of times, cost is the problem." Imported models bring weights you customized elsewhere into Bedrock. They serve through Bedrock APIs. On the SageMaker side, the same idea appears as LoRA. LoRA means Low-Rank Adaptation. Train only small weight deltas, called adapters.

Do not train all weights. Then version them in the SageMaker Model Registry with pipelines and rollback.

A fine-tuning job reads training and validation files from S3. It runs for hours. It makes a custom model with its own ARN. ARN means Amazon Resource Name. It is the unique ID of any AWS resource. Serving it usually needs Provisioned Throughput.

This is reserved inference capacity. The next section explains it. An exception is some models, like Nova custom models. They support on-demand. "The customization job succeeded but calls fail" means the custom model has no throughput provisioned. It does not mean bad training data.

The main trap: fine-tuning for knowledge instead of behavior. For quarterly document updates, citations, and fresh facts, use RAG. For tone, format, and stable behavior, use fine-tuning. The exam will make a knowledge problem look like a behavior problem. Read the requirement, not the appearance.

Capacity and cost levers: PT, profiles, routers

How to read this. Three boxes, three different jobs. Left: PT reserves hourly capacity for steady traffic. Middle: profiles route across regions for availability. Right: routers cascade simple prompts to cheap models for cost. Takeaway: match the lever to the symptom, they are not interchangeable.

Provisioned Throughput (PT) is reserved inference capacity. You buy model units. A model unit is a fixed amount of processing capacity for one model. You buy it for a commitment term. This is commonly 1 month or 6 months. You pay an hourly rate per unit.

You pay whether you use it or not. In return, requests to your provisioned model ARN get dedicated capacity. This means consistent latency. It also means no throttling from shared on-demand quotas. Create it with CreateProvisionedModelThroughput. Invocations must target the returned provisioned model ARN.

They must not target the base model ID. "Bought PT but still throttles" means the code passes the base model ID. It does not pass the provisioned ARN.

PT guarantees latency and capacity for steady production baselines. It is not a discount for spiky traffic. Idle hours still bill. So, bursty workloads stay on on-demand.

There are three confusing items. The exam tests them often. Inference profiles route for availability across regions. Prompt routers route for cost by prompt complexity. Provisioned Throughput reserves capacity by the hour. Regional failover needs a profile.

Simple queries on an expensive flagship model need a router. Throttling at peak on steady traffic needs PT. The exam also tests the cascade pattern for routers. A small classifier sends simple requests to a low-cost, lightweight model. Simple requests include classification, extraction, and short answers. It sends only complex requests to the flagship model.

Right-sizing means choosing the smallest model that meets the quality standard. This is the same idea stated in another way.

Data protection and compliance

How to read this. Three guarantees side by side. Left: your data never trains models. Middle: encryption at rest and in transit. Right: data stays in your account and region. Takeaway: the privacy answer is almost always already in one of these three boxes.

Bedrock traffic stays private. It uses VPC interface endpoints. This is PrivateLink. It is for the Bedrock, Bedrock runtime, agent, and agent-runtime APIs. There is no NAT gateway. There is no public internet.

IAM policies define which identities can invoke which model. They also define which knowledge base and agent ARNs. KMS encrypts data at rest. This is envelope encryption with customer-managed keys. TLS encrypts data in transit. Customer data sent to Bedrock is not used to train models.

This is under the service terms. Data you choose to log stays in your account.

The PII pipeline has three services in order. Amazon Macie finds PII at scale in S3. It scans buckets and flags sensitive data before ingestion. Amazon Comprehend detects PII entities in live text in real time. It finds more than 30 entity types. These include names, SSNs, and account numbers.

Bedrock Guardrails sensitive-information filters block or mask PII. This happens at the model boundary. It happens on inputs and outputs. Macie finds it at rest. Comprehend detects it in flight. Guardrails filter it at inference.

How to read this diagram

  1. Left box: Macie. It finds PII stored in S3 buckets.
  2. Middle box: Comprehend. It detects PII entities in text you send it.
  3. Right box: Guardrails. They filter PII at the model boundary.

In scenarios with high compliance, consider if model invocation logging should exist. This is the opt-in record of full prompt and response text. You can route it to S3 or CloudWatch. You can encrypt it with KMS. Logs can contain PII. So, retention policies and redaction are part of the design.

D1 decision rules: if the stem says X, pick Y

  • If the stem says "Facts change over time" or "must cite sources," pick RAG with Knowledge Bases. Never use fine-tuning.
  • If the stem says "New tone, format, style, behavior," pick fine-tuning or prompt engineering. Never use RAG.
  • If the stem says "Take actions," "call APIs," or "multi-step with tools," pick Bedrock Agents. Knowledge bases do not act.
  • If the stem says "Unstructured docs (PDF, HTML)," pick Knowledge Bases. If it says "Relational data, SQL questions," pick text-to-SQL on RDS. Never embed tables into a vector store.
  • If the stem says "Small vector dataset" (under about 1 million records), pick Aurora Serverless with pgvector. If it says "Large," pick OpenSearch Serverless. If it says "100% recall on small data," pick exact flat search.
  • If the stem says "Throttled at peak, steady traffic," pick Provisioned Throughput. Pass the provisioned ARN as modelId. If it says "Spiky or low traffic," pick on-demand.
  • Use cross-region inference profiles for regional failover and resilience. This is not possible with data-residency constraints.
  • Use a prompt router or cascade for simple queries on an expensive model. Never use Provisioned Throughput for a cost problem.
  • Use prompt caching for a repeated long system prompt. Check the cachePoint and the cache read hit rate. Use streaming or a smaller model for unique interactions.
  • If users report slow responses, use streaming (ConverseStream) for perceived latency. Provisioned Throughput fixes capacity. It does not fix first-token speed.
  • Use batch inference for nightly bulk work with no SLA. Put JSONL into S3. Put results into S3. This saves about 50% of the cost.
  • To swap models without redeploying, use a model ID in AppConfig. AppConfig is AWS's runtime configuration service. Read the model ID at runtime. CloudFormation changes are deployments.
  • Use InvokeModel for embeddings. Never use Converse. Use the same model and dimensions at ingest and query.
  • If answers are confident but wrong after a re-sync, check the embedding model version. Check for chunking drift. Debug the change.
  • Use Macie for PII across S3 buckets. Use Comprehend for PII in live text. Use Guardrails to redact at call time.
  • Use VPC interface endpoints for no public internet. A NAT gateway does not meet this constraint.

Retrieval quality: fix in this order

Bad RAG answers have a fix order. The exam asks what to change first. Memorize the ladder.

  1. Chunking strategy. Fixed, hierarchical, or semantic. About 300 tokens per chunk with overlap is the typical shape.
  2. Embedding model. A better model or better dimensions for the content type.
  3. Retrieval tuning. Top-k size, hybrid search, reranking. Too few chunks starve the answer. Too many add noise.
  4. Prompt and generation. Only after retrieval is solid.

How to read this diagram

  1. Top lever: chunking. Wrong cuts poison everything downstream.
  2. Second lever: the embedding model. It decides what "similar" means.
  3. Third lever: retrieval tuning. Top-k and reranking shape the candidate pool.
  4. Bottom lever: the prompt. It cannot fix bad chunks.

Bedrock Knowledge Bases give two query APIs. RetrieveAndGenerate is one managed call. Bedrock retrieves, builds the prompt, generates, and returns the answer with citations. Retrieve returns only the chunks. You build the prompt yourself.

The RAG pipeline has three stages

Retrieval is not one step. It has three stages. The exam asks which stage a fix belongs to. Learn the stages and the levers inside each one.

  1. Pre-retrieval. Indexing choices, chunking granularity, and data extraction. Query manipulation lives here too. Rewrite the query so it retrieves better.
  2. Retrieval. The actual search against the vector store. Vector search, keyword search, or hybrid.
  3. Post-retrieval. Re-rank the results. Filter the results. Augment the results before generation.

How to read this diagram

  1. Left box: pre-retrieval. Chunking, indexing, extraction, query rewriting.
  2. Middle box: retrieval. Vector, keyword, or hybrid search.
  3. Right box: post-retrieval. Re-ranking, filtering, augmentation.

Exam relevance. "Re-rank the retrieved chunks" is a post-retrieval fix. "Rewrite the user query" is a pre-retrieval fix. The exam separates them on purpose.

Failure modes per stage. Pre-retrieval fails silently: bad chunking poisons every later stage and no amount of reranking recovers it. Retrieval fails loudly: empty results or wrong-language chunks point at the index or the query. Post-retrieval fails subtly: an over-aggressive filter drops the one chunk that held the answer, and the model hallucinates on the survivors. When answers go wrong, debug in stage order. Never tune the prompt before the stages are clean.

Metadata: the second retrieval axis

Add a metadata.json file to your vector store. It carries facts about each chunk that are not in the text: document ID, category, access control, data lineage, creation date, source citation.

Metadata is not chunked like text. It rides alongside the vectors. Use it for hybrid retrieval: filter on metadata first, then run vector search on the survivors. A year filter can drop 90 percent of the corpus before the expensive search starts.

Exam relevance. "Filter documents by year before vector search" is a metadata play. "Relevance scoring against metadata" is the hybrid approach. The exam contrasts metadata filtering with pure vector similarity.

Embeddings: dimensions, density, freshness

Dimension tradeoff. Smaller vectors cost less to store and search. Smaller vectors retrieve worse. Amazon Titan defaults to 1024 or more dimensions. Ask whether your domain needs that many. Fewer dimensions can be enough for narrow corpora.

Sparse versus dense. Sparse vectors are long and mostly empty, like one-hot encodings. They compute similarity fast and suit recommender systems. Dense vectors are short and packed with meaning. They use less memory and suit semantic search.

Keep the KB fresh. Data source changes should trigger a sync. A Lambda can fire on the change event. If the source changes constantly, batch the syncs instead of syncing every change. Use EventBridge to schedule the sync or AWS Batch to run it. Syncing every single change wastes money and compute.

Exam relevance. "Reduce vector storage cost" points at smaller dimensions or quantization. "Source changes often" points at scheduled batch syncs, not per-change syncs.

Evaluating RAG: three relevances plus the job list

RAG evaluation is not exact science. Three concepts still show up on the exam.

  1. Context relevance. Is the retrieved context relevant to the original query?
  2. Groundedness. Is the generated response grounded in the retrieved context? If not, it is a hallucination.
  3. Answer relevance. Does the generated response answer the original query?

Bedrock runs RAG evaluation jobs. They score ten dimensions. Five measure quality: Correctness, Completeness, Helpfulness, Logical coherence, and Faithfulness. Faithfulness means the response aligns with the retrieved text. Four measure safety: Citation precision and coverage, Harmfulness, Stereotyping and Biases, and Refusal. Refusal means whether the model dodges the question.

Ground truth kills subjectivity. Provide an evaluation dataset in JSON. It states what you consider a good response. It is also called a prompt dataset. It holds prompts with instructions on how to judge. LLM-as-a-judge takes your system input and output, applies the prompt dataset with benchmarks and judging instructions, and returns scores. Different FMs can serve as the judges.

Exam relevance. "Context relevance versus groundedness versus answer relevance" is a vocabulary question. "Provide a ground truth dataset" is the answer to "how do you make RAG evaluation less subjective."

Rerankers: similarity is not relevance

Vector search is cheap and fast. But a chunk can be similar to the query without being relevant. The classic example uses an ice cream query about Tom. The top vector hit talks about Bob and vanilla. The sentence shape matches, so similarity ranks it first. A lower chunk holds the real answer about Tom. Similarity ranked the shape. Relevance needed the reranker.

The pattern. Vector search retrieves the top-k candidates fast. A reranker scores each candidate for true relevance to the query. Reranking is heavier than vector search, so it only runs on the top-k, never on the whole corpus.

In Bedrock. Use the Rerank API operation. Or set a reranker model on the Knowledge Base so reranking applies automatically. Bedrock offers rerankers from Amazon and from Cohere.

How to read this diagram

  1. Left: similarity ranking. "Bob's vanilla" wins on sentence shape.
  2. Right: after the Rerank API. "Tom's chocolate" wins on relevance.
  3. The arrow names the operation. It runs on the top-k, never the corpus.

Trap: "rerank the whole corpus." Wrong. Rerankers are expensive per candidate. The exam offers "run the reranker over all vectors" as a distractor. The correct shape is vector search for top-k, then rerank the k.

Under the hood. A reranker reads the query and the chunk together through a cross-encoder. Vector search never does this. It compares two precomputed vectors. That is why similarity is cheap and relevance costs more. The exam twist: a reranker cannot fix a bad candidate pool. If the top-k holds no relevant chunk, the reranker promotes the least wrong one.

Exam relevance. "Most similar is not most relevant" always means add a reranker. "Only on the top results" is the cost guardrail the exam checks.

Vector stores: OpenSearch, S3 Vectors, and the rest

Amazon OpenSearch Service. A managed search and analytics engine built on Apache Lucene. Two modes. Managed clusters: you size the nodes, scaling is manual but online. Serverless: on-demand autoscaling, capacity in OpenSearch Compute Units, collections instead of domains.

OpenSearch as a vector store. Serverless is the default backing for Bedrock Knowledge Bases. Deleting the KB does not delete the serverless collection. Delete both or you keep paying. Vector search engines: FAISS, NMSLib, Apache Lucene. The default algorithm is HNSW, an approximate kNN that is fast and high quality but memory hungry. Use larger shards for semantic search (30 to 50 GB) and smaller ones for hybrid (10 to 30 GB). The neural plugin lets OpenSearch call your Bedrock embedding model during ingest or search.

S3 Vectors. Store embeddings directly in S3 vector buckets. It is simpler and far cheaper than OpenSearch (up to 90 percent less) but slower: sub-second latency versus sub-millisecond. Operations are put_vectors and query_vectors. Data is strongly consistent. A bucket holds up to 10,000 indices with 2 billion vectors per index. Bedrock Knowledge Bases can use S3 Vectors as the store.

Multimodal models and pipelines

Multimodal models need a specialized encoder per media type: text, image, audio, video, documents. Each encoder turns its media into vectors that live in one shared space. Multimodal embedding models convert different media into compatible vectors, so one query can search across media by vector similarity.

Titan Multimodal Embeddings G1. The request body is JSON. It carries inputText and inputImage as a base64-encoded string. An optional embeddingConfig sets outputEmbeddingLength to 256, 384, or 1024. The default is 1024.

The pipeline does the encoding. Raw media is not model-ready. A data pipeline encodes it first: base64 for images, transcripts for audio, extracted text for documents. Build the pipeline with Glue, SageMaker, or Bedrock Data Automation. The model expects prepared data. Your app owns the preparation.

Under the hood. Each media type gets its own encoder. The encoders train to place matching text and images near each other in one shared space. That shared space is what makes "find photos with a sentence" work. The exam twist: multimodal search still needs the right chunking and metadata on the text side. Vectors do not replace the pipeline.

Exam relevance. "Image data must be base64-encoded in JSON" is the Titan multimodal input shape. "Search images with a text query" is the multimodal embedding use case.

Data into the model: shape it first

Bedrock FMs and SageMaker LLMs almost always expect JSON-structured input. Non-LLM SageMaker models may want CSV or Protobuf instead. It is your responsibility to send the right shape. Your app or endpoint owns this.

Unstructured text loses structure. OCR or PDF ingestion drops headings, tables, and metadata into a sea of text. Fixes: format the source as HTML (models read HTML well, and tables survive), or extract structure with Amazon Comprehend or Amazon Textract. Automate the formatting in a Glue ETL pipeline or with Bedrock Data Automation.

Divider strings control chunking. A divider string is a unique delimiter you insert between logical sections during preprocessing. A Lambda preprocessor can convert HTML headings into markers like <SECTION_BREAK:Title>. The chunker splits on the marker first, then applies size limits inside each section. Sections stay whole. Tables stop splitting mid-row. This is application code, not an AWS feature.

Converse API message shape. The Converse API takes JSON with a role (user or assistant) and content (the messages). Every call carries this structure no matter which model sits behind it.

Exam relevance. "Tables break during chunking" points at divider strings or HTML formatting. "Who formats the input" is always your application, never Bedrock.

Fighting FM bias: three fixes, three moments

Bias comes from training data. Groups with few examples in the data get poor or unfair results. An image model trained mostly on one group draws that group for every prompt.

Three fixes, each at a different moment.

  1. Disambiguation in the prompt. Name the group in the prompt. "Draw a doctor" becomes "Draw a female doctor of South Asian descent." This is the fastest fix. It needs no retraining.
  2. Fix the training data. Add the missing examples before training. Balance the classes. This is the deepest fix. It costs a retrain.
  3. Counterfactual data augmentation. Edit examples after the fact. Swap an attribute (name, gender, age) and keep the label. The model learns the label does not depend on the attribute.

Exam relevance. "The model favors one group" points at the data, not the prompt template. Guardrails filter biased outputs at the door. These three fixes stop the bias at the source: prompt, data, or augmented data.

Structured output: prompt or tool use

Sometimes the system must answer in an exact response format, like a fixed JSON schema. Two ways to enforce it.

  1. Enforce it in the prompt. State the format clearly and simply. Number the steps that build the output. Show one example. This needs some trust that the FM follows instructions.
  2. Enforce it with tool use. Define the schema as a tool in the Converse API toolConfig. The model fills the tool inputs, which must match the schema. Modern FMs handle this well.

Exam relevance. "Must return exact JSON" with no tools mentioned points at prompt enforcement with numbered steps and an example. "Tool definitions available" points at toolConfig schemas.

Titan. Amazon Titan covers text, image generation, and embeddings. Titan Text Embeddings is the workhorse for RAG vectors. Titan Multimodal Embeddings G1 handles text plus image in one vector.

Nova. Nova is the newer Amazon family. It spans fast cheap models (Nova Micro and Nova Lite class) to flagships (Nova Pro class) for complex reasoning. Nova also has multimodal variants. More D1 decision rules

These rules extend the D1 decision list above. Same format. Same exam.

  • If the stem says "same narrow task millions of times" and "cost is the problem," pick distillation. Never pick continued pre-training.
  • If the stem says "domain vocabulary" or "unlabeled text," pick continued pre-training. Never pick fine-tuning.
  • If the stem says "preference data" or "reward signals," pick reinforcement fine-tuning.
  • If the stem says "weights trained outside Bedrock," pick an imported model.
  • If the stem says "many tasks, one base model," pick LoRA adapters. Version them in the Model Registry.
  • If the stem says "multilingual content," pick Cohere Embed. Never pick Titan for 100+ languages.
  • If the stem says "custom reranking" or "custom citation format," pick Retrieve, then build the prompt with Converse. RetrieveAndGenerate cannot do custom reranking.
  • If the stem says "graph relationships between entities," pick Neptune for GraphRAG. Never use Neptune as a plain document store.
  • If the stem says "provider-specific parameter not in Converse," pick InvokeModel with the native body. Converse cannot carry every exotic parameter.
  • If the stem says "structured output" or "JSON schema," pick Converse with toolConfig. Define the schema for the tool inputs.
  • If the stem says "answers must cite sources," pick RAG with RetrieveAndGenerate. Fine-tuning cannot cite.
  • If the stem says "model choice must be evidence-based," pick a golden-dataset evaluation. Never trust provider benchmarks.

More D1 traps, with why the wrong answer fails

  • Distillation for new knowledge. Distillation copies behavior on a narrow task. It does not add facts. Knowledge questions need RAG.
  • Continued pre-training for a tone change. Continued pre-training teaches vocabulary from unlabeled text. It does not teach tone. Tone needs fine-tuning or prompts.
  • Fine-tuning for citations. Fine-tuned weights hold no source links. Only retrieval can cite. Pick RAG.
  • Converse for embeddings. Converse generates text. It cannot embed. Embeddings need InvokeModel with an embedding model.
  • Mixing embedding models between ingest and query. The vector spaces do not align. Retrieval breaks silently. Keep model and dimensions identical.
  • Neptune for document chunks. Neptune is a graph store. Document chunks need a vector store. Neptune serves GraphRAG only.
  • Kendra for RAG. Kendra is enterprise search. The RAG path is Knowledge Bases. Do not mix them.
  • ElastiCache as a vector store. ElastiCache is ephemeral. Vectors need durable storage. Use a real vector store.
  • Provider benchmark scores for model choice. Benchmarks do not measure your data or your prompts. Only your golden dataset counts.
  • Exact flat search on large data. Exact search scans everything. It is affordable only on small data. Large data needs approximate indexes.

D2: Implementation and Integration (26%)

D1 teaches you how to choose an approach. D1 teaches you how to call a model. D2 answers the next question. How do these calls become a working application?

D2 is the build domain. This domain includes agents that act. It includes workflows that orchestrate. It includes APIs that face users. It includes prompts that you treat as code. The exam often shows a failure mode here.

This is when you pick a dynamic tool for a fixed sequence. Or you pick a fixed sequence when the job needs reasoning. Learn the difference between an agent and a flow. Learn the timeout math. Then most of D2 is clear.

Bedrock Agents: when the model decides the steps

A Bedrock Agent is a foundation model. It has instructions. It has action groups. Action groups are tool definitions. Lambda functions or API schemas support these definitions. The agent reasons about a goal.

It decides which tools to call. It decides the order of the calls. It continues until the task is complete. Use agents when the scenario says the model reasons. Use agents when it says the model decides. Use agents when it says the model chooses tools.

Use agents for multi-step tasks with tools. This is the agent loop: Your application calls invoke_agent. It calls this on the bedrock-agent-runtime API. It uses agentId.

It uses agentAliasId. It uses sessionId. It uses inputText. The agent adds its instruction. It adds the conversation history for that session. It asks the model for the next step.

It executes tool calls. It repeats this process.

The exam tests four details. First, aliases: agentAliasId must point to the PROD alias for production. The agent ID alone routes to DRAFT. This is a common bug. It causes "production uses the wrong behavior." Second, PrepareAgent: You must run prepare-agent after any configuration change. This includes a new action group or a new instruction.

This compiles DRAFT into a prepared version. If you skip this, the agent silently runs the old configuration. "Agent ignores the new action group" always means you skipped prepare. Third, sessionId is the conversation memory key. Use one session ID per user session. Reusing one ID across users shares conversation history between them.

Fourth, enableTrace on invoke_agent returns the reasoning trace. This trace shows which tools the agent chose. It shows why the agent chose them. It is the exam's transparency answer. "Show why the agent did that" is always enableTrace.

The Lambda action function has a fixed contract. Both sides must follow this contract. Parameters arrive as a LIST of {"name": ..., "value": ...} dictionaries. They do not arrive as a plain dictionary. If you treat it as a dictionary, you lose every parameter. The response must echo the exact nested shape.

It must include messageVersion. It must include actionGroup. It must include function. The result string must be inside responseBody.TEXT.body. If the shape is wrong, the agent cannot parse the tool result. For multi-tenant agents, the supervisor pattern routes to collaborator agents.

IAM filtering for each knowledge base ensures this. Tenants only reach their own data.

Orchestration and the timeout math

GenAI work is rarely one call. A pipeline classifies data. It extracts data. It validates data. It waits for human review. Then it publishes data.

How to read this diagram

  2. Middle: the limit. API Gateway allows 29 seconds per call.
  3. Bottom: the fix. Stream the answer, or move the slow work to an async path.

A Lambda trying to do that hits its 15-minute (900-second) ceiling. It has no durable memory of its state if it crashes. Step Functions keeps execution state durably. It retries with backoff. It can pause. There are two types.

Never swap them. Standard runs up to 1 year. It costs about $0.025 for 1,000 state transitions. It supports wait-for-callback. A task token lets the workflow pause indefinitely. This is for human approval.

Then it resumes exactly where it stopped. The wait itself is free. Express is for short, high-volume flows. It has a 5-minute maximum duration. It has no callbacks. "Approval takes hours" is always Standard with wait-for-callback.

Express cannot pause.

For parallel bulk work, Distributed Map sends work to up to 10,000 parallel child executions. These executions work on S3 objects. This is the answer to "process 10k objects in a tight window." Sequential processing fails on time. Plain Lambda fan-out fails on orchestration overhead. You must do timeout math in your head. A REST API Gateway in front of a Lambda has a 29-second integration timeout.

A model streams 100 tokens per second. A 3,000-token answer takes 30 seconds. So a synchronous call through the gateway fails. This happens even if Lambda itself can run for 15 minutes. The fix is asynchronous. Return a job ID.

Poll or push the result. Or use WebSocket streaming.

Worked example: the timeout math

Streaming speed: 100 tokens per second. Answer size: 3,000 tokens. Time = 3,000 / 100 = 30 seconds. API Gateway REST integration timeout: 29 seconds. 30 is greater than 29. So the call fails at the gateway.

This happens even though the Lambda behind it can run for 900 seconds. The fix moves off the request-response path. Use WebSockets. Or use asynchronous with polling.

Strands Agents: the code-first loop

Strands Agents is an open-source Python SDK from Amazon for building agents. An agent has three parts: a model (the brain), tools (the hands), and a prompt (the personality and instructions). You create an Agent, hand it a list of tools, and call it like a function. The SDK runs the agent loop for you.

The loop. The model reasons, selects a tool, executes it, reads the result, and repeats until the answer is ready. Each tool is a Python function decorated with @tool. The decorator registers the name, the docstring, and a JSON schema built from the type hints. The Strands Bedrock model provider calls through the Converse API.

Why it exists. It is the code-first alternative to the Bedrock Agents console. Run the same agent on a laptop, in a container, on Lambda, or on AgentCore Runtime. How to read this diagram

  2. The red arrow loops back. The loop runs until the answer is ready.
  3. The bottom box is the prompt. It shapes every loop iteration.

Agent Squad: routing, not loops

AWS Agent Squad is an open-source framework for multi-agent workflows built around intent classification. The pip package is agent-squad. Register several specialist agents with one orchestrator. Each request passes through a classifier, usually a small fast model at temperature 0. The classifier picks the best specialist. The orchestrator hands over the request and returns the answer with routing metadata.

Why specialists beat generalists. A billing agent, a support agent, and a general assistant use different tools, prompts, and knowledge. Adding a fourth specialty means registering one more agent, not rewriting a router. The framework also supports a ChainAgent for fixed pipelines and a SupervisorAgent for coordination. Chat history uses a ChatStorage layer: in-memory by default, DynamoDB or SQL in production.

Exam relevance. "Route each request to the right specialist" names Agent Squad. "One agent using many tools in a loop" names Strands. The exam separates routing from tool use.

MCP: the USB-C port for AI

Servers expose three primitives. Tools (functions the model can call), resources (data the model can read), and prompts (reusable prompt templates). Popular MCP servers exist for Slack, PostgreSQL, GitHub, GitLab, and most SaaS tools. Any agent SDK worth using can call external MCP servers.

OpenAPI: the contract between model and tool

OpenAPI is the standardized specification for web service interfaces. It was first called Swagger. It defines function inputs, outputs, and error conditions in one machine-readable document.

Why agents care. Bedrock Agent action groups use OpenAPI schemas to define AI tools. You upload the schema to S3 or paste it in the console. The model reads the schema and knows exactly how to call the tool. Standardized definitions make tool calls more reliable than free-text descriptions.

Exam relevance. "Define the interface between the FM and an external web service" points at an OpenAPI schema. "Action group needs a tool definition" is the same answer.

D3: AI Safety, Security & Governance (20%)

D2 built the application. D3 guards the application. A working application can leak data. It can answer attacks. It cannot prove who did what. This is a failed application.

D3 tests the bouncer, the locks, and the audit trail. Guardrails filter content at the model boundary. IAM and organization controls decide who can touch what. CloudTrail, CloudWatch, and invocation logging record what happened at three different depths. The exam often offers a real service with an invented capability. Learn exactly what each control can and cannot do.

Guardrails: the bouncer at the model door

A Bedrock Guardrail is a named configuration. It holds your safety rules. Every request and every response passes it. There are six policies. You can switch each policy independently. These policies are: content filters, denied topics, word filters, sensitive information filters (PII detection and redaction), contextual grounding checks, and Automated Reasoning checks.

Attach it inline to a Converse call with guardrailConfig. This includes the guardrail identifier and version. It also has a trace flag that shows what fired. Or, apply it to any text with the standalone ApplyGuardrail API. This is the answer when the scenario says "we call an external model but need AWS guardrails."

Content filters are the toxicity screen. There are six fixed AWS-defined categories. These are hate, insults, sexual, violence, misconduct, and prompt attack. Each category has four sensitivity strengths. This means 24 independent settings per guardrail. Prompt attack is the category that catches jailbreaks.

This includes "ignore all previous instructions." It also catches injections smuggled through pasted documents or tool outputs. The guardrail evaluates it on inputs, where attacks arrive. Denied topics block named subjects on both inputs and outputs. "Block bullying topics" is a denied topic. "Notify on bullying but never block" is the same filter. It runs in a monitor mode.

This mode logs intervene events instead of blocking. Word filters block exact strings. This includes profanity lists and custom terms. Sensitive information filters detect and redact PII.

The two verifiers catch two different lies. Contextual grounding checks ask whether the source text supports the answer. This is the hallucination check for RAG. Automated Reasoning checks translate the response and your policy into formal logic. They prove if the response obeys the policy. This is the strongest guarantee in the guardrail set. You build the policy first: upload the policy document as a PDF to the CreateAutomatedReasoningPolicy API. Bedrock extracts the rules and variables from the document.

It is the answer to "most mathematically certain that outputs obey policy." Note its limit: Automated Reasoning checks run in detect mode only. They return findings (valid, invalid, ambiguous, too complex) instead of blocking inline.

What guardrails can never do

How to read this. Left: what guardrails do (filter content). Right: what they cannot do, each paired with the real service that does it. Takeaway: read every guardrail option for scope creep; a real service with an invented capability is a classic distractor.

Guardrails filter content. They cannot do IAM. IAM decides who may call the model. They cannot do tenant isolation. Tenant isolation decides which data a tenant may reach. They cannot do token quotas or billing.

They cannot do data extraction. An option says "use Guardrails to limit each tenant to 1,000 tokens per day." This is a fabricated feature. It is a real service with an invented capability. Tenant isolation is per-knowledge-base IAM filtering. Quotas are API Gateway usage plans. Access control is IAM.

Read every guardrail option for scope creep.

Identity and access: who can touch the model

How to read this. Top to bottom: the org-wide ceiling first, then the per-role cap, then the actual grants. Takeaway: the exam pairs them exactly this way; mix up the layers and the question is lost.

IAM is the first lock. It uses least-privilege policies. These policies scope which identities can invoke which model, knowledge base, and agent ARNs. They also scope which regions. Above IAM are the organization controls. Service Control Policies (SCPs) set organization-wide maximum permissions.

These apply across accounts in AWS Organizations. This is the answer to "restrict model access across 40 accounts." Deploy them at scale with StackSets. StackSets are multi-account deployments of CloudFormation templates. This prevents account drift. Permissions boundaries cap what a single role can ever receive. This is the per-role answer.

The exam pairs them as: SCPs bound the organization. Boundaries bound the role. IAM grants the actual access inside those bounds. "Built-in alignment is enough" is always wrong. The model provider's safety work never transfers evaluation and governance to you. The deployer owns both.

Observability: three logs, three depths

How to read this. Three columns. Red: who called what, metadata only, 90 days. Amber: what is happening now, metrics and alarms. Blue: the full prompt and response text, opt-in. Takeaway: match the question's depth to the column; only one column holds content.

CloudTrail is the audit plane. It records who called which Bedrock API. It records when, from where, and if it succeeded. It records API metadata only. It never records prompt or response content. Event history keeps 90 days.

Longer retention means delivering the trail to S3. "Who invoked which model at 2am" is always CloudTrail. CloudWatch is the operations plane. It has metrics and alarms on what happens now. It shows which prompts the guardrail blocked and why. It shows guardrail block rates, token counts, and throttling.

Use CloudWatch metrics and custom alarms. "Proactively alert" kills every reactive option. Count tokens before the call with client-side estimation. The InputTokenCount metric fires after the call runs. Model invocation logging is the content plane. It is the opt-in record of full prompt and response text.

It goes to S3 or CloudWatch. It is KMS-encryptable. It is the only source for "show us the exact blocked prompt." In regulated scenarios, you must justify keeping it at all. Use retention policies and redaction. Logs can contain PII.

Network and data protection

How to read this. Left to right: your VPC, the PrivateLink endpoint, Bedrock. The note below kills the NAT gateway option. Takeaway: no public internet always means VPC interface endpoints.

"Bedrock with no public internet" is always VPC interface endpoints (PrivateLink) for the Bedrock APIs. Use Lambda in private subnets. A NAT gateway gives public internet access. This violates the constraint. At rest is KMS. Use customer-managed keys, envelope encryption.

Log every key use. In transit is TLS. Customer data sent to Bedrock is not used to train models under the service terms. Any data you log stays in your account. Bedrock agent tracing: four trace types

When a Bedrock Agent answers, it records a trace. The trace shows the reasoning process, which knowledge bases it hit, and where errors happened. It is the fastest way to debug a misbehaving agent.

Trace types. Preprocessing traces cover input handling before the agent acts. Orchestration traces cover the agent loop: model reasoning, tool selection, tool results. Postprocessing traces cover output handling after the loop. The routing classifier trace shows which specialist the request went to.

Exam relevance. "Debug why the agent called the wrong tool" means read the orchestration trace. "Debug why the answer format broke" means read the postprocessing trace.

Token-level redaction: filter the text, not the weights

Tokens here mean input and output text, not model internals. When guardrails are too heavy or still not enough, filter the sensitive tokens directly.

Three filter points. Filter training data at ingest. Filter the request in a pre-processing handler before it reaches the FM. Filter the response in a post-processing handler as the last defense before output. Define the handlers as Lambda functions. Use simple logic like regex or banned-word lists, or call Amazon Comprehend for named entity recognition on what to ban.

Exam relevance. "Block PII in model output as a last resort" means a post-processing Lambda with token-level redaction. "Guardrails cannot cover this edge case" is the trigger phrase.

CloudTrail watches calls, CloudWatch watches prompts

Model invocation logging in CloudWatch Logs records prompts and answers. Use CloudWatch Logs to monitor prompt inputs and model outputs, to test prompt regressions, and to track quality, latency, and error rates.

CloudWatch RUM. Real User Monitoring measures real sessions: page load times, errors, app launch times. It suits mobile GenAI apps. It integrates with Application Signals, visible in X-Ray.

Trap: "use CloudTrail to find the bad prompt." Wrong. CloudTrail shows that InvokeModel ran. It never shows the prompt text. The exam uses this confusion as a distractor.

D4: Operational Efficiency and Optimization (12%)

D3 made the application safe. D4 makes the application cheap and fast. Safety is not important if the cost or the latency kills the project.

D4 is the smallest scored domain. It has the most decision rules. Each question is a cost, latency, or capacity scenario. The adjective in the question names the correct answer before you read the options. Learn the three adjectives and the three-way routing confusion set. Then D4 gives you free points.

The three adjectives, three different winners

"Least operational overhead" means the fewest self-managed components. Use Aurora Serverless instead of a self-managed OpenSearch cluster. Use Converse instead of hand-rolled provider bodies. Use managed routers instead of your Lambda code. "Least custom development effort" means managed features instead of your own code. Use Knowledge Bases instead of a hand-built ingestion pipeline.

Use prompt routers instead of your classifier Lambda. Use Guardrails instead of hand-rolled filters. "Most cost-effective" means token math. Use the smallest model that meets the quality standard. Use caching for repeated prefixes. Use batch for offline bulk.

Use cascading simple queries to cheap models. The exam changes these adjectives for the same scenarios. The scenario does not change. The correct answer changes.

Worked example: token math on one million requests

A chatbot handles 1,000,000 requests each month. Each request has 2,000 input tokens and 500 output tokens on average. Use these illustrative prices: $3 per million input tokens, $15 per million output tokens.

On-demand cost per request: input part = 2,000 / 1,000,000 x $3 = $0.006. Output part = 500 / 1,000,000 x $15 = $0.0075. Total per request = $0.0135. Monthly = $0.0135 x 1,000,000 = $13,500.

Batch inference is about 50% off: $13,500 x 0.5 = $6,750 each month. This is only if no one waits for the answers. That "roughly half" is the whole batch argument.

Prompt caching: 1,800 of the 2,000 input tokens are a repeated system prompt. Cache hits bill at one-tenth the rate ($0.30 per million). The input part drops to (200 / 1,000,000 x $3) + (1,800 / 1,000,000 x $0.30) = $0.0006 + $0.00054 = $0.00114 per request. The answers are the same. The input cost is about one-sixth. The precondition is real.

Resource utilization: stop paying for idle GPUs

Overprovisioning wastes money. Four techniques raise utilization.

  1. Batching. Group many requests into one GPU pass. Throughput rises. Latency per request rises too. Use it when no user waits: bulk scoring, offline evals, dataset generation.
  2. Tensor parallelism. Split the model weights across several GPUs. Each GPU holds one shard. This fits models that exceed one GPU and cuts latency for large models. It needs fast links between GPUs.
  3. Capacity planning. Match provisioned capacity to real traffic, not to peak guesses. Review the utilization numbers each month. Shrink what sits idle.
  4. Monitor model utilization. Track GPU use, queue depth, and throttle counts in CloudWatch. Low GPU use with long queues means the batch size is wrong, not the capacity.

Exam relevance. "GPUs idle while requests queue" points at batching or tensor parallelism, not at more GPUs. "One model too large for one GPU" points at tensor parallelism. For the largest distributed training and inference jobs, AWS points at UltraServers (Trn2, P6e-GB200): purpose-built servers with high-bandwidth links between accelerators.

Token efficiency: measure, prune, compress, limit

More tokens mean more processing time and more money. Four technique groups cut tokens.

  1. Count tokens first. The Bedrock CountTokens API returns the token count for an input without running inference. It accepts the same body as InvokeModel or Converse. It is free. Use it to check context-window fit and to estimate batch cost before any billed call.
  2. Prune context. Drop old chat history. Chunk big documents and send only relevant chunks. Retrieve fewer chunks. Filter chunks by metadata.
  3. Compress prompts. Summarize old chat history or large documents before sending. A small model can do the summarizing. Prefer RAG over stuffing full documents into the prompt.
  4. Limit responses. Set maxTokens. Force a short format through JSON output settings. State the length in the prompt. Use few-shot examples to set verbosity.

CloudWatch metrics. Track InputTokenCount and OutputTokenCount per model. Watch throttles and invocation errors. For streaming, watch TimeToFirstToken.

Under the hood. CountTokens runs the real tokenizer without running the model. Local tokenizers guess because each model family tokenizes differently. The exam twist: CountTokens can reject inference-profile model IDs that InvokeModel accepts. Test with the base model ID when unsure. The API is free either way.

Exam relevance. "Estimate cost before inference" means CountTokens. "Free" is the fact the exam checks: local tokenizers guess, CountTokens measures.

Intelligent Prompt Routing: route by complexity

Model size trades cost against capability. Small models handle preprocessing well: summarization, classification, chunking. A small model can even be the backbone when RAG and tool use do the heavy lifting.

Dynamic routing. Route simple queries to cheap models and hard queries to flagships, without custom code. Bedrock Intelligent Prompt Routing scores each prompt and picks the tier. Agents can also score complexity with a tool and route through conditional flows, Agent Squad, or Lambda.

Exam relevance. "Simple questions cheap, hard questions flagship, no custom routing code" names Intelligent Prompt Routing. "Cheapest model that meets the constraint" is the standing cost rule.

TTFT: the latency users feel

Time to first token is the delay between sending the request and receiving the first token. It only exists for streaming calls. Non-streaming calls have one end-to-end latency number.

What drives it. Long prompts drive TTFT up because the model processes the whole prompt before emitting anything. Large models, cold Provisioned Throughput, and throttling queues push it up. Shorter prompts, prompt caching, smaller models, and streaming push it down.

Measure it. Bedrock publishes TimeToFirstToken to the AWS/Bedrock CloudWatch namespace. InvocationLatency covers all calls. Set alarms on p95 TTFT so regressions page someone instead of silently annoying users.

Trap: "TTFT for a batch job." Wrong. Batch inference is not streaming. TTFT has no meaning there. The exam also confuses TTFT with end-to-end latency and with tokens per second. Name the metric the stem describes.

Retry: backoff with jitter

Throttling is a signal, not a bug. The client must retry with exponential backoff and jitter. Wait, then wait longer, and add a random offset so a fleet of clients does not retry in lockstep.

SettingValue
First waitAbout 1 second
GrowthDouble each time: 1s, 2s, 4s
JitterSmall random offset per retry
Attempts3 to 5, then surface the error

AWS SDK clients offer custom retry policies with these knobs. Provisioned Throughput solves sustained throttles. More retries do not.

Connection pooling. Keep a pool of open connections to the backend. It saves the cost of new handshakes. For HTTP clients in AWS, 10 to 20 connections per instance with a 60 to 300 second TTL is the working range. Balance utilization against reuse.

Exam relevance. "Throttled, retry" always means exponential backoff with jitter. "Sustained throttles at steady load" means Provisioned Throughput, not more retries.

A/B tests need statistics: Evidently

Comparing two CloudWatch dashboards by eye is not an experiment. It has no randomization and no significance test. CloudWatch Evidently runs real experiments: feature flags plus A/B tests with built-in statistics.

The two APIs. EvaluateFeature assigns the requesting user to variant A or B and returns the variant configuration. PutProjectEvents reports the outcome metric, like a thumbs-up or task success. Evidently computes whether B beats A with statistical significance. Define the feature with variations (model A versus model B, topK 10 versus 50), set traffic fractions, and pick the winning metric. A 90/10 split limits blast radius while the test runs.

Under the hood. EvaluateFeature assigns the variant deterministically per user so one user sees one variant. PutProjectEvents reports the outcome. Evidently runs the significance math. The exam twist: "we compared two dashboards" is not an experiment. No randomization and no significance test means no conclusion.

Exam relevance. "Statistically significant winner" or "which variant wins" points at Evidently. "Two Lambda versions, compare dashboards" is the distractor. Prompt Management variants cover prompt text only. Real experiments vary models, retrieval depth, temperature, or whole pipelines.

  • If the stem says "same long system prompt on every call," pick prompt caching. Mark the prefix with cachePoint.
  • If the stem says "users ask similar questions many times," pick semantic caching. It skips the call completely.
  • If the stem says "nightly bulk work, no SLA," pick batch inference. JSONL in S3. About 50% off.
  • If the stem says "steady traffic, throttling at peak," pick Provisioned Throughput for the baseline. Keep on-demand for peaks.
  • If the stem says "slow first token," pick streaming. Provisioned Throughput fixes capacity. It does not fix first-token speed.
  • If the stem says "simple queries on an expensive model," pick a prompt router or cascade. Never pick Provisioned Throughput for a cost problem.
  • If the stem says "latency SLA with steady volume," pick Provisioned Throughput. It buys guaranteed capacity.
  • If the stem says "spiky or low traffic," pick on-demand. Provisioned Throughput bills hourly whether you use it or not.
  • If the stem says "cut retrieval cost," tune top-k and chunking first. Smaller context means fewer input tokens.

More D4 traps, with why the wrong answer fails

  • Provisioned Throughput for a cost problem. PT is capacity. It does not make simple queries cheaper. Cost problems need routers, caching, or smaller models.
  • Provisioned Throughput for bursty traffic. PT bills hourly whether you use it or not. Bursty traffic needs on-demand.
  • Prompt caching on unique traffic. No repeated prefix means no hits. The cache never pays off.
  • Semantic caching for exact-only answers. Semantic caching returns similar answers. Exact needs need exact retrieval.
  • Batch inference for interactive requests. Batch has hours of latency. Waiting users need sync or streaming.
  • Fine-tuning to cut cost. Fine-tuning changes behavior. It does not cut per-call cost. Distillation or smaller models cut cost.
  • Bigger model for "most cost-effective." The flagship costs more per token. Do the math. The small model often wins.
  • Streaming to fix throttling. Streaming fixes perceived latency. Throttling is a capacity problem. It needs Provisioned Throughput.
  • Cross-region profiles for cost. Profiles route for availability. They do not cut cost. Prompt routers cut cost.
  • Ignoring the output reserve. Output tokens cost more than input tokens. A missing reserve breaks the budget.

D4 decision rules: if the question says X, pick Y

  • "Least operational overhead" means the fewest self-managed components. "Least custom development effort" means managed features. "Most cost-effective" means token math.
  • "Throttled at peak, steady traffic" means Provisioned Throughput (provisioned ARN as modelId). "Spiky or low traffic" means on-demand.
  • "80% simple queries on the flagship" means a prompt router or cascade. Never use PT for a cost problem.
  • "Repeated long prefix" means prompt caching. Proof is cache read hit rate. "Unique traffic" means caching is dead weight.
  • "Nightly bulk, no SLA" means batch inference (about 50% off). Never use it for interactive SLAs.
  • "Slow first token, users complain" means streaming. Not PT, not caching.
  • Use inference profiles for regional failover. Use prompt routers for cost by complexity. Do not swap them.
  • Choose the cheapest option that meets all requirements. Do not choose premium extras with no stated need.

D4 trap patterns

  • Use Provisioned Throughput (PT) to fix cost for bursty traffic. PT bills hourly. It bills even if you do not use it.
  • Use PT to fix latency for slow first token. Capacity is not perceived latency.
  • Use prompt routers for availability. Use inference profiles for cost. The options swap the pair.
  • Cache unique traffic. If there is no repeated prefix, there is no saving.
  • Batch for interactive Service Level Agreements (SLAs). Hours of latency breaks the SLA.
  • Total token spend shows if caching works. The metric is cache read hit rate.
  • Use a bigger model as the quality answer. Do not do this without a golden-dataset check. Right-size first.
  • Use reactive metrics for proactive requirements. Count before the call.

The evaluation ladder: automatic, then judge, then human

Automatic evaluation (programmatic) compares model outputs. It compares them with known-correct answers. It uses deterministic code. It needs a labeled dataset. Every prompt has a ground truth label. Built-in metrics are accuracy.

How to read this diagram

  1. Bottom rung: automatic. Code compares outputs to known answers.
  2. Middle rung: LLM as a judge. A separate model scores samples with a rubric.
  3. Top rung: human. People review a sample. It costs the most.

This shows if it matched. Another metric is stability. This shows if the answer stays correct with small prompt changes, like typos. The console calls this robustness. Another metric is toxicity. This checks for harmful content.

A 1,000-prompt automatic evaluation on a small model costs a few dollars. It finishes in minutes. This is why it is in every CI pipeline. LLM-as-a-judge uses a separate model. It scores outputs for correctness, completeness, faithfulness, harmfulness, refusal, and style/tone. You can define custom metrics.

It needs no labels. So, it works with unlabeled data. But a judge call costs a judge call. Human evaluation is the last option. It uses subjective judgment on samples only. Do not use it for everything.

Do not use it under a budget.

Use the ladder in practice. Compare models cheaply at scale. Use automatic metrics first. Run LLM-as-a-judge on the model that remains. Put humans on flagged samples only. "Two days to compare two models" means this ladder in cost order.

RAG has its own evaluation split. This is retrieval relevance. Did we get the correct chunks? This is also generation faithfulness. Is the answer supported by the chunks? LLM-as-judge powers this.

"Prove the RAG system does not hallucinate" means retrieval plus faithfulness. Do not use a bigger model. Provider benchmarks never decide your model choice. They measure the provider's prompts, not your prompts. Your own evaluation job on your golden dataset is the only score that matters. New prompt versions, new model versions, and new guardrail versions all pass through the same CI/CD eval gate.

This is an automated quality check inside the continuous integration and deployment pipeline. Score above the threshold or do not deploy. A/B testing uses two aliases. It uses shadow traffic. Shadow traffic copies real user requests. It routes them to the new version.

Users do not see them. This happens through inference profiles. This catches problems the gate misses.

Curveballs: the exam twists back

These are the questions that punish shallow reading. Each one changes a constraint, breaks an assumption, or pairs two confusing services. Read the twist. Work the answer. Name the trap.

CB01. The reranker made answers worse

Scenario. A RAG system adds a reranker on the top-20 vector hits. Answer quality drops. The team blames the reranker model. What do you check first?

Worked answer. Check what the vector search retrieves before the reranker runs. A reranker can only reorder the candidates it receives. If the top-20 contains no relevant chunk, the reranker promotes the least-bad wrong answer. The fix is upstream: chunking strategy, embedding model, or hybrid search. The reranker was never the problem. The retrieval stage starved it.

The trap. Blaming the last stage. Debug the pipeline in order: pre-retrieval, retrieval, post-retrieval.

CB02. Provisioned Throughput versus batch inference

Scenario. A nightly job scores 2 million support tickets with no SLA. A teammate proposes Provisioned Throughput for steady performance. What is wrong, and what wins?

Worked answer. Provisioned Throughput reserves capacity for consistent low-latency inference at high volume. A nightly job with no SLA needs the opposite: cheapest cost, latency irrelevant. Batch inference takes JSONL from S3, runs offline, and costs about half of on-demand. PT would burn money reserving capacity nobody needs during the day.

The trap. "Steady" sounds like PT. The exam means steady latency need, not steady schedule. No SLA plus bulk equals batch.

CB03. Guardrails versus IAM

Scenario. A multi-tenant app must block one tenant from calling an expensive flagship model, and must block PII in all model outputs. One control for both?

Worked answer. No. Two different controls. IAM (or the API gateway policy layer) decides who may call what: block the tenant at the model-access level. Guardrails decide what content may pass: the PII filter runs on inputs and outputs. IAM never inspects prompt text. Guardrails never manage tenant permissions. The exam pairs them to test whether you know the boundary.

The trap. One bouncer for two doors. Identity controls access. Guardrails control content.

CB04. AgentCore versus Strands versus Agent Squad

Scenario. A team builds a Python agent with custom tools, then needs to route customer requests across five specialist agents, then needs serverless deployment with memory. They ask for one service. What do you tell them?

Worked answer. Three different jobs, three different answers. Strands Agents builds the code-first tool-use loop. Agent Squad routes across the five specialists with an intent classifier. AgentCore Runtime hosts the whole thing serverless with Gateway, Memory, Identity, and Observability. No single service does all three. The exam wants the three names mapped to the three jobs.

The trap. "One service" framing. Split the scenario into build, route, and host.

CB05. The KB deletion that kept billing

Scenario. A team deletes a Bedrock Knowledge Base. The OpenSearch Serverless bill continues. What did they miss?

Worked answer. Deleting the KB does not delete the vector store. Deleting the vector store data does not delete the serverless collection. The collection keeps running with zero data and keeps billing. Delete three things: the KB in Bedrock, the data in the store, and the collection in OpenSearch Service. The exam tests this chain because it burns real money.

The trap. "Delete the KB" sounds complete. It is one of three deletions.

CB06. Cross-region inference with Provisioned Throughput

Scenario. A design uses a global inference profile for resilience plus Provisioned Throughput for steady latency. Will it work?

Worked answer. No. Cross-region inference does not work with Provisioned Throughput. PT pins a model to reserved capacity in specific regions. Cross-region routing needs on-demand capacity it can shift. Pick one: PT for guaranteed throughput in-region, or cross-region profiles for resilience and cost. The exam offers both together as a contradiction distractor.

The trap. Two good features that cancel each other. Check compatibility, not just desirability.

CB07. The prompt that outgrew the model

Scenario. A RAG prompt works on one model but fails on a cheaper model with a context error. The team wants to keep the cheap model. What is the fix order?

Worked answer. First measure with the CountTokens API (free, matches the bill). Then cut: retrieve fewer chunks, filter chunks by metadata before vector search, prune old chat history, compress with a small summarizer model. Only then consider prompt caching for the repeated prefix. Do not start by switching models again. The failure is input size, not model quality.

The trap. "The cheap model is broken." The model is fine. The prompt is too big.

CB08. Semantic caching returns stale answers

Scenario. A semantic cache serves RAG answers fast, but users get yesterday answers to today questions. The cache hit rate is high. What broke?

Worked answer. The similarity threshold is too loose, or the cached entries never expire. Semantic caching matches on embedding similarity, not exact text. Near-duplicate questions with different time context ("sales today" versus "sales yesterday") can score above the threshold and return the stale answer. Fixes: tighten the threshold, add TTLs, and include time-sensitive metadata in the cache key. High hit rate with wrong answers means the cache is confident and wrong.

The trap. "High hit rate means the cache works." Hit rate measures speed, not correctness.

CB09. The agent that forgot the customer

Scenario. A support agent remembers context within a chat but forgets the customer tier between sessions. Sessions end after 600 seconds idle. Where does the memory go?

Worked answer. Session memory is short-term by design. Cross-session facts need long-term storage optimized for persistence: DynamoDB keyed by customer ID with server-side encryption, read at session start and written at session end. ElastiCache would also forget. The exam checks the latency-versus-persistence split: in-session goes to fast stores, cross-session goes to durable stores.

The trap. "Memory" as one thing. Short-term and long-term memory are different stores with different goals.

CB10. The evaluation that graded itself

Scenario. A team uses the same flagship model as both the RAG generator and the LLM judge. Scores look great. Should you trust them?

Worked answer. No. A judge that shares the generator blind spots will miss the same failures. Use a different model as the judge for a second opinion. Also confirm the JSONL prompt dataset in S3 actually defines the judging criteria. Great scores from a self-judging loop measure agreement, not quality. The exam tests this as an independence requirement.

The trap. "The judge is a strong model." Strength does not fix shared bias. Independence does.

CB11. BDA chokes on the daily file dump

Scenario. 10,000 mixed files land in S3 each morning. The BDA pipeline processes them one by one from a Lambda. At peak, jobs fail and files pile up. What is the correct shape?

Worked answer. S3 events fire per file. An EventBridge rule routes by file type. InvokeDataAutomationAsync queues the jobs. BDA async jobs queue behind service quotas, so buffer the burst with SQS and let poison files land in a dead-letter queue after retries. One-by-one synchronous Lambda calls collapse under burst load. The async plus queue shape absorbs the peak.

The trap. "Lambda per file" sounds serverless and fine. Burst plus quotas needs buffering.

CB12. The fine-tune that should have been RAG

Scenario. A team fine-tunes a model on the product catalog so it can answer pricing questions. Prices change weekly. Answers go stale within days. What was the error?

Worked answer. Knowledge versus behavior. Fine-tuning bakes behavior into weights. It is the wrong tool for changing facts. RAG serves the live catalog at query time with citations. The team paid training cost for a system that decays weekly. The approach ladder says: changing knowledge means RAG, always.

The trap. "The model knows our data" as a goal. Models should reason. Stores should remember.

CB13. The cheaper model that cost more

Scenario. A team switches to a cheaper per-token model. The monthly bill rises. How?

Worked answer. Per-token price is not per-answer price. The cheaper model needs longer prompts, more retries, or more output tokens to reach the same quality. Total tokens times price is the bill. Measure with CountTokens and CloudWatch InputTokenCount and OutputTokenCount before and after the switch. Intelligent Prompt Routing exists for this reason: route simple queries to cheap models and hard queries to flagships instead of switching wholesale.

The trap. Price per token as the whole cost story. Tokens per task completes it.

CB14. The MCP server that could not scale

Scenario. A stateless MCP tool server runs on a single container. Traffic spikes and tool calls time out. The tools are simple JSON transforms. What is the fix?

Worked answer. Stateless and lightweight means Lambda, not a single container. Lambda scales each tool call independently and you pay per call. Containers fit complex tools with long runs or local state. The exam maps server shape to host: stateless goes serverless, complex goes containers, managed at scale goes AgentCore.

The trap. "Containers" as the default for everything. Match the host to the workload shape.

D5 · EASY · ONE ANSWER
QH13. A summary omits key facts from the reference. Which metric catches this?

  • B) ROUGE.
  • A) BLEU. BLEU measures precision: unsupported words in the output.
  • C) BERTScore. Measures semantic similarity, not reference coverage.
  • D) Exact match. Too strict for summaries with valid rephrasing.

Why B is correct: ROUGE measures recall: how much of the reference appears in the output. Missing reference content is a recall failure.

The trap: BLEU for missing content. BLEU is precision. Missing content is recall.

QH14. The team wants LLM-as-a-judge evaluation in Bedrock. What must they provide?

How to read this diagram

  1. Easy: answer in under 90 seconds. Bank the time.
  2. Medium: stay on the 2.4-minute pace.
  3. Hard: cap at 4 minutes. Flag and move on.

The question method

  1. Extract the constraints. Read the stem. List every constraint: facts change, no internet, must cite, notify only. If an option violates one constraint, eliminate it.
  2. Name the verb. The stem has one operative verb: block, cite, ground, act, cut cost, add capacity. Match the verb to the service.
  3. Climb the ladder. Prefer the cheapest rung that works. Managed over self-built. Prompt over RAG over agents over fine-tuning.
  4. Check the trap. Every wrong option is a real service doing the wrong job, an absolute word, or a reversed cause. Name the trap before you commit.
  5. Trust the first answer. Change it only when you find a violated constraint. Gut changes lose points.
