    1. The Converse API: one interface for every model

    Every system in this volume starts with one operation: calling a model. Inference means sending a model an input.

    Mechanism

    Every system in this volume starts with one operation: calling a model. Inference means sending a model an input. It means getting generated text back. The input you send is the prompt. This is the instructions and the user's question.

    Bedrock offers two doors for inference. These are the unified Converse API and the raw InvokeModel API. This chapter is about the unified door.

    Converse is the unified API. It has the same request shape for Claude, Llama, Titan, and Nova. It includes tool use, guardrails, and caching.

    Converse (and its streaming twin ConverseStream) is Bedrock's unified inference API. One request format works across model providers. The key fields are: modelId (which model to call: a base ID, an inference profile, or a provisioned model ARN), messages (the conversation, as a list of role and content blocks: user and assistant roles), system (system prompts that set behavior for the whole conversation), inferenceConfig (maxTokens, temperature, topP), toolConfig (the tools the model may call, each with a JSON schema for its inputs), guardrailConfig (guardrail identifier and version, applied inline, with an optional trace), additionalModelRequestFields (escape hatch for provider-specific parameters Converse does not natively support), cachePoint (marks where prompt caching starts, topic 2), outputConfig (structured output as JSON schema). Converse is only for text-generation. It cannot do embeddings.

    Before Converse, every provider needed its own request body. Claude wants anthropic_version and max_tokens. Llama wants prompt. Titan wants something else.

    Switching models meant rewriting code. Converse normalizes all of that. The model ID becomes a configuration value. This makes "switch models without code changes" work.

    Tool use (also called function calling) lets the model invoke your code. The loop runs in steps:

    1. Your app sends messages and toolConfig. The toolConfig describes each tool's name, description, and input schema.
    2. The model returns a toolUse content block. The model does not return text. The block shows the tool name. The block shows the arguments the tool chose.
    3. Your app executes the tool. This is a Lambda call, a database query, or an API request. Bedrock does not run your code. You run your code.
    4. Your app sends the result back. Your app sends the result as a toolResult block. This is in a new messages entry with the role user.
    5. The model produces the final text answer. The model includes the tool result.
    6. Steps 2 to 4 repeat for multi-step tool use.

    Converse also accepts document and image inputs as content blocks. PDFs and images travel inside messages. A model can read an attached invoice or chart directly. Format limits apply per model. These limits are for size and page count. Large documents belong in a KB or Data Automation.

    A travel assistant defines 4 tools with toolConfig. The tools are search flights, search hotels, check weather, and convert currency. A user asks for a weekend plan. Turn 1: The model returns 2 toolUse blocks in one response.

    The blocks are for flights and hotels. The app runs both in parallel. This is 2 Lambda invocations. Each invocation takes 1.2 seconds.

    Turn 2: The app sends both toolResult blocks. The model returns a weather toolUse. Turn 3: The model returns the final itinerary text. This is a total of 3 Converse calls. This is a total of 3 tool executions.

    This is one user-visible answer. The token cost roughly triples. This is because every turn resends the conversation history and tool schemas. The guide compares this to a no-tool call.

    Trap

    Converse cannot do embeddings.

    The exam asks, "generate embeddings for a vector store." The exam offers Converse as a distractor. Embeddings need InvokeModel with an embedding model. Examples are Titan Text Embeddings and Cohere Embed. Converse is only for text generation. Memorize this as a one-line rule.

    Common misunderstanding

    The model never executes tools.

    Beginners think the model calls the Lambda. This is not true. The model outputs a structured request (toolUse). Your application runs the code.

    Your application returns the result (toolResult). If a scenario says "the model directly updated the database," the architecture is wrong. The application layer is absent.

    The API returns a toolUse block. The model does not run anything. The model only asks.

    Step 3: your application executes the Lambda tool. It uses the model's chosen arguments.

    Step 4: the application sends the outcome back. It is a toolResult block inside a user-role message.

    Step 5: the API returns the final text. For multi-step tasks, steps 2 through 4 repeat before step 5.

    2. InvokeModel, provider specifics, and prompt caching

    Why this comes next. Chapter 1 gave you the unified door, Converse. It left a gap. Converse cannot express everything.

    Mechanism

    Why this comes next. Chapter 1 gave you the unified door, Converse. It left a gap. Converse cannot express everything. Provider-specific features, embeddings, and legacy code need the raw door. This chapter covers InvokeModel, provider bodies, and prompt caching.

    InvokeModel (and InvokeModelWithResponseStream) calls a model. It uses the provider's native request body. Claude needs anthropic_version: "bedrock-2023-05-31" and max_tokens. Llama, Titan, Mistral, and Cohere each have their own shapes.

    A wrong body returns ValidationException or a malformed-input error. This is the only Bedrock API that can generate embeddings. These are vectors for search. It uses embedding models like Titan Text Embeddings v2 or Cohere Embed.

    An embedding is a list of numbers. It captures a text's meaning. Texts with similar meaning get similar numbers. So, searching by meaning means searching for nearby numbers.

    How to read this diagram

    1. Read the three text boxes on the left. There are two password questions phrased differently. There is one refund question.
    2. Follow each into the embedding model. Text becomes a list of numbers. This is 1,024 numbers for Titan Embed.
    3. In vector space, the two password texts are close together. The refund text is far away. Closeness means similar meaning.
    4. The main point is the mechanism behind retrieval. The system compares a question's numbers against every chunk's numbers. The nearest chunks win.

    Embeddings are the first job InvokeModel does that Converse cannot. The second is about cost: when the same long prefix repeats on every call, you should not pay full price for it twice.

    Prompt caching reuses the computation for a repeated prompt prefix. You mark a cachePoint (Converse) or cache_control (InvokeModel). On the next call with the same prefix, Bedrock does not recompute it. It bills cached input tokens at a discount. Claude 3.5 and newer support this. Nova models also support it.

    Minimum token thresholds apply per model. These are in the order of thousands of tokens. The cache TTL (time to live) is 5 minutes by default. A 1-hour TTL is available on supported models. A cache write costs extra one time. Reads are cheap.

    These are two different problems. InvokeModel exists because providers innovate faster than any unified API. New sampling parameters, new modalities, and embeddings all appear here first. Prompt caching exists because real applications resend the same large system prompt. They resend few-shot examples or documents on every call. Recomputing a 20,000-token prefix on each of 10,000 daily calls is pure waste.

    InvokeModel body: You serialize the provider's JSON yourself. The exam's classic bug: sending a Claude body to a Llama model. Or forgetting anthropic_version. The error is always a validation error. It is never a model-quality problem.

    Cache matching: The prefix must match exactly. It must match token for token. This is from the start of the prompt up to the cache point. One changed character in the system prompt makes the cache invalid.

    Put volatile content after the cache point. This includes user questions and timestamps. Put stable content before the cache point. This includes instructions, examples, and documents.

    Cache economics: The first call writes the cache. This is a write surcharge. Subsequent calls with the same prefix read it within the TTL. This costs about 10% of the input price.

    This is an illustrative discount. The exact pricing changes. You need enough repeat calls within the TTL window to break even.

    TTL behavior: Each cache hit extends the 5-minute TTL. Steady traffic keeps the cache warm indefinitely. Spiky traffic with gaps over 5 minutes pays a rewrite on every spike.

    A support bot sends a 12,000-token system prompt on every call. This includes policy documents and 20 few-shot examples. It also sends a 200-token user question. The service bills every call in the same way.

    cost per call = input tokens × price per input token

    Input tokens number of tokens sent on one call. Price per input token cost in dollars per token at the published price.

    Worked example (illustrative). Without caching, the cost is $3 per million input tokens. This is $0.000003 each. The cost is 12,200 × $0.000003 = $0.0366 per call. With caching, the system caches the prefix. This is 12,000 cached tokens at 10% price ($0.0036).

    Plus 200 fresh tokens ($0.0006).

    This is about $0.0042 per call. This is about an 8x saving. At 50,000 calls per day, that is $1,830 versus $210 per day. The catch: if the policy documents change hourly, and traffic gaps are more than the TTL, rewrites remove the savings. A stable prefix plus steady traffic is the best case for caching.

    Trap

    Prompt caching versus Provisioned Throughput.

    This is the exam's favorite cost pair. Caching attacks repeated-input cost. This is the same long prefix on every call. Provisioned Throughput attacks latency and throughput guarantees. This gives a steady baseline and no throttling.

    Scenario says "same 15k system prompt on every call, costs rising". Then use caching. Scenario says "throttling at peak, steady baseline, latency SLA". Then use PT. Never swap them.

    Common misunderstanding

    Converse plus additionalModelRequestFields is not always enough.

    Converse has an escape hatch for provider-specific parameters. But truly provider-native features belong on InvokeModel. These include embeddings and the newest sampling controls. When the scenario names a provider-specific feature, InvokeModel is the distractor-proof answer.

    3. Long-running and non-interactive inference: asynchronous and batch

    Why this comes next. Chapters 1 and 2 answered the synchronous question. They covered calls that wait.

    Mechanism

    Why this comes next. Chapters 1 and 2 answered the synchronous question. They covered calls that wait. They did not cover calls that nobody waits for. These are nightly jobs, bulk work, and ten-minute analyses.

    This chapter covers asynchronous invocation and batch inference. These use the same models. They use a different contract.

    Not every model call needs an answer now. Asynchronous invocation and batch inference trade latency for cost and scale.

    Asynchronous invocation: You submit a request. You get a job ID. The model processes the request in the background. You poll for completion. Or you get a notification. Use this for single requests that take minutes.

    No user waits for these requests. Batch inference: You put many prompts in S3. Use JSONL. Put one request per line. Submit one batch job. Bedrock processes them over hours.

    It writes the results to S3.

    This is about 50% cheaper than on-demand. Use this for large non-interactive workloads. Examples are nightly summarization, bulk classification, and evaluation datasets. Compare this with real-time inference (Converse, InvokeModel).

    These take milliseconds to seconds. They cost full price. Use them for interactive tasks.

    Interactive capacity is expensive. It must be ready instantly. If your workload can wait hours, do not pay for instant capacity. Batch jobs run on spare capacity.

    This is why they cost about 50% less. Asynchronous single requests solve the problem of one slow call. A 10-minute document analysis does not need a user to wait. It should not keep an API Gateway connection open.

    Batch, step by step:

    1. Upload input.jsonl to S3.
    2. Each line is a complete model request. It includes the model ID and the body.
    3. Call CreateModelInvocationJob with the input S3 URI. Call CreateModelInvocationJob with an output S3 URI.
    4. Bedrock adds the job to a queue. It processes the job when capacity is available. This usually happens within hours.
    5. You can poll the job status. You can trigger on completion by using EventBridge.
    6. The results go to S3 as JSONL. There is one output line for each input line. The order is the same.
    7. Failed lines have error records. The system does not drop them silently.

    Async single: Submit one request. You will receive an invocation ARN. Poll GetAsyncInvoke or subscribe to completion events. The output goes to S3. Respect the limits.

    Input file size has a cap. The maximum number of records per job has a cap. Not every model supports batch processing. Check the documentation for each model at build time.

    A media company summarizes 200,000 articles per night. Each article has an average of 800 input tokens. Each article has an average of 150 output tokens. The cost per night follows one formula.

    cost per night = articles × ( input tokens per article × input price + output tokens per article × output price )

    Articles number of records processed per night. Input/output tokens per article average number of tokens per record. Input/output price cost in dollars per token.

    The cost follows this worked example (illustrative, on-demand pricing): 200,000 × (800 × $0.000003 + 150 × $0.000015) = 200,000 × ($0.0024 + $0.00225) = $930 per night. Batch processing costs about 50% less. This is about $465 per night. This saves about $170,000 per year.

    Batch processing is correct because summaries are necessary by 6 AM. Instant summaries are not necessary. If editors need summaries in less than 10 seconds, batch processing is not correct. This is true even with the cost savings.

    Walk through the code below. The code submits a batch inference job with boto3. It pairs with the sync/async decision diagram above. Read it in three steps.

    Build the control-plane client. AWS manages batch jobs as resources. So, they live on "bedrock." They do not live on "bedrock-runtime." Call create_model_invocation_job with the model ARN, the S3 input URI, and the S3 output URI. Then, poll the job status until it completes.

    import boto3, time

# WHAT: the Bedrock CONTROL-PLANE client. Batch jobs are managed resources
#   (create, poll, stop), so they live on "bedrock", not "bedrock-runtime".
# WHAT BREAKS: "bedrock-runtime" has no create_model_invocation_job method.
client = boto3.client("bedrock", region_name="us-east-1")

# WHAT: submit the batch job.
# WHY each field:
#   - jobName: your label. Useful when dozens of nightly jobs pile up.
#   - modelId: the model that runs every record. Not every model supports
#     batch. Check per model at build time.
#   - inputDataConfig.s3InputDataConfig.s3Uri: the JSONL file in S3, one
#     complete model request per line (model ID plus body per line).
#   - outputDataConfig.s3OutputDataConfig.s3Uri: where Bedrock writes results.
#     One output JSONL line per input line, in the same order.
# WHAT BREAKS: input lines must each be a complete valid request. One malformed
#   line does not fail the job; it produces an error record for that line.
job = client.create_model_invocation_job(
    jobName="nightly-summaries",
    modelId="arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-haiku-4-5-20251001-v1:0",
    inputDataConfig={"s3InputDataConfig": {"s3Uri": "s3://my-bucket/batch/input.jsonl"}},
    outputDataConfig={"s3OutputDataConfig": {"s3Uri": "s3://my-bucket/batch/output/"}},
)
job_arn = job["jobArn"]

# WHAT: poll until done. Bedrock also emits EventBridge events on completion,
#   which is the production pattern (no polling loop).
# WHY the statuses: Submitted and InProgress mean wait. Completed means results
#   are in S3. Failed, Stopped, or PartiallyCompleted mean check the output for
#   error records. PartiallyCompleted is the trap: some lines succeeded.
while True:
    status = client.get_model_invocation_job(jobIdentifier=job_arn)["status"]
    if status not in ("Submitted", "InProgress"):
        break
    time.sleep(60)
print("batch job finished with status:", status)

    For a single slow request, the async pattern is the same idea. It is at a smaller scale. start_async_invoke on the runtime client returns an invocation ARN. The result lands in S3. This is the exam distinction.

    Batch is many prompts from S3. Async is one slow prompt that nobody waits on. Streaming is tokens to a waiting user.

    Trap

    Batch is not a latency tool.

    The exam offers batch inference for "sub-3-second responses" as a distractor. The service measures batch latency in hours. This is the decision rule. Interactive and fast means real-time.

    Add Provisioned Throughput for guarantees. Non-interactive and hours-OK means batch. The scenario's latency sentence decides. The cost sentence does not decide.

    Common misunderstanding

    Async invocation is not streaming.

    Streaming delivers tokens to a waiting user in real time. Async delivers a complete result later to storage. "User watches the answer appear" means streaming. Use ConverseStream and WebSockets. "Job runs for 10 minutes, nobody waits" is async.

    5. Knowledge Bases: grounding answers in your documents

    As you learned in D1 , chunking and embeddings turn documents into vectors. Knowledge Bases runs that pipeline for you.

    Mechanism

    As you learned in D1, chunking and embeddings turn documents into vectors. Knowledge Bases runs that pipeline for you.

    Why this comes next. You can call the model. You can version your prompts. But the model's knowledge still ends at its training cutoff. Your private documents are not visible to it. This chapter answers where facts come from.

    They come from Knowledge Bases, the grounding layer.

    A model only knows what it learned in training. Your users ask about your documents. Retrieval is the connection between the two.

    Training has a cutoff. It knows nothing private. When answers must come from your documents, there are three options. Fine-tune the model on the documents. This is slow and expensive. It becomes old the day a document changes.

    Paste the documents into the prompt. This works for one page. It fails for ten thousand pages. This is because prompts have size limits. Every call re-pays for the tokens. The pasted copy becomes old.

    Retrieve at query time. Fetch only the relevant passages when the user asks the question. This is fresh. You pay per query. There is no retraining. For "answers must come from our documents," the exam's answer is almost always retrieval.

    Retrieval means to find the passages in your documents that are important for a question. Do this when the user asks the question. RAG (retrieval-augmented generation) means to retrieve first, then generate. The system pastes the retrieved passages into the model's prompt. So, your data forms the basis of the answer. The order stays fixed.

    It is always retrieve, then generate.

    Keyword search is not enough for this. "How do I reset my password" and "change my credentials" have almost no common words. But they mean the same thing. Keyword search misses the second phrasing.

    Meaning-based search finds it. Meaning-based search runs on embeddings (Chapter 2). Similar meanings produce similar numbers. So, "find the relevant passages" becomes "find the nearest numbers."

    Chunking means to split documents into small passages. Do this before you embed them. There are two reasons. First, an embedding captures one passage's meaning well. It captures a whole manual's meaning badly.

    Second, only the relevant passages must enter the prompt. The whole library must not enter the prompt. A typical chunk is a few hundred tokens. There is overlap between neighbors. This prevents cutting a sentence in half.

    A vector store is a database. It holds the embeddings. It finds the nearest embeddings to a query vector. It does this fast and at scale.

    The system stores each chunk's text next to its vector. It also stores source metadata. This metadata includes the document name and page. This allows answers to cite their sources.

    6. Bedrock Agents: Anatomy of an Agent

    As you learned in D1 , a foundation model takes a prompt and returns a completion. An agent wraps that loop with tools, memory, and a plan.

    Mechanism

    As you learned in D1, a foundation model takes a prompt and returns a completion. An agent wraps that loop with tools, memory, and a plan.

    Why this comes next. Knowledge Bases let the model answer from your documents. They do not let it act. They do not allow API calls. They do not allow database writes.

    They do not allow multi-step plans. This chapter introduces the action dimension. This is the anatomy of a Bedrock Agent.

    An agent is a Foundation Model. It includes instructions, tools, and memory. Bedrock Agents is the managed way to build an agent.

    A foundation model (FM) is a large AI model. Training on broad data built it. You access it through an API. Amazon Bedrock is the managed service that hosts Foundation Models. A Bedrock Agent adds four things to a Foundation Model. It adds an agent instruction.

    This is a system-level prompt that tells the agent its role and how to behave. It adds action groups. These are the tools the agent can call. Each action group runs code in a Lambda function or calls an external API described by an OpenAPI schema. It adds a knowledge base (KB). This means attached retrieval.

    It makes your documents searchable. Chapter 5 covers this. It adds guardrails. These are safety filters applied to inputs and outputs.

    Each agent also has an IAM role. IAM (Identity and Access Management) is how AWS controls permissions. The agent's role must grant permission to call the Foundation Model. It must also grant permission to call the Lambda functions behind its action groups and its Knowledge Base.

    A bare model can only answer from its training. A support bot must look up order status in a database. An HR bot must read policy documents and then file a ticket. Without agents, you build the reasoning loop manually. You send a prompt. You parse tool calls.

    You execute them. You feed results back. You repeat this process. Bedrock Agents manages that loop for you. This includes session memory across turns.

    This is the sequence when a user sends a message:

    1. Your application calls invoke_agent on the bedrock-agent-runtime API. It uses an agentId, an agentAliasId, and a sessionId.
    2. The agent adds the agent instruction and the conversation history for that sessionId. It asks the Foundation Model: what is the next step?
    3. The Foundation Model reasons. It returns either an answer or a tool call. This is the ReAct pattern: reason, then act.
    4. The agent invokes the matching action group for a tool call. The action group executor is a Lambda function or an API schema. Lambda runs and returns JSON.
    5. The agent feeds the tool result back to the Foundation Model. It repeats this process until it has a final answer.
    6. The final answer streams or returns to the user. The session state is kept. The next turn remembers the current turn.

    Three lifecycle concepts are important for the exam. Prepare agent: You must run prepare-agent after any configuration change. This includes a new action group or a new instruction. This compiles your changes from DRAFT to PREPARED. If you skip this, the agent silently runs the old configuration. Alias: This is a named pointer to a prepared version.

    It is like a tag.

    Production traffic uses an alias (for example, PROD). It never uses DRAFT. enableTrace: This is a flag on invoke_agent. It returns the agent's reasoning trace. This trace shows which tools the agent chose and why. This is the exam's transparency answer.

    This walkthrough shows how to start an agent turn. The code below uses boto3 (the AWS SDK for Python). It pairs with the orchestration diagram above. Read it in three steps.

    First, build the agent-runtime client. Then, call invoke_agent with the agent ID, the alias ID, a session ID, and the user's text. Then, read the streamed response events and print the final text.

    import boto3

# WHAT: the Bedrock agent-runtime client. invoke_agent lives here, not on
#   "bedrock" (control plane) or "bedrock-runtime" (model invocation).
# WHAT BREAKS: wrong client means no invoke_agent method at all.
client = boto3.client("bedrock-agent-runtime", region_name="us-east-1")

# WHAT: start one agent turn.
# WHY each field:
#   - agentId: which agent. agentAliasId: which prepared VERSION of it.
#     Production uses an alias (PROD), never DRAFT. The alias pins the version.
#   - sessionId: the conversation memory key. Same sessionId continues the
#     conversation; a new one starts fresh with no history.
#   - inputText: the user message for this turn.
#   - enableTrace: True returns the reasoning trace (which tools the agent
#     considered and why). The exam's transparency answer. Costs extra tokens.
# WHAT BREAKS: calling DRAFT in production means untested config serves users.
#   Reusing one sessionId across users leaks conversation history between them.
response = client.invoke_agent(
    agentId="ab-agent123",
    agentAliasId="PROD",
    sessionId="user-42-session-7",
    inputText="Where is my order #12345?",
    enableTrace=True,
)

# WHAT: reading the answer. invoke_agent returns an EVENT STREAM, not a dict.
# response["completion"] yields events: "chunk" (answer text pieces), "trace"
#   (reasoning steps, only with enableTrace), and file events.
# WHY the loop: chunks arrive as they generate. Concatenate them for the full
#   answer. For a chat UI, yield each chunk to the browser as it arrives.
# WHAT BREAKS: treating response["completion"] as a string raises TypeError.
#   It is a stream. You must iterate it.
answer = []
for event in response["completion"]:
    if "chunk" in event:
        answer.append(event["chunk"]["bytes"].decode("utf-8"))
print("".join(answer))

    A knowledge base (KB) gives the agent retrieval-augmented generation. It searches your documents. The documents are in a vector store like OpenSearch Serverless. The agent answers with citations. A guardrail is a set of safety policies.

    Apply the policies to the agent's inputs. Apply the policies to the agent's outputs. You can apply them to both. There are six controls. These are content filters.

    The policy denies these topics. These mean word filters. These mean sensitive information filters. These mean contextual grounding checks. These mean automated reasoning checks.

    Inside one invoke_agent call, the agent's orchestration interleaves all three. The order stays fixed.

    9. Lambda integration patterns: sync, async, streaming, timeouts, concurrency

    How to read this. Three boxes show the three invocation modes. The footer shows the limit: 15 minutes per Lambda.

    Mechanism

    How to read this. Three boxes show the three invocation modes. The footer shows the limit: 15 minutes per Lambda. The main point: A pipeline that waits for humans or has long chains belongs in Step Functions Standard. It does not belong in one Lambda.

    Why this comes next. The GenAI building blocks are ready. These include calls, grounding, and agents. Now, the question is about your code. Where does the connection run?

    This chapter explains Lambda integration patterns. These are the invocations, timeouts, and concurrency rules. They decide if your system survives.

    Lambda connects GenAI on AWS. How you invoke it decides if your application handles real traffic.

    AWS Lambda runs your code without servers. You upload a function. AWS runs it when triggered. AWS bills per millisecond. Three invocation modes are important. Synchronous (RequestResponse): The caller waits for the result.

    Use this for APIs where the user waits for the response. Asynchronous (Event): Lambda puts the event in a queue.

    It returns immediately. Use this for fire-and-forget tasks. An example is processing an uploaded file. Streaming responses: Lambda streams partial output back as the model produces it. It uses ResponseStream. Use this for token-by-token model output.

    The user sees text appear immediately.The default regional quota is 1,000. Reserved concurrency guarantees capacity for one function. Provisioned concurrency keeps instances ready to prevent cold starts.

    Model calls are slow and happen in bursts. A chat application has idle seconds. Then it has a spike of 500 users. Lambda scales to zero. It bursts on demand.

    So, you pay nothing when idle. But a 15-minute limit means Lambda cannot host long waits. It cannot host approvals. It cannot host multi-hour batch jobs. Choosing the wrong invocation mode is the exam's favorite Lambda error.

    Sync via API Gateway: The request thread stays open. API Gateway times out at 29 seconds for REST APIs. So, a synchronous Lambda behind it must finish. This includes the model call.

    It must finish within 29 seconds. Streaming helps perceived latency. But it does not extend the hard limit.

    Async: The event goes to an internal queue. Lambda retries two times on failure. Then it can send the event to a dead-letter queue (DLQ). Use SQS in front for clear control. SQS provides batching, visibility timeouts, and DLQs that you can see.

    Streaming: The function writes parts to the response stream. API Gateway does not support Lambda response streaming on REST endpoints in the classic pattern. So, streaming applications typically use API Gateway WebSockets. Or they use an Application Load Balancer. Or they use Lambda function URLs.

    Cold starts: The first invocation after a period of inactivity pays for container startup. This often takes 100 milliseconds to several seconds for large packages. Provisioned concurrency removes this cost. But it costs money even when idle.

    For GenAI, the model call usually takes much longer than the cold start. So, provisioned concurrency is rarely the solution. It is only the solution if the scenario requires strict latency service level agreements.

    A summarization API gets 10 requests per second at peak. Each model call takes 8 seconds. How many executions must run at the same time? The formula is:

    concurrent executions = requests per second × seconds per request

    Requests per second arrival rate at peak. Seconds per request duration of each execution.

    Worked example. 10 multiplied by 8 equals 80 concurrent executions. This is less than the default of 1,000. This is acceptable. But if a Bedrock throttle slows calls to 60 seconds, the concurrency need becomes 600. This is still acceptable.

    But queuing starts. If traffic increases 20 times to 200 requests per second, and each takes 60 seconds, you need 12,000 concurrent executions. This will cause throttling. The exam solution is not to increase the Lambda limit first. The solution is backpressure and asynchronous processing.

    Put SQS in front. Let the queue absorb the spike. Process at a controlled rate. Tell the client to poll.

    Timeout calculation: A Lambda has a 29-second API Gateway limit. It calls a model. The model streams 100 tokens per second. The answer has 3,000 tokens. This takes 30 seconds.

    Synchronous processing fails. The correct pattern is asynchronous or WebSocket streaming. Return a job ID immediately. Stream tokens over the socket. Store the result in DynamoDB.

    Do not use Lambda for long-running orchestration. A single Lambda cannot handle some scenarios. It cannot handle "wait for human approval." It cannot handle "pause for 2 hours." It cannot handle "runs overnight." Fifteen minutes is a hard limit. The solution is Step Functions (Chapter 11).Or the solution is batch inference (Chapter 3). The exam often hides a wait in a Lambda-like scenario.

    Streaming does not increase timeouts.

For streams longer than 29 seconds, use WebSockets. Or use an asynchronous method with polling. The exam tests this with scenarios like "streaming responses still time out."

    10. API Gateway in front of Bedrock

    Why this comes next. Lambda runs your logic. Users and frontends need a stable entry point.

    Mechanism

    Why this comes next. Lambda runs your logic. Users and frontends need a stable entry point. This entry point must have authentication. It must control the traffic. It must have one unchanging URL.

    This chapter explains API Gateway in front of Bedrock.

    Amazon API Gateway creates managed HTTP, REST, or WebSocket APIs. It provides many services for Bedrock. It gives a stable URL for your application. This URL does not change when you swap models. It controls the traffic.

    You can set rate limits per key or per route. It handles authentication. It uses Cognito user pools, Lambda authorizers, or IAM. It validates requests. It manages usage plans.

    The integration target is usually a Lambda function. This function calls Bedrock. It does not call Bedrock directly.

    Calling Bedrock from a browser or a mobile app has risks. It sends AWS credentials to the client. It does not control the traffic. It does not record the activity. Each model change affects every client.

    API Gateway manages these issues. It is the stable endpoint for the exam. The gateway URL stays fixed. The Lambda reads the model ID from AppConfig. This allows model changes without client redeployment.

    REST/HTTP API plus Lambda: The request hits the gateway. A Lambda authorizer validates the token. This can be Cognito or custom. Lambda calls Bedrock.

    This can be Converse or streaming. The response returns. REST APIs enforce the 29-second integration timeout. HTTP APIs allow 30 seconds.

    WebSocket API: The client opens a persistent connection. Lambda pushes tokens as they arrive from ConverseStream. This is the pattern for long streaming answers. These answers exceed REST timeouts.

    Throttling: Per-route and per-API-key limits protect Bedrock quotas. They protect from one noisy client. A 429 from API Gateway is your throttle. It is different from a Bedrock ThrottlingException.

    Token-limit management: The gateway or Lambda enforces maximum tokens per request. This blocks prompt-injection attempts. These attempts put 100,000 tokens into one call. This blows the budget.

    Retries and timeouts: The gateway can retry idempotent integrations. The Lambda behind it implements exponential backoff on Bedrock throttles. (Refer to topic 16).

    A SaaS copilot serves 5,000 users. API Gateway throttling is set to 100 requests per second steady. It has a 200 burst per API key tier. The Lambda behind it calls Converse. It has a 4,000-token limit per request. The worst-case token burn follows one formula:

    tokens per second equals requests per second multiplied by max tokens per request .

    Requests per second steady throttle rate. Max tokens per request enforced per-request token limit.

    Worked example. tokens per second equals 100 multiplied by 4,000. This is 400,000 tokens per second. The team maps this to their Bedrock quota. They set budget alerts.

    When a customer upgrades tiers, only the usage plan changes. No code deploys. No client updates.

    Mechanism

    Why this comes next. Lambda handles one request at a time. Some workflows span hours. They need human approvals. Lambda's 15-minute limit cannot hold them. This chapter covers Step Functions orchestration.

    It is for long GenAI workflows.

    12. S3 and EventBridge: Event-Driven GenAI Pipelines

    Why this comes next. Step Functions orchestrate workflows. You start these workflows. The other part of production is workflows that start themselves.

    Mechanism

    Why this comes next. Step Functions orchestrate workflows. You start these workflows. The other part of production is workflows that start themselves. They start when data arrives.

    This chapter covers event-driven pipelines. These pipelines use S3 events and EventBridge routing. They also use Bedrock Data Automation.

    Files land in S3. Events fire. Pipelines wake up. This is how GenAI processes data. No one clicks a button.

    Amazon S3 (Simple Storage Service) stores objects. It stores files, documents, videos, and model outputs. Amazon EventBridge is a serverless event bus. It receives events. It routes events to targets based on rules. Lambda and Step Functions work with Amazon EventBridge.

    They make the standard event-driven GenAI pipeline. An S3 upload emits an event. EventBridge routes the event. Processing starts automatically. Supporting services are SQS (Simple Queue Service), SNS (Simple Notification Service), and EventBridge Pipes. SQS buffers events.

    It controls the processing rate. SNS sends out notifications. EventBridge Pipes connects a source to a target. It can filter and enrich data. It needs no code.

    GenAI workloads are bursty and file-shaped. Ten thousand mixed files land per day. Nobody wants a cron job polling S3 every minute. Events give you instant, decoupled reaction. Each file triggers its own processing chain.

    Failures retry independently. Producers never know about consumers. Loose coupling is also the exam's resilience answer. If the extraction step is down, events queue up instead of being lost.

    The event-driven pipeline, stage by stage:

    1. A file lands in S3. S3 emits an ObjectCreated event to EventBridge. This happens via S3 event notifications.
    2. An EventBridge rule matches the event pattern. This pattern includes the bucket name, a prefix like uploads/invoices/, and a suffix like .pdf. It routes to targets. These targets are a Lambda function, a Step Functions state machine, or an SQS queue.
    3. Lambda reads the file. It calls Bedrock Data Automation or a model for extraction. It writes structured output to another prefix or bucket.
    4. That write emits another event. This triggers the next stage.

    The design decouples each stage. Each can scale and fail independently. For ordering or rate control, insert SQS between EventBridge and Lambda. Batch up to 10 messages per invocation.

    Set visibility timeouts longer than the processing time. Attach a dead-letter queue for poison messages. S3 versioning keeps every version of every object. The exam pairs this with audit and rollback scenarios.

    A lender receives 10,000 mixed files per day (PDF, PPT, video). S3 event notifications fire per file. An EventBridge rule routes PDFs to the document-extraction state machine. It routes videos to the transcription path. Peak hour brings 2,000 files in 10 minutes. This is about 3.3 events per second.

    Lambda concurrency per file is acceptable. The Bedrock Data Automation async jobs queue behind service quotas. SQS buffers with a 5-minute visibility timeout. A poison PDF crashes extraction.

    It retries 3 times. Then it lands in the DLQ for inspection. Nothing is lost. The 9,999 good files are not affected.

    Why this comes next. One mile remains: the code that already exists. SDKs, retries, throttles, structured output, the reliability layer between your app and Bedrock. This chapter closes the volume. It is at the last mile.Production traffic needs retries, backoff, fallbacks, and traces.

    The AWS SDK (boto3 in Python, and equivalents in every major language) is how applications call Bedrock. There are two clients. bedrock-runtime is for inference (Converse, InvokeModel). bedrock-agent-runtime is for agents. Reliability patterns are around those calls. exponential backoff with jitter (If a throttle occurs, wait 1 second. Then wait 2 seconds. Then wait 4 seconds. Add random jitter to each wait.

    This prevents a fleet of clients from retrying at the same time. Use fallback models. If the primary model throttles or errors, retry with a smaller model. Or retry with a different model.Or serve a cached response. This is graceful degradation). timeouts and circuit breakers (Limit how long you wait. Stop calling a failing dependency after N failures.

    Fail fast until it recovers). X-Ray tracing (Use distributed traces across API Gateway to Lambda to Bedrock to KB. This lets you see which hop is slow). model invocation logging (Bedrock can log requests and responses to S3 or CloudWatch. KMS can encrypt this. This is for forensics. In compliance environments, restrict or disable it.

    Logs can contain PII).

    Bedrock is a shared service with quotas. Throttles (ThrottlingException) are normal at scale. They are not bugs. An app without retries turns every throttle into a user-facing error.

    An app with naive retries (immediate, synchronized) turns one throttle into a retry storm. This makes it worse. The exam tests whether you build the disciplined version: backoff, jitter, fallback, and observability.

    The SDK signs every request with SigV4 using IAM credentials. Least-privilege IAM: the app's role allows only bedrock:InvokeModel on the specific model ARNs it needs, not bedrock:*.

    The SDK's built-in retry handler already retries throttles with exponential backoff. Production code configures it: max attempts (often 3 to 5 for interactive paths), and distinguishes retryable errors (throttling, 5xx) from fatal ones (validation errors, access denied).

    On repeated failure, the circuit breaker opens. Calls fail fast for a cooldown period. This prevents hammering Bedrock. A fallback serves: a smaller model, a cached answer, or a graceful "try again" message.

    X-Ray segments wrap each hop. CloudWatch metrics (Invocations, InputTokenCount, OutputTokenCount, InvocationThrottles) feed dashboards and anomaly alarms on token-spend spikes.

    Access errors have a known misleading shape. AccessDeniedException can mean the model is not available in the region. It does not always mean a bad policy. The debug order is: check region availability first, then the IAM policy.

    A checkout-time recommendation call has a 2-second budget. The app configures: SDK timeout 1.5s, 2 retries with backoff (100ms, 200ms plus jitter), then fallback to a cached "popular items" response. P99 path: primary model answers in 800ms. Throttle path: 100ms wait, retry, 800ms answer, total about 1.7s, still inside budget.

    Double-throttle path: fallback served from ElastiCache in 20ms. The user never sees an error. CloudWatch counts the fallback rate. This lets the team buy Provisioned Throughput if fallbacks exceed 1%.
