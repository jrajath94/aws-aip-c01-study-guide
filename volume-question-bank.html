Domain 1: Foundation Model Integration, Data Management, and Compliance (31% of the exam, 61 questions)

Decision reference. Climb in order. Stop at the cheapest ladder rung that works.

1
Prompt engineering: New format, tone, few-shot (examples given in the prompt), chain-of-thought (asking the model to reason step by step). No new knowledge.
2
RAG (retrieval-augmented generation) / Knowledge Bases: Private, current, or cited facts the model was not trained on.
3
Agents: Actions: API calls, databases, multi-step tool use, session memory.
4
Fine-tuning: New behavior baked into weights. Labeled data in S3, then usually Provisioned Throughput.
5
Custom model: Last resort. Out of scope for this exam as a build task.

How to read this diagram.

  1. Do you need format, tone, or examples only? Stay on ladder rung 1: zero infrastructure.
  2. Do you need private, current, or cited facts? Move to ladder rung 2.
  3. Does the system need to call APIs, query databases, or chain tools? Go to ladder rung 3.
  4. Do you need a repeatable behavior or voice that the base model does not have? Rung 4: Put it into the weights with labeled data.
  5. Do you want a full custom model? Rung 5 is almost never the correct answer on the exam. Distractors like this answer.
  6. If this ladder breaks (you skip rungs), you pay training costs for a retrieval problem. Or you pay retraining costs for a prompt problem.

  • E) Latency percentiles as the quality gate. Latency is a performance metric. It is not an answer-quality metric.

Why A, B is correct: Context relevance and coverage measure retrieval quality. (Did we get the correct articles?) Faithfulness and citation precision measure generation quality. (Are claims supported? Do citations resolve?) If you mix them (faithfulness for retrieval, relevance for generation), you give failures to the wrong layer. This sends debugging to the wrong layer.

The trap AWS set here: Stage-to-metric mapping. Retrieval metrics and generation metrics are different sets. Swapping them sends debugging in the wrong direction.

D4 · MEDIUM · ONE ANSWER, q-d4-207 · 4.3 Cost monitoring Q193. A team calls several Bedrock models with large document contexts.   • A) Estimate the input token count before each Bedrock call. Alert when it is near the model's documented limit.
  • B) Set a CloudWatch alarm on the Bedrock InputTokenCount metric. The alarm pages when the average crosses 90 percent of the limit. The metric is sent after the call runs. An oversized request fails first. Then the alarm fires. This is reactive. The stem asks for proactive.
  • C) Catch the ValidationException from oversized requests. Retry with a truncated prompt. The stem rules out the retry-after-failure pattern. The request already failed. The user already waited.

  • B) Run LLM-as-a-judge scoring. Do this on the top candidate's outputs. This assesses summary quality at scale.
