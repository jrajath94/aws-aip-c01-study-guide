Unit1

Unit 1 · Failures

What can go wrong: the four failures

From the lesson Section 1

Four failures built every control in this volume. Failure 1: the confident wrong answer. A model states a false fact with full confidence. The lesson case is a refund claim of 3 to 5 days against a policy of 5 to 7 days. Failure 2: instructions from the wrong author. A hidden instruction in a pasted document or a tool output steers the model. The direct form is a jailbreak. The user tries to break the system prompt rules.

Failure 3: personal data flowing through the model. Names, addresses, phone numbers, and card numbers pass into prompts and out of answers. Failure 4: harmful, off-brand, or non-compliant outputs. The output harms a user or breaks a rule. The map: every failure points to its control. Each later section names the control for one failure class.

RAG alone stops no failure on this list. A model can misread a chunk, merge two chunks, or fill a gap with a plain invention. Governance is the process that gives a real answer when a regulator asks what took place.

Unit 2 · Guardrails

One policy object, six policies

From the lesson Section 2

A guardrail is one named policy object in Bedrock. The object holds six policies. The six policies are content filters, denied topics, word filters, sensitive information filters, contextual grounding checks, and Automated Reasoning checks.

One policy object, six policies. The request path: input check, model call, output check. A guardrail evaluates input first. The model generates text next. The guardrail evaluates output last. The six policies at a glance give one job per policy. No policy does the job of a second policy.

A version is a frozen snapshot of the guardrail setup. Production traffic uses a version. Production traffic never uses the draft. A trace record states which policy fired and why. The trace passes through the guardrailConfig field in Converse. Model safety training alone is never the full answer. Base training knows no product rules. A guardrail holds the rules of one organization.

6 policiesheld in one guardrail policy object
Nugget 2 · Six policies in one object From the lesson Section 2
The lesson

One guardrail object holds six policies, from content filters to Automated Reasoning checks.

Why it matters. Teams that treat a guardrail as one switch miss five controls. Each policy answers a distinct scenario verb.

Transfer. Learn the six policy names as one list. Match the verb in the scenario to one name.

Unit 3 · Placement

3. Where Guardrails apply

From the lesson Section 3

Where the guardrail sits decides what the guardrail can see. The five attachment points are inline on model calls, standalone on any text, on Knowledge Base answers, on agent outputs, and inside prompt flows.

ApplyGuardrail is the standalone API. The API screens any text against a guardrail. No model call takes place. A team with a model on SageMaker can screen a prompt before the send and screen the answer on return. The model stays in place.

Agent coverage has one gap. A guardrail on an agent reads the user input and the final response. The guardrail does not read each tool call inside the reasoning loop.

Unit4

Unit 4 · Filters

4. Content filters and prompt attack detection

From the lesson Section 4

Content filters screen for toxicity. Six categories, one sensitivity dial each. The six categories are hate, insults, sexual, violence, misconduct, and prompt attack. Each dial takes NONE, LOW, MEDIUM, or HIGH. HIGH blocks even mild content.

Prompt attack: the jailbreak detector. The prompt attack category finds jailbreak and injection attempts in inputs. A tutor for children needs violence, sexual content, and prompt attack at HIGH on input and output.

Over-filter work harms a product. Every dial at HIGH blocks good content with the bad. Harmful content in a scenario points to content filters. A must-not-discuss limit points to denied topics.

6 dialsone sensitivity dial per content category
Nugget 3 · Six dials, four levels From the lesson Section 4
The lesson

Six content categories each carry a dial with NONE, LOW, MEDIUM, and HIGH levels.

Why it matters. One global level for all categories either leaks harm or blocks good text. Per-category levels fit per-category risk.

Transfer. Set a control per risk class. A single blunt level serves no class well.

Unit 5 · Topics

5. Denied topics and word filters

From the lesson Section 5

Denied topics: banning ideas, not words. A denied topic names a subject area in plain words, such as medical diagnosis or investment advice. The control judges sense. A paraphrase fails as well. A denied topic has no severity dial.

Word filters: banning literal strings. A word filter holds exact words and phrases. The filter has no fuzzy match and no stem match. A brand case with two banned strings, a project code name and a rival name, fits a word filter with exact precision.

A word filter fails for investment advice. Advice in fresh words holds no listed string. The sense-based denied topic is the fit control.

Unit6

Unit 6 · Privacy filters

6. Sensitive information filters and the PII pipeline

From the lesson Section 6

A sensitive information filter finds personal data by entity type. The filter does not match raw strings. Each entity type takes BLOCK or MASK. BLOCK refuses the full request or response. MASK swaps the value for a placeholder and lets the text pass.

PII by entity type, not by string. The three-stage PII pipeline runs Macie at rest, Comprehend in real time, and guardrail filters at inference. Macie finds personal data in S3. Macie does no request-path work. Comprehend detects personal data in live text. The guardrail filter enforces BLOCK or MASK at the model boundary.

BLOCK fits data that must never pass through the system. MASK fits text that stays useful with the value hidden, such as a card dispute note with the card number masked.

3 stagesMacie, Comprehend, guardrail filters, in order
Nugget 4 · Three stages for personal data From the lesson Section 6
The lesson

Macie at rest, Comprehend in real time, guardrail filters at inference: three stages, three jobs.

Why it matters. One tool in the wrong stage gives a false sense of cover. A rest scanner cannot guard a live chat.

Transfer. Place each privacy tool at the stage the tool was built for. Test each stage apart.

Unit 7 · Checks

7. Contextual grounding checks and Automated Reasoning checks

From the lesson Section 7

Contextual grounding: is it supported by the source? The check scores support from 0 to 1 against a threshold a team sets. A low score marks an answer the source fails to support. Automated Reasoning: does it violate the policy? The check tests an answer against a formal policy with fixed logic. The check runs in detect mode only. Detect mode returns findings such as VALID or INVALID. Detect mode blocks no answer on its own power.

The split is the core distinction of this domain. Invented facts need a grounding check. A broken formal rule, such as a refund cap in a written policy, needs Automated Reasoning.

Grounding proves support, not truth. A wrong source chunk yields a well-grounded wrong answer. Source quality stays a separate duty.

Unit8

Unit 8 · Defense

8. Defense in depth: injection and jailbreak defense

From the lesson Section 8

Two attacks, different doors. A jailbreak comes direct from the user. An indirect injection comes from a tool output, a retrieved chunk, or a web page. The user in the second case may be innocent.

The four-layer stack runs in order. A Comprehend pre-filter screens input. Bedrock Guardrails screen input and output. A Lambda post-processor enforces business rules on the response. An API response filter guards the edge. What the tooling cannot do matters as much. Prompt attack detection is pattern-based and probabilistic. A claim of full injection prevention is always wrong on this exam.

An agent that reads untrusted pages needs post-process work and human approval on actions. An input filter cannot see poison inside page content that arrives later.

4 layerspre-filter, guardrails, post-processor, edge filter
Nugget 5 · Four layers in order From the lesson Section 8
The lesson

The defense stack runs a pre-filter, guardrails, a post-processor, and an edge filter in order.

Why it matters. Each layer catches a class the prior layer misses. One layer alone leaves the other classes open.

Transfer. Stack controls with distinct catch classes. Count a control once per class the control covers.

Unit 9 · Data plane

9. The data security plane

From the lesson Section 9

IAM: who may call what. Least privilege gives each identity the permissions the identity needs and no more. KMS at rest, TLS in transit. A customer managed key gives the team control, rotation, and revocation. PrivateLink: Bedrock without the internet. VPC interface endpoints keep Bedrock traffic off the public internet.

Privacy and data residency turn on geography. Region choice sets where data can sit. Encryption changes no geography. A cross-region inference route moves prompt and response data across regions. A residency rule can bar that route outright.

CloudTrail vs invocation logging: two logs, two jobs. CloudTrail records who called which API and when. The record holds metadata and no prompt content. Model invocation logging records prompt and response content. The content log is opt-in and goes to S3 or CloudWatch. The plane summary is short. IAM controls who. KMS encrypts what. The VPC isolates where. Logs prove the full chain.

2 logsCloudTrail for actors, invocation logs for content
Nugget 6 · Two logs, two jobs From the lesson Section 9
The lesson

CloudTrail answers who did what. Invocation logging answers what was said.

Why it matters. A team that reads one log for both jobs gets half an audit. The gap shows up at the worst time, in a formal review.

Transfer. Name the audit question first. Pick the log that holds that answer.

Unit 10 · Governance

10. Governance and compliance

From the lesson Section 10

Model cards: documentation, not a control. A model card is a structured versioned record. The card states intended use, limits, training data, and evaluation results. A card stops no bad output. A card proves a team knew the limits.

Data lineage: which data produced this answer. Stored citations link an answer to chunks. Chunks map to versioned documents through metadata tags. Documents map to catalog sources. CloudTrail shows who asked. Audit and continuous monitoring close the loop. A one-time evaluation before launch is never enough. Fairness and safety drift as the world changes.

Compliance framework alignment maps controls to a framework such as the NIST AI Risk Management Framework with Govern, Map, Measure, and Manage steps. AWS Artifact holds AWS compliance proof for the shared responsibility model. No AWS service makes a team compliant. Compliance is controls plus proof plus process.

Unit11

Unit 11 · Responsible AI

11. Responsible AI, evaluation, and agent governance

From the lesson Section 11

Transparency: decisions you can inspect. Three forms count. Reasoning traces show steps. Confidence signals show grounding and retrieval scores. Citations give source proof. Fairness and bias detection use SageMaker Clarify for bias metrics.

Human in the loop puts a person before an action takes effect. Governance of agents: action group approval flows. An agent that issues refunds returns control to the application before execution. A manager approval step routes through Step Functions. Step Functions issues a task token and waits for the human call.

Model evaluation for safety runs as a trio. Programmatic checks, judge model checks, and human review run once as a launch gate. The trio then runs on a schedule as monitor work.

3 checksprogrammatic, judge, human, as gate and monitor
Nugget 7 · The evaluation trio runs twice From the lesson Section 11
The lesson

Programmatic, judge, and human checks run once as a gate and then on a schedule as monitors.

Why it matters. A launch-only check misses drift. The world moves and the score from launch day decays in silence.

Transfer. Gate at launch and monitor after launch. One run proves a day. A schedule proves a trend.

Illustration Step through one guarded request. Open one step at a time.

Step 1 · Input check

Content filters, denied topics, word filters, and personal data filters screen the user message.

Step 2 · Model call

The model reads the screened message and any retrieved context, then drafts an answer.

Step 3 · Output check

Grounding and policy checks score the draft. Filters screen the draft text.

Step 4 · Release or block

A pass releases the answer. A block returns the guardrail message and writes a trace record.
