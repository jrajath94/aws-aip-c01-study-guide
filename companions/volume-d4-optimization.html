    01. On-demand inference pricing and token economics

    On-demand inference bills per token with no commitment. Idle hours cost zero. Input tokens cover the system prompt, history, tool data, and the user message.

    Mechanism

    From the lesson Topic 01

    On-demand inference bills per token with no commitment. Idle hours cost zero. Input tokens cover the system prompt, history, tool data, and the user message. Output tokens bill at a higher rate than input tokens.

    A worked example in the lesson prices one call from token counts and per-token rates. The silent cost driver is history. Each turn rebills the full conversation history as input tokens. A long chat costs more per turn even with no model change.

    On-demand is the cheapest choice for spiky, irregular, or low traffic. Reserved capacity charges for idle hours. Spiky traffic wastes that charge.

    02. Token efficiency and prompt optimization

    The free lever, pulled first. Token efficiency means the fewest tokens that still complete the job.

    Mechanism

    From the lesson Topic 02

    Compression is a process, not one edit. A team cuts tokens, evaluates quality, and cuts again. A cut past the quality line trades cost for wrong answers. The gain compounds. Fewer tokens make each later lever work on a smaller base.

    Prompt caching

    The discount for static prefixes. Prompt caching bills repeated static input tokens at a lower input rate.

    Mechanism

    From the lesson Topic 03

    The discount for static prefixes. Prompt caching bills repeated static input tokens at a lower input rate. A cache point marks the end of the cached prefix. The first call pays a small cache-write surcharge. Later calls read the prefix at the discount rate.

    The default cache life is near 5 minutes. An expired cache needs a fresh write. Any change before the cache point voids the hit. A timestamp at the start of a prompt is the classic fault. Dynamic fields belong after the cache point.

    Prompt caching is a cost control, not a capacity control. The feature gives no relief at a throttle limit. Throttle relief needs reserved capacity or rate control.

    Semantic caching

    Answering from memory instead of the model. A semantic cache stores past answers. A new question gets an embedding.

    Mechanism

    From the lesson Topic 04

    Answering from memory instead of the model. A semantic cache stores past answers. A new question gets an embedding. Cosine similarity compares the new embedding with cached embeddings. A score at or above a threshold, such as 0.95 in the lesson case, counts as a hit. A hit returns the stored answer with no model call.

    The hit rate decides value. A FAQ bot with repeat questions in fresh words gains cost and latency wins. A personal recommendation engine has near-unique queries. The hit rate falls to near zero and the cache adds cost with no gain. A team measures the hit rate on real traffic before adoption.

    Semantic caching and prompt caching differ in one point. Semantic caching removes the call. Prompt caching discounts input tokens on a call that still runs.

    0.95 the lesson similarity threshold for a cache hit Nugget 3 · Measure the hit rate first From the lesson Topic 04 The lesson A semantic cache pays only at a real hit rate, and unique queries drive the hit rate to near zero. Why it matters. A cache design sold on hope adds a store, a threshold, and a stale-answer risk for no return. Transfer. Measure repeat share on live traffic before you build a cache.     05. Retrieval tuning: fewer, better chunks

    Every chunk is input tokens. Retrieval tuning sends the fewest context tokens that still hold the answer.

    Mechanism

    From the lesson Topic 05

    Every chunk is input tokens. Retrieval tuning sends the fewest context tokens that still hold the answer. A top-k cut is the cheapest lever. A drop from 10 chunks to 3 chunks cuts retrieval tokens by 70 percent in the lesson case, where the answer sits in the top three.

    A reranker scores candidate chunks and passes the best few to the prompt. Metadata filters shrink the candidate set before vector search. A smaller set needs a smaller top-k.

    More chunks are the wrong fix for wrong answers. Extra chunks raise cost and add noise. Noise lowers answer quality. The fix order is top-k, rerank, then chunk design.

    Mechanism

    From the lesson Topic 06

    Match the model to the difficulty. Right-size work sends simple requests to a cheap model. A cascade escalates hard requests to the flagship. A prompt router is the managed form. The router sends each prompt to the cheapest model that can handle the prompt.

    07. Fine-tuning a small model for your workload

    The most expensive lever, for the most repeated work. Fine-tuning trains a behavior into weights.

    Mechanism

    From the lesson Topic 07

    The most expensive lever, for the most repeated work. Fine-tuning trains a behavior into weights. The lever pays at a narrow, stable, repeated task at huge volume. One-time training cost plus an hourly serve commitment must stay below the flagship token spend the change saves.

    A custom model needs Provisioned Throughput before calls work in most cases. The serve commitment runs each hour of the term. A low-volume case loses money.     08. Latency vs throughput: streaming and perceived speed

    Perceived latency is the metric that matters. Perceived latency turns on time to first token, or TTFT.

    Mechanism

    From the lesson Topic 08

    Perceived latency is the metric that matters. Perceived latency turns on time to first token, or TTFT. TTFT covers prompt process time plus the wait for the first token. Total latency runs to the last token. Streaming sends tokens as the model produces tokens. Users see words in near one second. Streaming changes no total time.

    Inference parameters: temperature, top-p, top-k, max tokens. Temperature 0 is the most fixed setting. Temperature is a randomness control. Temperature is no cost control and no latency control.

    A hard sub-3-second guarantee needs more than streaming. A smaller model, reserved capacity, and streaming form the full answer. Streaming alone improves feel and leaves the guarantee unmet.

    Batch inference

    Overnight work at roughly half price. Batch inference runs prompts from S3 over hours. The price sits near 50 percent below on-demand for the same model.

    Provisioned Throughput

    Buying certainty by the hour. Provisioned Throughput reserves capacity per model unit per hour.

    Mechanism

    From the lesson Topic 10

    Buying certainty by the hour. Provisioned Throughput reserves capacity per model unit per hour. Terms run from 1 month to 6 months. Each model unit holds a fixed process capacity for one model. Autoscale rules add or drop units as use crosses thresholds, inside set limits.

    Code must call the provisioned model ARN. A call to the base model ID stays on the on-demand pool and throttles there. The ARN fault is the most tested fault in this topic.

    The hybrid pattern is the production standard. Reserved capacity serves the predictable base load. On-demand serves spikes. A team provisions for the floor and never for the peak.

    11. Inference profiles and cross-region routing

    One identifier, many regions. An inference profile routes a request to a model in one of several regions.

    Mechanism

    From the lesson Topic 11

    One identifier, many regions. An inference profile routes a request to a model in one of several regions. Geographic prefixes bound the route. The us., eu., apac., and global. prefixes keep data inside residency lines. An application profile wraps a system profile and adds tags and metrics.

    Profiles pool capacity across regions. A throttled region fails over to a second profile region with no client change. Residency stays a scope decision. EU data stays in EU regions under an eu. profile.

    Three route ideas stay distinct. Profiles route across regions for availability. Prompt routers route by complexity for cost. Provisioned Throughput reserves capacity for a guarantee.

    12. Rate limits, quotas, and throttling with retries

    Throttling is a signal, not a bug. A ThrottlingException means a client passed a quota. The client answer is exponential backoff with jitter.

    Mechanism

    From the lesson Topic 12

    Throttling is a signal, not a bug. A ThrottlingException means a client passed a quota. The client answer is exponential backoff with jitter. Waits run near 1 second, then 2 seconds, then 4 seconds. Jitter adds a random offset so clients avoid a joint retry.

    API Gateway usage plans cap rate per client and protect the backend from one loud client. A quota increase fits sustained real growth. A brief sub-minute spike is a retry case. A quota request for a spike is the wrong answer.

    Retries need a ceiling. A max attempt count plus a fallback path ends a storm. A circuit breaker pattern from Domain 2 pairs with backoff at scale.

    13. CloudWatch metrics for Bedrock

    From the lesson Topic 13
