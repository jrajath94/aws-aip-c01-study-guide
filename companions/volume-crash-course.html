Unit 1 · L0 foundation ramp

L0: the foundation ramp, AI minimums and AWS minimums

From the lessonL0 · The problem

The problem is simple. Every later lesson names AI terms and AWS services without a fresh teach. A reader with no ramp stops cold at the first token or the first Lambda mention. This lesson builds the minimum map first.

From the lessonL0 · Mental model

The mental model starts with the token. A model reads tokens, not words. The source splits one word into two tokens as its first example. Billing counts tokens in and tokens out, so tokens are money. The context window caps the tokens in one request. Input plus output must fit inside that cap. An embedding places a text piece on a meaning map, and nearness on the map means similar meaning. Temperature is a randomness dial. Top-p and top-k trim the candidate set before the pick. An agent is a model that calls tools in a loop until the job ends.

From the lessonL0 · Mental model

Three ways change what a model does, from cheap to costly. Prompt work changes the instructions only. RAG pastes fresh facts into the prompt at query time and leaves the weights alone. Fine-tuning trains the weights on your examples and bakes behavior in. The rule for the whole course sits here: pick the cheapest rung that solves the problem.

From the lessonL0 · Worked example, minimum map

The worked example walks tokens and the window with real counts. The minimum map then names the AWS parts. EC2 is a rented virtual server that runs until you stop it. Lambda runs one function on one event and then vanishes, with a hard cap of minutes per run. Step Functions is a workflow engine that can wait hours and call services in order. S3 is durable object storage and the home for documents.

From the lessonL0 · Limits, traps, closest alternative

Limits and traps close the concept pass. The closest alternative section asks which compute fits a stated job, server, function, or workflow. The valid but inferior section then splits answers that work yet lose from answers that break a hard rule. Check yourself gives original exam-style practice. Deep reference and evidence notes close the lesson, and that ten-part rhythm repeats in every lesson of this volume.

Unit 2 · L1 requirements and models

L1: requirements, model selection, resilience, the customization lifecycle

From the lessonL1 · The problem

The problem is order. Teams pick a model first and never pick a technique. A fine-tune where RAG fits burns months of data work and goes stale at the first manual update. A giant model where a small one fits burns money on every request. The lesson covers skills 1.1.1 to 1.1.3 and 1.2.1 to 1.2.4.

From the lessonL1 · Mental model

The mental model is an escalation ladder. The rungs run prompt work, then RAG, then fine-tuning, then training from scratch. The last rung sits out of scope for this exam. Climb one rung only when the lower rung fails a named test. A proof of concept tests three things before scale: feasibility, speed, and value. A proof on Bedrock costs little and answers all three in days. Skill 1.1.3 then turns the winner into standard reusable parts, checked against the Well-Architected Framework GenAI Lens.

4 axescapability, cost, latency, and regional availability in L1
Nugget 1 · From the lesson L1 · Mental model
The lesson

Decide the technique first, the model second, the plumbing third. Model choice is a trade across four axes: capability, cost, latency, and regional availability.

Why it matters. A model that wins on capability but has no service in your Region loses by default. The axis check comes before the benchmark.

Transfer. Name the decision order before you compare options. Most bad picks are good options chosen at the wrong step.

Unit 3 · L2 data pipelines

L2: data validation and processing pipelines

From the lessonL2 · The problem

The problem is trust. A model reads what you feed it and answers with full confidence. A corrupt PDF, a mislabeled audio file, or a table with shifted columns yields a fluent wrong answer. No prompt trick fixes data that the pipeline never checked. The lesson covers skills 1.3.1 to 1.3.4.

From the lessonL2 · Mental model

The mental model is a kitchen prep line with four stations. Validation asks if the data is fit to use: complete, fresh, free of duplicates, correct in type. Processing asks if the data has the shape the model can read: audio becomes text, scans become text, tables become rows. Formatting asks if the request body matches the target model, and providers differ. Enrichment asks if the pipeline can add signal before the call: entities, standard spellings, clean text.

8%of 10,000 PDFs rejected at validation in the L2 example
Nugget 2 · From the lesson L2 · Worked example
The lesson

Quality gates belong before inference, not after it. In the worked example, validation rejects 800 of 10,000 PDFs before any money goes to the model.

Why it matters. An 8 percent reject rate at the gate is cheap. The same files at the model become paid tokens and confident errors.

Transfer. Put the cheapest check at the earliest point where the defect is visible. Late checks pay full price for bad input.

Unit4

Unit 4 · L3 retrieval core

L3: vector stores and retrieval mechanisms, the RAG core

From the lessonL3 · The problem

The problem is frozen knowledge. A model answers from weights fixed at train time. Ask about a policy change from last month or a private runbook, and the model invents a fluent answer with no basis. The cost is a wrong answer with total confidence. This is the largest lesson in D1, with skills 1.4.1 to 1.4.5 and 1.5.1 to 1.5.6.

From the lessonL3 · Mental model

The mental model is a library. An embedding gives every chunk a coordinate on a meaning map. The vector store is the card catalog, sorted by meaning rather than by alphabet. Retrieval walks in with the question coordinate and pulls the nearest chunks. RAG pastes those chunks into the prompt, so the model reasons from your text. Two searches exist. Keyword search matches exact words and misses paraphrase. Semantic search matches meaning and misses exact codes and names. Hybrid search runs both and merges the lists, and a reranker re-scores the merged list.

300 tokensthe chunk size in the L3 worked example
Nugget 3 · From the lesson L3 · Worked example
The lesson

The pipeline splits documents into 300-token pieces, embeds each piece, and stores the vectors in an index such as OpenSearch Serverless.

Why it matters. Chunk size decides what retrieval can see. Bad chunk splits break tables, and a mix of embedding models between ingest and query breaks the match.

Transfer. Debug retrieval before generation. If the fetch misses, the answer invents, and no model swap fixes a fetch miss.

Unit 5 · L4 prompt governance

L4: prompt engineering, management, and governance

From the lessonL4 · The problem

The problem is control. Prompts start as strings pasted into code. Six months later, no one can say which version answered a customer. A careless edit ships with no test, and a small tweak drops accuracy in silence. The lesson covers skills 1.6.1 to 1.6.6.

From the lessonL4 · Mental model

The mental model treats a prompt as production code. The lifecycle runs draft, save an immutable version, test a variant, deploy by version ARN. A version gives rollback. A variant test changes one thing at a time, so the metric names the cause. A deploy by ARN needs no code release. Bedrock Prompt Management is the version store. Prompt Flows is the visual builder for chains with branches. Guardrails is the policy layer, with a full teach later in D3.

From the lessonL4 · Craft and worked example

Prompt craft uses named techniques. Role definition tells the model its job. Few-shot gives input and output examples. Chain-of-thought asks for step-by-step reason steps and costs more output tokens. Structured output forces machine-readable answers via a JSON schema. Feedback loops feed bad outputs into the next revision. The worked example pairs a regression gate with a prompt bloat case: more prompt text is not free, and the gate proves each edit.

From the lessonL4 · Alternatives and traps

The closest alternative weighs Prompt Management against S3 templates and against hard-coded strings. Hard-coded text forces a redeploy per edit and loses history. Limits and traps, the valid but inferior split, check yourself, deep reference, and evidence notes close the lesson.

Unit6

Unit 6 · L5 agentic AI

L5: agentic AI, agents, safeguards, human in the loop, MCP

From the lessonL5 · The problem

The problem is sequence. A model answers one question per call. Real jobs need steps in order: find the order, check the policy, refund the card. One prompt cannot run that sequence. The lesson covers skills 2.1.1 to 2.1.7 and 2.5.5.

From the lessonL5 · Mental model

The mental model is a junior analyst with a phone and a rulebook. The loop runs reason, act, observe, repeat. Reason: the model picks the next step, and a weak model picks wrong tools. Act: the agent calls a tool, and a miss in IAM permission fails the call. Observe: the agent reads the tool result, and an ignored error loops forever. Repeat: the cycle runs until the model answers, hits a step cap, or asks for approval. ReAct names this pattern, and the written trace keeps each step open to inspection.

4 stepsreason, act, observe, repeat in the L5 agent loop
Nugget 4 · From the lesson L5 · Mental model
The lesson

The agent loop has four steps: reason, act, observe, repeat. No step cap means runaway cost, so the cap is a safety part, not a detail.

Why it matters. The model keeps no memory between calls. Session state is the scratchpad, and persisted memory holds user facts and standing rules across sessions.

Transfer. Every loop you ship needs a stop rule and a trace. A loop with no stop rule is a bill with no cap.

Unit 7 · L6 deployment and APIs

L6: model deployment strategies and FM API integrations

From the lessonL6 · The problem

The problem is fit. Teams pick one call shape and one capacity shape for every job. A chat bot that waits for the full answer feels slow. A batch job that streams ten million rows wastes money. A steady fraud check on on-demand price overpays each day. The lesson covers skills 2.2.1 to 2.2.3, 2.4.1 to 2.4.4, and 2.5.1.

From the lessonL6 · Mental model

The mental model is a power contract. On-demand is the wall socket: plug in and pay per unit. Provisioned throughput is a leased generator: a fixed price, yours at all hours. Batch is the night-shift crew: cheapest, with results in the morning. Self-hosted on SageMaker is your own plant: full control, and you run it. The call shape is a second choice: one-shot, chat, stream, or RAG in one call.

350,000requests per month at the L6 break-even point
Nugget 5 · From the lesson L6 · Worked example
The lesson

One provisioned unit at 7,000 dollars per month breaks even with on-demand at 0.02 dollars per request at 350,000 requests per month.

Why it matters. Above the break-even count, the provisioned unit wins. Below it, on-demand wins. The model assumes steady use, so spiky traffic pays for idle hours.

Transfer. Convert every capacity debate into one break-even count. A count ends arguments that adjectives cannot end.

L7: enterprise integration, CI/CD, the GenAI gateway, dev tools

From the lessonL7 · The problem

The problem is scale across teams. One team with direct Bedrock calls works. Fifty teams with direct calls means fifty auth setups, fifty log formats, and no cost control. 240,000messages of backlog after ten minutes in the L7 spike
Nugget 6 · From the lesson L7 · Worked example
The lesson

A sale spike at 500 requests per second against a drain rate of 100 per second builds a backlog of 240,000 messages in ten minutes.

Why it matters. SQS holds the queue and the app answers queued in place of a failure. An alarm on the age of the oldest message pages the team before answers go stale.

Transfer. Queue depth is a capacity decision. Do the subtraction early: inflow minus drain, times the window, is the backlog you must hold.

Unit 9 · L8 safety controls

L8: input and output safety controls, defense in depth

From the lessonL8 · The problem

The problem is hostile text. Users type attack prompts. Retrieved pages hide orders. The model reads each token the same way, so hostile text can read as a command. One check misses what another catches. The lesson covers skills 3.1.1 to 3.1.5.

From the lessonL8 · Mental model

The mental model is an airport checkpoint line: an ID check, a bag scan, a body scan. One check misses some threats. The stack catches more. The threat list has five names. A prompt injection tries to override the system instructions. An indirect prompt injection hides the order inside content the model reads. A jailbreak uses craft input to break the safety train of the model. Data exfiltration leaks secrets inside an answer. Tool abuse shapes tool arguments toward a dangerous call.

5 threatsthe named threat list in L8
Nugget 7 · From the lesson L8 · Mental model
The lesson

Five threats drive the safety design: prompt injection, indirect prompt injection, jailbreak, data exfiltration, and tool abuse.

Why it matters. L5 set the trust rule: tool output is data, never instructions. L8 applies that rule to every input channel, so retrieved text enters the model as quoted data only.

Transfer. Trust follows provenance, not content. Text from an untrusted source stays data even when it reads like an order.

Unit 11 · L10 cost and performance

L10: cost optimization, performance, monitoring

From the lessonL10 · The problem

The problem is the first production bill. Token totals arrive with no breakdown, so no one can name the prompt or the tenant behind the spend. Latency looks fine in the demo and breaks at launch, because the average hides the tail. Quality slips in silence as each prompt edit changes answers with no test on watch. The lesson covers skills 4.1.1 to 4.1.4, 4.2.1 to 4.2.6, and 4.3.1 to 4.3.6.

From the lessonL10 · Mental model

The mental model asks three questions. Where does the money go. Where does the time go. How do we know the answers stay good. One call costs input tokens times the input price plus output tokens times the output price. Latency has two faces: TTFT, the wait for the first token, and full-completion latency, the wait for the last. Three waits stack inside one call: queue time, model time, tool time. Observability has four lenses: metrics in CloudWatch, logs in CloudWatch Logs, traces in X-Ray, and the audit trail.

3 leversfewer tokens, fewer calls, cheaper calls in L10
Nugget 9 · From the lesson L10 · Mental model
The lesson

The unit of optimization is cost per successful task, never cost per call. Three levers move the bill: fewer tokens per call, fewer calls, cheaper calls.

Why it matters. A cheap call that fails twice costs more than a dear call that succeeds once. Cost per success counts the retries that cost per call hides.

Transfer. Divide spend by finished work, not by attempts. Any system with retries lies to you in per-attempt units.

Unit 12 · L11 evaluation

L11: evaluation systems and troubleshooting

From the lessonL11 · The problem

The problem is proof. A new prompt version ships on Friday and users complain on Monday. No one measured the old version, so no one can prove the new one is worse. Arguments replace data. The lesson covers skills 5.1.1 to 5.1.9 and 5.2.1 to 5.2.5.

From the lessonL11 · Mental model

The mental model rests on three data sets. A golden dataset holds inputs with known-good answers and a rubric. A holdout set stays away from all tune work and measures honest skill. Leakage is test data inside the tune set, and a leaked score measures memory, not skill. Tests stack in layers: unit, integration, contract, end-to-end, adversarial, regression. Four quality dimensions frame each assessment: relevance, factual accuracy, consistency, fluency.

4 dimensionsthe quality dimensions in L11
Nugget 10 · From the lesson L11 · Mental model
The lesson

Lock the holdout away from tuning and score it once per release. A holdout inside the tune loop gives a great score that means nothing.

Why it matters. Human raters add judgment that metrics miss, and raters score blind to the version. Raters also drift, so the rubric and the blind keep scores honest.

Transfer. Protect one clean measure from every optimization pass. The measure you tune against stops as a measure.

Stage 8C: L12 worked-scenario drills and the 7-step best-answer method

From the lessonStage 8C · The 7-step method

Six end-to-end scenarios across domains run one decision method. Step 1 extracts the objective and names the scenario phrase. Step 2 extracts the hard constraints. 7 stepsthe best-answer method in Stage 8C
Nugget 11 · From the lesson Stage 8C · The 7-step method
The lesson

Run the seven steps in order and never skip: objective, constraints, layer, eliminate, rank, check dependencies, validate.

Why it matters. The worked case makes the steps concrete: 80,000 support articles, three engineers, tenant isolation, monthly updates, a three-week launch. The method lands on a managed knowledge base with a tenant filter and a sync trigger.

Unit 18 · Addendum B playbook

Addendum B: the senior decision playbook

From the lessonAddendum B · Study mode, timed mode

Study mode builds the moves in ten steps. Timed mode runs them under pressure as ASK, MUST, LAYER, ELIMINATE, RANK, CHECK SET. ASK names what the question asks and the lifecycle stage. MUST names the hard constraints in the words of the stem. LAYER names the layer that decides. ELIMINATE drops each option that breaks a hard constraint, with the exact clause as the cite. RANK orders the rest by the stated objective. CHECK SET tests a multi-select set as one unit: the set must cover all required controls with no clash.
