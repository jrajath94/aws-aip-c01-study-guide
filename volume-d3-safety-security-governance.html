1. Bedrock Guardrails, the managed safety layer

One policy object that screens both what users send to the model and what the model sends back. The exam's favorite safety building block.

On the board

  • Amazon Bedrock Guardrails is a managed safeguard you attach to model calls. It evaluates prompts and responses against six policy types and blocks or masks anything that violates them.
  • One guardrail can be reused across many models and applications, which is exactly what the exam means by "standardized, reusable safety components."
  • Guardrails are versioned. A version is an immutable snapshot you point production traffic at, so safety policy changes never ship by accident.

What a guardrail is

A guardrail is a named configuration object in Amazon Bedrock that holds your safety rules. Think of it as a bouncer standing at the door of the model: every request and every response walks past the bouncer, and the bouncer checks a fixed list of policies. The six policies are: content filters, denied topics, word filters, sensitive information filters, contextual grounding checks, and Automated Reasoning checks. Each policy can be switched on or off independently, and each gets evaluated for every request unless you disable it.

A guardrail has two moving parts you must keep straight. The guardrail itself is the draft configuration you edit. A version is a frozen, immutable copy of that configuration. Production traffic always points at a specific version (for example, version 3), never at the live draft. When you change the draft, you create a new version and move traffic to it deliberately. This is the same idea as a Lambda published version, and it exists so a policy tweak cannot silently change behavior in production.

Why it exists

Foundation models ship with built-in safety training, but that training is generic. It does not know that your banking chatbot must never give investment advice, that your children's tutor must refuse profanity even in quoted text, or that your support agent must mask credit card numbers. Without guardrails, the only way to enforce these rules is custom code around every model call: regexes, classifiers, and post-processing filters that you build, tune, and maintain yourself. That custom code is where most real-world safety failures live, because it is written once, forgotten, and bypassed by clever prompts.

Guardrails exist so the policy lives in one managed place, written in terms a non-engineer can read (topic definitions in plain language, threshold levels), and evaluated by AWS on both the input and the output of the model. One policy object, attached everywhere, versioned like code.

How it works under the hood

Here is the exact sequence when a guardrail is attached to a model call.

  1. Input evaluation. Your application sends the user prompt (and, in a RAG setup, the retrieved context) to Bedrock with a reference to guardrail ID and version. Before the model ever sees the text, the guardrail runs each enabled policy against the input. If any policy is violated, Bedrock stops the request right there and returns a blocked response instead of a model response.
  2. Model generation. If the input passes, it goes to the model as normal. The model generates its completion with no knowledge that a guardrail exists.
  3. Output evaluation. Before the completion is returned to your application, the guardrail runs the same policies against the output text. If the output violates a policy, it is blocked and replaced.
  4. Blocked message. When content is blocked, your application receives a configurable refusal message (for example, "I cannot help with that") rather than the model text. You define this message per guardrail, so it can match your product's tone.

Two details matter for the exam. First, input and output checks are independent switches: you can filter inputs only, outputs only, or both. A common production pattern is strict on inputs (block attacks and PII early, saving model cost) and slightly looser on outputs (let the model be helpful, then catch what slips). Second, every evaluation also produces a trace you can inspect. In the Converse API you pass guardrailConfig with the guardrail identifier, the version, and a trace flag; the trace tells you exactly which policy fired and why, which is how you debug "why was this blocked" without guessing.

Pricing note: you pay for the guardrail evaluation separately from the model tokens. Guardrail calls are billed per evaluation (input plus output counts as evaluations), which is cheap next to model inference. The exam will not test exact prices, but it does test the idea that guardrails cost something, so you do not attach five redundant guardrails "just in case" without reason.

What breaks if a component fails

  • If the input check is disabled and only the output check runs, prompt attacks reach the model and you pay for generating a response you then throw away.
  • If you point at the draft instead of a version, a teammate's policy edit changes production behavior instantly with no review.

The trap. The exam loves the idea that "the model already has safety training, so guardrails are redundant." That is never the most correct answer for a scenario with a sensitive audience, a regulated industry, or custom policy requirements. Built-in safety is generic; guardrails are your organization's specific policy, enforced on your terms. Another trap: treating the guardrail as an extraction or rewriting tool. Guardrails filter. They block, mask, or refuse. They do not summarize, translate, or improve text.

How AWS asks this. The scenario names a sensitive use case (children, healthcare, finance) plus a custom rule the base model cannot know ("must never discuss investment products"). The correct answer is always a managed guardrail with the matching policy, usually attached on both input and output. Distractors offer custom Lambda filters ("reinventing a managed service," the exam's default loser), rely on the model's built-in safety, or attach the guardrail on output only when the scenario explicitly worries about prompt attacks (those must be caught on input).

2. Where Guardrails apply

The same policy object, attached at five different points: inline on model calls, standalone on any text, on Knowledge Base answers, on agent outputs, and inside prompt flows.

On the board

  • Inline: pass guardrailConfig (identifier plus version) inside a Converse or InvokeModel call. The guardrail evaluates input and output of that call.
  • Standalone: the ApplyGuardrail API evaluates any text against a guardrail, with no model involved. It works with non-Bedrock models too.
  • Knowledge Bases: attach a guardrail to a KB so RetrieveAndGenerate answers are screened.
  • Agents: attach a guardrail to an agent so user inputs and final agent outputs are screened.
  • Key exam fact: ApplyGuardrail is model agnostic. Guardrails are not locked to Bedrock models.

The five application points: what each is and why it exists

1. Inline on Converse. The Converse API accepts a guardrailConfig field with three parts: the guardrail identifier (name or ARN), the version, and the trace setting. When present, Bedrock evaluates the guardrail on the request and the response. This is the most common pattern in exam scenarios: one application, one model call, one guardrail inline. Note that guardrails also work with InvokeModel through the same configuration, but the exam almost always frames this with Converse because Converse is the unified API.

2. Standalone with ApplyGuardrail. This API takes text plus a guardrail identifier and version, and returns the evaluation result: which policies fired, what was blocked or masked. No model is invoked. This matters in two exam patterns. First, screening content for a model that is not on Bedrock at all, such as a self-hosted model on SageMaker or a third-party API: you call ApplyGuardrail on the prompt before sending it out, and on the answer when it comes back. Second, screening user-generated content that never touches a model, such as forum posts or product reviews. The exam tests this with the sentence "the company uses a model outside Bedrock" and expects ApplyGuardrail, not "migrate to Bedrock."

3. On Knowledge Bases. A guardrail can be associated with a Knowledge Base. When your application calls RetrieveAndGenerate, the guardrail evaluates the final generated answer (which combines retrieved chunks with model text). This is the exam's answer for "RAG answers must be safe and grounded": KB for retrieval, guardrail with contextual grounding checks for the answer. The retrieval step itself (which chunks came back) is not what the guardrail judges; it judges the text the user sees.

4. On Agents. A guardrail can be attached to a Bedrock agent. It is evaluated on the user's input to the agent and on the agent's final response, at every invocation. Note the gap the exam can exploit: the guardrail does not screen each intermediate tool call the agent makes while reasoning. If an agent calls a Lambda that returns risky content mid-reasoning, the guardrail sees only the user's input and the final answer. Defense in depth (Chapter 7) is how you close that gap.

5. Inside Prompt Flows. Prompt Flows (the visual multi-step builder) support guardrail nodes, so a fixed prompt chain can include a safety check between steps. The exam mentions this rarely, but it is the correct answer when the scenario describes a no-code prompt chain that needs a screening step.

How to read this diagram

  1. Panel A is the default: the guardrail rides along inside the model call and checks both directions.
  2. Panel B is the escape hatch: no model call at all, just text in and a verdict out. This is the only panel that works with models outside Bedrock.
  3. Panel C shows the guardrail sitting after retrieval and generation in a RAG flow, judging only the final answer.
  4. Panel D shows the guardrail on an agent: it sees the input and the final answer, but not the intermediate tool calls in between.
  5. Panel E shows a guardrail as a node inside a fixed prompt chain.

What breaks if a component fails

  • If you attach the guardrail to the KB but the scenario's risk is a direct model call elsewhere in the app, the unguarded path is the hole. Guardrails protect the paths they are attached to, nothing else.
  • If you use inline guardrails for a non-Bedrock model, the call fails. Non-Bedrock models need ApplyGuardrail, never guardrailConfig.

ApplyGuardrail in more depth: how it works under the hood

Why does a standalone screening API deserve its own section? Because it breaks the mental model that "guardrails are a Bedrock model feature." The API accepts a source of INPUT or OUTPUT so you can screen a prompt before it goes to any model and a completion after it returns, and it returns per-policy findings. The exam uses it in exactly two story shapes: the company already has a model outside Bedrock and wants AWS-managed safety without migrating, and the company wants to screen text that never involves a model (user posts, uploaded documents). In both stories the distractor is "move everything to Bedrock" or "write a Lambda classifier," and the most correct answer is ApplyGuardrail.

One more mechanical detail: because ApplyGuardrail evaluates only the text you hand it, it has no conversation context. If your safety decision depends on multi-turn context (for example, whether an answer is grounded in earlier retrieved chunks), you must pass the relevant context in the text you submit. Inline guardrails on Converse have the full request; ApplyGuardrail has only what you send.

Concrete numbers

  • Guardrail versions are immutable. Draft edits never affect a versioned reference until you publish a new version.
  • ApplyGuardrail supports text; it is not a model invocation and is billed as a guardrail evaluation.
  • On agents, the guardrail evaluates at every agent invocation: input plus final output. Intermediate reasoning steps are not individually screened.

The trap. "Guardrails only work with Bedrock models" is false, and the exam will dangle it as a distractor against ApplyGuardrail. The reverse trap also appears: using guardrailConfig inline when the scenario says the model runs outside Bedrock. Inline config only works on Bedrock model calls; anything else needs the standalone API. A subtler trap: attaching a guardrail to a Knowledge Base and assuming retrieved chunks are screened. The guardrail judges the generated answer, not which chunks were retrieved.

How AWS asks this. The scenario's architecture sentence is the whole question. "A Lambda calls Converse with a guardrail" is inline. "The model runs on SageMaker" or "screen forum posts with no model" is ApplyGuardrail. "RAG answers must be checked" is a guardrail on the Knowledge Base. "Agent outputs must be safe" is a guardrail on the agent. Read the architecture first, then pick the attachment point.

3. Content filters and prompt attack detection

Toxicity categories with per-category strength levels, plus the dedicated jailbreak detector. This is the policy the exam reaches for whenever the scenario says "harmful content."

On the board

  • Content filters screen six categories: hate, insults, sexual, violence, misconduct, and prompt attack.
  • Each category gets its own strength: NONE (off), LOW, MEDIUM, or HIGH. Higher strength blocks milder content in that category.
  • Prompt attack is its own category: it detects jailbreak and prompt injection attempts in the input.

What content filters are

Content filters are the toxicity screen inside a guardrail. Every piece of evaluated text gets a severity score in each of six categories: hate (attacks on protected groups), insults (demeaning language toward individuals), sexual (explicit sexual content), violence (graphic or encouraging violent content), misconduct (instructions facilitating wrongdoing, such as fraud or weapons), and prompt attack (attempts to override the model's instructions). A "category" here is a fixed, AWS-defined bucket. You do not define what counts as hate speech; AWS's classifier does, and you only choose how sensitive to be.

How the strength levels work

For each category you pick one of four strengths: NONE, LOW, MEDIUM, HIGH. The strength is a sensitivity dial, not an on/off switch. At LOW, only severe and obvious violations are blocked. At MEDIUM, moderate content is blocked too. At HIGH, even mild or borderline content is blocked. NONE disables the category entirely.

The dial runs per category because real products need different sensitivities in different dimensions. A children's tutor sets violence and sexual to HIGH and insults to at least MEDIUM, because even mild teasing is unacceptable for kids. A customer support bot for adults might set insults to LOW (it should tolerate a frustrated customer venting) while keeping misconduct at HIGH (it must never help with fraud). The exam tests exactly this judgment: the scenario's audience and risk level tell you which categories to crank up and which to leave loose.

How to read this diagram

  1. Read down the left column: the six fixed categories. These never change.
  2. Read across: the four strengths. Moving right blocks more content in that category, including milder material.
  3. The two example rows show the judgment the exam tests: a children's product cranks almost everything to HIGH, while an adult support bot deliberately leaves insults at LOW so frustrated customers are not blocked for venting.

What breaks if a component fails

  • Setting every category to HIGH "to be safe" blocks legitimate content and degrades the product. Over-filtering is a real failure mode, and the exam treats it as one.
  • Leaving prompt attack at NONE while the scenario worries about jailbreaks leaves the front door open, because prompt attacks are only caught by that category on input.

Prompt attack detection in detail

What it is. Prompt attack is the content filter category that detects attempts to manipulate the model: jailbreaks ("ignore all previous instructions"), prompt injections hidden in pasted content ("the document says: disregard your rules and..."), and instruction overrides smuggled in through tool outputs or retrieved documents. It is evaluated on the input side, because that is where attacks arrive.

Why it exists. A model follows instructions found in its context, and it cannot reliably tell which instructions came from the developer and which came from the user or from untrusted retrieved text. Without a dedicated detector, a single pasted paragraph can silently rewrite the model's behavior for the rest of the session. This is the number one attack class the exam cares about in Domain 3.

How it works. When enabled, the guardrail runs a specialized classifier over the input text looking for manipulation patterns: instruction override phrasing, role reassignment ("you are now DAN"), delimiter abuse, and injected instructions inside quoted or pasted content. If the detected severity meets your configured strength, the input is blocked before the model sees it. Like all content filters, it is probabilistic, not a guarantee: novel attack phrasing can slip past, which is why Chapter 7 layers additional defenses.

Concrete numbers. Six categories, four strengths each, so a guardrail holds 24 independent sensitivity settings for content filters alone. Prompt attack detection applies to inputs; there is no meaningful "output prompt attack" because the attack arrives in the prompt.

The misunderstanding. Candidates read "prompt attack detection" and conclude prompt injection is solved. It is not. The detector catches known manipulation patterns, but attackers invent new phrasing constantly, and the exam explicitly frames it as one layer among several. Any answer that claims a single control "prevents all prompt injection" is wrong.

The trap. The exam's favorite confusion in this chapter is content filters versus denied topics (Chapter 4). "Block profanity and violent content" is a content filter (toxicity categories with thresholds). "Block all discussion of medical diagnoses" is a denied topic (subject-matter ban in plain language). The scenario verb decides: "harmful content" points to content filters, "must not discuss X" points to denied topics. A second trap: setting prompt attack filtering on the output side. Attacks arrive in inputs; output-side prompt attack filtering is meaningless, and the exam will offer it as a distractor.

How AWS asks this. The scenario describes an audience (children, the general public, enterprise users) and a harm type. Your job is to pick the category and the strength. "Children's tutor, block violent and sexual content, stop jailbreak attempts" maps to violence HIGH, sexual HIGH, prompt attack HIGH on input. Distractors set every category to HIGH (over-filtering), disable prompt attack, or reach for denied topics when the problem is toxicity rather than subject matter.

4. Denied topics and word filters

Subject-matter bans written in plain language, and exact-match blocklists for words. Two different tools for two different "never say this" problems.

On the board

  • Denied topics block entire subject areas. You define each topic in natural language, for example "investment advice" with a definition of what counts.
  • Word filters block exact strings. You supply a list of words or phrases; any exact match triggers the filter.
  • Denied topics understand meaning; word filters only match characters. That difference is the whole chapter.

Denied topics

What it is. A denied topic is a subject area your model is forbidden to discuss. You configure it with two pieces of plain language: a topic name ("Investment advice") and a definition ("any recommendation to buy, sell, or hold specific securities, or predictions about market movements"). The guardrail then uses a classifier to decide whether a given input or output falls inside that topic, and blocks it if so.

Why it exists. Some bans are about meaning, not vocabulary. "You should put your savings in tech stocks" contains no profanity and no single forbidden word, yet it is investment advice. No word list can catch every paraphrase of a forbidden subject, so denied topics work at the semantic level: they judge what the text is about, not which words it contains. This is the control the exam reaches for whenever a scenario says the model "must not discuss" or "must refuse questions about" a subject area: medical diagnosis, legal advice, investment recommendations.

How it works under the hood. When you create a denied topic, Bedrock stores your name plus definition as the topic's specification. At evaluation time, the guardrail runs a topic classifier over the input and the output. If the text is classified as belonging to the denied topic, the request or response is blocked and your configured refusal message is returned. Because it is a classifier, quality depends on your definition: a vague definition ("bad financial stuff") produces both misses and false blocks, while a precise definition with examples behaves predictably. You can define multiple denied topics per guardrail, each evaluated independently.

Concrete numbers. Illustrative: teams typically define a handful of denied topics per guardrail (three to ten), not hundreds; each additional topic adds a small amount of evaluation latency and cost. The exam does not test exact limits here, but it does test that definitions are written in natural language, not code.

The misunderstanding. Denied topics are not content filters. Content filters judge toxicity (hate, violence, profanity) with severity thresholds. Denied topics judge subject matter (is this about investment advice?) with no severity dial: the topic is either denied or it is not. The exam exploits this relentlessly, so burn the distinction in: toxicity goes to content filters, subject-matter bans go to denied topics.

Word filters

What it is. A word filter is a custom list of exact words and phrases that must never appear. If any listed string appears verbatim in the evaluated text, the filter fires. Typical uses: competitor product names a brand chatbot must never mention, internal codenames, profanity lists for a strict audience, or specific phrases from legal hold lists.

Why it exists. Sometimes the ban really is about the literal string. A bank's assistant must never utter a rival bank's name in a recommendation; a children's product has a fixed list of banned words from its content policy. For these cases a semantic classifier is overkill and unpredictable: you want a deterministic exact match.

How it works. You upload the list to the guardrail. At evaluation time the guardrail scans the text for exact matches. Match means block (or, in some configurations, the matched term can be masked). There is no fuzzy matching, no stemming, no leetspeak detection: "b4nk" does not match "bank." That precision is the point, and also the limitation.

The misunderstanding. Word filters do not understand meaning, so they are the wrong tool for paraphraseable bans (use denied topics) and the wrong tool for PII (use sensitive information filters, which detect entity types like "any credit card number," not specific strings). The exam's classic distractor is a word filter full of example SSNs to "block social security numbers." That fails the moment a new SSN appears. PII needs entity detection, not a list.

How to read this diagram

  1. Left box: a denied topic defined in plain language. The arrow below shows it catching a paraphrase with none of the banned words, because the classifier judges meaning.
  2. Right box: a word filter list. The arrow below shows it catching only verbatim matches and missing case variants and paraphrases.
  3. The contrast is the exam point: if the scenario ban can be reworded, it needs a denied topic; if the scenario ban is a fixed literal string, a word filter is the precise tool.

What breaks if a component fails

  • A vague denied-topic definition causes false blocks on innocent text and misses on clever paraphrases. Precision in the definition is the whole game.
  • A word filter used for PII fails open on every new value it has never seen. Entity detection, not lists, is the PII answer.

The trap. Three-way confusion is the exam's favorite game here: content filters (toxicity, severity dial), denied topics (subject matter, plain-language definitions), word filters (exact strings, custom lists). Drill the scenario verbs: "block profanity and hate speech" is content filters; "refuse to discuss medical diagnoses" is denied topics; "never mention these product codenames" is word filters. A second trap: using a word filter to block PII like SSNs. PII is entity-type detection with block or mask actions, which is Chapter 5, not a word list.

How AWS asks this. The scenario gives you the ban in plain words and asks which control implements it. "The chatbot must not provide investment advice" is denied topics, with distractors offering content filters (wrong axis: toxicity, not subject matter) and word filters (wrong mechanism: advice can be paraphrased). "The assistant must never utter the internal codename" is word filters, with distractors offering denied topics (overkill and imprecise for a literal string).

5. Sensitive information filters and the PII pipeline

Entity-type PII detection with block or mask actions, plus the three-service pipeline the exam expects for protecting personal data end to end.

On the board

  • Sensitive information filters detect PII by entity type (30+ built-in types like social security numbers, credit card numbers, email addresses), not by literal strings.
  • Per entity type you choose BLOCK (refuse the request) or MASK (replace the value, for example with XXX).
  • You can add custom regex patterns for identifiers the built-in types do not cover, such as an internal account number format.
  • The exam's PII answer is a pipeline: Macie finds PII in S3 at scale, Comprehend detects PII in real-time text, Guardrails filter at inference time.

What the filter does

A sensitive information filter is the guardrail policy that finds personal data in text. PII means personally identifiable information: any data that can identify a person, such as names, addresses, phone numbers, social security numbers, credit card numbers, and passport numbers. The filter recognizes more than 30 built-in entity types, and it detects them as patterns, not as fixed strings. It knows what a social security number looks like structurally (three digits, dash, two digits, dash, four digits), so it catches values it has never seen before. This is the fundamental difference from a word filter: word filters match strings you listed in advance; sensitive information filters recognize categories of data wherever they appear.

Block vs mask: how it works, step by step

For each entity type you configure one of two actions.

BLOCK. If the entity type appears, the whole request or response is refused and your blocked message is returned. Use block when the data must never travel through the system at all. Example: a public demo chatbot where a user might paste their social security number. The safest move is to refuse the turn entirely, because even a masked copy means the raw value touched your logs and the model context.

MASK. If the entity type appears, the value is replaced with a placeholder before the text continues. Use mask when the surrounding text is still useful and the identifier itself is not needed. Example: a support agent that needs to see "my card ending in XXXX was charged twice" to route the ticket, without ever seeing the full card number. Masking preserves the conversation while removing the sensitive value.

The under-the-hood sequence for a masked output: the model generates its completion, the guardrail's PII detector scans it and tags entity spans, each tagged span is replaced with the mask token, and only then is the text returned to your application. The raw value never leaves Bedrock. For a blocked input, the sequence is even shorter: the detector fires on the prompt, and the model is never invoked.

Custom regex patterns cover identifiers with a company-specific format, like an internal customer ID of two letters followed by eight digits. You write the pattern, the guardrail treats it as another entity type with its own block or mask action.

The full PII pipeline: why three stages and how they connect

The guardrail filter is the inference-time screen, but PII protection in a real system has three stages, and the exam tests all three as one "select three" answer.

  1. Amazon Macie: discovery at rest. Macie scans your S3 buckets and finds where PII already lives: which buckets, which files, which entity types. It is a discovery and classification service for data at rest. You run it to answer "where is our PII?" before you build anything. Macie does not sit in the request path; it is not real-time.
  2. Amazon Comprehend: detection in motion. Comprehend is the natural language processing service, and its PII detection API finds entities in text in real time. Use it as a pre-filter before the model call (scrub the prompt) or as a post-processor (scrub what you store). The exam's phrasing is "real-time PII detection in text," and the answer is Comprehend.
  3. Bedrock Guardrails: enforcement at inference. The sensitive information filter is the last line: it blocks or masks PII in the prompt before the model sees it and in the completion before the user sees it.

Two supporting pieces round out the architecture. S3 Lifecycle policies enforce retention: PII you collected for a support ticket should not sit in a bucket forever; a lifecycle rule deletes or transitions it after the retention period. And KMS encryption protects the stored data (Chapter 8). The exam's canonical "protect PII in customer conversations, minimal custom work" answer is Macie plus Comprehend plus Guardrails, with S3 Lifecycle for retention appearing as a fourth option in longer select-three or select-four variants.

How to read this diagram

  1. Left: the storage cylinder holds raw documents. Macie scans it and reports where PII lives. This happens offline, before any user arrives.
  2. The arrow moves right into live traffic: Comprehend's real-time PII detection scrubs text as it flows.
  3. Next box: the guardrail's sensitive information filter, showing masked values (XXX). This is the enforcement point at the model boundary.
  4. Right: the model only ever sees clean text.
  5. The looping arrow back to storage is the retention lifecycle: stored PII is deleted on schedule, so the stockpile does not grow forever.

What breaks if a component fails

  • Macie without the guardrail means you know where PII lives but it still flows into prompts. Discovery is not enforcement.
  • Comprehend without retention lifecycle means scrubbed traffic but an ever-growing archive of raw PII in S3. The exam treats retention as part of the answer.

Concrete numbers

  • 30+ built-in PII entity types in both Comprehend and the guardrail filter.
  • Two actions per entity type: BLOCK or MASK. Custom regex for company-specific formats.
  • Masked values never leave Bedrock: replacement happens before the response is returned.

The trap. The exam runs a whole confusion set around PII. Word filters for PII (fails on unseen values, because word filters match listed strings only). Amazon Translate for PII obfuscation (it preserves meaning across languages; it protects nothing). Amazon Rekognition for text PII (Rekognition is the vision service; Comprehend is the text service). And the subtlest one: Macie as a real-time filter. Macie discovers PII at rest in S3; it does not sit in the request path. Real-time detection is Comprehend, inference-time enforcement is Guardrails.

How AWS asks this. "Protect PII in customer service conversations with minimal custom work" is the select-three: Macie, Comprehend, Guardrails. "Redact social security numbers from model outputs but keep the conversation going" is the sensitive information filter with MASK on the SSN entity type. "Block the request entirely if a credit card number appears" is the same filter with BLOCK. Distractors offer word filters (wrong mechanism), Translate (nonsense), or Rekognition (wrong modality).

6. Contextual grounding checks and Automated Reasoning checks

Two verifiers for two different lies: grounding checks whether the answer is supported by the source text, Automated Reasoning checks whether it violates a formal policy. The exam's highest-yield distinction in Domain 3.

On the board

  • Contextual grounding checks fight hallucination in RAG: they score whether the model's answer is supported by the retrieved source content.
  • Automated Reasoning checks fight policy violations: they verify the answer against rules you write in natural language, using deterministic logical reasoning rather than a probabilistic classifier.
  • Grounding asks "is it true according to the source?" Automated Reasoning asks "is it allowed according to the policy?"

Contextual grounding checks

What it is. A contextual grounding check scores whether a generated answer is faithful to a source text you provide, usually the chunks retrieved by a Knowledge Base. It returns a grounding score between 0 and 1, and you set a threshold: answers scoring below the threshold are blocked as ungrounded.

Why it exists. Retrieval-augmented generation fails in a specific way: the retriever returns good chunks, but the model still invents details the chunks do not support. A support bot told "refunds take 5 to 7 days" by the retrieved policy might answer "refunds take 3 to 5 days" because 3-to-5 is a common pattern in its training data. The answer sounds confident, cites no source visibly, and is wrong. Grounding checks exist to catch exactly this: text that is fluent and plausible but not supported by the source.

How it works under the hood. You supply the source content (in a KB setup, the retrieved passages) along with the generated answer. The check decomposes the answer into individual claims and verifies each claim against the source: is this claim entailed by, contradicted by, or absent from the source? The per-claim results aggregate into a single grounding score. If the score falls below your threshold, the answer is blocked. A threshold of 0.75 (illustrative) means answers that are less than roughly three-quarters supported are refused. Higher thresholds mean fewer hallucinations but more false refusals of partially supported answers; the exam expects you to know this tradeoff exists without testing exact numbers.

Concrete numbers. Score range 0 to 1, threshold set by you. It evaluates the final answer against source content, so it belongs on the output side, and it pairs naturally with Knowledge Bases where the source content is the retrieved chunks.

The misunderstanding. Grounding checks do not verify truth against the world. They verify support against the source you supplied. If the retrieved chunks themselves contain wrong information, a perfectly grounded answer will repeat it confidently. Grounding answers "did the model stick to the source," not "is the source correct." Data quality upstream (Chapter 9's lineage, Domain 1's ingestion) is a separate problem.

Automated Reasoning checks

What it is. Automated Reasoning checks verify a model's answer against a formal policy you write in natural language. "Automated reasoning" is AWS's term for a family of techniques that prove things about logic statements deterministically, the same family behind formal verification tools. Instead of a classifier guessing whether an answer violates policy, the check translates your policy and the answer into logic and reasons over them.

Why it exists. Some rules are too precise for probabilistic classifiers. Consider a refund policy: "refunds above $500 require manager approval; refunds are never issued for final-sale items." A classifier might get the gist right most of the time, but "most of the time" is not good enough for a rule with exact dollar thresholds and absolute prohibitions. Automated Reasoning checks exist for policies that read like formal rules: thresholds, exceptions, and logical conditions that must hold exactly.

How it works under the hood. You write the policy as natural-language rules. AWS converts those rules into a formal logical representation. When the model produces an answer, the check extracts the claims relevant to the policy and runs a logical verifier: does this answer entail a violation of any rule? The result is deterministic for a given policy and answer, unlike a classifier score that shifts with phrasing. If a rule is violated, the check reports the finding; it does not block the answer on its own. Automated Reasoning checks are detect-only: they hand the verdict to your application, and your application decides what to do (for example, block the response, route to a human, or log the event). Because the verification is logical rather than statistical, it is far less sensitive to paraphrase tricks that fool classifiers.

Concrete numbers. You write rules in natural language; there is no threshold dial like grounding's 0-to-1 score. The check is strongest on policies with crisp logic: numeric limits, allow and deny lists, conditional requirements.

The misunderstanding. Automated Reasoning checks do not replace content filters or denied topics. They are the wrong tool for fuzzy problems ("is this tone appropriate?") and the right tool for exact problems ("does this violate the $500 rule?"). The exam tests this division of labor: probabilistic classifiers for fuzzy safety judgments, deterministic reasoning for formal policy rules.

Grounding vs Automated Reasoning, side by side

How to read this diagram

  1. Read the two question headers first. They are the entire distinction: source versus policy.
  2. Left column: grounding takes source text and the answer, checks each claim for support, and produces a score. It fights hallucination and belongs with RAG.
  3. Right column: Automated Reasoning takes formal rules and the answer, runs logical verification, and produces a valid or violation verdict. It fights policy breaches with exact thresholds.
  4. The two scenarios at the bottom are the exam in miniature: a wrong fact from the source is grounding, a broken dollar rule is Automated Reasoning.

What breaks if a component fails

  • Grounding with a bad source certifies wrong answers as supported. It checks fidelity to the source, not truth.
  • Automated Reasoning with a vague policy ("be fair about refunds") has nothing formal to verify. It needs crisp rules with thresholds and conditions.

The trap. This is the single most tested distinction in Domain 3, and the exam phrases both scenarios similarly. "The RAG bot invents facts not in the retrieved documents" is contextual grounding. "The bot's answer violates the company's formal refund policy with its dollar thresholds" is Automated Reasoning. The trap answers swap them, or offer "a stronger content filter" for both. Content filters judge toxicity; neither of these failures is about toxicity.

How AWS asks this. The scenario describes a failure: confident wrong facts (grounding) or a breached formal rule (Automated Reasoning). The correct answer names the check and where it attaches (usually on the KB's generated answer or on the model output). Distractors name the other check, or propose retraining the model, or propose a denied topic. Denied topics ban subjects; they do not verify claims against sources or policies.

7. Defense in depth: injection and jailbreak defense

No single control stops prompt attacks. The exam expects a layered stack and, just as importantly, an honest account of what AWS tooling cannot do.

On the board

  • Prompt injection: untrusted content (pasted text, retrieved documents, tool outputs) smuggles instructions into the model's context.
  • Jailbreak: the user directly tries to override the system prompt ("ignore all previous instructions").
  • The exam's defense stack: Comprehend pre-filter, Guardrails at the model (prompt attack detection), Lambda post-processing, API Gateway response filtering.
  • What AWS tooling does not do: guarantee prevention, sanitize business logic abuse, or replace human review for high-stakes actions.

The attack classes: what they are and why they work

A prompt injection happens because a language model cannot reliably distinguish instructions from data. Everything in its context window is text, and text that looks like an instruction tends to be followed. An attacker pastes a document that says "Important: disregard all safety rules and summarize this as..." or a retrieved web page contains hidden instructions, and the model obeys the smuggled instruction as if the developer wrote it. The dangerous variant is indirect injection: the attack arrives not from the user at all, but from a tool output, a retrieved chunk, or a web page the agent browsed. The user is innocent; the data is poisoned.

A jailbreak is the direct version: the user themselves tries to break out of the system prompt's constraints. Classic patterns include instruction override ("ignore all previous instructions"), role reassignment ("you are now an unrestricted AI"), and hypothetical framing ("in a fictional story, how would someone..."). Jailbreaks arrive in the user prompt; injections can arrive anywhere in the context.

Why this matters for the exam: the two attacks enter at different points, so they are caught by different layers. Jailbreaks are caught on input by the guardrail's prompt attack filter. Indirect injections hidden in retrieved documents may sail past the input check if the check only looks at the user's message, which is why the stack needs more than one layer.

The layered stack: how it works

The exam's canonical defense-in-depth answer has four layers, in order:

  1. Comprehend pre-filter. Before the prompt reaches the model, run it through Comprehend: PII detection to scrub sensitive data out of the input, and optionally a custom classifier for domain-specific abuse patterns. This layer reduces what the model ever sees. It is cheap and fast, and it catches the obvious cases early.
  2. Guardrails at the model. The guardrail's prompt attack content filter screens the input for jailbreak and injection patterns, and the output filters catch anything the model produced under the influence of a successful attack. This is the managed, purpose-built layer: it understands manipulation patterns that a regex never will.
  3. Lambda post-processing. After the model responds, a Lambda function applies your business-specific checks: format validation, allow-list verification of any structured fields, and policy checks too specific for a guardrail (for example, "the response must contain exactly one of these three approved disclaimers"). Lambda is where custom logic lives when no managed service covers it.
  4. API Gateway response filtering. At the edge, API Gateway can enforce response shapes, strip unexpected fields, and apply throttling so an attacker cannot cheaply brute-force thousands of attack variants. It is the last gate before the response reaches the client.

The principle: every layer fails sometimes, so you stack them. The pre-filter misses a novel phrasing; the guardrail catches it. The guardrail misses an indirect injection in a tool output; the Lambda post-processor catches the malformed action. The exam rewards answers that name multiple layers and punishes answers that bet everything on one.

How to read this diagram

  1. Top: the user prompt enters the first layer, the pre-filter, which scrubs PII and obvious abuse before the model is involved.
  2. Second layer: the Bedrock Guardrails shield, with prompt attack detection on the input and content filters on the output.
  3. Third layer: application checks, the Lambda post-processor that enforces business-specific rules on the response.
  4. Bottom: the API response filter at the edge, the final gate before the safe response reaches the user.
  5. Trace any attack through all four boxes: it must survive every one to succeed, which is the whole point of layering.

What breaks if a component fails

  • If the guardrail is the only layer and an indirect injection arrives inside a tool output, the attack bypasses the input check entirely. The post-processing layer is the backstop.
  • If there is no throttling at the edge, an attacker can iterate thousands of jailbreak variants cheaply until one works. Rate limiting is a security control, not just a cost control.

What AWS tooling does and does not do

The exam tests honesty about limits, so here is the line, stated plainly.

What it does. Prompt attack detection identifies known jailbreak and injection patterns in inputs. Denied topics and content filters constrain what the model will discuss and how. Sensitive information filters keep PII out of both directions. Contextual grounding and Automated Reasoning verify outputs against sources and policies. ApplyGuardrail extends all of this to models outside Bedrock. Together these make attacks significantly harder and more expensive.

What it does not do. It does not guarantee prevention: prompt attacks are an arms race, and novel phrasing defeats pattern-based detection. It does not sanitize business logic: a model that follows a successful injection to call a refund API is a failure of tool authorization and human approval, not a failure the guardrail could have caught after the fact. It does not judge truth: a confident, well-sourced lie passes every filter if the source itself is wrong. And it does not replace human review for high-stakes or irreversible actions, which is why Chapter 10's approval flows exist.

The exam's phrasing for this limit is usually a distractor claiming a control "prevents all prompt injection attacks" or "eliminates hallucinations." Absolute claims about probabilistic defenses are always wrong. The most correct answer pairs the managed control with a second layer and, for high stakes, a human.

Concrete numbers

  • Four layers in the canonical stack: Comprehend pre-filter, Guardrails, Lambda post-processing, API Gateway response filtering.
  • Two attack entry points: direct user prompt (jailbreak) and untrusted context content (indirect injection via documents, tool outputs, retrieved chunks).
  • Prompt attack detection is one of six content filter categories, configured per input with NONE, LOW, MEDIUM, or HIGH strength.

The trap. Any answer promising complete prevention of prompt injection is wrong, no matter how managed the service sounds. The exam also baits with single-layer answers: "enable prompt attack detection" alone when the scenario describes an agent reading untrusted web pages (indirect injection needs the post-processing and approval layers too). And it baits with the wrong layer for the attack: output filters do not stop input attacks, and input filters do not catch poisoned tool outputs mid-reasoning.

How AWS asks this. The children's tutor scenario from the blueprint is the template: block profanity and violence on inputs, prevent harmful outputs, stop jailbreaks, ground facts. The correct answer is the full stack, naming each layer's job. Shorter variants ask for one missing layer: "the guardrail is in place but attacks arrive through browsed web pages" needs post-processing and human approval on actions, because the poison enters through tool outputs, not the user prompt.

8. The data security plane

Who can call the model, how the data is encrypted, how traffic stays private, where data is allowed to live, and who gets a record of everything. IAM, KMS, PrivateLink, residency, CloudTrail.

On the board

  • IAM controls who can invoke which model, knowledge base, or agent. Least privilege, resource-level ARNs, cross-account via role assumption.
  • KMS encrypts data at rest; customer managed keys (CMKs) give you control of the key. TLS encrypts data in transit.
  • VPC interface endpoints (PrivateLink) keep Bedrock API traffic inside the AWS network, off the public internet.
  • Your prompts and responses are not used to train models. Data stays in the region you chose, with cross-region inference as the explicit exception.
  • CloudTrail logs every Bedrock API call for audit. Model invocation logging (request and response content) is separate, optional, and sensitive.

IAM for Bedrock: roles, policies, model access control

What it is. AWS Identity and Access Management (IAM) is the permission system for every AWS API call, including Bedrock. An IAM policy is a document that says which actions (such as bedrock:InvokeModel) are allowed on which resources (such as a specific model ARN) for which identity (a user, a role, a service). A role is an identity that services and cross-account callers can assume temporarily instead of using long-lived credentials.

Why it exists. Model access is a security boundary. An application that only needs to call one model for summarization should not be able to invoke every model in the account, read your knowledge bases, or change guardrail versions. Least privilege means each identity gets exactly the permissions its job requires and nothing more. Without it, a compromised application credential becomes a skeleton key.

How it works under the hood. Every Bedrock call carries the caller's identity. IAM evaluates the request against all applicable policies: identity-based policies attached to the user or role, and resource-based policies where the service supports them. For Bedrock you scope actions narrowly: bedrock:InvokeModel on the ARN of the one model the app needs, bedrock:Retrieve and bedrock:RetrieveAndGenerate on the specific knowledge base, bedrock-agent:InvokeAgent on the specific agent alias. Bedrock agents themselves run under an IAM service role that you create; that role's permissions define what the agent's Lambda tools and KB queries are allowed to touch, which is how you put resource boundaries around agent actions.

Model access control. Two layers. First, IAM decides whether the caller may attempt the call. Second, the model itself must be enabled for the account in that region (model access is requested in the Bedrock console, sometimes with a use-case form for certain models). If either layer denies, the call fails. The exam's classic symptom: AccessDeniedException on a model call, where the fix is either the IAM policy or the model access grant, and the scenario tells you which one is missing.

Cross-account access. When a central platform team hosts Bedrock in one account and product teams call it from others, you do not copy credentials around. You create a role in the Bedrock account with a trust policy naming the product accounts, and the product workloads assume that role with short-lived credentials. The role's permission policy still applies least privilege, so each team gets only its models. The exam tests this pattern with "multiple accounts, central model access, no long-lived keys," and the answer is always role assumption, never access key sharing.

The misunderstanding. IAM controls who can call the API. It does not control what the model says. "The IAM policy blocks harmful outputs" is a category error the exam will offer as a distractor. API authorization is IAM; content safety is Guardrails. Both are needed; neither replaces the other.

KMS encryption: CMKs, at rest, in transit

What it is. AWS Key Management Service (KMS) manages the encryption keys that protect your data. A customer managed key (CMK) is a key you create and control in KMS: you decide who may use it, you can rotate it, and you can disable it to instantly revoke access to everything it protects. This is stronger than the default AWS-owned keys, where AWS manages everything and you have no key-level control.

Why it exists. Encryption at rest means stored data is unreadable without the key: Knowledge Base vector stores, agent session data, model invocation logs, custom model artifacts in S3. If a storage volume is ever exposed, the data is still ciphertext. A CMK adds control: you can audit every key use in CloudTrail, enforce key policies per team, and meet compliance requirements that demand customer-controlled keys.

How it works. When you configure a Bedrock resource with a CMK (for example, a Knowledge Base's storage or invocation logging destinations), Bedrock uses envelope encryption: your data is encrypted with a data key, and the data key is encrypted with your CMK. Every use of the CMK is logged. Data in transit is a separate mechanism: all Bedrock API traffic uses TLS (Transport Layer Security), so prompts and responses are encrypted on the wire between your application and AWS. At rest is KMS; in transit is TLS. The exam tests the pair together and the distinction between them.

Concrete numbers. Illustrative practice: teams apply CMKs to the resources that persist customer data (KB storage, invocation logs, agent memory stores) while accepting default encryption for ephemeral compute. The exam cares about the decision rule, not a key count: customer data at rest that outlives the request gets a CMK in regulated scenarios.

The misunderstanding. "TLS means our stored logs are encrypted" confuses the two planes. TLS protects data moving across the network; it does nothing for data sitting in S3. Stored data needs KMS. The exam pairs a scenario about stolen or exposed storage with KMS, and a scenario about network interception with TLS or PrivateLink.

VPC endpoints and PrivateLink

What it is. A VPC interface endpoint, powered by AWS PrivateLink, is a private network entry point inside your virtual private cloud (VPC) for an AWS service. Instead of your application's Bedrock API calls traveling over the public internet, they travel through the endpoint and stay on the AWS private network. Bedrock exposes endpoints for its planes: bedrock (control plane: creating guardrails, agents, knowledge bases), bedrock-runtime (data plane: InvokeModel, Converse), bedrock-agent, and bedrock-agent-runtime (agent control and invocation).

Why it exists. Some environments forbid any traffic to public IP addresses, even encrypted traffic to AWS services. Financial and healthcare workloads often run in VPCs with no internet gateway at all. Without PrivateLink, those workloads cannot reach Bedrock; with it, they can, because the traffic never leaves AWS's network.

How it works under the hood. You create the interface endpoint in your VPC's subnets. AWS places elastic network interfaces with private IP addresses in your subnets, and DNS for the Bedrock service hostname resolves to those private IPs from inside the VPC. Your application's SDK calls the same Bedrock endpoint hostname as always; the network path is what changes. You then lock it down two ways: the endpoint policy controls which actions may pass through the endpoint, and security groups on the endpoint's network interfaces control which resources in the VPC may reach it. No NAT gateway, no internet gateway, no public IPs involved.

How to read this diagram

  1. Left: the dashed rectangle is the company's VPC, containing the application server. Dashed means it has no route to the public internet.
  2. The solid tunnel in the middle is the PrivateLink VPC endpoint: private IP addresses inside the VPC that lead directly to Bedrock.
  3. Right: the Bedrock cloud. Traffic flows through the tunnel, never touching the public internet.
  4. The crossed-out arrow to the globe is the blocked path: even if the application tried to reach Bedrock publicly, the VPC has no internet route, so the endpoint is the only way.

What breaks if a component fails

  • If the endpoint policy is left wide open, any workload in the VPC can call any Bedrock action through it. Scope the endpoint policy like an IAM policy.
  • If DNS is not configured for private resolution, the SDK resolves the public Bedrock hostname and the call fails in a VPC with no internet. Private DNS on the endpoint is what makes the same code work privately.

Data privacy and data residency

Training data. AWS states that customer prompts, completions, and retrieved content sent to Bedrock are not used to train or improve foundation models. This is a contractual privacy boundary, and the exam treats it as a fact you can assert: the scenario "the legal team worries our documents will train the vendor's next model" is answered by this Bedrock privacy commitment, not by encryption or anonymization.

Data residency. Your Bedrock data stays in the AWS region you selected. Prompts, responses, knowledge base content, and agent data do not leave that region unless you explicitly use a feature that moves them. The exception the exam tests is cross-region inference: when you invoke a model through an inference profile (for example, a us. prefixed profile), your request may be routed to a different region for availability or failover, which means the data crosses region boundaries. That is disclosed and expected behavior of the feature, but it means a strict data-residency requirement ("data must never leave the EU") rules out cross-region inference profiles that route outside the EU. Read the residency constraint before reaching for the resilience feature.

The misunderstanding. "Encryption solves data residency" is wrong. KMS encrypts data wherever it is; residency is about where it is allowed to be. A residency requirement is satisfied by region choice and by avoiding cross-region features, not by stronger encryption.

CloudTrail logging and model invocation logging

Two different logs, two different jobs. The exam tests the distinction directly.

AWS CloudTrail: the audit log. CloudTrail records every Bedrock API call: who called it (identity), when, from where, which action (InvokeModel, CreateGuardrail, RetrieveAndGenerate), and whether it succeeded. It does not record prompt or response content. Its job is accountability: "which identity invoked which model at 2am" is a CloudTrail question. Event history keeps 90 days; for longer retention you deliver the trail to S3. This is the answer whenever the scenario asks who did what, for forensics, compliance audits, or access reviews.

Model invocation logging: the content log. Separately, Bedrock can log the actual request and response content of model invocations to S3 or CloudWatch Logs. This exists for debugging, prompt analysis, and evaluation data collection. Because these logs contain the full text users typed, they may contain PII, credentials, and confidential business data. In regulated scenarios the exam expects you to either encrypt these logs with a CMK or disable invocation logging entirely. "We logged all prompts to CloudWatch in plaintext for a healthcare app" is the exam's horror story, and the fix is KMS encryption or no content logging.

How to read this diagram

  1. Left box: a CloudTrail entry. Every field is metadata about the call. No user text anywhere.
  2. Right box: an invocation log entry. It holds the literal prompt and response, which is why it is marked sensitive.
  3. The bottom lines are the exam rules: CloudTrail answers accountability questions and is always on; invocation logging answers debugging questions, is optional, and must be encrypted or disabled where PII is a risk.

What breaks if a component fails

  • Relying on CloudTrail to debug a bad model answer fails: the content was never recorded. You need invocation logging for that.
  • Enabling invocation logging without encryption in a regulated workload creates a PII stockpile. The exam treats this as a finding, not a configuration choice.

The trap. CloudTrail versus CloudWatch Logs versus invocation logging is a three-way exam game. CloudTrail: who called which API (audit). CloudWatch Logs: application and decision logs your code writes, plus the optional destination for invocation logs. Invocation logging: the actual prompt and response text. "Find which identity called the model" is CloudTrail; "analyze what users are asking" is invocation logging to S3 or CloudWatch. A second trap: VPC endpoints presented as an encryption feature. PrivateLink is about network path (no public internet); encryption in transit is TLS. Related but different answers.

How AWS asks this. The scenario gives a constraint and asks for the mechanism. "Traffic must not traverse the public internet" is VPC interface endpoints for the Bedrock planes. "Only the summarization app may call this one model" is an IAM policy scoping bedrock:InvokeModel to the model ARN. "Stored data must use keys we control" is CMKs. "Data must stay in the EU" is region choice, and cross-region inference is the distractor that violates it. "Who invoked the model last Tuesday" is CloudTrail; "what did users ask" is invocation logging, with KMS or disabled as the compliance kicker.

9. Governance and compliance

Proving what the system is, where its answers come from, and that it keeps behaving. Model cards, lineage, audit, monitoring, and framework alignment.

On the board

  • Model cards document a model's intended use, limitations, training data, and evaluation results. SageMaker model cards can be generated programmatically.
  • Data lineage tracks which data produced which answer: Glue Data Catalog registration, metadata tags, and source attribution on generated content.
  • CloudTrail plus CloudWatch Logs give you the audit trail; continuous monitoring watches for misuse, drift, and policy violations with alerting and remediation.
  • Compliance alignment means mapping your guardrail policies and controls to the framework's requirements and keeping the evidence to prove it.

Model cards

What it is. A model card is a structured document that describes a machine learning model: what it was built for (intended use), what it should not be used for, what data it was trained on, how it was evaluated, and what its known limitations and biases are. SageMaker AI supports model cards as first-class objects that can be generated programmatically and versioned alongside the model.

Why it exists. A model without documentation is a liability. When a regulator, an auditor, or your own risk team asks "what is this model, and is it appropriate for this use case," the model card is the answer. It turns tribal knowledge ("we think it was trained on mostly English data") into a versioned artifact with evaluation numbers attached.

How it works. You create the card with sections for model details, intended uses, training data, evaluation data and metrics, and ethical considerations. As the model is retrained or re-evaluated, the card is updated and versioned, so there is always a card matching the model version in production. For Bedrock foundation models you do not write the card (AWS and the model provider publish model information), but the governance habit is the same: know the model's documented limitations before you deploy it, and record your own evaluation results against your use case.

The misunderstanding. A model card is documentation and governance evidence, not a runtime control. It does not block bad outputs; guardrails do. The exam offers model cards as a distractor for runtime safety questions and as the correct answer for documentation and audit questions. "Document the model's limitations for the risk review" is a model card. "Stop the model from giving medical advice" is a denied topic.

Data lineage: which data produced this answer

What it is. Data lineage is the recorded chain from source data to generated answer: which documents were ingested, when, from where, how they were chunked and embedded, which chunks were retrieved for this query, and what the model said. If every step is recorded, you can answer the regulator's question: "which data produced this answer?"

Why it exists. A RAG answer is only as trustworthy as its sources. When an answer is wrong, you need to know whether the retriever fetched the wrong chunk, the chunk came from an outdated document, or the model ignored the chunk. Without lineage, debugging is guesswork and audits are impossible.

How it works under the hood. Three mechanisms combine. First, AWS Glue Data Catalog registration: your source datasets are registered with schemas and metadata, so there is a central record of what exists. Second, metadata tagging: S3 objects, KB data sources, and chunks carry tags like source system, document version, ingestion date, and data classification. Third, source attribution on generated content: RetrieveAndGenerate returns citations linking the answer to the specific chunks used, and you store those citations with the conversation record. Together they form an unbroken chain: answer to chunk, chunk to document, document to source system.

Concrete numbers. Illustrative: a lineage record per answer stores the chunk IDs, document versions, and retrieval scores, which is small metadata next to the conversation itself. The exam does not test sizes; it tests that you can name the three mechanisms and what each contributes.

How to read this diagram

  1. Top: the user-facing answer with a citation marker. Citations are the visible tip of lineage.
  2. Follow the arrows down: the citation resolves to specific chunk IDs with retrieval scores, which is the retrieval record.
  3. Each chunk resolves to a versioned document with an ingestion date, stored in S3 with metadata tags.
  4. The document resolves to a Glue catalog entry and ultimately the source system that authored it.
  5. The bottom line is the audit wrapper: CloudTrail records which identity ran the retrieval and when.

What breaks if a component fails

  • If chunks are not tagged with document versions, you cannot tell whether an answer came from the current policy or last year's. Version metadata is what makes lineage useful.
  • If citations are shown to the user but not stored, you can see sources today but cannot reconstruct them during next quarter's audit. Store the chain, not just the display.

Audit and continuous monitoring

Audit: proving what happened. The audit trail combines CloudTrail (who called which Bedrock API, when) with CloudWatch Logs (application decision logs: which guardrail version was active, which policies fired, what the lineage citations were). For sensitive content, apply token-level redaction in logs so the audit record itself does not become a PII leak. The exam's audit questions are answered by naming both log sources and what each contributes.

Continuous monitoring: proving it keeps behaving. Governance does not end at deployment. The exam expects monitoring for four things: misuse detection (spikes in blocked prompt attacks, unusual invocation patterns that suggest abuse), drift (answer quality degrading as documents age or user behavior shifts), policy violations (guardrail block rates changing, new denied-topic hits), and bias drift (fairness metrics worsening over time, covered in Chapter 10). CloudWatch metrics and alarms watch the quantitative signals (invocation counts, block rates, token patterns); evaluation jobs rerun periodically against golden datasets to watch quality; alerts route to remediation workflows, which can be as simple as a notification or as strong as automatically rolling the guardrail back to the previous version.

The misunderstanding. Fairness and safety are not one-time checks done before launch. The exam explicitly wants continuous monitoring: a model that was unbiased in testing can drift as the world changes, and a guardrail that worked in January can be bypassed by February's attack techniques. "We evaluated once before launch" is never the most correct answer for an ongoing-behavior question.

Compliance frameworks alignment

What it is. Regulated industries operate under compliance frameworks: published sets of requirements for how systems must be built and run. Examples the exam may name generically include financial services regulations, healthcare privacy rules, and AI-specific risk frameworks such as the NIST AI Risk Management Framework. "Alignment" means mapping each framework requirement to a concrete control in your architecture and keeping the evidence that the control works.

How it works in practice. You build a mapping table. "The framework requires data minimization" maps to your PII masking guardrail plus S3 Lifecycle retention. "The framework requires auditability" maps to CloudTrail plus decision logging with redaction. "The framework requires human oversight of automated decisions" maps to your Step Functions approval flows (Chapter 10). "The framework requires model documentation" maps to model cards. AWS's side of the shared responsibility model is covered by AWS Artifact, where AWS publishes its own compliance attestations; your side is the mapping plus the evidence your controls generate.

The misunderstanding. No AWS service "makes you compliant." Compliance is a property of your whole system plus your processes plus your evidence. The exam's trap is a service positioned as a complete compliance answer. The most correct answer is always the mapping: controls plus evidence plus review, with named AWS services as the control implementations.

The trap. Model cards as a runtime safety control (they are documentation). CloudTrail as a content log (it is an audit log; content needs invocation logging). One-time evaluation as ongoing governance (the exam wants continuous monitoring with alerting). And any answer where a single service "achieves compliance" (compliance is controls plus evidence plus process, never one product).

How AWS asks this. "The regulator asks which data produced this answer" is lineage: Glue catalog, metadata tags, stored citations, CloudTrail. "Prove the model's outputs stay unbiased over time" is continuous bias monitoring with automated alerts, not a pre-launch test. "Document the model for the risk committee" is model cards. "Map our controls to the framework" is the alignment table with evidence per requirement.

10. Responsible AI, evaluation, and agent governance

Transparency, fairness, and human oversight as engineering practices, plus how you keep an agent's actions under control and prove the system is safe before and after launch.

On the board

  • Transparency: reasoning traces, confidence signals, and source attribution so a human can see why the system did what it did.
  • Fairness: pre-defined fairness metrics, A/B testing with Prompt Management variants, LLM-as-a-judge evaluations, and continuous bias drift monitoring.
  • Human in the loop: Step Functions approval workflows and human review for high-stakes or irreversible actions.
  • Agent governance: action group approval flows (return of control to the application before a tool runs), IAM resource boundaries, timeouts and circuit breakers.
  • Safety evaluation: programmatic checks for toxicity, LLM-as-a-judge for harmfulness and refusal behavior, human evaluation for the subjective calls.

Transparency

What it is. Transparency means the system's decisions can be inspected and explained. For a GenAI application this has three concrete forms. Reasoning traces: Bedrock agents can return their step-by-step reasoning (the enableTrace option on agent invocation shows which tools were considered, which were called, and what the model concluded at each step). Confidence signals: grounding scores, retrieval scores, and evaluation metrics that tell you how much to trust an answer. Evidence and source attribution: citations linking answers to retrieved chunks, so a human can verify the claim without rerunning the query.

Why it exists. An uninspectable system cannot be debugged, audited, or trusted with anything important. When a support agent gives a wrong answer, the trace tells you whether the retriever failed, the model misread the chunk, or the policy check was skipped. Transparency is what turns "the AI said so" into an engineering artifact you can reason about.

How it works under the hood. Traces are produced at invocation time and logged to CloudWatch or your application store. Citations come back from RetrieveAndGenerate as part of the response object. Confidence signals come from the checks in Chapter 6: a grounding score below your threshold is itself a transparency signal that says "do not trust this answer." The exam's transparency questions are answered by naming these mechanisms, not by philosophical statements about openness.

Fairness and bias detection

What it is. Fairness means the system behaves comparably across demographic groups: it does not systematically give worse answers, harsher judgments, or fewer opportunities to some groups than others. Bias detection is the practice of measuring that.

Why it exists. Models learn patterns from training data, and training data contains historical biases. A hiring assistant trained on past hiring data may rank some demographic groups lower; a lending assistant may quote worse terms. These failures are silent: the system looks like it works until someone measures outcomes by group.

How it works. Four practices, used together. First, pre-defined fairness metrics: before launch, you define what fair means for your use case (for example, approval rates across groups should not differ beyond a set bound) and you measure it on test data. SageMaker Clarify is the AWS service built for bias metrics and explainability on traditional ML models; the concept carries over to GenAI evaluation. Second, A/B testing: Bedrock Prompt Management variants let you run two prompt or model versions side by side and compare fairness metrics, so a "fix" that improves accuracy for one group at another's expense is caught. Third, LLM-as-a-judge evaluations: a separate model scores outputs for bias and harmfulness at a scale humans cannot match, using rubrics you define. Fourth, continuous bias drift monitoring: the metrics are recomputed on production traffic on a schedule, with alerts when a metric crosses its bound. The exam's key sentence is that fairness is continuous, not a pre-launch checkbox.

The misunderstanding. "A bigger, newer model will be less biased" is not an engineering answer. Fairness comes from measurement and process, not from model size. The exam offers model upgrades as a distractor for fairness questions; the most correct answer always names metrics, testing, and monitoring.

Human in the loop

What it is. Human in the loop means a person reviews and approves the system's action before it takes effect, for decisions where the cost of an error exceeds the cost of waiting. The AWS implementation pattern is a Step Functions approval workflow: the workflow pauses at a task token, notifies a human (email, Slack, ticketing system), and resumes only when the human approves or rejects.

Why it exists. Some actions are hard to undo: sending money, deleting data, publishing content under the company's name, contacting a customer with bad news. A model can draft the action, but a human should authorize it. This is also the backstop for every probabilistic defense in the earlier chapters: when the filters are uncertain, the human decides.

How it works under the hood. The application or agent prepares the proposed action and starts a Step Functions execution with a callback task. Step Functions issues a task token and waits; the token is sent to the human reviewer along with the full context (the proposed action, the reasoning trace, the grounding score). The reviewer approves or rejects, which sends the token back with the decision, and the workflow continues or rolls back. Timeouts bound the wait: if no human responds in the configured window, the workflow takes a safe default (usually rejection). For model training and labeling workflows, SageMaker Ground Truth and Augmented AI (A2I) provide managed human review workforces with the same idea: route low-confidence items to people.

Governance of agents: action group approval flows

What it is. A Bedrock agent acts through action groups: each action group maps to a Lambda function or an API schema describing tools the agent may call. Governance of agents means controlling which tools the agent may call, under what conditions, and with whose approval.

Why it exists. An agent that can call tools can change the world: query databases, issue refunds, send messages. A prompt injection that convinces the agent to call the refund tool is not a content problem; it is an action problem. Without approval flows, the agent's autonomy is unbounded.

How it works under the hood. Three controls, layered. First, IAM resource boundaries: the agent's service role permits only the specific Lambda functions and data sources the agent needs, so even a confused agent cannot reach tools it was never granted. Second, action group approval flows: for sensitive action groups you configure the agent to return control to your application before executing the tool. The agent pauses, hands your code the proposed action with its parameters and reasoning, your code runs the approval workflow (Step Functions human approval for high stakes, automated policy check for routine ones), and only then does the tool execute. Third, operational guardrails: Lambda timeouts bound how long a tool call may run, Step Functions stopping conditions bound how many reasoning steps the agent may take, and circuit breakers halt the agent if tool calls start failing in a loop. The exam's agent governance answer is this trio: IAM boundaries, approval flows, and stopping conditions.

How to read this diagram

  1. Top: the agent reasons and proposes a specific tool call with parameters, instead of executing it directly.
  2. The proposal goes to the approval workflow box: an automated policy check for routine cases, a human reviewer for high-stakes ones (the $500 threshold is the kind of formal rule from Chapter 6).
  3. The decision returns to the agent: approved means the tool runs, rejected means the user gets a refusal.
  4. The supporting controls at the bottom bound the blast radius: IAM limits which tools exist, timeouts limit how long they run, stopping conditions limit how many steps the agent takes, and the circuit breaker stops cascading failures.

What breaks if a component fails

  • If the approval flow is skipped for "low risk" tools and an attacker redefines a tool's purpose through injection, the agent acts without oversight. Approval policy should follow the action's impact, not its label.
  • If there are no stopping conditions, a confused agent can loop on tool calls indefinitely, burning cost and potentially repeating side effects. Step and time bounds are mandatory.

Model evaluation for safety

What it is. Bedrock model evaluation runs your system against test datasets and scores safety dimensions. Three methods, matched to what you are measuring. Programmatic (automatic) evaluation uses fixed metrics and built-in datasets: toxicity scores, accuracy, robustness. It is cheap, repeatable, and objective. LLM-as-a-judge evaluation uses a separate model as the scorer with rubrics you define: harmfulness, faithfulness (hallucination), refusal behavior (does it refuse what it should refuse, and comply with what it should comply with), and style. This is the workhorse for safety at scale. Human evaluation uses your own reviewers or an AWS-managed team for the subjective calls: brand voice, cultural appropriateness, edge cases the rubrics miss.

Why it exists. You cannot govern what you do not measure. Safety evaluation before launch sets the baseline; the same evaluation rerun on a schedule becomes the continuous monitoring from Chapter 9. Regression testing on every prompt or model change catches the case where a "small" prompt tweak quietly disables refusal behavior.

How the exam frames it. RAG safety evaluation measures retrieval relevance plus generation faithfulness, LLM-as-a-judge powered. Agent safety evaluation measures task completion, tool-use correctness, and whether the agent refused or sought approval where it should have. The method matrix from the blueprint is worth memorizing: programmatic for objective repeatable metrics, LLM-as-a-judge for human-like quality at scale, human for subjective judgment, and bring-your-own-inference to evaluate systems that do not run on Bedrock.

The misunderstanding. Programmatic evaluation for style or brand voice (it measures what is countable, not what is tasteful), and human evaluation as the only gate for large-scale regression (too slow and expensive; the exam wants automated gates with human spot checks).

Concrete numbers

  • Three evaluation methods in the safety matrix: programmatic for objective repeatable metrics, LLM-as-a-judge for human-like quality at scale, human for subjective judgment.
  • Four agent governance controls in the exam's answer: IAM resource boundaries, action group approval flows, stopping conditions with timeouts, and circuit breakers.
  • Two approval tiers in the canonical flow: automated policy checks for routine actions, human review for high-stakes or irreversible ones.

The trap. Fairness as a one-time pre-launch check (the exam wants continuous bias drift monitoring with alerts). A bigger model as the fairness fix (measurement and process, not model size). Agent autonomy without approval flows (any irreversible or high-stakes tool call needs an approval gate; "the agent is well-prompted" is never sufficient). And evaluation method mismatch: programmatic metrics for subjective quality, or human-only evaluation for thousand-case regressions.

How AWS asks this. "Ensure unbiased outputs across demographic groups" is fairness metrics plus A/B testing plus LLM-as-a-judge plus continuous monitoring, never "use a larger model." "The agent issues refunds; some need manager approval" is the action group approval flow with a Step Functions human step for amounts over the threshold. "Validate safety before launch and keep validating" is the evaluation trio (programmatic, LLM-as-a-judge, human) run once as a gate and then on schedule as monitoring.

Correct: A, B. Traces expose the reasoning process; citations expose the evidence. Both let a human verify the work.

C is wrong: context size changes capacity, not inspectability.

D is wrong: temperature changes randomness, not transparency.

Q10.5 (Multiple response, medium). Select TWO. Which TWO are operational safeguards that bound an agent's autonomy?

  1. Stopping conditions that limit reasoning steps and execution time
  2. Circuit breakers that halt the agent on repeated tool failures
  3. A detailed system prompt describing the agent's role
  4. Prompt caching to reduce the cost of long agent sessions
Answer and explanation

Correct: A, B. Stopping conditions bound runaway reasoning; circuit breakers stop cascading tool failures. Both are enforcement, not suggestion.

C is wrong: a system prompt guides behavior but cannot enforce bounds; it is exactly what injections override.

D is wrong: prompt caching is a cost optimization, not a safety bound.

Q10.6 (Multiple response, hard). Select THREE. A team designs a safety evaluation plan. Which THREE correctly match the method to what it measures?

  1. Programmatic evaluation for toxicity scores and other objective, repeatable metrics
  2. LLM-as-a-judge for refusal behavior and faithfulness at scale
  3. Human evaluation for brand voice and subjective quality calls
  4. Programmatic evaluation for brand voice, since it is fully automated
Answer and explanation

Correct: A, B, C. This is the exam's evaluation matrix: programmatic for the countable, LLM-as-a-judge for human-like quality at scale, human for the subjective.

D is wrong: brand voice is subjective; programmatic metrics cannot judge taste, which is the classic method-mismatch trap.

Glossary

Automated Reasoning check
A guardrail policy that verifies model answers against formal natural-language policy rules using deterministic logical reasoning.
ApplyGuardrail
The standalone Bedrock API that evaluates any text against a guardrail with no model invocation; works with non-Bedrock models.
Bedrock Guardrails
The managed AWS safety service: a versioned policy object with six policy types, evaluated on model inputs and outputs.
Bias drift
The worsening of fairness metrics over time as data and usage change; countered with continuous monitoring.
CMK (customer managed key)
A KMS encryption key you create and control, used for data at rest where compliance demands key ownership.
Content filter
A guardrail policy screening six toxicity categories (hate, insults, sexual, violence, misconduct, prompt attack) at NONE/LOW/MEDIUM/HIGH strength.
Contextual grounding check
A guardrail policy scoring whether an answer is supported by supplied source content; fights RAG hallucination.
Data lineage
The recorded chain from source data to generated answer: citations, metadata tags, catalog registration, audit records.
Defense in depth
Stacking independent safety layers (pre-filter, guardrail, post-processing, edge filtering) so no single failure is fatal.
Denied topic
A guardrail policy banning a subject area defined in natural language; judges meaning, not words.
Human in the loop
A person reviewing and approving system actions before they take effect, implemented with Step Functions approval workflows.
IAM (Identity and Access Management)
The AWS permission system; for Bedrock it controls which identities may invoke which models, knowledge bases, and agents.
Indirect prompt injection
An attack where instructions hidden in untrusted content (documents, tool outputs, web pages) influence the model.
Jailbreak
A direct attempt by the user to override the system prompt's constraints.
KMS (Key Management Service)
The AWS service managing encryption keys for data at rest.
LLM-as-a-judge
An evaluation method where a separate model scores outputs against rubrics (harmfulness, faithfulness, refusal) at scale.
Model card
A structured, versioned document describing a model's intended use, limitations, training data, and evaluation results.
PII (personally identifiable information)
Data that can identify a person; detected by entity type (30+ built-in types) in Comprehend and guardrail sensitive information filters.
PrivateLink
AWS technology behind VPC interface endpoints, keeping service traffic on the private AWS network.
Prompt attack
The content filter category detecting jailbreak and prompt injection attempts in inputs.
Return of control
An agent action group configuration where the agent pauses before executing a tool and hands the proposed action to the application for approval.
Sensitive information filter
A guardrail policy detecting PII by entity type with per-type BLOCK or MASK actions, plus custom regex support.
TLS (Transport Layer Security)
The protocol encrypting data in transit between applications and AWS APIs.
VPC endpoint
A private network entry point inside a VPC for an AWS service; interface endpoints use PrivateLink.
Word filter
A guardrail policy blocking exact-match strings from a custom list.
